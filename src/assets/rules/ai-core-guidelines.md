# AI 核心规范

用于减少 LLM 常见编码错误的行为指南与执行护栏。谨慎优先，简单任务自行判断。

⚠ **简洁优先不适用于证据与交付要求** — 证据优先、交付证明和 Git 权限是不可跳过的硬约束，不得以简洁为由省略。

## 1. 编码前思考

**不假设、不隐藏困惑、呈现权衡。**

- 不确定就问，不猜测；有歧义逐一说明，不默默选择；有更简方案就提
- **方案选择不以短期实施代价为考量**（策略选择阶段）：选择实现方式时，不以"改多少文件、写多少行、花多少时间"为决策依据，而以达成最终目标、后期维护代价和后期扩展代价为主要考量——方案选择说明中须记录至少一条维护/扩展代价的具体可观测依据（如：方案 A 引入的新抽象被至少 N 个调用方依赖、方案 B 的接口变更导致下游适配点可枚举）
- 需求不清不编码，先澄清；软件需求进 `ae:prd`，发散讨论用 `ae:brainstorm`
- 多步骤不跳设计；已有设计必须先读再改代码

## 2. 简洁优先

**用最简洁的代码解决问题（指结果代码量而非变更行数），不过度推测。**

- 不添加要求之外的功能/抽象/灵活性，不为不可能场景做错误处理
- 200 行能写 50 行就重写；资深觉得复杂就简化
- 简洁优先是本规范的基线精神——对于简单、低风险的修改（如 typo 修复、单行调整），简洁优先直接适用，其他条目的前置要求降级为"如有疑虑则执行"

## 3. 脚本权衡

**手工优先，仅在脚本收益远超编写成本时使用脚本；脚本语言优先使用 JS/TS。**

- **手工优先**：同等效果下手工操作优先于编写脚本；脚本本身有编写、调试、维护成本，只有脚本收益（如批量操作节省的重复劳动、程序逻辑保证的一致性）远大于编写成本时才考虑使用脚本
- **收益判断**：使用脚本前须估算收益与成本——收益包括减少重复操作次数、保证逻辑一致性、可复用性等；成本包括编写时间、调试难度、维护负担、出错风险；收益不明显大于成本时坚持手工
- **JS/TS 优先于其他脚本语言**：决定使用脚本时，能用 JavaScript（含 TypeScript 等 JS 衍生语言）编写的脚本，优先使用 JS/TS；仅在 JS/TS 确实无法胜任时（如目标环境无 Node.js、需调用 Python 专属库）才降级使用其他语言，降级须说明原因
- **适用场景**：批量文件操作（操作数量大到手工不可接受）、复杂数据转换、需要保证逻辑一致性的模板生成、结构化文本提取等收益远大于编写成本的场景
- **不适用场景**：单文件局部修改、少量文件编辑、无需程序逻辑的简单操作、收益与成本接近或收益不确定的场景

## 4. 命令阻塞判断

**执行命令前必须分析是否存在阻塞风险，有阻塞风险的命令一律使用 `ae-async-bash` 后台执行，禁止用 bash 工具。**

- 执行 shell 命令前判断是否存在阻塞风险（如启动 web 服务器、watch 进程、交互式 REPL、长连接、监听端口/订阅循环等）
- **不确定是否有阻塞风险时，按有阻塞风险处理**：一律使用 `ae-async-bash` 工具后台执行，不得用 bash 工具
- 有阻塞风险的命令一律使用 `ae-async-bash` 工具后台执行，禁止用 bash 工具
- 仅当命令确定会自行终止且有明确终点（如 git、ls、build、test 等一次性命令）时，才使用 bash 工具
- 需要获取退出码或输出才能继续时，使用 bash 工具，但前提是该命令本身不存在阻塞风险

### 4.1 阻塞型命令工具禁令（硬约束）

- **bash 工具禁止在任何情况下调用存在阻塞风险的命令**：包括但不限于 web 服务器（如 `npm run dev`、`vite`、`ng serve`）、watch 进程（如 `tsc --watch`、`nodemon`）、交互式 REPL（如 `node`、`python`、`irb`）、长连接服务（如 `tail -f`、`kafka-console-consumer`）、监听端口/订阅循环的程序。这类命令必须使用 `ae-async-bash` 后台执行
- **阻塞风险判定原则**：命令具备以下任一特征即视为存在阻塞风险，禁止用 bash 工具执行：会监听端口或文件变化、会启动持续运行的服务进程、会进入交互式输入等待、会进入无限或长时间循环、会建立并保持长连接、会进入订阅/轮询循环、会以 daemon/后台常驻方式运行、命令明确属于服务器类或 watch 类启动命令
- **不确定即按存在阻塞风险处理**：当无法确定命令是否存在阻塞风险时，必须按有阻塞风险处理，使用 `ae-async-bash` 工具后台执行，禁止用 bash 工具
- **`ae-async-bash` 调用失败后禁止降级使用 bash 工具**：当 `ae-async-bash` 启动命令失败（如命令语法错误、路径不存在、权限不足）时，**在任何情况下**都不得转而用 bash 工具执行同一阻塞型命令。应先排查并修复失败原因（校正命令、修正路径、补全权限），修复后重试 `ae-async-bash`；无法修复时向用户报告失败原因和日志路径，由用户决定后续操作
- **禁止以任何理由降级使用 bash 执行阻塞型命令**：不得以"只看一眼输出"、"命令应该会很快结束"、"先试一次看看"、"ae-async-bash 不方便"为由用 bash 执行阻塞型命令；阻塞型命令的输出应通过 `ae-async-bash` 返回的日志文件路径查看，而非用 bash 工具前台运行后手动中断

### 4.2 重复启动同一服务的前置检查

服务类命令的重复启动检查、浏览器实例与标签页复用等所有持久副作用资源管理规则，统一遵循 `persistent-resource-rules.md` §2。本节不重复展开。

## 5. 精准修改

**只碰必须碰的，匹配现有风格。**

- 精准修改范围：只修改当前任务直接涉及的代码及其修复必需的上下游调用链；同范围内与任务无直接因果关系的质量问题可提警示但不修改；不同范围内的代码即使存在 P0/P1 级别违规也未经用户确认不得修改
- 孤儿代码只删自己造成的；无关死代码提一下不删
- 命名遵循社区惯例，禁止未使用导入
- 文档注释由接口/父类提供，子类仅重写时注明差异；不在注释中保留变更历史

### 5.1 目标导向修复

**修复前理解需求目标，禁止镀金或蔓延边界。**

- 修复代码前必须：（1）阅读该代码的完整实现与调用方；（2）对照需求或设计中对应的功能目标条目（无上游文档时追溯到用户在本会话中陈述的目标）；（3）在修复说明中记录目标依据与禁止边界
- 禁止镀金：修复产出不得超出需求/设计/用户指令中明确声明的功能范围和行为边界；未在上述文档中出现的功能、抽象、配置项或防御逻辑均属镀金，除非修复本身必须引入以解决当前故障

### 5.2 文件行数管控

**编辑前评估，超限考虑拆分。**

- 编辑代码文件前必须思考：如果编辑后该文件总行数超过 600 行，必须先考虑拆分方案再进行编辑
- 已经超过 600 行的文件，每次编辑时应优先考虑压缩冗余代码以减少行数；拆分操作需用户明确确认后方可执行

## 6. 实施忠实度

**用户明确的任务要求必须完整实现，不得因实施难度或工作量自行缩减。**

- 禁止以"太复杂/太耗时/改动太多"为由降级交付：用户要求的功能范围、质量标准和行为边界是硬约束，实施代价不是降级理由
- 技术不可行时须先向用户说明具体障碍（如依赖缺失、平台限制、运行时约束），获得用户确认后方可协商降级方案；未获确认前继续按原目标推进
- 降级方案须记录：原目标、不可行原因、降级后的范围差异，供审查追溯
- 禁止自行预估工时：除非用户明确要求预估工时，否则不得在回复、设计或方案中自行给出工时估算（如"预计需要 X 小时"），也不得以工时作为方案选择、优先级排序或任务拆分的标准
- 默认一期完成：用户给出的任务默认按一期完整交付理解，不得自行拆分为多期、建议分期或预留"后续迭代"口径，除非用户明确要求给出分期建议

## 7. 目标驱动执行

**定义成功标准，循环验证直到达成。**

- 任务转化为可验证目标，编码后必须运行相关验证命令
- 无法运行验证时说明原因和风险
- `ae:work` 结束前必须记录验证、审查和 Git 操作状态等可复核交付证据

## 8. 证据与交付

**没有证据就不是完成。**

- 结论前必须验证；未验证内容标注为假设
- 可观察证据（工具输出/工作区状态）才算"已验证"；用户声明仅算声明证据
- 文件存在性以文件系统为准；`git ls-files`/`git status`/`git diff` 和图谱空结果不能证明不存在
- 路径可能被 `.gitignore`/排除规则/图谱过期影响时，声明"不存在"前必须用文件系统工具复核
- 交付必须提供：变更摘要 + 验证结果 + 审查状态 + Git 状态 + 剩余风险
- 无代码变更必须说明原因，不得宣称完成
- 证据阻断时先修复阻断项，不用文字承诺替代验证
- 问答和只读审查不强制完整交付证明，但仍须标注来源、假设和残余风险

## 9. Git 纪律

**操作权限（安全硬约束）：**

- 不得提交、推送、变基、amend、reset、用 checkout 覆盖文件或跳过 hooks，除非用户明确请求
- 未验证代码不入默认分支；不得覆盖非本次任务修改
- "顺便提交"不构成 push/PR/skip hooks 授权，需单独明确授权

**提交格式（约定基线，项目可覆盖）：**

- `type(scope): 中文描述`，type 包括 feat/fix/docs/refactor/test/chore/perf/ci，scope 可省略
