# 需求规格与软件双向同步

`ae:spec-html` 编排两个代理实现需求规格（纯静态 HTML + 业务描述文件）与软件源码的双向同步：

- **`@spec-author`**：从需求描述、现有源码或用户描述生成纯静态 HTML 需求产物 + 业务描述文件
- **`@spec-translator`**：将需求规格产物翻译为目标软件源码，或将已有软件源码同步到与需求一致

## 核心原则

1. **意图驱动编排** — 通过自然语言描述分析用户是需要生成需求、翻译为软件还是同步软件源码与需求。
2. **需求规格产物约束（硬约束）** — 产物为纯静态 HTML + Markdown 描述文件，扁平自包含，仅保留业务闭环、功能完整、交互完整所必需的最小需求，不含安全需求、并发需求和非功能需求。
3. **双向同步** — 需求可同步到源码（翻译为软件），源码变更也可同步回需求（反向更新需求产物）。
4. **涉及源码时强制一致性分析（硬约束）** — 当编排路径涉及软件源码（2b 翻译或同步）时，最后一步必须分析需求规格与软件源码是否完全一致；不一致时分析同步方向，不确定时列出所有不一致项询问用户。仅生成需求且用户拒绝翻译时不执行一致性分析。一致性分析只校验硬约束项（页面、路由、表单字段、业务功能、业务逻辑、响应式行为、布局区域划分、交互行为），不校验视觉美化项（配色、字体、动画等允许翻译代理自由设计的表层视觉）。

## 执行流程

### 步骤 1：意图分析

通过自然语言描述分析用户意图：

| 用户表达特征 | 意图 | 调度代理 | 说明 |
|-------------|------|---------|------|
| 描述功能需求、问题、改进想法 | 生成需求 | `@spec-author` | 生成新需求产物 |
| 提供源码路径 + "提取需求"/"反向生成" | 从源码生成需求 | `@spec-author` | 源码为真源 |
| 提供规格产物路径 + "翻译为软件"/"生成代码" | 翻译为软件 | `@spec-translator` | 需求为真源 |
| 提供规格产物路径 + 源码路径 + "同步" | 双向同步 | 先 `@spec-translator` 后一致性分析 | 默认 spec-to-code |
| "修改需求"/"改一下规格" | 修改已有需求 | `@spec-author` | 修改模式 |
| "修改源码到指定需求" | 同步软件到需求 | `@spec-translator` | 同步模式（spec-to-code） |
| "更新需求到源码"/"需求同步到源码" | 源码反向同步需求 | `@spec-author` | code-to-spec 方向 |
| 描述功能 + "开发这个"/"写代码" 但无规格产物 | 先生成需求再翻译 | 先 `@spec-author` 后 `@spec-translator` | 需先有规格产物 |

**意图不明确时询问用户**：当无法从描述确定意图时，使用 `question` 工具询问用户选择。

### 步骤 2：编排执行

根据意图分析结果调度对应代理：

#### 2a. 生成需求（意图：生成需求 / 从源码生成需求 / 修改已有需求）

**新建需求模式时先执行 ae:grill**：意图为"生成需求"时，编排层先调用 `ae:grill` 技能向用户逐层追问所有决策分支，达成共识后将追问结果作为输入传入 `@spec-author`。修改已有需求时聚焦变更部分 grill。从源码生成需求时跳过 grill（源码为真源）。

调度 `@spec-author`，传入：
- 需求描述或源码路径或规格产物路径
- 工作模式（新建 / 从源码同步 / 修改已有产物）
- ae:grill 追问结果（新建需求时）

`@spec-author` 完成后产出 `ae/specs/<topic>-<date>/` 下的需求规格产物。

**询问用户是否翻译为软件**：需求生成完毕后，询问用户是否需要将需求翻译为软件源码或同步到已有软件源码。
- 用户确认翻译为软件 → 进入 2b
- 用户确认同步到已有软件 → 进入 2b（同步模式）
- 用户拒绝 → 结束，输出需求产物路径

#### 2b. 翻译为软件 / 同步软件（意图：翻译为软件 / 同步软件到需求）

调度 `@spec-translator`，传入：
- 需求规格产物路径（`ae/specs/<topic>-<date>/`）
- 目标平台（如已知）
- 项目源码路径（同步模式）

`@spec-translator` 完成后产出目标软件源码。代理层步骤 4 自行验证翻译完整性（表单字段、交互行为、布局结构、业务逻辑是否完整翻译），编排层步骤 3 做最终一致性分析，两者不重复。

**用户直接要求"修改源码到指定需求"时**：先执行 2b 将源码同步到需求一致，完成后进入步骤 3 分析源码与需求是否一致。不一致时按步骤 3 的同步方向逻辑处理（不自动反向同步）。

### 步骤 3：需求与源码一致性分析（硬约束，涉及源码时不可跳过）

> **前置条件（硬约束）**：本步骤仅在编排路径涉及软件源码时执行（2b 翻译或同步）。仅生成需求（2a）且用户拒绝翻译时跳过本步骤，直接输出总结。

分析需求规格产物与软件源码是否完全一致：

1. **读取需求规格产物**：读取 `ae/specs/<topic>-<date>/` 下所有文件，提取页面清单、表单字段、交互行为、布局结构、业务逻辑、响应式声明、主题色。
2. **读取软件源码**：通过 glob/grep 扫描源码，提取已实现的页面、表单字段、交互行为、布局结构、业务逻辑、响应式实现、主题色。
3. **逐项比对**：对照需求与源码，标记每项为"一致"或"不一致"。

**一致时**：输出一致性通过结论，结束。

**不一致时**：
- 分析不一致项的同步方向：
  - 需求正确、源码缺失或偏离 → `spec-to-code`（从需求同步到源码）
  - 源码正确、需求过时或遗漏 → `code-to-spec`（从源码同步到需求）
- **无法确定方向时（硬约束）**：列出所有不一致项，通过 `question` 工具询问用户每项的同步方向：

```
检测到需求规格与软件源码存在以下不一致项：

1. [不一致项描述] — 同步方向不确定
2. [不一致项描述] — 同步方向不确定
...

请告知每项应从需求同步到源码（spec-to-code），还是从源码同步到需求（code-to-spec）。
```

- 用户确认同步方向后，调度对应代理执行同步：
  - `spec-to-code` → 调度 `@spec-translator` 同步模式
  - `code-to-spec` → 调度 `@spec-author` 从源码同步模式
- 同步完成后重新执行步骤 3 验证一致性，最多 2 轮同步-验证循环。2 轮后仍有不一致项，标注为残余风险并输出。

### 步骤 4：输出总结

```
## 需求规格与软件同步总结

**用户意图:** [生成需求 / 翻译为软件 / 同步软件 / 修改需求 / 修改源码]
**编排代理:** [@spec-author / @spec-translator / 两者]
**需求产物:** ae/specs/<topic>-<date>/
**软件源码:** [源码路径或"全新项目"]

**一致性分析:**
| 项目 | 需求 | 源码 | 状态 | 同步方向 |
|------|------|------|------|---------|
| [项目名] | [需求值] | [源码值] | [一致/不一致] | [spec-to-code/code-to-spec/无需] |

**同步执行:** [未执行 / 执行N轮 / 残余风险]

### 剩余风险
- [一致性分析中未解决的不一致项（如有）]
```

## 代理调度

| 代理 | 职责 | 调度时机 |
|------|------|---------|
| `@spec-author` | 生成 / 修改 / 从源码同步需求规格产物 | 意图为生成需求、修改需求、从源码反向同步 |
| `@spec-translator` | 翻译需求为软件 / 同步软件到需求一致 | 意图为翻译为软件、同步软件、修改源码到指定需求 |

## 边界

- **不直接生成产物** — 编排层不直接写 HTML 或源码，通过调度代理完成
- **涉及源码时必执行一致性分析** — 步骤 3 在涉及软件源码的编排路径中为硬约束；仅生成需求且用户拒绝翻译时跳过
- **一致性分析只校验硬约束项** — 页面、路由、表单字段、业务功能、业务逻辑、响应式行为、布局区域划分、交互行为；不校验视觉美化项
- **不确定方向时必须询问** — 不自行决定同步方向，列出不一致项询问用户
- **不执行 Git 操作**
- **不修改需求产物或源码** — 编排层只读取和分析，修改由代理执行

## 验证方式

- 需求规格产物（HTML + 描述文件）满足扁平自包含、最小需求、业务闭环、功能完整、交互完整
- 需求产物中不含安全需求、并发需求和非功能需求
- 软件源码与需求规格一致性分析通过（或残余风险已标注）
- 不一致项的同步方向已由用户确认或已分析明确
- 双向同步循环不超过 2 轮
