# 创建或修改需求文档

**注意：当前年份是 2026 年。** 在为需求数据文档标注日期时使用此年份。

`ae:prd` 通过协作对话回答**构建什么（WHAT）**。它在 `ae:design` 之前进行，后者回答**如何构建（HOW）**。

`ae:prd` 统一处理创建新需求和修改已有需求：当输入参数指向已有需求文档时，恢复并修改该文档；当输入参数为新描述时，创建新需求文档。定版是人为约定，无需技术标记——用户通过选择 `ae:prd`（修改）或重新运行 `ae:prd`（创建新需求）表达当前状态。

此工作流的持久输出是一份**需求数据文档**。它不是汇报材料；只记录后续设计必须知道的产品行为、范围边界、成功标准和待定问题，使设计阶段不需要再发明这些内容。

此技能不实现代码。它探索、澄清并记录决策，供后续设计或执行使用。

**重要：生成的文档中所有文件引用必须使用仓库相对路径（例如 `src/models/user.rb`），绝不能使用绝对路径。**

## 核心原则

1. **先评估范围** - 根据工作的大小和模糊程度匹配相应的流程规范。
2. **做思考伙伴** - 建议替代方案、质疑假设、探索假设情境，而不是仅仅提取需求。
3. **在此解决产品决策** - 面向用户的行为、范围边界和成功标准属于此工作流。详细的实现属于规划阶段。
4. **默认不将实现细节写入需求数据文档** - 除非需求讨论本身涉及技术或架构变更，否则不要包含库、Schema、接口、文件布局或代码级设计。
5. **禁止主动追问技术栈与实现路线（硬约束）** - 不得主动询问用户使用什么前端框架、后端语言、数据库、UI 组件库、构建工具等技术栈选型，也不得追问具体实现方案（如"用 REST 还是 GraphQL""用 JWT 还是 Session"）。仅当用户需求中**已明确提及**特定技术栈（如"用 React 实现""基于 Spring Boot"）或已明确技术实现路线时，才在需求文档中记录该技术栈约束作为范围边界，且不追问超出用户已述范围的选型细节。技术选型和实现路线属于 `ae:design` 职责。
6. **合理调整产物规模** - 简单的工作获得紧凑的需求数据文档或简短对齐。较大的工作获得更完整的文档。
7. **将 YAGNI 应用于维护成本而非编码工作量** - 优先选择能交付有意义价值的最简方案。
8. **只保留对后续执行有用的需求语义** - 不为了"读起来完整"新增用户与场景、术语表、视觉辅助或其他解释性章节；这些内容只有在直接影响需求行为、验收或范围时才记录。
9. **模块边界是初始提议而非冻结** - prd 阶段识别的模块边界标注为"初始边界"，design 阶段可通过置信度门控提调整申请。
10. **自包含约束（硬约束）** - 需求文档目录完全自包含，禁止引用外部工作空间文件。目录内文件只通过稳定 ID 相互引用。版本演化 = 独立新目录，不指向旧版本。

## 交互规则

1. **一次只问一个问题** - 不要在一次消息中批量提出多个不相关的问题（同维度关联紧密的问题除外，见第6条）。
2. **优先使用单选** - 在选择方向、优先级或下一步时使用单选。
3. **谨慎使用多选** - 仅用于可共存的集合（目标、约束、非目标）。
4. **使用平台的提问工具** - 优先使用 opencode 的 `question` 工具。
5. **每个提问必须提供选项** - 提问时给出 2-5 个选项供用户选择，而非纯开放式问题。基于仓库扫描和上下文推断给出合理默认值，在推荐选项后标注"(推荐)"。用户始终可选择自定义输入。
6. **同维度可合并提问** - 同一维度内关联紧密的问题可通过一次 `question` 工具调用包含多个 question 项，但跨维度仍逐个推进。

## 输出指引

- **保持输出简洁** - 优先使用简短的章节、简明的要点。
- **使用仓库相对路径** - 引用文件时使用相对路径，绝不使用绝对路径。

## 产物结构

```
ae/prds/<topic>-YYYY-MM-DD/
├── overview.md                     # 问题框架、范围边界、模块清单
├── decisions.md                    # 跨模块决策（可选）
├── non-functional.md               # 全局非功能（可选）
├── tech-stack.md                   # 技术栈约束（可选，用户明确指定时）
├── design-vision.md                # 设计愿景 + 路由表 + 导航结构（可选，涉及 UI 时）
└── modules/
    └── <NN>-<module-name>/         # 模块子目录（两位数字序号 + 模块名）
        ├── requirements.md          # 模块需求 + 成功标准
        └── pages/                   # 每个页面独立文件（涉及 UI 时）
            ├── <NN>-<page-name>.md   # 路由、布局结构、交互流程、字段清单、响应式布局
            └── ...
```

**各文件职责：**

| 文件 | 内容 | 必产出 |
|------|------|--------|
| `overview.md` | 问题框架、范围边界（In/Out Scope）、模块清单（含边界声明） | 是 |
| `decisions.md` | 跨模块决策 D1, D2...（含理由） | 有决策时 |
| `non-functional.md` | 全局非功能 NFR1, NFR2... | 有非功能时 |
| `tech-stack.md` | 用户明确指定的技术栈约束 | 用户指定时 |
| `design-vision.md` | 主题色 HEX、响应式声明、视觉风格关键词、路由表、导航结构 | 涉及 UI 时 |
| `requirements.md` | 模块需求 R1, R2... + 成功标准 SC1, SC2... | 是 |
| `pages/<NN>-<page-name>.md` | 页面 ID、路由、布局结构、交互流程、字段清单、响应式布局 | 涉及 UI 时 |

**页面文件内容（每个 `<NN>-<page-name>.md`）：**
- 页面 ID、名称、路由
- 布局结构
- 交互流程
- **字段清单**：字段名、类型、必填、验证规则、所属区域
- 响应式布局（仅响应式时）

**核心约束：**
- **自包含**：目录完全自包含，禁止引用外部工作空间文件，目录内文件只通过稳定 ID 相互引用
- **无行数限制**：单个文件不限制大小

## 执行流程

### 阶段 0：恢复、评估和路由

#### 0.1 在适当时恢复已有工作

仅从以下来源识别要恢复的需求文档，文件名必须完全匹配：
- 当前会话上下文中用户明确提到的需求文件名或路径
- 当前会话中已产出的需求文档

不要扫描 `ae/prds/` 目录寻找内容相似的需求文件。如果识别到匹配的文档：
- 阅读该文档
- 在恢复之前与用户确认
- 如果恢复，从其现有决策和待定问题继续，更新现有文档而非创建重复文档

**创建新需求 vs 修改已有需求**：当输入参数指向已有需求文档路径时，恢复并修改该文档；当输入参数为新的功能描述时，创建新的独立需求目录。

#### 0.1b 分类任务领域

如果任务是快速帮助请求、错误消息或事实性问题，直接回复，跳过需求文档流程。

**如果检测到非软件需求**（活动策划、学习计划、流程设计、组织变革等）：不套用软件语境的需求或实施假设；根据重要程度或影响程度匹配语气；仍产出标准 `type: prd` 文档，保留后续 `ae:design` 交接。

#### 0.2 评估是否需要需求探索

**需求清晰的指标：** 提供了具体的验收标准、引用了现有模式、描述了精确的预期行为、范围受限且定义明确。

**如果需求已经清晰：** 保持交互简短。确认理解并呈现简洁的下一步选项。仅当对规划或后续审查的持久交接有价值时才编写简短的需求数据文档。跳过阶段 1.1 和 1.2，直接进入阶段 1.3 或阶段 3。

#### 0.3 评估范围

使用功能描述加上轻量仓库扫描来分类工作：

- **轻量** - 小型、边界明确、低模糊性
- **标准** - 常规功能或有边界的重构，需要做一些决策
- **深入** - 跨领域的、战略性的或高度模糊的

### 阶段 1：理解需求

#### 1.1 现有上下文扫描

在实质性需求讨论之前扫描仓库。根据范围匹配深度：

**轻量** — 搜索主题，检查是否已有类似内容，然后继续。

**标准和深入** — 两轮扫描：约束检查（可选读取存在的 `AGENTS.md`、`CLAUDE.md` 或同类项目标准文件，缺失时跳过）和主题扫描（相关术语、现有产物、邻近示例）。

约束规则：
1. **声称前先验证** — 涉及可检查的基础设施时，阅读相关源文件确认实际存在的内容。未验证的断言必须标记为未经验证的假设。
2. **将设计决策推迟到规划** — 实现细节属于规划阶段，除非需求讨论本身是关于技术/架构决策的。

#### 1.2 需求压力测试

在生成方案之前，质疑请求以发现错误的框架。根据范围匹配深度：

**轻量：** 是否解决真实问题？是否重复已有内容？是否有更好的框架？

**标准：** 这是正确的问题吗？什么成果真正重要？如果什么都不做会怎样？现在单一最高杠杆的行动是什么？

**深入：** 标准问题加上：这应创造什么持久能力？是推动前进还是局部补丁？

**深入和标准范围的追问衔接：** 压力测试结束后，如果仍存在多个相互依赖的未解决决策，提示用户："需求方向上仍有悬而未决的决策，是否使用 `ae:grill` 逐个追问直到达成共识？"用户接受后转交 `ae:grill` 处理当前需求文档，追问结果带回本技能继续阶段 1.3。轻量范围跳过追问衔接。

#### 1.3 协作对话

遵循交互规则。使用 opencode 的 `question` 工具进行提问。

- 先问用户已经在考虑什么
- 从广泛开始（问题、目标、范围），然后收窄（约束、排除、边界情况）
- 使需求足够具体，让规划不需要再发明行为
- 带来想法、替代方案和挑战

**提问维度矩阵：** 按以下维度系统化推进提问。每个维度提供选项供用户选择，用户跳过的维度标记为"使用默认/推迟到设计"。根据阶段 0.3 的范围评估调整覆盖深度——轻量范围可跳过标注为"可选"的维度。

| 维度 | 提问内容 | 选项示例 | 必问 |
|------|---------|---------|------|
| **目标与问题** | 要解决的核心问题是什么？当前痛点？期望达成什么？ | 选项基于功能描述推断 | 是 |
| **用户角色与权限** | 系统涉及哪些用户角色？各角色的操作边界？ | 多选角色（如：管理员/普通用户/访客/匿名）+ 单选权限模型（如：基于角色 RBAC/基于资源 ABAC/无权限控制） | 是 |
| **核心业务流程** | 主要业务流程是什么？关键入口和出口？ | 单选流程模式（如：表单提交驱动/列表查看驱动/审批流转/数据导入导出/混合） | 是 |
| **数据与状态** | 核心数据实体有哪些？数据来源？是否存在状态流转？ | 多选实体类型 + 单选数据来源（如：用户输入/系统生成/外部导入/已有数据库） | 是 |
| **异常与边界** | 关键异常场景？数据校验规则？不可逆操作确认？ | 多选异常场景（如：网络中断/数据冲突/权限不足/并发冲突/数据丢失） | 可选 |
| **非功能需求** | 预期并发量/响应时间/数据规模？是否需要国际化？是否需要审计日志？ | 单选性能档位（如：低并发<100QPS/中等/高并发）+ 多选非功能项 | 可选 |
| **集成与依赖** | 是否需要与外部系统交互？是否复用已有系统模块？ | 单选集成模式（如：无集成/读取外部 API/双向同步/消息队列/数据库共享） | 可选 |
| **范围边界** | 哪些功能明确不做？MVP 边界在哪里？ | 多选排除项（基于功能描述推断可能被误纳入的功能） | 是 |
| **优先级** | 如果分期交付，哪些功能优先级最高？ | 单选优先级策略（如：核心流程优先/数据完整性优先/用户体验优先/安全优先） | 可选 |

**UI 基础信息提问（当需求涉及用户界面时）：**

在上述通用维度提问完成后，如果需求涉及任何用户界面（页面、表单、可视化展示等），追加以下 UI 基础信息提问。**只询问基础信息，不追问详细设计**（不问具体组件选型、间距、字号、动画、图标等），这些属于 `ae:design` 职责。

| UI 维度 | 提问内容 | 选项示例 |
|---------|---------|---------|
| **界面类型** | 系统属于哪种界面类型？ | 单选：Web 后台管理系统 / Web C 端门户 / 移动端 H5 / 桌面客户端 / 数据大屏 / 嵌入式组件 |
| **基础布局** | 整体布局结构偏好？ | 单选：顶部导航+侧边栏+内容区 / 顶部导航+内容区 / 侧边栏+内容区 / 居中卡片式 / 自由流式 / 多 Tab 切换 |
| **主题色调** | 主题色调偏好？ | 单选：冷色-蓝色系 / 冷色-青色系 / 暖色-橙色系 / 暖色-红色系 / 中性色-灰色系 / 绿色系 / 紫色系 / 自定义 HEX |
| **视觉风格** | 视觉风格关键词？ | 单选：极简 / 商务严谨 / 活泼明快 / 科技感 / 扁平化 / 拟物化 |
| **响应式** | 是否需要响应式布局？ | 单选：是-需适配多端（PC/平板/手机）/ 否-固定布局（仅 PC）/ 否-仅移动端 |
| **导航模式** | 导航结构偏好？ | 单选：顶部导航栏 / 左侧边导航栏 / 顶部+侧边混合 / 面包屑导航 / Tab 页签切换 / 无导航（单页） |
| **页面规模** | 预计页面数量级？ | 单选：单页面 / 少量页面（2-5 页）/ 中等规模（6-15 页）/ 大规模（15+ 页）/ 不确定 |

UI 提问结果用于填充 `design-vision.md` 的主题色、响应式声明、视觉风格关键词和导航结构字段。具体 HEX 值由阶段 3 根据色调选择映射，无需在此追问精确色值。

**退出条件：** 所有适用维度均已覆盖（用户跳过的维度标记为"使用默认/推迟到设计"），或用户明确表示要继续。轻量范围至少覆盖"目标与问题"和"范围边界"两个维度。

### 阶段 1.4：模块边界识别

协作对话结束后，基于已澄清的需求，主代理识别模块边界。

- **模块划分依据**：业务域内聚（同域实体高内聚），跨模块耦合点通过 API 暴露
- **向用户展示建议模块划分**（模块名、包含需求、理由），用户确认
- **跨模块依赖**：记录在 `overview.md` 范围边界的模块清单中，标注依赖类型（API 调用、数据共享、事件订阅）
- **模块边界标注为"初始边界"**：design 阶段可通过置信度门控提调整申请

### 阶段 2：探索方案

如果仍然存在多个可行的方向，提出 **2-3 个具体方案**。否则直接陈述推荐方向。

至少使用一个非显而易见的角度：逆向思维、约束移除、或类比。

先展示方案，再评估。让用户在听到推荐之前看到所有选项。

对于每个方案：简要描述、优缺点、关键风险或未知因素、最适合的场景。

在展示所有方案后，陈述你的推荐并解释原因。

### 阶段 3：捕获需求

仅当对话产生了值得保留的持久决策时，才编写或更新需求数据文档。阅读 `references/requirements-capture.md` 获取文档模板、格式规则和完整性检查。

**产物结构**：

1. **主代理产出 `overview.md`**（总览）：
   - §问题框架 — 用户目标、当前痛点、成功判据
   - §范围边界 — In/Out Scope + 模块清单（含边界声明和可调整标记）

2. **主代理按需产出全局方向文件**：
   - `decisions.md` — 跨模块决策 D1, D2...（含理由），有决策时产出
   - `non-functional.md` — 全局非功能 NFR1, NFR2...，有非功能时产出
   - `tech-stack.md` — 仅当用户明确指定技术栈时产出
   - `design-vision.md` — 仅当涉及 UI 时产出（主题色 HEX、响应式声明、视觉风格关键词、路由表、导航结构）

3. **主代理为每个模块产出 `modules/<NN>-<m>/requirements.md`**（模块需求）：
   - §需求 — R1, R2...（含 `-> 验收:` 语法和模块内依赖）
   - §成功标准 — SC1, SC2...（仅本模块可验证部分）

   当模块 `involvesUI=true` 时，同时产出 `modules/<NN>-<m>/pages/` 目录，每个页面独立文件 `<NN>-<page-name>.md`：
   - 页面 ID、名称、路由
   - 布局结构、交互流程
   - **字段清单**（字段名/类型/必填/验证规则/区域）
   - 响应式布局（仅当 `design-vision.md` 声明为响应式时）

**页面产物技术栈隔离规则（硬约束）：** 原型设计产物（`pages/<NN>-<page-name>.md`）禁止出现任何前端开发技术栈或第三方依赖名称（如 React/Vue/Angular、Ant Design/Element Plus、Tailwind CSS、axios 等）。页面产物只描述产品逻辑层语义（页面要做什么、长什么样、怎么交互），不描述用什么技术实现。如果需求中确实需要明确技术栈，必须将技术栈信息集中收录到 `tech-stack.md`，不得散落在各页面描述中。

**确定性边界约束：** 任何人据此 md 生成的原型 HTML，在页面数量、路由、布局区域划分、交互跳转、表单字段和必填规则、主题色和次要颜色 HEX 值、响应式行为方面必须完全一致。允许差异的仅限视觉实现细节（间距、字号、动画）。

**原型验证**：提示用户可根据 `pages/` 下文件自行生成原型 HTML 用于验证。用户反馈后更新对应页面文件。

对于**轻量**需求探索，保持文档紧凑。当用户只需要简短对齐且不需要保留持久决策时，跳过文档创建。

### 阶段 3.1：原型设计（涉及前端时）

当需求涉及前端页面或用户交互时，在各模块的 `modules/<NN>-<m>/pages/` 目录下产出原型设计。详见 `references/requirements-capture.md` 原型设计章节。

**原型内容要求**：
- 页面清单（页面 ID、名称、路由、功能域）
- 路由表（集中在 `design-vision.md`）
- 导航结构（集中在 `design-vision.md`）
- 主题声明（**必填**：主题色 HEX 值、次要颜色 HEX 值、色调、视觉风格关键词）— 集中在 `design-vision.md`
- 响应式声明（**必填**：是否响应式；响应式时给出断点定义和各断点下的布局变化描述；非响应式时明确写明"不支持响应式，固定布局"）— 集中在 `design-vision.md`，全局只声明一次
- 每页面的布局结构、交互流程、**字段清单**、响应式布局（仅响应式时产出各页面在各断点下的布局变化描述）

### 阶段 3.5：技能内 review 闭环

当创建或更新了需求数据文档时，运行技能内 review 闭环。此环节复用现有文档审查逻辑，补强 auto 修复范围和收敛协议。

**审查调用：** 调用 `ae:review mode=headless domain=document <requirements-doc-path>/overview.md`，审查者为 `document-reviewer`（通过文件类型路由加载需求检查框架）。`mode=headless` 表示 ae:review 被技能内部调用时不输出"下一步推荐技能"引导，仅返回审查结果（status/findings/summary）给本技能，由 ae:prd 自身负责下一步引导。

**auto 修复范围：** 格式不规范、章节缺失、成功标准不可验证、In/Out Scope 模糊。ae:review 返回的 auto 可修复发现由本技能自动应用修复，修复后重新运行审查。

**置信度门控（替代硬性不镀金）：** 审查需求文档时，除了 P0/P1 阻断 + P2/P3 抑制外，新增 INFO 级别"工程建议"——当检测到"需求未提及但工程上必要"的内容时以 INFO 报告，用户决定是否纳入。置信度计算：`confidence = 0.5 × 需求明确提及 + 0.3 × 工程基线必要性 + 0.2 × 缺失后果严重度`。≥ 0.8 产出，0.5-0.8 INFO 报告"建议补充"，< 0.5 不产出不报告。

**收敛协议（上限 2 轮）：**
- 第 1 轮：初次审查 → auto 修复 → 重新审查
- 收敛判定：重新审查后无新增 P0/P1 发现即为收敛
- 未收敛处理：2 轮后仍有 P0/P1 阻断，回退用户澄清（返回阶段 1.3 继续提问），不进入阶段 4

**结果呈现：** 若文档审查返回了自动应用的发现，在呈现交接选项时简要提及。若收敛后有 INFO 级别工程建议，提及它们以便用户决定是否纳入。收敛后进入阶段 4。

### 阶段 4：交接

呈现下一步选项并执行用户的选择。阅读 `references/handoff.md` 获取选项逻辑、调度指令和结束摘要格式。

**交接选项**包含：
- 运行 `ae:design` 进入设计阶段
- 结束
