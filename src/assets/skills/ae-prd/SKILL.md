# 创建需求文档

**注意：当前年份是 2026 年。** 在为需求数据文档标注日期时使用此年份。

`ae:prd` 通过协作对话回答**构建什么（WHAT）**。它在 `ae:design` 之前进行，后者回答**如何构建（HOW）**。

此工作流的持久输出是一份**需求数据文档**。它不是汇报材料；只记录后续设计必须知道的产品行为、范围边界、成功标准和待定问题，使设计阶段不需要再发明这些内容。

此技能不实现代码。它探索、澄清并记录决策，供后续设计或执行使用。

**重要：生成的文档中所有文件引用必须使用仓库相对路径（例如 `src/models/user.rb`），绝不能使用绝对路径。**

## 核心原则

1. **先评估范围** - 根据工作的大小和模糊程度匹配相应的流程规范。
2. **做思考伙伴** - 建议替代方案、质疑假设、探索假设情境，而不是仅仅提取需求。
3. **在此解决产品决策** - 面向用户的行为、范围边界和成功标准属于此工作流。详细的实现属于规划阶段。
4. **默认不将实现细节写入需求数据文档** - 除非需求讨论本身涉及技术或架构变更，否则不要包含库、Schema、接口、文件布局或代码级设计。
5. **合理调整产物规模** - 简单的工作获得紧凑的需求数据文档或简短对齐。较大的工作获得更完整的文档。
6. **将 YAGNI 应用于维护成本而非编码工作量** - 优先选择能交付有意义价值的最简方案。
7. **只保留对后续执行有用的需求语义** - 不为了“读起来完整”新增用户与场景、术语表、视觉辅助或其他解释性章节；这些内容只有在直接影响需求行为、验收或范围时才记录。

## 交互规则

1. **一次只问一个问题** - 不要在一次消息中批量提出多个不相关的问题。
2. **优先使用单选** - 在选择方向、优先级或下一步时使用单选。
3. **谨慎使用多选** - 仅用于可共存的集合（目标、约束、非目标）。
4. **使用平台的提问工具** - 优先使用 opencode 的 `question` 工具。

## 输出指引

- **保持输出简洁** - 优先使用简短的章节、简明的要点。
- **使用仓库相对路径** - 引用文件时使用相对路径，绝不使用绝对路径。

## 功能描述

<feature_description> #$ARGUMENTS </feature_description>

**如果上面的功能描述为空，询问用户：** "您想定义什么需求？请描述您正在考虑的功能、问题或改进。"

在获得用户的功能描述之前不要继续。

## 执行流程

### 阶段 0：恢复、评估和路由

#### 0.1 在适当时恢复已有工作

仅从以下来源识别要恢复的需求文档，文件名必须完全匹配：
- 当前会话上下文中用户明确提到的需求文件名或路径
- 当前会话中已产出的需求文档

不要扫描 `ae/prds/` 目录寻找内容相似的需求文件。如果识别到匹配的文档：
- 阅读该文档
- 在恢复之前与用户确认
- 如果恢复，从其现有决策和待定问题继续，更新现有文档而非创建重复文档

#### 0.1b 分类任务领域

如果任务是快速帮助请求、错误消息或事实性问题，直接回复，跳过需求文档流程。

**如果检测到非软件需求**（活动策划、学习计划、流程设计、组织变革等）：不套用软件语境的需求或实施假设；根据重要程度或影响程度匹配语气；仍产出标准 `type: prd` 文档，保留后续 `ae:design` 交接。

#### 0.2 评估是否需要需求探索

**需求清晰的指标：** 提供了具体的验收标准、引用了现有模式、描述了精确的预期行为、范围受限且定义明确。

**如果需求已经清晰：** 保持交互简短。确认理解并呈现简洁的下一步选项。仅当对规划或后续审查的持久交接有价值时才编写简短的需求数据文档。跳过阶段 1.1 和 1.2，直接进入阶段 1.3 或阶段 3。

#### 0.3 评估范围

使用功能描述加上轻量仓库扫描来分类工作：

- **轻量** - 小型、边界明确、低模糊性
- **标准** - 常规功能或有边界的重构，需要做一些决策
- **深入** - 跨领域的、战略性的或高度模糊的

### 阶段 1：理解需求

#### 1.1 现有上下文扫描

在实质性需求讨论之前扫描仓库。根据范围匹配深度：

**轻量** — 搜索主题，检查是否已有类似内容，然后继续。

**标准和深入** — 两轮扫描：约束检查（可选读取存在的 `AGENTS.md`、`CLAUDE.md` 或同类项目标准文件，缺失时跳过）和主题扫描（相关术语、现有产物、邻近示例）。

约束规则：
1. **声称前先验证** — 涉及可检查的基础设施时，阅读相关源文件确认实际存在的内容。未验证的断言必须标记为未经验证的假设。
2. **将设计决策推迟到规划** — 实现细节属于规划阶段，除非需求讨论本身是关于技术/架构决策的。

#### 1.2 需求压力测试

在生成方案之前，质疑请求以发现错误的框架。根据范围匹配深度：

**轻量：** 是否解决真实问题？是否重复已有内容？是否有更好的框架？

**标准：** 这是正确的问题吗？什么成果真正重要？如果什么都不做会怎样？现在单一最高杠杆的行动是什么？

**深入：** 标准问题加上：这应创造什么持久能力？是推动前进还是局部补丁？

**深入和标准范围的追问衔接：** 压力测试结束后，如果仍存在多个相互依赖的未解决决策，提示用户："需求方向上仍有悬而未决的决策，是否使用 `ae:grill` 逐个追问直到达成共识？"用户接受后转交 `ae:grill` 处理当前需求文档，追问结果带回本技能继续阶段 1.3。轻量范围跳过追问衔接。

#### 1.3 协作对话

遵循交互规则。使用 opencode 的 `question` 工具进行提问。

- 先问用户已经在考虑什么
- 从广泛开始（问题、目标、范围），然后收窄（约束、排除、边界情况）
- 使需求足够具体，让规划不需要再发明行为
- 带来想法、替代方案和挑战

**退出条件：** 继续直到需求清晰，或用户明确表示要继续。

### 阶段 2：探索方案

如果仍然存在多个可行的方向，提出 **2-3 个具体方案**。否则直接陈述推荐方向。

至少使用一个非显而易见的角度：逆向思维、约束移除、或类比。

先展示方案，再评估。让用户在听到推荐之前看到所有选项。

对于每个方案：简要描述、优缺点、关键风险或未知因素、最适合的场景。

在展示所有方案后，陈述你的推荐并解释原因。

### 阶段 3：捕获需求

仅当对话产生了值得保留的持久决策时，才编写或更新需求数据文档。阅读 `references/requirements-capture.md` 获取文档模板、格式规则和完整性检查。

**Frontmatter 字段填写规则：** 需求数据文档的 frontmatter 必须包含 `type: prd`、`status: drafted`、`date` 和 `topic`。`origin` 和 `originFingerprint` 仅在有上游产物时成对填写。`origin` 必须使用仓库相对路径。`originFingerprint` 的值为上游产物 frontmatter 中 `date` + `-` + `topic` 的 kebab-case 拼接；若上游没有 `topic`，则使用 `date` + `-` + `title`。

对于**轻量**需求探索，保持文档紧凑。当用户只需要简短对齐且不需要保留持久决策时，跳过文档创建。

### 阶段 3.5：技能内 review 闭环

当创建或更新了需求数据文档时，运行技能内 review 闭环。此环节复用现有文档审查逻辑，补强 auto 修复范围和收敛协议。

**审查调用：** 调用 `ae:review mode=headless domain=document <requirements-doc-path>`，审查者为 `requirements-reviewer`。`mode=headless` 表示 ae:review 被技能内部调用时不输出"下一步推荐技能"引导，仅返回审查结果（status/findings/summary）给本技能，由 ae:prd 自身负责下一步引导。

**auto 修复范围：** 格式不规范、章节缺失、成功标准不可验证、In/Out Scope 模糊。ae:review 返回的 auto 可修复发现由本技能自动应用修复，修复后重新运行审查。

**收敛协议（上限 2 轮）：**
- 第 1 轮：初次审查 → auto 修复 → 重新审查
- 收敛判定：重新审查后无新增 P0/P1 发现即为收敛
- 未收敛处理：2 轮后仍有 P0/P1 阻断，回退用户澄清（返回阶段 1.3 继续提问），不进入阶段 4

**结果呈现：** 若文档审查返回了自动应用的发现，在呈现交接选项时简要提及。若收敛后仍有非阻断的 P2/P3 发现，提及它们以便用户决定是否在继续之前解决。收敛后进入阶段 3.6。

### 阶段 3.6：产物行数校验与拆分

当创建或更新了需求数据文档时，运行拆分脚本：

    node <ae-prd技能目录>/scripts/split-prd.mjs <prd文件路径>

脚本自动完成：
1. 校验文件行数，≤ 300 行则退出
2. > 300 行时按 `**[分组标题]**` 切分需求章节，全局章节保留在主文件
3. 各模块需求写为 `type: prd-shard` 子文件
4. 主文件 frontmatter `sharded` 改为 `true`，`## 需求` 章节替换为分片引用列表

拆分后运行校验脚本确认：

    node <ae-prd技能目录>/scripts/check-prd-lines.mjs <prd目录路径>

校验通过后进入阶段 4。

### 阶段 4：交接

呈现下一步选项并执行用户的选择。阅读 `references/handoff.md` 获取选项逻辑、调度指令和结束摘要格式。
