# 需求捕获

此内容在阶段 3 开始时加载——在协作对话产生了值得保留的持久决策之后。

---

此文档是给 AI 工作流使用的需求数据文档，不是 PRD 汇报材料。只包含规划需要良好执行的内容，跳过对范围没有价值的章节。

需求数据文档用于产品定义和范围控制。**不要**包含实现细节（库、Schema、端点、文件布局），除非需求讨论本身是技术性的且这些细节是决策的主题。

需求文档同时面向人读和 AI 工作流。结构应偏向稳定、显式、可解析：保留固定章节名、稳定 ID、验收条件、范围边界和待定问题分类。文档正文必须自包含。

format: human-readable-requirements

**分片规则：** 需求文档以目录形式产出时，采用 `index.md` + `global.md` + `modules/<m>.md` 三层结构。模块文件采用 section anchor 分区（`##` 章节带 `{#anchor}`），不按章节拆分为独立子文件。模块文件 frontmatter 声明 `type: prd-module`、`parent:`（指向 index.md）和 `module:`（模块名）。超 300 行硬上限时按章节拆分为 `modules/<m>/` 目录。

**省略没有实质内容的可选章节**，避免生成无内容占位章节。

**非简单工作的必需内容：**
- 问题框架
- 带有稳定 ID 的具体需求或预期行为
- 范围边界
- 成功标准

**在有实质帮助时包含：**
- 关键决策及其理由
- 依赖或假设
- 待定问题
- 考虑过的替代方案

## 产物结构

需求文档以目录形式产出：

```
ae/prds/<topic>-YYYY-MM-DD/
├── index.md                        # L0 索引（自动生成，≤ 100 行）
├── global.md                       # 全局共识（单文件，section anchor 分区，≤ 300 行）
└── modules/
    └── <module-name>.md            # 模块需求（单文件，section anchor 分区，≤ 300 行）
```

**小项目模式**（<3 模块且无跨模块依赖）：
```
ae/prds/<topic>-YYYY-MM-DD/
├── index.md                        # L0 索引（自动生成，≤ 100 行）
└── prd.md                          # 全局 + 唯一模块合并单文件（≤ 300 行）
```

## Frontmatter 字段说明

### index.md

| 字段 | 值 | 说明 |
|------|-----|------|
| `type` | `prd-index` | 固定值 |
| `autoGenerated` | `true` | 自动生成标记 |
| `generatedAt` | ISO 时间戳 | 生成时间 |
| `sourceHash` | 哈希值 | 所有文件 contentHash 的聚合 |
| `version` | `"1.0"` | 版本号 |

### global.md

| 字段 | 值 | 说明 |
|------|-----|------|
| `type` | `prd-global` | 固定值 |
| `parent` | `"index.md"` | 指向索引文件 |
| `ids` | ID 数组 | 全局定义的所有稳定 ID |

### modules/\<m\>.md

| 字段 | 值 | 说明 |
|------|-----|------|
| `type` | `prd-module` | 固定值 |
| `parent` | `"index.md"` | 指向索引文件 |
| `module` | 模块名 | kebab-case 模块名 |
| `involvesUI` | `true`/`false` | 是否涉及 UI |
| `ids` | ID 数组 | 模块定义的所有稳定 ID |
| `dependsOn` | 模块名数组 | 依赖的模块 |
| `dependedBy` | 模块名数组 | 被依赖的模块 |
| `changes` | 变更数组 | 变更记录（初始为空数组） |

## superseded_by 变更追踪

需求条目变更时使用 `superseded_by` 软删除，保留历史：

1. 旧记录保留，标记 `supersededBy: <新ID>`，不从文件中删除
2. 新记录添加 `supersedes: <旧ID>` 链接
3. 默认读取只返回 `supersededBy` 为 null 的记录（当前态）
4. 单向箭头，允许链式（R1→R1.v2→R1.v3），禁止环
5. Superseded 记录用 HTML 注释隐藏：`<!-- ### R1.v1: 用户注册（已废弃） -->`

### changes 数组格式

```yaml
changes:
  - id: change-001
    date: "2026-07-24"
    type: modify          # modify | add | remove
    targetId: R1
    fromVersion: R1.v1
    toVersion: R1
    changeSummary: "密码强度要求增强"
    affectedDimensions: [api, database, ui-ux, test-cases]
    affectedIds: [EP-001, T-users, PAGE-001, ST-001, TC-001]
    blastRadius: 2
    reason: "用户反馈密码强度不足"
```

## 原型设计

### 定位

原型设计是 ae:prd 的组成部分，用于在需求阶段确定产品逻辑层的确定性边界。**不是最终页面设计**。最终页面详细设计（HTML 结构、CSS 样式、组件选型、技术栈）属于 ae:design 的 ui-ux 维度。

原型设计用 Markdown 描述页面结构和交互，内化在各模块的 `modules/<m>.md` §原型章节中。**不生成独立文件**。

### 技术栈隔离规则（硬约束）

原型设计产物（`modules/<m>.md` 的 §原型章节）**禁止出现任何前端开发技术栈或第三方依赖名称**。页面产物只描述**产品逻辑层语义**：页面要做什么、长什么样、怎么交互。技术栈信息集中收录到 `global.md` §技术栈约束。

### 确定性边界

原型必须明确锁定**产品逻辑层**的所有确定性内容：

**必须确定的：**
- 页面数量和页面列表
- 每页面的路由
- 导航结构
- 主题色声明（HEX 值，集中在 global.md §设计愿景）
- 响应式声明
- 每页面的布局结构
- 每页面的核心交互流程
- 页面间跳转关系
- 表单字段清单和必填规则

**允许差异的：**
- 具体间距、字号、圆角数值
- 字体选择
- 动画效果
- 图标样式

### 原型与 ae:design ui-ux 的关系

| | ae:prd 原型 | ae:design ui-ux |
|--|-----------|-----------------|
| **目的** | 确定产品逻辑层确定性边界 | 最终页面详细设计，供 ae:work 实施 |
| **位置** | modules/\<m\>.md §原型 | design modules/\<m\>.md §UI/UX |
| **技术栈** | **禁止出现** | 集中声明在 design global.md |
| **消费者** | 用户（验证产品逻辑确定性） | LLM（生成实现代码） |

## 行数限制

| 文件 | 限制 | 超限处理 |
|------|------|---------|
| index.md | ≤ 100 行 | - |
| global.md | ≤ 300 行硬上限 | 按章节拆分为 global/ 目录 |
| modules/\<m\>.md | ≤ 300 行硬上限 | 按章节拆分为 modules/\<m\>/ 目录 |

**所有文件生成时即保证不超限，不产出大文件再后置拆分。**

## 完整性检查

在最终确定之前，检查：
- 如果这个需求探索现在结束，`ae:design` 还需要发明什么？
- 是否有任何需求依赖于声称在范围之外的东西？
- 是否有任何未解决的项目实际上是产品决策而非规划问题？
- 是否有不应该出现的实现细节泄漏了进来？
- 是否有不应该出现的汇报型内容泄漏了进来？
- 是否有任何需求声称基础设施不存在而该声明尚未对照代码库验证？
- 每个需求条目是否都有明确的验收条件？
- 是否保留了足够稳定 ID，使 `ae-doc-extract` 可按 ID 或模块提取所需上下文？
- `global.md` 的模块清单与实际产出的 `modules/` 文件是否一致？

如果规划需要发明产品行为、范围边界或成功标准，需求探索还没有完成。

在写入之前确保 `ae/prds/` 目录存在。需求文档以目录形式产出，目录名为 `<topic>-YYYY-MM-DD`。

## 视觉辅助

视觉辅助以内容模式为条件，而非以深度分类为条件。

**何时包含：**

| 需求描述的是... | 视觉辅助 | 放置位置 |
|---|---|---|
| 多步骤用户工作流或流程 | Mermaid 流程图（`flowchart`） | 在 global.md §问题框架之后 |
| 3+ 种行为模式、变体或状态 | Markdown 比较表 | 在 modules/\<m\>.md §需求内 |
| 3+ 个交互参与者 | Mermaid 关系图 | 在 global.md §问题框架之后 |
| 多个竞争方案 | 比较表 | 在阶段 2 方案探索中 |

**格式选择：** Mermaid（默认）用于流程图、关系图和时序图；Markdown 表格用于模式/变体比较。文字是权威的：视觉辅助与文字不一致时以文字为准。
