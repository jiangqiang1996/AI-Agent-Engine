# 需求捕获

此内容在阶段 3 开始时加载——在协作对话产生了值得保留的持久决策之后。

---

此文档是给 AI 工作流使用的需求数据文档，不是 PRD 汇报材料。只包含规划需要良好执行的内容，跳过对范围没有价值的章节。

需求数据文档用于产品定义和范围控制。**不要**包含实现细节（库、Schema、端点、文件布局），除非需求讨论本身是技术性的且这些细节是决策的主题。

需求文档同时面向人读和 AI 工作流。结构应偏向稳定、显式、可解析：保留固定章节名、稳定 ID、验收条件、范围边界和待定问题分类。文档正文必须自包含。

format: human-readable-requirements

**自包含约束（硬约束）：** 需求文档目录完全自包含，禁止引用外部工作空间文件。目录内文件只通过稳定 ID 相互引用。版本演化 = 独立新目录，不指向旧版本目录。

**省略没有实质内容的可选章节**，避免生成无内容占位章节。

**非简单工作的必需内容：**
- 问题框架
- 带有稳定 ID 的具体需求或预期行为
- 范围边界
- 成功标准

**在有实质帮助时包含：**
- 关键决策及其理由
- 依赖或假设
- 待定问题
- 考虑过的替代方案

## 产物结构

需求文档以目录形式产出：

```
ae/prds/<topic>-YYYY-MM-DD/
├── overview.md                     # 问题框架、范围边界、模块清单
├── decisions.md                    # 跨模块决策（可选）
├── non-functional.md               # 全局非功能（可选）
├── tech-stack.md                   # 技术栈约束（可选，用户明确指定时）
├── design-vision.md                # 设计愿景 + 路由表 + 导航结构（可选，涉及 UI 时）
└── modules/
    └── <NN>-<module-name>/         # 模块子目录（两位数字序号 + 模块名）
        ├── requirements.md          # 模块需求 + 成功标准
        └── pages/                   # 每个页面独立文件（涉及 UI 时）
            ├── <NN>-<page-name>.md   # 路由、布局结构、交互流程、字段清单、响应式布局
            └── ...
```

## overview.md 模板

```markdown
---
type: prd-overview
---

# 问题框架

[用户目标、当前痛点、成功判据]

## 范围边界

### In Scope
- 用户认证与授权
- 资源 CRUD

### Out Scope
- 社交功能
- 支付集成

### 模块清单
| 模块 | 边界声明 | 可调整 |
|------|---------|--------|
| auth | 认证域，不包含权限策略 | 是 |
| resource | 资源域，依赖 auth 的会话 | 是 |
```

## modules/\<NN\>-\<m\>/requirements.md 模板

```markdown

---

## 需求

### R1: 用户注册
用户可使用邮箱和密码注册账号。密码需至少 8 位含大小写字母和数字。
- -> 验收: SC1

### R2: 用户登录
已注册用户可使用邮箱和密码登录。
- -> 验收: SC2
- 依赖: R1

## 成功标准

### SC1: 注册成功后用户存在于系统中
### SC2: 登录成功后返回有效会话令牌
```

## 原型设计

### 定位

原型设计是 ae:prd 的组成部分，用于在需求阶段确定产品逻辑层的确定性边界。**不是最终页面设计**。最终页面详细设计（HTML 结构、CSS 样式、组件选型、技术栈）属于 ae:design 的 ui-ux 维度。

原型设计用 Markdown 描述页面结构和交互，产出在各模块的 `modules/<NN>-<m>/pages/` 目录下，每个页面独立文件。仅当模块 `involvesUI=true` 时产出。

### 技术栈隔离规则（硬约束）

原型设计产物（`pages/<NN>-<page-name>.md`）**禁止出现任何前端开发技术栈或第三方依赖名称**。页面产物只描述**产品逻辑层语义**：页面要做什么、长什么样、怎么交互。技术栈信息集中收录到 `tech-stack.md`。

### 确定性边界

原型必须明确锁定**产品逻辑层**的所有确定性内容：

**必须确定的：**
- 页面数量和页面列表
- 每页面的路由
- 导航结构
- 主题色声明（HEX 值，集中在 design-vision.md）
- 响应式声明
- 每页面的布局结构
- 每页面的核心交互流程
- 页面间跳转关系
- **每页面的字段清单和必填规则**

**允许差异的：**
- 具体间距、字号、圆角数值
- 字体选择
- 动画效果
- 图标样式

### 原型与 ae:design ui-ux 的关系

| | ae:prd 原型 | ae:design ui-ux |
|--|-----------|-----------------|
| **目的** | 确定产品逻辑层确定性边界 | 最终页面详细设计，供 ae:work 实施 |
| **位置** | modules/\<NN\>-\<m\>/pages/\<NN\>-\<page-name\>.md | design modules/\<NN\>-\<m\>/pages/\<NN\>-\<page-name\>.md |
| **技术栈** | **禁止出现** | 集中声明在 design ui-ux.md |
| **消费者** | 用户（验证产品逻辑确定性） | LLM（生成实现代码） |

## 完整性检查

在最终确定之前，检查：
- 如果这个需求探索现在结束，`ae:design` 还需要发明什么？
- 是否有任何需求依赖于声称在范围之外的东西？
- 是否有任何未解决的项目实际上是产品决策而非规划问题？
- 是否有不应该出现的实现细节泄漏了进来？
- 是否有不应该出现的汇报型内容泄漏了进来？
- 是否有任何需求声称基础设施不存在而该声明尚未对照代码库验证？
- 每个需求条目是否都有明确的验收条件？
- 是否保留了足够稳定 ID，使各文件可按 ID 或模块提取所需上下文？
- `overview.md` 的模块清单与实际产出的 `modules/` 文件是否一致？

如果规划需要发明产品行为、范围边界或成功标准，需求探索还没有完成。

在写入之前确保 `ae/prds/` 目录存在。需求文档以目录形式产出，目录名为 `<topic>-YYYY-MM-DD`。

## 视觉辅助

视觉辅助以内容模式为条件，而非以深度分类为条件。

**何时包含：**

| 需求描述的是... | 视觉辅助 | 放置位置 |
|---|---|---|
| 多步骤用户工作流或流程 | Mermaid 流程图（`flowchart`） | 在 overview.md 问题框架之后 |
| 3+ 种行为模式、变体或状态 | Markdown 比较表 | 在 modules/\<NN\>-\<m\>/requirements.md 需求内 |
| 3+ 个交互参与者 | Mermaid 关系图 | 在 overview.md 问题框架之后 |
| 多个竞争方案 | 比较表 | 在阶段 2 方案探索中 |

**格式选择：** Mermaid（默认）用于流程图、关系图和时序图；Markdown 表格用于模式/变体比较。文字是权威的：视觉辅助与文字不一致时以文字为准。
