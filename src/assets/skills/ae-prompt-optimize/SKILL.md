# 提示词优化

## 角色与目标

将用户随意输入的提示词优化为结构化、利于 AI 执行的提示词，经用户确认或通过 `mode` 参数预先指定后，在新会话中提交执行或暂停等待。优化必须忠实于用户原始意图，禁止与原始逻辑违背。

## 适用场景

- 用户输入口语化、模糊或结构松散的提示词，希望提升 AI 执行效果。
- 用户提示词信息不足、意图不清，需要先追问澄清再优化。
- 用户希望在新会话中执行优化后的提示词，避免当前会话上下文污染。
- 用户明确要求"提交并暂停执行"，希望新会话仅作为历史上下文承载，等待后续输入。
- 用户通过 `mode=auto` 或 `mode=pause` 参数预先指定提交方式，希望跳过确认提问实现一键提交。

## 不适用场景

- 用户提示词已经结构化、清晰且无需优化。
- 用户明确要求在当前会话内继续执行，而不是开新会话。

## 执行流程

### 阶段 0：解析参数

解析用户输入中的 `mode` 参数，决定后续阶段 5 的确认提问策略：

| 参数值 | 含义 | 阶段 5 行为 |
|--------|------|-------------|
| `mode=auto` | 直接提交并自动执行 | 跳过确认提问，进入阶段 6 直接以"提交并自动执行"方式提交 |
| `mode=pause` | 直接提交并暂停 | 跳过确认提问，进入阶段 6 直接以"提交并暂停执行"方式提交 |
| 未提供 | 询问确认 | 展示优化结果并通过 `question` 工具询问用户选择 |

参数解析规则：

1. 支持 `key=value`、`key:value`、纯值自动推断三种格式（AE 技能参数通用约定）。
2. 纯值 `auto` 或 `pause` 自动推断为 `mode` 参数。仅当 `auto`/`pause` 作为独立 token 出现时才推断为 `mode` 参数；若嵌入在句子中作为普通词语（如"帮我优化 auto 这个词的用法"），按普通提示词处理，不推断为 `mode`。
3. `mode` 参数缺失或值非 `auto`/`pause` 时，按"未提供"处理。
4. `mode=auto` 或 `mode=pause` 只跳过阶段 5 的"提交确认"提问；阶段 2 的意图澄清追问不跳过——提示词本身模糊时仍需先追问澄清。
5. 跳过确认提问后，优化结果展示与提交连续执行；若用户发现优化结果与意图冲突，可在新会话创建后于目标会话中修正或中止。

### 阶段 1：解析用户输入

1. **识别引用**：扫描提示词中用户明确提到的命令、代理、技能、工具引用：
   - `/xxx` —— 以 `/` 开头的命令
   - `@xxx` —— 以 `@` 开头的代理
   - 包含 `:` 或 `-` 连接的多词标识符（如 `ae:brainstorm`、`task-loop`）

   匹配到的引用原样保留，不校验其是否真实存在，不当作普通词语对待。

2. **提取实际提示词**：识别引用后，将引用与非引用部分分离，准备对非引用部分进行优化。

### 阶段 2：意图澄清

用户原始提示词可能存在信息不足或意图模糊的情况。在进入优化前，必须评估提示词的清晰度：

**模糊信号检测：**

| 信号 | 示例 |
|------|------|
| 目标缺失 | "帮我搞一下那个东西" — 无明确目标 |
| 范围模糊 | "优化一下" — 优化什么？哪些方面？ |
| 对象不清 | "改一下文件" — 哪个文件？改什么内容？ |
| 条件缺失 | "做个功能" — 什么功能？给谁用？有什么约束？ |
| 动词空洞 | "处理一下"、"完善一下" — 具体做什么操作？ |

**追问规则：**

1. 如果检测到模糊信号，使用 `question` 工具向用户发起追问，每次只问一个最关键的澄清问题。
2. 追问问题必须聚焦于对优化结果影响最大的缺失信息（目标、范围、对象、约束）。
3. 追问问题附带推荐理解方向，帮助用户快速补充信息。
4. 用户补充信息后，合并到原始提示词，重新评估清晰度。
5. 最多追问 3 轮；如果 3 轮后仍不清晰，以当前最佳理解为基础继续优化，并在优化结果中标注仍存在的模糊点。
6. 如果提示词足够清晰（目标明确、范围可界定、无关键信息缺失），跳过追问，直接进入阶段 3。

**追问与 `ae:grill` 的区别：**

- 本技能的追问是快速澄清提示词意图，1-3 轨内完成，目的是让优化有足够输入。
- `ae:grill` 是对已有方案的逐层决策压力测试，追问更深入、更系统。
- 如果追问过程中发现用户需要深度探讨决策合理性，建议转交 `ae:grill`。

### 阶段 3：工作空间相关性分析

在优化前，判断用户提示词是否与当前工作空间的文件相关：

- **相关信号**：提示词显式或隐式指向当前工作空间内的文件、目录、模块、代码符号、配置、资产或项目结构。例如提到具体路径、文件名、模块名、技能名、命令名，或描述针对当前项目的修改、审查、构建、测试等操作。
- **无关信号**：提示词是通用问答、纯概念讨论、与当前项目无关的外部任务，或用户已提供完整自包含上下文。

判断结论决定阶段 4 的优化策略：

| 相关性 | 优化策略 |
|--------|----------|
| 无关 | 禁止镀金、禁止蔓延边界。仅对非引用部分做结构化与清晰度优化，不补充工作空间上下文，不假设文件路径或技术栈 |
| 有关 | 可结合当前工作空间情况适度优化。补充的上下文必须有可观察依据（用户已提及、文件系统可见、图谱线索），并标注来源；不得凭空假设 |

工作空间相关性判断的依据必须可复核：若结论为"有关"，至少说明一条可观察信号；若证据不足，按"无关"处理。

### 阶段 4：优化提示词

对非引用部分的文本执行优化：

1. **结构化**：将模糊、口语化的表述转为结构化的任务描述（目标、约束、验收标准）。
2. **补充上下文**：仅在"有关"分支下，根据可观察依据补充隐含信息（如文件范围、技术栈、运行环境）。补充内容必须标注来源。
3. **改善清晰度**：消除歧义表述，使 AI 能一次理解完整意图。

**硬规则（绝不可违反）：**

- 不得改变用户原始意图和逻辑。
- 优化后的提示词不得与原始逻辑违背：用户未要求的步骤、范围、约束不得擅自添加；用户明确排除的不得擅自保留。
- 用户提到的命令、代理、技能引用原样保留，不做任何修改。
- 优化后提示词应直接表达目标任务，避免在新会话中再次触发提示词优化流程。
- "无关"分支下禁止补充工作空间上下文；禁止凭空假设文件路径、模块名或技术栈。

**指导原则（可据情调整）：**

- 优化后提示词的长度应适中——不过度膨胀，也不遗漏关键信息。
- 优先保持用户原有表述风格，仅在确实模糊时才改写。
- 补充的上下文应有明确依据（用户已提及或显而易见），不凭空假设。

**浏览器能力门禁：**

- 如果优化后提示词会引导目标新会话使用 `chrome-devtools-mcp`、`ae:web-forge`、`/ae-web-forge`、`@ui-architect`、`@logic-weaver`、`@browser-inspector`，优化后的提示词必须明确要求目标新会话先使用 `ae:chrome-devtools` 技能完成浏览器 MCP 动态注册；`ae:chrome-devtools` 是浏览器 MCP 的唯一管理入口，不应直接调用 `ae-chrome-devtools-mcp` 工具。得到 MCP 连接就绪结果后再执行浏览器流程。
- 同一工作区的 chrome-devtools MCP 注册状态可以跨会话复用；MCP 未注册、注册失败或连接状态非 connected 时，目标新会话必须自行完成动态注册。
- chrome-devtools MCP 已在配置中声明、用户声称已配置或本地进程检查成功，都不能替代 MCP 注册校验。

**自检清单（优化完成后逐项确认）：**

- [ ] 用户原始意图是否完整保留？
- [ ] 优化结果是否未与原始逻辑违背？
- [ ] 用户提到的引用是否都已保留且未被修改？
- [ ] 是否未添加任何元描述或引导文本？
- [ ] 工作空间上下文补充是否有可观察依据并标注来源（仅"有关"分支）？
- [ ] "无关"分支是否未补充工作空间上下文？

### 阶段 5：用户确认

1. **展示优化结果**：直接输出优化后的完整提示词，不得包含"这是优化后的提示词"、"优化结果如下"等任何元描述或引导文本。
2. **参数分流**：
   - 若阶段 0 解析到 `mode=auto`：跳过确认提问，展示后直接进入阶段 6 以"提交并自动执行"方式提交。
   - 若阶段 0 解析到 `mode=pause`：跳过确认提问，展示后直接进入阶段 6 以"提交并暂停执行"方式提交。
   - 若未解析到 `mode` 参数：使用 `question` 工具询问用户选择，选项包括：
     - **提交并自动执行**：在新会话中提交提示词并触发 AI 回复
     - **提交并暂停执行**：在新会话中作为历史上下文注入，不触发自动回复，等待用户新输入
     - **修改**：结合用户新的输入继续优化

     这是强制步骤，绝不能跳过。
3. **多轮修改**：若用户选择修改，根据反馈迭代调整，修改完成后再次展示并询问确认。
   - 始终以原始输入作为参考锚点，避免多轮迭代后偏离原始意图。
   - 若用户修改意见与硬规则冲突（如要求删除引用），告知冲突但遵从用户最终决定。
   - 每轮修改后重新执行自检清单。
4. **确认提交**：用户明确选择"提交并自动执行"或"提交并暂停执行"后方可进入阶段 6。`mode=auto` 或 `mode=pause` 跳过本步骤。

### 阶段 6：提交执行

统一调用 `ae-create-session` 工具创建新会话。提交方式由阶段 0 的 `mode` 参数或阶段 5 的用户确认结果决定：

| 提交方式来源 | ae-create-session 参数 |
|--------------|------------------------|
| `mode=auto` 或用户选择"提交并自动执行" | `user_prompt=优化后提示词`，`auto_execute=true`，`navigate=true`，`require_confirmation=false` |
| `mode=pause` 或用户选择"提交并暂停执行" | `context_message=优化后提示词`，`auto_execute=false`，`navigate=true`，`require_confirmation=false` |

- `title`（可选）：若用户指定了标题则传入。
- "提交并暂停执行"模式下，优化后的提示词作为 `context_message` 注入新会话，不发送为 user_prompt，因此不会触发自动回复；用户切换到新会话后可基于该上下文继续输入。
- `require_confirmation=false`：默认流程下阶段 5 已完成用户确认；`mode=auto`/`mode=pause` 场景下用户已通过参数预先指定提交方式。调用 `ae-create-session` 时不再二次请求确认。
- 若工具返回错误，展示错误信息并将已确认的提示词完整展示给用户，提供重试或手动复制的选项。

## 边界

- 不得修改当前工作空间的任何文件；本技能只优化提示词并创建新会话。
- 工作空间相关性判断和上下文补充必须基于可观察证据（文件系统、图谱线索、用户已提及内容）；不得凭空假设。
- 图谱和文件系统证据冲突时，以最新可观察证据为准；图谱空结果不得作为"文件不存在"的结论。
- 不替代 `ae:handoff` 的结构化会话摘要提取；需要交接历史会话上下文时使用 `ae:handoff`。
- 不在当前会话内执行目标任务；目标任务由新会话承载。

## 输出要求

- 优化结果展示必须干净利落：直接输出提示词内容本身，不得包含任何元描述或引导文本。
- 提交执行后，简述新会话创建结果（会话地址、是否导航、是否提交提示词），不重复展示完整提示词。
- 失败时输出错误信息和可恢复提示词，提供重试或手动复制选项。

## 验证方式

- 结构校验：通过 `/ae-help ae:prompt-optimize` 确认技能可被帮助目录发现。
- 提交执行后，确认 `ae-create-session` 工具返回新会话地址、导航状态和提示词提交结果。

## 禁止事项

- 不得改变用户原始意图和逻辑。
- 不得在"无关"分支补充工作空间上下文。
- 不得凭空假设文件路径、模块名或技术栈。
- 不得跳过阶段 5 的用户确认（除非阶段 0 解析到 `mode=auto` 或 `mode=pause`）。
- `mode=auto` 或 `mode=pause` 只跳过阶段 5 的提交确认提问，不得跳过阶段 2 的意图澄清追问。
