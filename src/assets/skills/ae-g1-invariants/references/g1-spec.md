# G1 步骤摘要

## 目标

把模糊的业务需求转化为可判定的不变量和清晰的系统边界。

## 核心规则

- 不变量必须能回答 true/false，不允许模糊表述
- 好的不变量示例："用户余额不可为负"——查任意用户记录，balance < 0 即违反
- 坏的不变量示例："系统要安全"——无法判定 true/false

## 任务清单

| 任务 | 说明 |
|------|------|
| T1 提取业务不变量 | 从需求中提取约束，每条含 id、statement 可证伪表述、scope 全局/模块级、falsification 证伪方法、severity P0/P1/P2 |
| T2 编写证伪条件 | 为每条不变量编写可操作的证伪步骤 |
| T3 划定系统边界 | includes 纳入项、excludes 排除项+理由、modules 模块/端列表+职责+类型 |
| T4 识别模块/端拆分点 | 列出所有模块，检查职责不重叠 |
| T5 标注端/模块类型 | Web前端/移动端/桌面端/后台服务/开放API/嵌入式等 |
| T6 记录需求歧义点 | 每个歧义点给出AI默认推断，最终由用户裁定 |

## 验收关卡

| 编号 | 检查项 | 通过标准 |
|------|--------|---------|
| G1-K1 | 不变量可证伪 | 每条可通过 falsification 字段构造出反例 |
| G1-K2 | 不变量无矛盾 | 不存在 A 说"X 必须为真"而 B 说"X 可以为假" |
| G1-K3 | 模块职责不重叠 | 任意两个模块的职责描述无语义交叉 |
| G1-K4 | 歧义已裁定 | 无 resolved: false 的条目 |
| G1-K5 | 用户确认边界 | 用户确认纳入/排除范围无遗漏 |
| G1-K6 | 文件行数合规 | 所有产物文件不超过 500 行 |

## 变更传播

本步是起点，修改本步产物后需要向下游传播，但本步本身不会被下游步骤回退触发。

## 通用产物规格

- 单轨格式：YAML Frontmatter 为唯一真源，正文为人类阐释
- 文件行数硬约束：每个产物文件不超过 500 行
- 超过时拆分为目录结构，含 index.md 汇总索引
- 不变量贯穿全链路：每条不变量必须在后续每步产物中有对应条目
