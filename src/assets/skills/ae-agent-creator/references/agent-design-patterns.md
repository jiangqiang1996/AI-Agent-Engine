# 代理设计模式

## 设计原则

- 让代理专注于一个明确职责，而不是写成万能助手。
- 描述应说明何时使用、何时不使用，以及代理能交付什么结果。
- 正文应给出可执行工作流和输出格式，而不是只写抽象人格。
- 权限和工具按最小需要配置，默认不放宽。
- 更新既有代理时采用最小编辑，避免整篇重写造成职责、边界或禁用项被意外覆盖。

## 更新既有代理

- 先读取旧代理，识别仍有效的职责边界、适用场景、不适用场景、工作流、输出契约和安全边界。
- 草案应说明保留哪些旧内容、修改哪些段落、删除或重写哪些段落，以及为什么需要这些变化。
- 不把单一职责代理改成万能助手；新增能力必须能追溯到用户目标。
- 不删除旧正文中的确认要求、禁止事项、Git 边界、浏览器 setup 要求或权限限制，除非用户明确要求且已单独确认风险。
- 如果校验失败，只修复导致失败的最小问题；涉及语义、权限或命令绑定变化时再次确认。

## 推荐结构

代理正文建议包含这些部分：

```markdown
# Role

说明代理的专业身份和目标。

## When To Use

列出适用场景。

## When Not To Use

列出不适用场景和应交回主会话的情况。

## Workflow

列出代理执行任务的步骤。

## Output

说明输出结构、证据要求和未完成项表达方式。

## Boundaries

说明权限、验证、Git 操作和安全边界。
```

## subagent 写法

- 强调输入输出契约，便于主代理委派。
- 输出要短而结构化，避免把上下文污染扩大到主会话。
- 如果只做研究或审查，应明确不修改文件。

## primary 写法

- 强调持续对话行为、默认执行策略和用户确认边界。
- 对写操作、Git 操作、浏览器操作等高风险行为写清确认条件。
- 避免与 OpenCode 内置主代理职责完全重叠。

## 命名建议

- 使用 `kebab-case`。
- 名称表达专业职责，例如 `api-contract-reviewer`、`release-note-writer`。
- 避免 `helper`、`assistant`、`expert` 这类泛化名称。

## 质量标准

- 代理能说明自己不该处理什么。
- 代理能给出可验证产物或清晰结论。
- 代理不会建议跳过测试、跳过权限确认或绕过 Git 安全边界。
- 代理不会提供推送、创建 PR、创建 Release 等远程写操作流程；需要外部协作时只输出摘要、证据和建议。
