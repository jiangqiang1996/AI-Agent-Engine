# L2 子模块独立设计

## 角色

L2 步骤的执行者，在 A1 契约约束下为单个指定模块完成内部逻辑设计，产出可直接指导编码的设计文档和 DDL。

## 适用场景

- L1 步骤已完成，紧邻前序技能为 L1（界面文档描述），需要为各模块做内部设计
- 用户说"设计模块 X"、"完成模块设计"、"写模块设计文档"、"生成 DDL"
- 已有上游产物（G1/G2/G3/G4/G5/A1/A2/L1），需推进到模块级设计

## 不适用场景

- 前序技能产物（G1/G2/G3/G4/G5/A1/A2/L1）未就绪时不得执行本技能
- 未完成 L1 或更早阶段（应先执行对应上游技能）
- 需要修改上游产物（本技能只读上游）
- 需要修改其他模块的设计（本技能只处理 `module` 参数指定的模块）
- 跨模块协调（属于 A1 契约层职责）

## 输入自动发现

本技能需要用户指定 `module` 参数（目标模块名），其余输入自动发现：

1. **产物根目录发现**：在工作区 `docs/ae/galv/` 下搜索 `galv-manifest.yaml`，取其 `project_name` 字段定位根目录 `docs/ae/galv/<项目名>/`（若搜索到多个 manifest，提示用户选择目标项目）
2. 若未找到 manifest，提示用户先执行 G1 创建 manifest
3. **上游产物发现**：从产物根目录按上游依赖表自动读取已存在的上游产物文件；缺失时记录警告，不阻断执行
4. **模块名来源**：用户通过 `module=<模块名>` 参数指定；若未指定，从 G4 数据模型或 A1 契约中提取模块列表供用户选择
5. 用户也可显式传入项目名覆盖自动发现结果

## 输入

| 参数 | 必填 | 说明 |
|------|------|------|
| module | 是 | 目标模块名，决定产物写入路径 |

## 产物根目录

所有产物写入**产物根目录**下。默认根目录为 `docs/ae/galv/<项目名>/`。

`<项目名>` 由以下规则确定：
1. 若产物根目录下已存在 `galv-manifest.yaml`，读取其中的 `project_name` 字段作为项目名
2. 若不存在，在工作区 `docs/ae/galv/` 下搜索已有的 `galv-manifest.yaml` 自动定位
3. 若仍未找到，提示用户先执行 G1 技能创建 manifest

整个根目录自包含、可移植：内部所有路径均为相对路径，目录可整体移动到任意位置。读取全部阶段产物后，任何 AI 工具可据此生成功能等价、结构等价的软件系统。

本阶段的产物位于根目录下 `l2/` 子目录。

## 产物独占

**独占产物**：只有本技能可以创建或修改（路径相对于产物根目录）：

```
l2/{module}/design/
  index.md                  ← 模块职责概览、功能清单、契约合规声明总表
  design-{feature}.md       ← 按功能拆分的设计文档

l2/{module}/ddl.sql            ← 数据库表结构定义
```

目录形式时，`index.md` Frontmatter 必须包含 `type: directory_index` 和 `slices` 字段。

**共享产物**：`galv-manifest.yaml`（首次创建时由当前执行的技能负责，后续技能可读取和追加信息）

**禁止修改**上游技能产物（G1/G2/G3/G4/G5/A1/A2/L1），对上游产物只读。同时禁止修改下游技能产物（L3/V1/V2）。

## 上游依赖（只读）

- G1、G2、G3、G4、G5、A1、A2 的所有产物
- L1 产物：`l1/ui-spec/`、`l1/restore-score.md`

## 执行流程

### 前置检查

1. 确认 `module` 参数已提供，否则提示用户指定
2. 读取上游产物，确认关键依赖可用；缺失时提示用户先完成对应阶段

### T1 确认职责范围

- 读取 `a1/contracts/index.md` 中 source 或 target 为本模块的契约条目
- 从 `g2/business-scenarios/` 中提取本模块相关的业务场景
- 整理本模块参与的契约清单，明确角色（source / target / 双向）
- 确认职责边界，识别不属于本模块的功能并排除

### T2 设计内部逻辑

按功能拆分，为每个功能编写 `design-{feature}.md`，包含：

- **API 路由**：路径、方法、中间件链、处理流程
- **消息处理**：消息类型、消费逻辑、幂等策略
- **定时任务**：调度规则、执行逻辑、并发控制
- **业务计算**：算法描述、输入输出、边界条件
- **数据访问**：查询模式、缓存策略、批量操作

每条逻辑必须：
- 引用 `g4/data-model/` 中归属本模块的实体和不变量
- 引用 `g2/business-scenarios/` 中本模块相关的操作序列
- 明确 preconditions 和 postconditions
- 标注与契约 obligations 的对应关系

### T3 设计数据库表结构

基于 `g4/data-model/` 中归属本模块的实体，生成 `l2/{module}/ddl.sql`：

- 完整的 CREATE TABLE 语句（含字段类型、约束、默认值、注释）
- 禁止 FOREIGN KEY 约束，引用在注释 `-- ref: Entity.field` 中声明
- 索引定义（含索引类型、覆盖字段、并发策略）
- 分区策略（如适用，标注分区键和分区规则）
- 性能暗示注释（标注预期数据量、查询模式、索引选择理由）

### T4 设计接口实现

细化每个对外接口：

- **参数校验规则**：类型、范围、格式、必填/选填、嵌套校验
- **错误码和错误响应格式**：编码规则、HTTP 状态码映射、响应体结构
- **重试策略**：可重试条件、退避算法、最大重试次数
- **降级方案**：降级触发条件、降级行为、恢复策略
- **安全约束**：引用 `g3/security.md` 认证授权约束

### T5 设计状态管理

基于 `g4/state-machines/`，为涉及状态迁移的功能：

- 实现状态迁移守卫逻辑（guard conditions）
- 定义迁移触发器和副作用
- 处理非法迁移的拒绝逻辑和错误响应
- 确保与 `g4/state-machines/` 定义完全一致

### T6 填写契约合规声明

在 `index.md` 中列出契约合规声明总表：

| 契约ID | 本模块角色 | obligations | 满足方式 | 合规检查方式 |
|--------|-----------|-------------|---------|-------------|
| C-xxx | source | ... | 引用设计文档章节 | 对应测试/验证点 |

确保本模块参与的所有契约 obligations 均已声明满足。

### T7 编写内部推演用例

- **正常路径**：每条逻辑至少 1 个，含完整输入→处理→输出链路
- **前置条件违反**：每条前置条件至少 1 个违反用例，验证守卫生效
- **不变量守卫**：每个不变量至少 1 个守卫用例，验证不变量不被破坏

### T8 定义全局错误处理策略

为多模块场景定义统一错误处理策略，写入 `l2/{module}/design/error-strategy.md` 或合并到 `index.md`：

1. **错误码全局编码规则**：模块前缀 + 序号，确保跨模块唯一
2. **错误传播规范**：同步调用返回错误码，异步事件携带错误上下文
3. **关联ID标准**：全链路 trace_id 传递规则
4. **结构化日志格式**：统一字段名、时间格式、日志级别

### T9 产物审查

对当前阶段全部产物执行自检：

1. 逐条对照验收关卡 L2-K1~L2-K10
2. 确认每个产物文件不超过 500 行
3. 确认所有 Frontmatter 引用可解析到上游产物
4. 不通过项立即修复后重新检查
5. 调用 `ae:review mode=autofix domain=document` 审查 `l2/{module}/` 目录

## 单轨格式规则

所有产物文件采用 Markdown + YAML Frontmatter 单轨格式：

- Frontmatter 为机器可读的唯一真源，正文为人类阐释
- 正文不允许出现 Frontmatter 中不存在的实体名、字段名、规则名
- 正文只允许包含：Frontmatter 字段的业务含义解释、设计决策的理由、用户确认记录
- 如需补充信息，必须先在 Frontmatter 中添加对应条目，再在正文中解释
- 每条 Frontmatter 条目可标注 `origin` 字段：`derived`（从上游推导，可信度最高）、`inferred`（AI 推断补充，需人工确认）、`asserted`（人类断言，最可靠）

## 验收关卡

| 编号 | 检查项 | 通过标准 |
|------|--------|---------|
| L2-K1 | 无跨模块硬编码 | 外部引用指向 A1 契约，不硬编码其他模块内部 |
| L2-K2 | 契约合规完整 | 本模块参与的所有契约 obligations 均已满足 |
| L2-K3 | DDL 可执行 | ddl.sql 与 g4/data-model/ 中本模块实体一致，无 FOREIGN KEY |
| L2-K4 | 状态机一致 | 与 g4/state-machines/ 一致 |
| L2-K5 | 界面对应 | 如有界面，与 l1/ui-spec/ 中本模块视图一一对应 |
| L2-K6 | 不变量有实现 | 本模块范围的不变量全部有实现条目 |
| L2-K7 | 文件行数合规 | 所有产物文件不超过 500 行 |
| L2-K8 | 人工审核通过 | 用户确认模块设计合理、契约合规、DDL 可落地 |
| L2-K9 | 全局错误策略一致 | 错误码/传播/关联ID/日志格式在所有模块间一致 |
| L2-K10 | 审查通过 | ae:review 审查 l2/{module}/ 目录无阻断发现 |

## 回退说明

| 问题类型 | 回退目标 |
|---------|---------|
| 契约理解偏差 | A1 |
| 模块内部设计错误 | 仅本模块重做受影响子文件 |

## 安全边界

- 禁止修改上游产物，对上游产物只读；发现上游问题时标注并建议回退
- 本技能禁止读取或引用执行顺序在本技能之后的任何技能产物（L3/V1/V2），以保证回退时后续产物不可见
- 禁止修改其他模块的设计产物
- 禁止在设计中硬编码其他模块的内部实现细节
- 外部交互必须通过 A1 契约引用，不得绕过契约层
- DDL 仅包含本模块实体的表定义

## 并行说明

多模块场景下，用户应多次调用本技能，每次指定不同的 `module` 参数。各模块设计互不阻塞，可并行执行。L2-K8 须由用户确认后方可视为本步骤完成。
