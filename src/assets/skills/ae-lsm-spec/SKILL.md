# LSM 需求规格

## 角色

把用户目标转化为详细的软件工程需求文档，固定 `R-*` 需求 ID、上游边界和后续阶段入口。

## 适用场景

- 用户明确要求 LSM 链路、`ae:lsm-spec` 或完整需求规格
- 需要把目标拆成可追溯的需求和下游输入
- 需要从明确上游路径或交接文件继续

## 不适用场景

- 普通"修复 bug""给功能写计划""执行小改动"
- 非软件任务或单阶段软件任务
- 仅需要通用 `ae:prd`、`ae:plan`、`ae:work`、`ae:lfg` 或 `ae:review`
- 需求已明确且已有需求文档，应直接进入 `ae:lsm-design`

## 输入处理

1. 用户显式传入目标描述、需求路径或上游交接路径时，以显式输入为准
2. 无显式输入时，根据当前会话讨论的主题，在工作区 `ae/lsm/` 下搜索最符合的产物路径
3. 推测不到对应的输入产物时，明确拒绝执行并提示用户传入目标描述或路径
4. 不自动选择历史目录中的产物，不猜测历史来源

## 执行流程

1. 解析输入：目标描述 / 需求路径 / 上游交接路径 / 会话推测
2. 与用户澄清需求范围、成功标准、非目标和约束
3. 拆分需求为可追溯的 `R-*` 需求条目
4. 生成需求文档；文档过大时按模块或功能域拆分为多个子需求文件
5. 不包含人员分工等通用模板内容，只聚焦软件工程需求
6. 调用 `ae:review domain=document kind=document targets=document` 对 spec 产物进行审查
7. 审查通过后，向用户推荐下一步技能

## 产物要求

- 产物路径：`ae/lsm/spec/`
- 使用 `references/spec-template.md` 作为结构参考
- 包含上游路径、输入 ID、输出 ID、追溯表、验证证据、未验证项和下一步入口
- 需求文档过大时拆分为多个子需求文件，主文件建立索引

## 安全边界

- 不自动选择历史目录中的产物
- 不新增 GitHub Issue、Pull Request、Release 或推送远程分支流程
- 不引用 `ae:review` 之外的任何非 LSM 技能
- 返工时仅修改本技能产物（spec），不修改下游产物

## 完成标准

- 产物包含 `R-*` 需求 ID
- spec 已通过 `ae:review` 审查，审查结论为 passed 或有明确的未阻断发现
- 下一步推荐：`ae:lsm-design`（将规格转为设计）
