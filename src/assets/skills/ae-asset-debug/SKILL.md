# AE 资产调试

把一次性纠偏转化为可持久化的 opencode 资产修复。核心目标只有一个：找出当前会话中真正生效并导致偏航的资产，给出证据，在安全条件下修复项目级自然语言资产，或明确说明为什么只能诊断。

## 执行铁律

必须按阶段顺序执行。没有满足当前阶段退出条件，不得进入下一阶段。

- 先定位生效资产，再分析偏差；不得直接改文档。
- 入口资产不等于执行资产；命令、别名、转发技能必须拆开看。
- 没有实际调用链或用户确认时，不得仅凭触发入口自动选择资产。
- 全局资产默认只读诊断；不得写全局资产、用户主目录、外部插件目录或其他项目。
- 代码实现资产默认只读诊断；不得复刻全局工具、hook、service、schema。
- 创建项目级覆盖不等于覆盖已生效；无证据时必须标注“候选覆盖，尚未验证生效”。
- 修改前必须展示修复草案并取得用户确认。
- 写入前路径安全、并发基线和脱敏检查任一项无法完成时，降级为只读诊断。

## 适用场景

- 用户指出某个技能、命令、代理或规则没有按预期执行。
- 用户希望把本次纠偏固化到可复用资产中，而不是只修当前回复。
- 需要判断偏差来自入口包装、下游执行资产、规则文件、命令模板、帮助目录或代码实现层。
- 需要检查修改资产后，原有引用、帮助文本、命令参数或测试断言是否同步。

## 退出条件

- 偏差不是资产问题：说明这是一次性任务理解偏差或应改用其他技能。
- 资产无法唯一定位：向用户补问，不继续猜测。
- 目标只能通过全局资产或代码资产修复：输出诊断和人工迁移建议，不写入。
- 安全门禁无法通过：输出只读诊断，不写入。

## 阶段 1：收集输入

从用户输入和当前会话中提取四项信息：

- 入口：用户触发的命令、技能、代理或文件路径。
- 实际行为：刚才偏航做了什么。
- 期望行为：用户纠偏后希望怎么做。
- 证据：会话调用链、工具调用、文件内容、错误输出或用户明确说明。

支持输入形式：`ae:plan`、`/ae-plan`、`ae-plan`、`plan`、`@correctness-reviewer`、项目内 `SKILL.md`、命令模板、规则文件或代理文件路径。

若缺少实际行为或期望行为，立即补问：

```text
请补充资产调试所需信息：
1. 你认为偏航的资产名或触发入口是什么？
2. 刚才实际发生了什么？
3. 你期望它以后怎么做？
4. 是否有相关消息片段或文件路径？
```

阶段 1 退出条件：得到入口或候选资产，并得到实际行为与期望行为。

## 阶段 2：归一化候选

归一化规则：

- `/ae-foo`、`ae-foo` 和 `foo` 可归一化为候选技能 `ae:foo` 或命令 `ae-foo`。
- `@agent-name` 归一化为代理名 `agent-name`。
- 文件路径优先作为项目级资产候选，不反推出全局资产写入目标。
- 命令入口可能只是包装，必须区分入口资产与下游执行资产。

按以下顺序查找候选：

1. 明确资产名或文件路径。
2. 当前会话中的实际调用链、命令模板、技能加载记录或工具调用记录。
3. 用户明确纠偏对象。
4. 项目级同名覆盖定义。
5. 全局或插件提供的只读定义。

候选输出格式：

```text
候选资产：
- 类型：技能|代理|命令|规则|代码实现|未知
- 归一化名称：...
- 来源层级：项目级|全局/插件|未知
- 证据：...
- 是否只是入口包装：是|否|未知
```

若有多个候选，必须使用 `question` 让用户选择。若只有单一触发入口但没有调用链证据，必须补问确认要修入口还是下游执行资产。

阶段 2 退出条件：得到一个目标资产，或因无法唯一定位而停止并补问。

## 阶段 3：判定动作

| 资产类型 | 首版动作 | 全局处理 | 覆盖验证要求 |
|------|------|------|------|
| 技能 | 项目级文本修复；全局资产默认只诊断，证据充分时可创建候选覆盖 | 只读全局定义，默认不写 | 需运行时或配置证据；无证据不得宣称生效 |
| 代理 | 项目级文本修复；全局资产默认只诊断，证据充分时可创建候选覆盖 | 只读全局定义，默认不写 | 需 agent 加载证据；无证据不得宣称生效 |
| 命令 | 项目级文本修复；全局资产默认只诊断，证据充分时可创建候选覆盖 | 只读全局定义，默认不写 | 必须区分命令模板问题与被转发技能问题 |
| 规则 | 项目级文本修复；全局规则默认只诊断 | 只读全局规则，必要时建议项目级规则 | 验证规则文件被 instructions 或 AGENTS 链路引用 |
| 工具/hook/service/schema | 只读诊断和补丁建议 | 全局代码不写、不复刻 | 不宣称已修复，只给人工迁移或源码模式计划 |

动作只能是以下三种之一：

- `write-project-asset`：已存在项目级自然语言资产，可在确认后修改。
- `candidate-project-override`：全局自然语言资产有明确覆盖证据，可在确认后创建候选项目级覆盖。
- `diagnose-only`：全局资产、代码实现资产、覆盖机制不可靠或安全门禁无法通过。

阶段 3 退出条件：明确动作类型，并说明为什么允许或禁止写入。

## 阶段 4：偏差分析

输出偏差清单，字段固定如下：

- 标准预期：资产应驱动的行为。
- 实际行为：本次偏航表现。
- 纠偏证据：用户纠正、会话调用链、文件内容或测试失败证据。
- 影响范围：入口、下游技能、规则、帮助文本、命令模板、测试断言。
- 根因假设：定义层、包装层、规则层、帮助目录、代码实现层或多层组合。
- 推荐修复层级：文本资产修复、引用同步、代码补丁建议或人工决策。
- 证据置信度：高、中、低，并说明原因。

遇到 `SKILL.md` 与代码逻辑不一致时，先识别运行时权威来源和字段一致性要求。若两套机制是有意双轨，不能仅因重复而自动删除或同步；无法裁决时输出人工决策项。

阶段 4 退出条件：偏差清单能解释“为什么这次会偏航”和“修哪个层级最小正确”。

## 阶段 5：提出修复草案

写入前必须向用户展示草案，不得跳过确认。草案格式：

```text
准备修复：
- 目标路径：<仓库相对路径>
- 来源层级：项目级|候选项目级覆盖
- 动作类型：write-project-asset|candidate-project-override|diagnose-only
- 变更摘要：...
- 引用影响：...
- 验证方式：...
- 风险：...

是否执行写入？
```

如果动作是 `diagnose-only`，不询问写入，只输出诊断和人工修复建议。

阶段 5 退出条件：用户确认写入，或流程以只读诊断结束。

## 阶段 6：写入安全门禁

写入前逐项检查，任何一项失败都降级为只读诊断：

- 写入范围只允许当前工作空间内项目级资产路径。
- 写入前必须做路径规范化和真实路径解析，确认真实路径位于 workspace 根目录内。
- 拒绝路径穿越、绝对越界路径、符号链接、junction、Windows reparse point 或等价链接导致的越界写入。
- 新建文件时逐级确认父目录在 workspace 内；无法可靠检查目标文件和每一级父目录时，降级为只读诊断。
- 修改已有文件前记录内容哈希或等价基线；写入前重新读取并比对，若变化则停止并要求用户决定。
- 遇到用户或其他代理已有无关修改，不回滚、不覆盖；同文件冲突时只展示冲突和建议。
- 所有读取内容和输出都必须脱敏，包括项目级资产、全局资产、diff、错误片段、会话摘录和引用影响报告。
- 疑似凭证、私钥、token、cookie、个人目录或私有 URL 出现时，停止自动修复并只报告相对路径和脱敏摘要。

阶段 6 退出条件：安全门禁通过并完成写入，或降级为只读诊断。

## 阶段 7：引用影响检查

普通项目模式每次修复至少检查静态引用：

- 同名技能、代理、命令、规则定义是否存在项目级覆盖。
- `opencode.json`、`AGENTS.md`、`.opencode/rules/**/*.md` 中是否引用相关资产或入口。
- 项目文档中是否有调用方式、参数约定或流程说明需要同步。
- 若修改命令或参数约定，检查命令模板、转发目标和用户文档。

还必须报告动态来源检查状态：插件动态注册、TUI 命令、帮助索引、生成目录或运行时注入来源若无法检查，必须在最终报告中列为“未验证动态来源”。不得笼统声称引用影响检查完整。

最终报告必须包含“引用影响检查”小节，列出已检查引用点、受影响项、同步修改项和无需修改理由。

阶段 7 退出条件：引用影响检查完成，或明确列出未验证动态来源。

## 阶段 8：验证与报告

每次修复后输出：

- 修复前失败样例。
- 修复后期望行为。
- 相同输入复现实验或可执行验证命令。
- 人工验收步骤。
- 已创建候选覆盖或已验证生效的状态。
- 剩余风险。

LLM 行为验证只能降低风险，不能承诺根除。无法自动验证时必须明确说明。

最终回复必须使用以下结构：

```text
资产定位
- 目标资产：...
- 来源层级：...
- 证据：...

偏差清单
- 标准预期：...
- 实际行为：...
- 根因假设：...
- 证据置信度：...

修复结果
- 动作类型：write-project-asset|candidate-project-override|diagnose-only
- 已修改文件：...
- 覆盖状态：无|候选覆盖尚未验证|已验证生效

引用影响检查
- 已检查引用点：...
- 受影响项：...
- 同步修改项：...
- 无需修改理由：...
- 未验证动态来源：...

验证结果
- 自动验证：...
- 人工验收步骤：...
- 剩余风险：...
```

## 源码维护附录

仅当当前工作区被明确识别为 `ai-agent-engine` 源码仓库时，才启用本附录。普通项目用户不需要执行这些步骤。

新增或修改公开 AE 技能时至少检查：

- `src/schemas/ae-asset-schema.ts` 的 `SKILL` 与 `AeSkillNameSchema`。
- `src/services/ae-catalog.ts` 的 `PHASE_ONE_ENTRIES`、`description`、`argumentHint` 和排序。
- `src/assets/skills/<skill>/SKILL.md` frontmatter 的 `name`、`description`、`argument-hint`。
- `src/services/command-registration.ts` 是否由 catalog 自动生成基础命令、`-po`、`-pa`，以及是否存在磁盘命令覆盖。
- `src/services/help-catalog-service.ts` 和相关测试是否仍符合帮助输出预期。
- `tests/schemas/ae-asset-schema.test.ts`、`tests/services/command-registration.test.ts`、`tests/services/help-catalog-service.test.ts`、`tests/services/help-catalog-service.integration.test.ts` 是否需要同步断言。
- `src/index.ts`、`src/services/skills-path-service.ts`、`src/services/runtime-asset-manifest.ts` 是否仍通过 `config.skills.paths` 注入 `src/assets/skills`；不要把复制到 `.opencode/skills/` 当作公开技能生效路径。
