# 设计增量更新

`ae:design-update` 直接对比 prd 当前态与 design 当前态，确定差异并更新受影响的设计文件。

此技能不实现代码。它更新设计文件。

**重要：修改文件时所有文件引用必须使用仓库相对路径，绝不能使用绝对路径。**

## 核心原则

1. **直接对比** - 读取 prd 当前态和 design 当前态，直接对比确定差异，不依赖变更信号数组。
2. **scoped regeneration** - 维度文件是相互依赖的连续体，重跑受影响子代理整体替换文件，保证维度间一致性。
3. **仅处理受影响模块** - 只处理有差异的模块，不触碰未受影响模块。
4. **方案确认** - 更新前必须向用户展示方案（原始内容 → 修改后内容 → 变更依据），确认后才执行。
5. **自包含约束** - 设计文档目录完全自包含，禁止引用外部工作空间文件。
6. **无变更追踪** - 直接修改文件内容。版本演化 = 独立新目录。
7. **局部校验** - 仅校验受影响文件的 ID 引用闭合，不全量校验。

## 交互规则

1. **方案展示** - 用表格展示原始内容、修改后内容和变更依据。
2. **使用平台的提问工具** - 优先使用 opencode 的 `question` 工具。
3. **跨模块影响确认** - blast radius ≥ 2 时需额外确认。

## 参数说明

### 模块名（位置参数）

- **格式**：`<模块名>`
- **作用**：仅同步指定模块的设计。
- **默认**：扫描所有模块确定差异。

### --dry-run

- **格式**：`--dry-run`
- **作用**：预览变更方案不执行。
- **默认**：不启用。

## 执行流程

### 阶段 0：对比分析

1. 读 prd `overview.md` → 获取模块清单和范围边界
2. 读 design `overview.md` → 获取模块清单
3. 对每个模块：
   - 读 prd `modules/<NN>-<m>/requirements.md`（当前态需求）
   - 读 design `modules/<NN>-<m>/` 下各维度文件（当前态设计）
   - 对比确定差异
4. 无差异 → 输出"设计已是最新" → 结束
5. 有差异 → 列出有差异的模块 + 对应的差异内容

### 阶段 1：按差异精确加载

对每个有差异的模块（或用户指定的模块）：

1. 读 prd `modules/<NN>-<m>/requirements.md`（当前态需求）
2. 读 prd `modules/<NN>-<m>/pages/`（如涉及 UI）
3. 读 design `modules/<NN>-<m>/<dimension>.md`（当前设计）
4. 读 design `overview.md` + `architecture.md`（全局上下文）
5. 不读取无差异模块

### 阶段 2：设计变更方案生成

对每个有差异的模块：

1. 对比 prd 当前态 vs design 当前态
2. 生成设计变更方案表格：

   | 设计文件 | 章节 | 原始内容 | 修改后内容 | 变更依据 |
   |---------|------|---------|-----------|---------|
   | modules/01-auth/api.md | EP-001 | password: string | password: string (≥12位含特殊字符) | R1 变更 |
   | modules/01-auth/database.md | T-users | password_hash VARCHAR(255) | password_hash VARCHAR(255) + 密码策略 | R1 变更 |
   | modules/01-auth/ui-ux.md | 路由表 | — | — | — |
   | modules/01-auth/pages/01-register.md | 字段映射 | password(必填,≥8位) | password(必填,≥12位含特殊字符) | R1 变更 |
   | modules/01-auth/test-cases.md | TC-001 | 验证8位密码注册 | 验证12位含特殊字符密码注册 | R1 变更 |

3. 计算设计变更的 blast radius：
   - Radius 1: `modules/<NN>-<m>/` 下各维度文件间一致性
   - Radius 2: `cross-mapping.md`（如 API 签名变更影响跨模块映射）
   - Radius 3: 其他模块（如 auth API 变更影响 resource 的鉴权调用）
4. 展示方案 → 用户确认
   - 确认 → 进入阶段 3
   - 拒绝 → 询问是否调整 → 回到阶段 2
   - 取消 → 结束

### 阶段 3：scoped regeneration

对每个有差异的模块：

1. 确定受影响子代理集合（从差异内容推导）
2. 重跑受影响子代理：
   - 读取该子代理的完整输入上下文（prd 当前态 + design overview + architecture + 该模块当前设计）
   - 子代理产出可替换的完整维度文件内容
3. 主代理用 edit 工具将该维度文件整体替换
4. 更新 `cross-mapping.md`（如 blast radius ≥ 2）

如 blast radius ≥ 3：
- 更新受影响的其他模块
- 提示用户这些模块已更新

### 阶段 4：局部校验

1. 局部一致性校验：
   - 校验受影响模块的 ID 引用闭合
   - 校验跨模块 API 调用一致性（仅校验变更涉及的端点）
   - 校验 api ↔ database 字段对齐（仅校验变更涉及的字段）
2. 校验失败 → 标记不一致 → 提示用户
3. 校验通过 → 输出结果：
   - 设计变更摘要
   - 更新的文件列表
   - 一致性校验结果
   - 提示: "设计已同步，可运行 `/ae-work` 实施变更"

## 与全量 ae:design 的区别

| | ae:design（全量） | ae:design-update（增量） |
|---|---|---|
| 触发条件 | 首次设计或全量重建 | prd 变更后同步设计 |
| 读取范围 | 全部 prd 产物 | 仅对比差异部分 |
| 生成范围 | 全部 design 产物 | 仅受影响模块（scoped regeneration） |
| 子代理 | 全部 design 子代理 | 仅受影响模块涉及的子代理 |
| 一致性校验 | 全量校验 | 局部校验（仅受影响文件） |

## 安全边界

- 仅处理有差异的模块，不触碰无差异模块
- 设计变更方案必须经用户确认
- 更新同一份文件（edit 替换），不删除不重建
- 跨模块影响（blast radius ≥ 2）需额外确认
- 局部校验失败时不自动回退，标记不一致由用户决定
- 不修改 prd 文件

## 何时触发全量重建

以下情况提示用户运行 `ae:design` 全量重建而非增量更新：

| 触发条件 | 理由 |
|---------|------|
| 模块边界变更 | 影响范围无法精确计算 |
| 全局文件结构变更 | 影响所有模块 |
| 增量校验失败且用户选择全量 | 不一致可能超出局部 |
| 多模块同时有差异 | 批量增量不如全量 |
| 用户显式请求 | 用户判断 |

## 交接

更新完成后呈现下一步选项：
- 运行 `/ae-work` 实施变更
- 继续同步其他有差异模块（如有）
- 运行 `/ae-prd-update` 继续变更其他需求
