# 步骤 9-10：综合、展示和审查后

新架构采用全并行 + 合并层设计。所有激活代理在同一轮一次性发出 Task 调用，只找问题不做修复；合并层负责去重、冲突解决、因果分析和修复方案生成。

## 步骤 9：合并发现结果（5 步综合流水线）

### 5.1 校验

根据 findings schema 检查每个代理返回的 JSON。丢弃缺少必填字段的发现。记录格式不正确的代理。

### 5.2 置信度门控

- 代码发现：抑制低于 0.60 的发现（P0 在 0.50+ 保留）
- 文档发现：抑制低于 0.50 的发现（P0 在 0.50+ 保留）

将低于阈值的文档发现存储为残余风险。

### 5.3 合并去重 + 冲突解决 + 因果分析（合并层）

合并层是全并行架构的核心后处理环节，由 `ae-specialist-aggregate` 执行，包含三个子步骤。

#### 5.3.1 指纹去重

使用 `normalize(file) + normalize(location.type) + normalize(location.line|section) + normalize(title)` 生成指纹。

- 代码发现 location.type 为 `line`，使用 `line` 字段
- 文档发现 location.type 为 `section`，使用 `section` 字段

当指纹跨代理匹配时：
- 如果发现建议**相反的操作**，不合并——保留两者，转入冲突解决
- 否则合并：保留最高严重级别和置信度，合并证据，记录所有同意的审查者
- 归属于置信度最高的代理，减少其他代理的计数

#### 5.3.2 冲突解决

同一问题被多个代理标记为不同 severity 时，取最高 severity 保留。建议方向相反的发现保留双方，标记为 `conflict` 并写入冲突证据。

#### 5.3.3 因果分析

遍历所有发现的 `causes` 和 `caused_by` 字段构建依赖图，识别"修复 A 自动解决 B"的链式关系：

1. 构建 finding ID 之间的依赖图（有向图）
2. 检测环依赖并断开（标记为 `circular_dependency`，保留双方）
3. 识别根因发现（无 caused_by 的发现）：修复根因可自动消除其 causes 列表中的所有发现
4. 将被自动解决的发现标记为 `auto_resolved_by: <root_finding_id>`，从待修复队列中移除
5. 生成修复方案时优先排列根因发现，减少实际需要执行的修复数量

### 5.4 排序

- 代码发现：严重级别 → 置信度 → 文件路径 → 行号
- 文档发现：严重级别 → 置信度 → 文件路径 → 章节顺序

根因发现排在同严重级别的前列，因其修复可消除下游发现。

### 5.5 高风险零发现对抗

如果满足以下全部条件，触发对抗式补充审查：
1. 变更包含高风险信号（security/migration/api）
2. 所有激活代理均返回空 findings
3. 变更行数 >= 50

触发时对全部变更文件进行补充审查，补充审查结果重新进入合并层。

### 已退化步骤

以下步骤在全并行架构中已退化，不再单独执行：

- **共识提升** — 合并层指纹去重时天然包含跨代理共识信息，不单独提升置信度
- **残余风险提升** — 合并层因果分析已覆盖跨代理佐证场景
- **分歧解决** — 合并层冲突解决子步骤统一处理
- **autofix 提升** — 代理只找问题不做修复，autofix 判定移至修复方案生成阶段
- **路由划分** — 合并层统一产出修复队列，不按域分路由
- **补全问题队列** — 合并层因果分析后直接生成修复方案，不单独构建补全问题队列

## 自动修复流程

全并行架构的自动修复流程：

```
所有代理并行找问题
        ↓
   合并去重（5.3.1）
        ↓
   冲突解决（5.3.2）
        ↓
   因果分析（5.3.3）
        ↓
   生成修复方案
        ↓
   执行修复（仅 autofix 模式）
```

**生成修复方案：** 对每个待修复发现，根据 suggested_fix 生成最小编辑方案。根因发现优先排列，被 auto_resolved 的发现不生成独立修复方案。

**执行修复：** 仅在 `mode=autofix` 或 `mode=headless` 时执行。应用修复队列中的所有 `auto` 发现，使用一个修复器和 `max_rounds=2`。应用前复核每项不触发受保护产物、安全边界或互斥建议。

## 步骤 10：合成并展示

使用审查输出模板（`references/review-output-template.md`）展示发现。

### 模式驱动的展示

- **交互模式** — 应用 `auto` 修复，展示因果分析结果和剩余待处理发现
- **自动修复模式** — 应用 `auto` 修复，保留其余发现，输出因果链供用户理解
- **只读模式** — 不应用修复，仅展示发现和因果分析
- **无头模式** — 单轮应用 `auto` 修复，结构化文本输出，包含无法安全应用的未决项

### 受保护产物

丢弃任何建议删除以下目录中文件的发现：
- `ae/prds/`
- `ae/designs/`
- `ae/solutions/`
- `.opencode/`

## 审查后

### 步骤 1：应用修复

仅在 `mode=autofix` 或 `mode=headless` 时执行。按因果分析排列的顺序应用修复队列，根因优先。`mode=headless` 还必须应用无头推荐修复队列。

### 步骤 2：写入运行产物

调用 `ae-review-proof` 写入 `ae/reviews/<run-id>/metadata.json`。`metadata.json` 必须包含 `generatedBy: "ae:review"`、`reviewRunIdOrMessageRef`、`worktree`、`branch`、`head`、`statusSummary`、`reviewStatus`、`reviewOutputHash`，便于后续审计和交付引用。`source_review_output` 必须来自当前会话中真实审查输出，包含可解析的通过/失败状态、worktree、branch、HEAD 和 statusSummary。

### 步骤 3：最终下一步（仅交互模式）

**内部调用行为：** 当本技能以 `mode=headless` 被其他技能内部调用时，跳过本步骤，仅返回审查结果给调用方。

提供两个选项：
1. **再次优化** — 处理发现后重新审查
2. **审查完成** — 进入下一步

经过 2 次优化迭代后，建议完成。

### 步骤 4：更新状态文件

更新 `.opencode/review-state.json`（写入当前 worktree 身份、branch、HEAD、工作区状态摘要和审查时间）。后续读取时必须校验这些字段，缺失或不匹配时保守视为未审查。

## 质量门

1. 每个发现都是可操作的
2. 没有因未仔细阅读代码/内容导致的误报
3. 严重级别校准正确
4. 位置信息准确（代码发现：行号；文档发现：章节）
5. 受保护产物得到尊重
6. 发现不重复 linter 输出
7. 因果链无环依赖（合并层已保证）

## 禁止事项

- 代理不得执行修复，只找问题
- 不要重写整个文件/文档来修复一个小问题
- 不要添加用户未讨论过的新功能/新章节
- 不要创建单独的审查文件或添加元数据章节到源文件
