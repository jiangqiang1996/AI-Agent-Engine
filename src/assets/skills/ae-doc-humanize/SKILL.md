# 文档人性化转换器

将 AE 的 AI 结构化产物转换为更适合人类阅读、评审和存档的等价视图。

**核心约束：产物正文必须完全自包含，可记录上游路径用于溯源，只能重排和改写源产物中已有或可直接推出的内容，禁止镀金，不改原意。**

## 与其他技能的关系

- `ae:brainstorm` 是需求真源，产出 `type: brainstorm`，定义做什么、为什么做和范围边界。
- `ae:plan` 是计划真源，产出 `type: plan`，定义怎么做、实现单元、验证和执行边界。
- `ae:refactor` 不是独立文档类型；它只是进入 `ae:plan` 的重构专项入口，最终产物仍是 `type: plan`。
- `ae:doc-humanize` 只把 `type: brainstorm` 或 `type: plan` 转成人读等价视图，不创建新的需求、设计、风险、验证或论证。
- `ae:doc-structure` 只把人读等价视图转回 `type: brainstorm` 或 `type: plan`，用于恢复 AI 可执行结构。

因此，`ae:doc-humanize` 与 `ae:doc-structure` 是互转层；`ae:brainstorm` 与 `ae:plan` 才是可继续规划和执行的结构化真源。
给 AI 的结构化需求和计划不需要干系人、读者对象、用户画像、业务价值、市场论证、背景介绍或汇报型影响说明；若源产物没有这些元素，人读文档也不得为了“更像人写的文档”而增加。

## 适用场景

- 用户提供 `ae:brainstorm` 产物，需要转换为自包含需求文档。
- 用户提供 `ae:plan` 产物，需要转换为自包含详细设计文档。
- 用户提供 `ae:refactor` 产物（本质是 `type: plan` 的重构计划），需要转换为自包含详细设计文档。
- 用户同时提供需求文档和计划文档，需要生成配套的人读需求文档和详细设计文档。

## 不适用场景

- 用户要求从零编写需求或设计，应先使用 `ae:brainstorm`、`ae:plan` 或 `ae:refactor`。
- 用户要求美化、润色、扩写或添加说服性内容。本技能只做等价转换。
- 用户要求生成更利于机器识别的文件，应使用 `ae:doc-structure`。

## 核心原则

1. **正文完全自包含** — 输出文档不得要求读者打开原始 `ae:brainstorm`、`ae:plan` 或 `ae:refactor` 产物才能理解需求或设计。
2. **允许溯源但禁止替代内容** — 输出文档可以在 frontmatter 或“文档说明”中记录上游文件路径，但正文必须完整展开全部需求或设计内容，不得写“详见上游文件”“来自某文件故省略”等替代表达。
3. **零镀金** — 不添加原文档没有、且不能由原文档明确字段直接推出的信息、功能、理由、风险、约束、决策、章节或示例；尤其不得新增干系人、读者对象、用户画像、业务价值、市场论证、背景介绍或汇报型影响说明。
4. **零改意** — 只改变表达形式和章节组织，不改变语义、范围、优先级或执行顺序。
5. **保留可互转锚点** — 需求 ID、实现单元 ID、决策 ID、开放问题 ID 等稳定标识必须保留在文档中，便于 `ae:doc-structure` 反向转换。
6. **往返结构可恢复** — 若源文档 A 经本技能得到 B，再由 `ae:doc-structure` 得到 C，C 的正文必须能恢复为与 A 几乎完全一致的规范结构、章节顺序和稳定 ID 布局。
7. **模板字段也需有来源** — 人读模板中的每个章节、表格、字段和小标题都必须能映射到 `ae:brainstorm` 或 `ae:plan` 的既有正文元素；源产物没有对应语义时删除该元素，不写空壳或通用最佳实践。
8. **反复打磨** — 输出前至少做两轮自检：完整性对照和语义漂移检查。

## 输入处理

### 单个文件路径

读取指定文件，必须先根据 frontmatter `type` 判断源文件类别，再选择目标模板：

- `type: brainstorm` → 源文件是结构化需求文件，使用 `references/requirements-template.md` 转换为人读需求文档。
- `type: plan` → 源文件是结构化设计/计划文件，使用 `references/design-template.md` 转换为人读详细设计文档。
- `type: requirements` 或 `type: design` → 已是人读文档，说明无需转换；如用户明确要求，按模板规范化但不得改意。
- 无法识别为需求或设计时，停止并询问用户，不得猜测模板。

### 目录路径

扫描目录下 `*-requirements.md`、`*-plan.md`、`*.md`，仅转换可识别的 AE 产物。

### 无参数

搜索 `docs/ae/brainstorms/` 和 `docs/ae/plans/` 中最近修改的候选文件，询问用户选择。

## 工作流程

### Phase 1：读取、分类与语义抽取

1. 读取源文档完整内容。
2. 先识别源文档类别：`type: brainstorm` 是需求，`type: plan` 是设计/计划；分类失败时停止。
3. 再提取标题、日期、需求 ID、实现单元 ID、决策、范围、验证和开放问题。
4. 建立语义清单，清单只用于内部对照，不写入输出文档：
   - 需求清单：ID、描述、验收条件、分组、非功能属性。
   - 设计清单：单元 ID、目标、依赖、文件、方法、测试、验证、风险。
   - 附属清单：决策、假设、开放问题、参考信息。
5. 建立模板元素来源表：输出模板中准备保留的每个章节、字段、表格和示例，都必须标注对应的源章节、源 ID 或源字段；无法标注来源的元素必须删除。

### Phase 2：选择模板并转换

模板文件位于 `references/`：

- 源文件是结构化需求时，只使用 `references/requirements-template.md`。
- 源文件是结构化设计/计划时，只使用 `references/design-template.md`。
- 不混合两个目标模板，不把计划实现单元写进需求文档，也不把需求条目直接当成设计单元。

转换规则：

- 必选章节必须有实质内容；如果源文档缺少必选语义，停止并说明缺口，不得编造。
- `[可选]` 章节仅在源文档存在对应语义时出现。
- 模板示例只表示可映射结构，不是输出时必须补齐的内容；不得因为人读文档“看起来更完整”而增加源产物没有的章节。
- 需求条目保留 ID，例如 `R1`，但用自然语言表达。
- 实现单元保留 ID，例如 `U1`，并保持原依赖顺序。
- Mermaid 图、文件路径、接口路径、表名、字段名、命令和配置键保持原样。

### Phase 3：自检与打磨

至少执行两轮：

1. **完整性检查** — 源文档中的每个需求 ID、实现单元、决策、约束、验证项都能在输出中找到。
2. **语义检查** — 输出文档没有新增功能、范围扩大、决策改写、风险淡化、验收条件变化，也没有新增源产物中没有的模板元素。
3. **自包含检查** — 输出文档可记录上游路径，但没有“见原文档”“来自某文件故省略”等外部依赖表达；即使不阅读上游文件，也能完整理解并评审。
4. **可逆性检查** — 输出文档包含足够稳定 ID 和结构，可由 `ae:doc-structure` 转回 AI 结构化文件。
5. **往返结构检查** — 预演 `ae:doc-structure` 的目标模板，确认反向转换后的正文能恢复源文档的规范章节和 ID 结构。
6. **等价性子代理审查** — 转换完成后自动调用 `doc-equivalence-reviewer`，让它对源文档和输出文档做等价性检查；若存在 high/medium 发现，先修复后再输出完成摘要。

### Phase 4：输出

默认输出到源文档同目录，文件名使用 `*-human-readable.md` 后缀。若用户指定路径，使用用户路径。

输出摘要必须包含：

- 输出文档路径。
- 转换类型：需求文档或详细设计文档。
- 需求数量或实现单元数量。
- 自检结果。
- 如有无法等价转换的缺口，明确列出并停止写入或请求用户确认。

## 边界

- 不把本技能产物写成 AE 工作流依赖；它是人读交付物，不替代 `ae:work` 所需的 AI 结构化计划。
- 不把人读文档写成独立 PRD、独立详细设计或最佳实践建议书；它只是结构化真源的等价阅读版本。
- 不把项目源码仓库路径或 AE 插件维护路径写成普通用户项目的前提。
- 不创建 Issue、PR、Release 或远程写操作。
