# work-report

## 目标

基于 Git 提交记录、提交涉及的内容、当前未提交变更和已保存的历史报告，生成面向非技术领导可读的日报、周报或指定时间段工作总结，并写入便于复制的 Markdown 文件。总结必须深入识别变更在解决什么问题、推进什么功能或调整什么流程，并转写成业务进展、效率提升、风险收敛或交付保障，不能罗列文件名、提交标题或技术细节。

## 适用场景

- 用户要求生成日报，默认汇总当天 00:00 到当前时刻的提交和未提交变更，输出约 50 字。
- 用户要求生成周报，默认从本次连续上班周期第一天到当前时刻汇总提交和未提交变更；若对应日期存在日报，则读取最近对应几天的日报作为参考。
- 用户要求按指定时间段、日期范围、分支范围或提交范围生成工作总结。
- 用户要求根据未提交文件补充当天或本周期尚未提交的工作内容。
- 用户要求把日报或周报生成到文件中，方便复制和转发；若需要写入文件，应明确仅限报告文件，不扩大为 Git 写操作。

## 不适用场景

- 用户只要求解释某个单独提交、单个技术变更或单条 diff 时，不强行扩展为日报或周报。
- 用户要求提交、推送、重置或清理 Git 状态时，本技能不执行这些写操作。
- 无法从本地 Git 历史或工作区获得足够证据时，不编造工作内容。

## 输入识别

- “日报”“今天”“当天”：生成日报，默认时间范围为本地当天 00:00 到当前时刻。
- “周报”“本周”：生成周报，默认时间范围为本次连续上班周期第一天 00:00 到当前时刻。
- “从 A 到 B”“最近 N 天”“某提交到某提交”“某分支范围”：按用户指定范围生成总结。
- 未说明输出长度时，日报约 50 字；周报和指定范围总结可稍长，但应保持精炼。

## 工作流程

1. 判定报告类型和范围：优先使用用户明确给出的时间段、提交范围或分支范围；缺失关键信息且无法合理默认时，先询问一个简短澄清问题。
2. 计算周报起点：周报必须从本次连续上班周期第一天开始；默认认为周末休息时从本周一开始；若存在调休或法定节假日信息，例如上周六放假、周日补班，则从实际连续上班第一天（该例为周日）开始。无法确认调休时，说明按默认工作周计算。
3. 读取历史报告：检查 `ae/work-reports/` 下目标时间范围内已有日报、周报和指定范围总结。
4. 收集提交证据：使用只读 Git 命令查看范围内提交，例如 `git log --since=<时间> --until=<时间> --name-status --stat`，必要时读取关键提交的 diff 或相关文件内容。
5. 收集未提交证据：使用 `git status --short` 和只读 diff 命令查看暂存、未暂存和未跟踪文件；对未跟踪文件读取实际内容后再纳入总结。
6. 深入归纳变更意图：把提交信息、文件路径、diff、文件内容和历史报告合并判断，识别功能推进、问题修复、文档完善、测试补充、重构或配置调整的真实目的，再转换成非技术表述。
7. 执行互斥去重：日报必须只写本日新增完成内容，不重复写入历史日报中已表述为完成的内容；历史周报仅作为上下文和措辞参考，不作为日报完成项排除依据。如果昨天已写“完成某工作”，今天只能写该工作的新增增量、验证收尾、风险处理或后续推进，不能继续说完成同一工作。周报条目之间也必须互斥，不能把同一完成项在不同段落或不同日期重复计入。
8. 生成报告：日报控制在约 50 字，周报或指定范围总结按用户要求精炼输出；如果存在未提交变更，将其自然合并为“正在推进的工作”，不要暴露未提交状态本身。
9. 写入报告文件：默认写入 `ae/work-reports/` 目录；如果目录不存在，可以创建该目录。文件内容只放可复制的报告正文，必要时加一个简短标题，不附命令过程。
10. 标注证据边界：如果某些未跟踪文件过大、二进制文件无法读取、范围内无提交或未提交变更为空，应在回复中说明这些限制，不要写入面向领导的报告正文。

## 周报日报参考规则

- 周报沿用基于 Git 提交、diff、文件内容和未提交变更的原有生成逻辑；日报不是周报的主信息源，不能替代 Git 证据分析。
- 生成周报时，检查目标周期内最近对应几天的日报；如果日报存在，则读取并作为工作脉络、成果表述和去重参考。
- 参考日报时，每天只使用该日期最新的一份日报；优先按文件名中的日期和 `HHmm` 后缀排序，无时分后缀视为当天最早版本；仅当文件名无法解析或同优先级冲突时，才使用文件修改时间兜底。
- 周报必须结合 Git 证据和日报参考合并同义工作项：同一成果只能出现一次，按最终交付价值表述；每天的新增增量可以合并为一个连续推进成果，但不得重复宣称多次完成。

## 文件命名

- 日报：`ae/work-reports/YYYY-MM-DD-daily-report.md`。
- 周报：`ae/work-reports/YYYY-MM-DD_to_YYYY-MM-DD-weekly-report.md`，起止日期必须对应本次连续上班周期第一天和当天。
- 指定时间段总结：`ae/work-reports/YYYY-MM-DD_to_YYYY-MM-DD-work-report.md`。
- 如果同名文件已存在，不覆盖旧文件；追加当前时分后缀，例如 `YYYY-MM-DD-daily-report-HHmm.md`。
- 用户明确指定保存路径或文件名时，优先使用用户指定值；仍应使用 Markdown 文件，除非用户要求其他格式。
- 用户指定路径必须位于当前工作区内，或位于用户本轮明确授权的外部路径内；目标文件已存在时仍然默认不覆盖，改用后缀命名或先询问确认。

## 输出要求

- 默认将最终报告写入文件，并在回复中给出文件路径和报告正文；不附长篇过程。
- 报告使用中文，面向不懂技术、不熟悉项目细节的领导，聚焦“今天或本周推进了什么”“解决了什么问题”“对交付有什么价值”。
- 不提具体文件、提交哈希、分支名、命令输出、代码实现细节或内部工具名，除非用户明确要求技术版。
- 避免“修改、调整、优化若干文件”这类空泛表述，应概括成可理解的工作成果。
- 日报示例风格：`今天主要完善工作总结能力，让系统能自动梳理当天进展，帮助更清楚地向管理层汇报工作成果。`

## 安全边界

- 除创建或更新本次报告文件及必要目录外，只执行只读 Git 和文件读取操作，不执行 `git add`、`commit`、`push`、`reset`、`checkout`、`clean` 等写操作。
- 除创建或更新本次报告文件外，不修改其他用户文件。
- 写入用户指定路径前必须确认路径边界；路径越界、目标已存在且用户要求覆盖、或可能改动非报告文件时，先询问确认。
- 发现敏感文件或疑似密钥内容时，只概括为“敏感配置变更”，不要泄露具体值。
