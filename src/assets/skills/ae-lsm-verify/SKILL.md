# LSM 测试执行

## 角色

基于测试用例文档或用户描述的测试行为，编写并执行测试脚本，得出测试结果，固定 `V-*` 验证 ID。支持浏览器测试和接口测试。

## 适用场景

- 用户明确要求 LSM 链路、`ae:lsm-verify` 或测试执行
- 已有测试用例文档，需要执行测试并得出结果
- 用户通过目标描述直接启动测试执行，无需上游文件
- 需要执行浏览器端到端测试
- 需要执行接口测试（通过 `ae:api-tester`）

## 不适用场景

- 仅需要生成测试用例文档，应使用 `ae:lsm-test`
- 需要编码实现，应使用 `ae:lsm-build`

## 输入处理

1. 用户传入目标描述时，基于描述直接推导测试范围和行为；目标描述是最基本的输入形式，无需任何上游文件；用户需详细描述测试行为，包括测试类型（浏览器测试 / 接口测试 / 单元测试等）、测试目标和预期结果
2. 用户显式传入 test 路径和/或 build 产物路径时，以显式路径为准
3. 无显式输入时，根据当前会话讨论的主题，在工作区 `ae/lsm/test/` 和 `ae/lsm/build/` 下搜索最符合的产物
4. 推测不到对应产物且无目标描述时，要求用户传入目标描述或路径

## 执行流程

1. 解析输入：目标描述 / test 路径 / build 产物路径 / 会话推测
2. 若输入为目标描述（无上游文件）：根据描述推导测试范围、测试类型和预期结果，与用户确认后继续；此时 `TC-*` ID 由本技能内联生成
3. 若输入为 test 路径：读取测试用例文档
4. 根据测试类型选择执行方式：
   - 浏览器测试：先通过 `ae:chrome-devtools` 完成 MCP 注册，然后编写浏览器测试脚本并执行
   - 接口测试：通过 `ae:api-tester` 执行接口测试
   - 单元测试 / 集成测试：编写测试脚本并执行
5. 执行测试脚本
6. 修复测试脚本中的问题（脚本错误、环境问题等），重新执行
7. 汇总测试结果，固化 `V-*` 验证 ID
8. 生成测试结果报告，根据项目实际情况动态裁剪模板可选字段，裁剪标记使用 `<!-- trimmed: 原因 -->`
9. 调用 `ae:review domain=document scenes=code` 对 verify 产物进行审查
10. 审查通过后，向用户推荐后续操作

## 产物要求

- 产物路径：`ae/lsm/verify/`
- 使用 `references/verify-template.md` 作为结构参考，裁剪指引见 `references/lsm-trimming-guide.md`
- 元数据（上游路径、输入 ID、输出 ID、追溯表、验证证据、未验证项）全部由 frontmatter 承载，正文不含"元信息"章节
- 测试结果报告记录每个 `TC-*` 的执行结果、测试类型和执行方式；可选字段按模板 trimmingGuide 裁剪
- 包含测试脚本路径和执行日志

## 安全边界

- 浏览器测试必须先通过 `ae:chrome-devtools` 完成 MCP 注册
- 不直接调用 chrome-devtools MCP 工具
- 接口测试通过 `ae:api-tester` 执行，不绕过认证或安全机制
- 返工时仅修改本技能产物（verify），不修改上游 test/build 和其他产物
- 修复测试脚本时只修脚本问题，不修改被测代码（被测代码问题记录在测试结果报告中）
- 不新增远程写操作流程

## 完成标准

- 产物包含 `V-*` 验证 ID
- 测试结果报告记录每个 `TC-*` 的执行结果
- verify 已通过 `ae:review` 审查，审查结论为 passed 或有明确的未阻断发现
- 下一步推荐：
  - 全部通过 → LSM 流程完成
  - 存在失败 → 建议返工对应阶段（`ae:lsm-build` 修复代码 或 `ae:lsm-test` 补充用例）
  - 或重新执行 `ae:lsm-verify` 返工
