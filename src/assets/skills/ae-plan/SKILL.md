# 创建通用实施计划

**注意：当前年份是 2026 年。** 在计划日期和搜索最新文档时使用此年份。

`ae:prd` 定义**做什么**。`ae:plan` 定义**怎么做**。`ae:work` 执行计划。

**当被直接调用时，始终进行计划。** 永远不要将直接调用分类为"不是计划任务"而放弃。如果输入不清晰，提出澄清问题——但始终留在计划工作流中。

本工作流产生一份持久的实施计划。它**不会**直接完成交付物、运行验证，或从执行时结果中学习。任务涉及软件时，计划必须包含代码验证要求；任务不涉及软件时，计划必须包含产物验证、追溯或人工可检查标准。

**重要：计划文档中的所有文件引用必须使用仓库相对路径，永远不要使用绝对路径。**

## 核心原则

1. **以需求为真相来源** - 如果有需求文档或上游产物，基于它构建
2. **决策，不是交付** - 捕获方法、边界、风险和验证场景，不预先完成产物
3. **先研究再结构化** - 在最终确定计划之前探索相关材料、代码库或外部指导
4. **合适的产物规模** - 小工作获得紧凑计划
5. **将计划与执行发现分离** - 在此解决计划时的问题，推迟执行时的未知事项
6. **保持计划可移植** - 作为活文档使用，不嵌入工具特定指令

## 交互方式

当可用时使用平台的 `question` 工具。每次只问一个问题。

## 工作流

### Phase 0：恢复、来源和范围

#### 0.1 恢复已有计划工作

如果用户引用了现有计划文件，或在 `ae/plans/` 中有明显的近期匹配计划：
- 读取它
- 确认是就地更新还是创建新计划

**深化意图：** "深化"一词是深化的触发器。一旦计划被识别且看起来完整（所有主要章节存在、实现单元已定义、`status: active`），短路到 Phase 5.3（信心检查）的交互模式。

#### 0.1b 分类任务领域

如果任务涉及软件，继续 Phase 0.2 并保留代码研究、测试和构建验证要求。如果是非软件的多步骤目标，读取 `references/universal-planning.md`，仍然产出标准 `type: plan` 文档，并保留后续 `ae:work` 交接。

#### 0.2 查找上游需求文档

搜索 `ae/prds/` 中匹配 `*-prd.md` 的文件。如果多个匹配，询问使用哪一个。

#### 0.3 将源文档作为主要输入

如果存在需求文档：阅读它，宣布作为源文档，携带所有内容（问题框架、需求、成功标准、范围边界、决策、待定问题）。不要静默省略源内容。

#### 0.4 计划引导（无需求文档或输入不清晰）

如果不存在需求文档或输入需要更多结构：
- 评估是否足够清晰以直接计划
- 如果模糊主要是产品框架，推荐 `ae:prd`，必要时先用 `ae:brainstorm` 发散讨论，再提供继续计划的选择
- 如果用户继续，运行计划引导建立问题框架、范围、成功标准

#### 0.5 在计划之前分类待解决问题

如果源文档有阻塞问题：仅技术/架构问题重新分类为计划拥有的工作。产品阻塞项必须解决。

#### 0.6 评估计划深度

- **轻量级** - 小型、边界明确
- **标准** - 正常功能，有一些技术决策
- **深度** - 跨切面、高风险或高模糊性

### Phase 1：收集上下文

#### 1.1 本地研究（始终运行）

并行运行或按任务类型裁剪：
- 软件任务：Task research:repo-research-analyst(范围: 技术、架构、模式)
- 所有任务：Task research:research-reviewer(计划上下文摘要、材料或外部参考)

#### 1.1b 检测执行姿态信号

寻找 TDD、测试优先或特征化测试优先的信号。当信号明确时，在相关实现单元中静默携带。

#### 1.2 决定外部研究

利用本地材料、代码库上下文或已有产物做精确决策。高风险主题、薄弱本地模式或事实会过时的信息，倾向于外部研究。

#### 1.3 外部研究（条件性）

如果需要，运行 research-reviewer 搜索外部最佳实践和框架文档。

#### 1.4 整合研究

总结相关代码库模式、制度经验、外部参考资料。

#### 1.4b 重新分类深度

如果轻量级计划触及外部契约面（环境变量、公共 API、CI 配置），重新分类为标准。

#### 1.5 流程和边界情况分析（条件性）

对于标准或深度计划，运行 spec-flow-analyzer。

### Phase 2：解决计划问题

从源文档、研究和仓库中构建问题列表。仅当答案实质性影响架构、范围或风险时才询问用户。**不要**在此运行测试或构建应用。

### Phase 3：结构化计划

#### 3.1 标题和文件命名

文件名：`ae/plans/YYYY-MM-DD-NNN-<type>-<descriptive-name>-plan.md`

**Frontmatter 字段填写规则：** 计划文档的 frontmatter 必须包含 `type: plan`、`status: drafted`、`date`、`title`、`format: human-readable-plan` 和 `sharded`。`origin` 和 `originFingerprint` 仅在有上游产物时成对填写。`origin` 必须使用仓库相对路径。`originFingerprint` 的值为上游产物 frontmatter 中 `date` + `-` + `topic` 的 kebab-case 拼接；若上游没有 `topic`，则使用 `date` + `-` + `title`（如 `2026-04-27-artifact-template-restructure`）。`supersededBy` 不由计划技能填写，由后续技能在替代旧文档时写入。`depth` 仅对标准和深度计划填写。仅当模块数量大于 1，或用户明确要求分片时，`sharded` 才为 `true`。

Frontmatter 模板：
```yaml
---
type: plan
status: drafted
date: YYYY-MM-DD
title: <kebab-case-title>
origin: <上游产物路径，若无则删除此行>
originFingerprint: <上游指纹，若无则删除此行>
depth: <standard|deep>  # 轻量计划删除此行
format: human-readable-plan
sharded: false
---
```

#### 3.2 范围与风险来源约束

标准或深度计划：仅记录会改变实现、验证、迁移、发布或回滚决策的范围、约束或风险。不得为了完整性补充干系人、利益相关者、读者对象、业务价值或汇报型影响介绍；若需求文档没有这些信息，计划也不得发明。

#### 3.3 将工作拆分为实现单元

每个单元：聚焦于一个组件或行为，按依赖排序，使用 `U1`、`U2` 等稳定 ID 和复选框语法。

#### 3.4 高层技术设计（可选）

当工作涉及 DSL、多组件集成、复杂数据流、状态密集生命周期时包含。

#### 3.5 定义每个实现单元

每个单元必须包含：目标、覆盖需求、唯一产出物、依赖、文件、方法、需遵循的模式、测试场景（正常路径、边界情况、错误路径、集成）、验证。存在明确模块边界时还必须包含所属模块。重构计划还必须包含行为保持要求和回滚信号。

#### 3.6 保持计划时和实现时的未知事项分离

显式记录推迟的实现说明。

### Phase 4：编写计划

读取并使用 `references/plan-template.md` 作为计划文档唯一结构契约。轻量/标准/深度只影响内容详略；正文章节名、字段名和实现单元结构保持稳定，frontmatter 可选字段按规则省略。

所有文件路径必须是仓库相对路径。不包含实现代码。鼓励使用 Mermaid 图。

计划必须偏向 AI 识别和遵守：保留 `AI 解析契约`、稳定 ID、需求追溯、明确范围、实现单元、验证和一致性检查。`type: plan` 文档必须能被 `ae:plan`、`ae:work`、`ae:refactor` 和 `ae-doc-extract` 直接使用，因此不得依赖外部解释。计划必须同时人读清晰且机器可抽取，不得因为常见设计文档结构而补齐额外介绍或论证。

### Phase 5：最终审查、写入文件和交接

#### 5.1 写入前审查

检查：计划没有发明产品行为、每个决策有依据、实现单元具体且按依赖排序、测试场景覆盖所有适用类别。

#### 5.2 写入计划文件

**必需：** 在呈现任何选项之前将计划写入磁盘。

**管道模式：** 跳过交互式问题，自动决策。

#### 5.3 信心检查和深化

评估计划是否需要加强。两种模式：
- **自动模式**（默认）：无需用户批准直接综合
- **交互模式**（深化快速路径）：逐个呈现发现供审查

**管道模式：** 始终以自动模式运行。

##### 5.3.1-5.3.2 分类和门控

从文档确定深度和风险概况。证据支撑不足时的兜底规则：如果 Phase 1.2 触发了外部研究，始终继续评分。

##### 5.3.3-5.3.7 深化执行

当深化有必要时，读取 `references/deepening-workflow.md`。

##### 5.3.8-5.4 文档审查和交接

读取 `references/plan-handoff.md`。文档审查是强制性的。

永远不要写代码！研究、决策，然后编写计划。
