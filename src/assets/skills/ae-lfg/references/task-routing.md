# S1-S7 任务路由

在进入 `ae:lfg` 主管道前，先按下表分类任务。只有 S4 多步骤实现进入完整 `ae:brainstorm` → `ae:plan` / `ae:refactor` → `ae:work` → `ae:review` → `ae-gate` 链路。

| 场景 | 输入信号 | 推荐路径 | 允许直接处理 | 最小证据 | 阻断或降级 |
|------|----------|----------|--------------|----------|------------|
| S1 简单问答 | “是什么”“解释”“命令含义”“代码说明” | 直接回答；必要时只做只读搜索/读取 | 是 | 已读文件、帮助输出、官方文档，或明确标注为通用知识 | 不进入 `ae:lfg` 管道，不要求需求、计划或门禁 |
| S2 模糊想法 | 目标、范围、验收不清 | 先澄清，或进入 `ae:brainstorm` | 否 | 已确认目标、约束、未决问题，或需求文档路径 | 需求模糊时不得直接编码 |
| S3 小修复 | 明确 bug、错误栈、单点故障、范围可控 | 直接修复或 `ae:work` 轻路径 | 是 | 定位证据、预估影响文件数、升级判断、验证命令；使用 `ae:work` 或正式代码交付时调用 `ae-gate workflow:work checkpoint:final` | 无计划可接受，但必须说明为何无需计划；范围扩大时升级到 S4 |
| S4 多步骤实现 | 新功能、重构、跨文件、架构决策 | `ae:brainstorm` → `ae:plan` / `ae:refactor` → `ae:work` → `ae:review` → `ae-gate` | 否 | 需求或充分性说明、计划路径、验证结果、审查结果、最终门禁证明 | 无计划不得进入实现 |
| S5 只读审查 | “review”“审查”“不要修改” | `ae:review report-only` | 是，只读 | 审查范围、发现证据、文件/行号、未修改说明 | 默认不修改用户工作区源文件、暂存区或业务交付产物 |
| S6 提交请求 | “提交”“commit”“push”“创建 PR” | `/ae-commit` 或 Git 安全流程 | 仅在明确授权后 | `status`、`diff`、`log`、敏感文件检查、纳入/排除文件、授权、提交结果 | 未授权提交、推送、创建 PR、跳过 hooks、强推默认分支必须阻断 |
| S7 混合意图 | “实现并测试并提交” 等复合目标 | 先按 S3/S4 实现并验证，再按 S6 提交 | 分阶段允许 | 阶段拆分、验证结果、门禁/审查结果、Git 授权与提交证据 | 提交不得早于验证和文件筛选 |

## S3 轻路径约束

S3 必须先经过只读定位子阶段。定位阶段只允许读取和搜索文件，不允许修改工作区文件。最小输出包括：

- 问题定位证据
- 预估影响文件数
- 是否触发升级停点
- 无需计划原因，或升级为 S4 的原因

只有明确判定仍属 S3 后，才允许开始修改。

出现以下任一信号，必须停止轻路径并升级到 S4：

- 预估会影响超过 2 个生产文件
- 涉及认证、授权、数据迁移、外部 API 或 API 契约
- 引入新抽象或修改公共配置
- 需要新增流程或用户可见行为决策
- 需求在定位后仍不清晰，无法给出稳定验收标准

## 交付边界

- S1 问答和 S5 只读审查不强制走完整门禁证明。
- S3 和 S4 只要形成正式代码交付，就必须区分已完成、已验证、未验证/无法验证、Git 操作状态、门禁结果和剩余风险。
- S6 和 S7 的 Git 写操作必须建立在用户明确授权之上；泛化的“顺便提交”不构成授权证据。
