# ae:api-tester

## 角色

业务流程驱动的接口测试编排器。以真实业务流程为主线编排多个接口的调用顺序与数据传递，确保流程端到端走通；流程测试通过后再补充接口边界测试。认证流程、接口采集和模板组装均服务于业务流程编排。

## 适用场景

- 用户要求按业务流程编写接口自动化测试脚本（如"测试从创建到审批的完整流程"）
- 用户提供了接口文档（Swagger/OpenAPI）、接口描述或接口实现代码，需要生成业务流程测试
- 用户需要对一组接口按业务顺序进行联调测试
- 用户需要先登录再测试的认证场景
- 用户提供了已有 JS 测试脚本，需要根据接口变更或新增接口更新该脚本
- 用户要求对单个接口进行边界/异常测试（作为流程测试的补充）

## 不适用场景

- 非 HTTP 接口测试（如 WebSocket、gRPC）
- UI 自动化测试
- 性能/压力测试

## 能力边界声明

以下场景**超出核心能力范围**，技能不会静默降级，而是显式警告：

| 超界场景 | 行为 |
|---------|------|
| 非 JSON 响应（文件下载、SSE 流、XML、HTML 错误页） | 仅做 status 断言，跳过 body 断言，输出警告 |
| 长轮询/WebSocket 升级 | 不支持，提示用户使用专用工具 |
| 并发依赖编排（A+B并行→C） | 当前仅支持顺序+条件分支，提示用户手动拆分 |
| 补偿事务（Saga 回滚） | `finally` 清理是粗粒度的，无法做精确补偿，输出警告 |
| 不可逆副作用（发邮件、触发 webhook） | 标记为 `irreversible`，跳过清理，输出警告 |
| OAuth2 PKCE / mTLS / AWS SigV4 | 不内置支持，提示用户通过 auth plugin 扩展 |

## 工作流程

### 0. 判断模式

检查用户是否提供了已有脚本：

- **提供了已有脚本** → 进入更新模式：读取并解析该脚本，识别其中已有的 baseUrl、认证逻辑、接口请求和断言结构；后续步骤在已有脚本基础上增删改，而非从零生成
- **未提供已有脚本** → 进入新建模式，继续步骤 1

### 1. 确认是否需要登录

向用户询问是否需要登录认证：

- **不需要登录** → 跳到步骤 3
- **需要登录** → 进入步骤 2

### 2. 认证流程（→ references/auth.md）

加载 `references/auth.md`，按其中的流程执行：

1. 询问认证方式（直接提供 Token / 编写登录脚本 / Basic Auth / 其他）
2. 若选择编写登录脚本：搜索项目中登录接口 → 找到则要求用户确认 → 未找到则询问用户
3. 生成认证代码片段（`authSnippet` + `headersSnippet`），包含 401 三路分流逻辑
4. **多认证支持**：若用户需要同一测试套件中使用不同认证（如管理员+普通用户），为每个认证角色生成独立的 auth 片段，在编排方案中按步骤指定使用的认证角色

### 3. 业务流程识别与编排

以真实业务流程为主线，识别接口之间的调用顺序和数据传递关系：

1. **理解业务流程**：向用户确认要测试的业务流程（如"创建→提交→审批→归档"），或从用户描述、接口文档和现有测试代码中推断流程
2. **接口信息采集**（→ references/collector.md）：按流程顺序采集各步骤涉及的接口定义
   - 优先参考项目中已有的集成测试代码（如 Java JUnit/TestNG 测试类），读取其业务流程顺序、请求参数和断言条件
   - 当来源为 Swagger/OpenAPI 时，**优先调用 `ae-swagger-parser` 工具**解析文档，将工具返回的结构化摘要映射为接口定义列表；仅当工具不可用时降级为 LLM 自行解析
   - 从代码/描述/直接信息中提取结构化接口定义
3. **编排流程**：确定接口调用顺序、上下游数据传递（如创建接口返回的 ID 作为后续接口的参数）、前置条件依赖
   - 为每个步骤分配**稳定 stepId**（`method + "_" + path + "_" + operationId`，无 operationId 时降级为 `method + "_" + path`），分隔符为 `_`
   - 识别**条件分支**：当流程中存在根据响应状态走不同路径的分叉时（如审批/自动确认），在编排方案中用 `when` 条件标记
   - 识别**循环步骤**：当流程中存在分页遍历、批量处理等重复调用时，在编排方案中用 `loop` 标记
   - 标记**不可逆副作用**：发邮件、触发 webhook 等不可逆操作标记为 `irreversible`，清理时跳过
4. **输出流程编排方案**：以结构化方式展示业务流程（步骤序号 → stepId → 接口 → 输入来源 → 预期输出 → 下一步依赖 → 认证角色 → 条件分支/循环/不可逆标记），经用户确认后继续

### 4. 模板组装：业务流程测试（主）

加载 `references/templates.md`，按业务流程编排方案组装主测试脚本：

1. 根据接口数量选择输出模式：
   - **接口数 ≤ 5**：单文件内联模式，所有代码写入一个 `.mjs` 文件
   - **接口数 > 5**：模块化模式，公共部分拆入 `lib/` 目录，流程脚本只含编排逻辑
2. 从模板库中选取所需的请求方法（GET/POST/PUT/DELETE 等）
3. 组合：基础配置 + 环境安全护栏 + 认证片段（步骤 2 产出，含 401 三路分流）+ 流程化请求序列 + 流程间数据传递 + 断言 + 运行器 + JSON report 输出
4. **流程数据传递**：使用上下文对象（`const ctx = {}; ctx.orderId = result.data.id`）传递数据，替代散落的 const，便于追踪和调试
5. **条件分支生成**：编排方案中带 `when` 条件的步骤，生成 `if/else if` 代码块
6. **循环步骤生成**：编排方案中带 `loop` 标记的步骤，生成 `while` 循环代码块
7. **接口 URL 优先使用现有代码中的 URL**：搜索项目中已有的测试代码或配置文件（如 `application.yml`、`.env`、测试常量类），提取其中实际使用的 baseUrl 和接口路径；若现有代码中存在域名形式的 URL（如 `http://flood.example.com/api/...`），直接沿用，不要擅自替换为 `127.0.0.1` 或 `localhost`
8. 生成业务流程测试脚本（文件名如 `xxx-flow-test.mjs`）

### 5. 模板组装：接口边界测试（辅）

业务流程测试脚本生成后，根据需要补充接口边界测试：

1. **识别边界场景**：对流程中涉及的关键接口，识别边界条件（必填字段缺失、参数类型错误、越界值、重复操作、无权限访问等）
2. **询问用户**：向用户确认需要补充哪些接口的边界测试，用户可跳过此步骤
3. **组装边界测试脚本**：为每个接口的边界场景生成独立测试用例，复用流程测试中的认证和基础配置
   - **权限边界注意**：若边界测试需要不同权限级别的认证（如普通用户测试无权限访问），需生成独立的认证片段，不得复用管理员 token 测试权限拒绝场景
4. 生成边界测试脚本（文件名如 `xxx-boundary-test.mjs`），与流程测试脚本分开存放

### 6. 确认与写入

- **新建模式**：默认写入路径为项目下 `ae/api-tests/` 目录，用户可配置其他目录
  - 模块化模式额外创建 `<输出目录>/lib/` 目录
  - 业务流程测试脚本命名：`<业务名>-flow-test.mjs`
  - 接口边界测试脚本命名：`<业务名>-boundary-test.mjs`
  - 用户可调整文件名和输出目录
- **更新模式**：写入路径为用户提供的已有脚本路径，不得另存为新文件
- **增量更新**：若已有 `xxx-overlay.yaml`（人工补充层），读取并与新生成的步骤合并；合并策略按字段：`customAssertions` 追加到生成层断言之后，`meta` 保留不覆盖生成层同名字段，其余字段 overlay 覆盖生成层；overlay 中不存在的 stepId 标记为 orphan 并输出警告
- 向用户展示完整脚本内容（更新模式下高亮变更部分）
- 确认后写入对应路径

### 7. 自动测试与修复

脚本写入后按**先流程后边界**的顺序自动运行测试并修复问题：

#### 7.1 业务流程测试（必须通过）

1. **运行流程测试脚本**：使用 `node <流程脚本路径>` 执行
2. **检查结果**：
   - 退出码为 0 且无断言失败 → 流程测试通过，进入 7.2
   - 退出码非 0 或存在断言失败 → 进入分层归因修复
3. **分层归因修复**（最多 3 轮）：
   - **L1 语法/运行时错误**（SyntaxError、ReferenceError、TypeError）：确定性修复——按模板补全缺失函数/变量，修复成功率接近 100%
   - **L2 协议/网络错误**（ECONNREFUSED、DNS 解析失败、401、403）：**受边界守卫约束的确定性修复**——
     - 401 → 走三路分流（token过期→重登录 / 账号禁用→报告不修 / 权限不足→报告不修）
     - 403 → **不自动修复**，标注为权限问题交用户判断
     - 网络错误 → 校验 BASE_URL，可自动修
     - **L2 修复只修请求构造错误，不修授权语义错误**
   - **L3 语义/断言失败**（状态码或字段值不匹配）：**不自动修复**——输出结构化差异报告，包含预期值、实际值、差异字段，交用户判断是脚本错误还是接口行为变更
   - 每轮修复后重新运行脚本验证
   - 若通过则退出循环；若仍失败且未达上限则继续下一轮
4. **流程测试未通过**：3 轮后仍失败 → 向用户展示错误输出、已尝试的修复和 L3 差异报告，**不继续边界测试**，请求用户介入

#### 7.2 接口边界测试（流程通过后执行）

仅在业务流程测试全部通过后执行：

1. **运行边界测试脚本**：使用 `node <边界脚本路径>` 执行
2. 检查结果与分层归因修复逻辑同 7.1
3. 边界测试失败不阻断交付，但需在最终报告中标注失败项

#### 7.3 最终报告

- 流程测试通过 + 边界测试通过 → 全部通过
- 流程测试通过 + 边界测试部分失败 → 流程通过，标注边界失败项
- 流程测试未通过 → 不执行边界测试，报告流程失败详情
- 报告必须包含：每轮修复的修改内容和原因（修复 diff）、L3 层差异报告（如有）
- **结构化 JSON report** 写入 `ae/reports/api-tester/<run-id>.json`，可被 `ae:work-report` 和 CI 消费
- **退出码语义**：0=全部通过，1=存在失败用例，2=基础设施错误（认证/网络/配置），3=定义校验错误

## 约束

- 生成的脚本使用 Node.js 原生 `fetch`（Node >= 18），不引入第三方 HTTP 库；用户可自行替换为 axios/got 等
- 每次生成前必须向用户确认脚本内容和写入路径
- 登录接口搜索范围限定在项目源码目录，排除 `node_modules`、`.git`、构建产物
- 所有请求方法统一返回 `{ status, data }` 结构；非 JSON 响应（204、文件下载）返回 `{ status, data: null }`
- 生成的脚本默认保存到项目下 `ae/api-tests/` 目录，用户可配置其他目录
- 若项目中已有对应接口的集成测试代码，必须优先参考其逻辑编写 JS 脚本，而非仅凭接口文档推断
- 接口 URL 优先从现有代码中提取；不得将域名 URL 擅自替换为 `127.0.0.1` 或 `localhost`，本地项目可能通过域名 + hosts 解析到本地
- 更新模式下，保留已有脚本中未被本次修改影响的代码（认证逻辑、其他接口请求、辅助函数等），仅增删改目标接口相关部分
- 脚本写入后必须自动运行测试，不得仅提示用户手动验证
- 测试修复循环上限为 3 轮，超过后必须向用户报告失败详情并请求介入
- 修复时只修改导致失败的代码，不得重写整份脚本或删除无关的已有逻辑
- **L2 修复边界守卫**：L2 自动修复只修请求构造错误（网络、URL），不修授权语义错误（403、权限不足）；401 走三路分流而非一律重登录
- **并发 401 去重**：多个并发请求同时收到 401 时只触发一次 token 刷新，防止认证风暴
- **L3 语义/断言失败禁止自动修复**：断言值不匹配时只输出差异报告交用户判断，不得放宽断言来"通过"测试
- **业务流程优先**：必须先生成业务流程测试脚本并验证通过，再考虑接口边界测试；不得跳过流程测试直接生成边界测试
- **流程测试未通过时不执行边界测试**：业务流程测试是门禁，未通过则不进入边界测试阶段
- **流程间数据传递必须显式编排**：前序接口的响应数据作为后续接口的输入时，必须通过上下文对象显式传递并在脚本中标注数据流向，不得硬编码
- **边界测试复用流程测试的认证和配置**：边界测试脚本不得重复实现登录和基础配置，应复用流程测试中的认证逻辑；但权限边界测试需使用对应权限的独立认证
- **多认证支持**：同一测试套件支持不同认证角色（如 admin/user/guest），每个角色独立的 auth 片段，编排方案中按步骤指定认证角色
- **环境安全**：生成的脚本必须包含环境安全护栏（`NODE_ENV=production` 拒绝运行、`API_TEST_HOSTS` 白名单校验）和副作用数据清理（`finally` 块中按创建逆序删除）
- **Swagger 来源优先调用 ae:swagger-parser 工具**：当接口来源为 Swagger/OpenAPI 文档时，优先调用 `ae-swagger-parser` 工具获取结构化结果，仅当工具不可用时降级为 LLM 自行解析
- **结构化报告**：每次运行输出 JSON report 至 `ae/reports/api-tester/<run-id>.json`，退出码遵循 0/1/2/3 语义
- **增量更新**：更新模式下读取 overlay 层与生成层合并，不删除人工补充；orphan stepId 输出警告
- **能力边界显式声明**：超出核心能力范围的场景（非JSON响应、并发依赖、补偿事务等）必须输出警告而非静默降级
- **classify401 最佳努力**：401 响应分类依赖响应体关键词和数值 code 匹配，不同框架格式差异大，`unknown` 分类时不自动重登录交用户判断
