# 深度追问

`ae:grill` 逐层追问需求或设计的每个决策分支，一问一答推进直到双方达成共识。

此技能只做一件事：**逐个追问决策 → 达成共识**。不产出持久文档，不做需求澄清，不做路由决策。追问结果需要沉淀为正式设计文档时，由调用方转交 `ae:design`。

## 核心原则

1. **逐个追问** — 每次只问一个问题，等用户反馈后再继续。同时抛出多个问题会让用户无所适从。
2. **沿决策树推进** — 从顶层决策开始，沿依赖分支逐层深入，一个节点解决后再推进下一个。
3. **每问必荐** — 每个问题附带推荐答案和理由，不让用户独自面对空白。
4. **代码库优先** — 能从代码库推断的事实（依赖关系、现有实现、配置约束），先探索代码库获取，不再追问用户。
5. **不产出持久产物** — 追问结果以会话内摘要呈现，除非用户明确要求，不写文件。

## 适用场景

- 用户提示词模糊、信息不明确，需要逐层追问澄清意图和关键细节
- 用户说 "grill me"、"压力测试方案"、"挑战我的设计"
- 用户说 "质疑这个设计" 或 "质疑这个需求"、"帮我检查方案有没有漏洞"
- 用户在 `ae:prd` 或 `ae:design` 之后想检验产出
- 用户主动提交一个方案并要求深度审查
- 任何需要在构建前逐层检验决策合理性的场景

## 不适用场景

- 创建新需求或新设计 → 使用 `ae:prd` 或 `ae:design`
- 执行已有设计 → 使用 `ae:work`
- 正式代码审查 → 使用 `ae:review`
- 头脑风暴发散 → 使用 `ae:brainstorm`

## 执行流程

### 阶段 1：准备

1. 确认目标方案。如果是文件路径，读取文件内容。
2. 从方案中提取关键决策节点，梳理决策依赖关系。
3. 与用户对齐追问范围和优先级。如果方案范围过大，先收窄追问边界。

### 阶段 2：逐层追问

**追问循环：**

1. 选择决策依赖图中优先级最高的未追问节点。
2. 如果该节点的答案可以从代码库推断（依赖关系、现有实现、配置约束），先探索代码库，用发现的事实替代追问。
3. 如果无法从代码库推断，向用户提出一个聚焦的问题：
   - 问题聚焦于一个决策点
   - 附带推荐答案和推荐理由
   - 格式：**问题** → **推荐答案** → **推荐理由** → 等待用户反馈
4. 收到用户反馈后：
   - 用户接受推荐 → 标记节点已解决，记录决策
   - 用户提出不同方案 → 评估合理性，合理则记录新决策，不合理则追问理由
   - 用户不确定 → 提供更多背景或替代方案帮助决策
5. 根据已解决决策更新依赖图，选择下一个最高优先级节点。
6. 重复步骤 1-5，直到所有关键决策节点已解决或用户主动停止。

**追问优先级：**

- 影响面最大的决策优先（被其他决策依赖的节点）
- 风险最高的决策优先（失败后果严重的节点）
- 描述最模糊的决策优先（方案中交代最不明确的节点）
- 同一层级的决策按用户关心程度排序

**推荐答案原则：**

- 基于当前方案上下文和代码库事实
- 必须是具体、可执行的选择，不是抽象建议
- 说明为什么这个选择比其他选择更合适
- 说明潜在风险和缓解方式

### 阶段 3：共识确认

1. 汇总所有已解决决策，列出共识清单。
2. 检查是否有用户跳过的未追问节点。
3. 确认共识是否完整覆盖方案的关键部分。
4. 如有重要未追问节点，提示用户是否继续。
5. 呈现最终共识摘要：每个关键决策的结论、依赖关系、遗留风险和下一步建议。

## 追问维度

| 维度 | 关注点 | 示例 |
|------|--------|------|
| **架构决策** | 技术选型、模块划分、通信方式 | "为什么选微服务而非单体？推荐单体起步，理由：团队规模小，部署复杂度低" |
| **边界条件** | 极端输入、故障模式、容量极限 | "请求量突然增长 10 倍怎么办？推荐限流 + 降级，理由：已有同类系统经验" |
| **依赖假设** | 外部依赖可靠性、版本兼容性 | "是否假设第三方 API 永久可用？推荐本地缓存兜底，理由：该 API 去年宕机 2 次" |
| **数据一致性** | 并发、幂等、状态流转 | "双写如何保证一致性？推荐事件驱动异步同步，理由：一致性要求为最终一致" |
| **安全边界** | 认证、授权、数据暴露 | "谁可以访问这个接口？推荐 RBAC 按角色限制，理由：当前已有角色体系" |
| **可观测性** | 日志、监控、告警阈值 | "如何发现这个模块出问题？推荐结构化日志 + 指标上报，理由：运维团队依赖指标告警" |
| **回退策略** | 失败恢复、降级方案 | "新模块上线失败怎么办？推荐灰度发布 + 一键回滚，理由：历史部署故障平均修复 30 分钟" |
| **测试策略** | 测试范围、覆盖优先级 | "最低测试覆盖要求？推荐核心路径 e2e + 关键边界单测，理由：模块逻辑复杂度高" |

## 交互方式

- 使用平台的 `question` 工具每次只问一个问题
- 等待用户反馈后再继续下一个问题
- 禁止在同一消息中提出多个问题
- 用户可以随时打断，指定想重点追问的方向

## 边界

- 不修改代码库文件
- 不创建或修改设计文档（除非用户明确要求）
- 不替代正式审查流程
- 追问结束时不自动执行下一步，由用户决定转交 `ae:design`、`ae:work` 或其他技能

## 输出

追问结束时呈现：

1. **共识清单** — 每个关键决策的结论和理由
2. **决策依赖图** — 各决策之间的依赖关系摘要
3. **遗留风险** — 共识中仍存在的风险或不确定性
4. **下一步建议** — 推荐的后续技能和操作

除非用户明确要求，否则不写文件。
