# 重构计划包装器

`ae:refactor` 是 `ae:plan` 的重构专项入口。它不维护独立计划流程，而是在进入 `ae:plan` 前补充强约束，让 `ae:plan` 以重构语义创建标准计划文档。

本技能不会直接写代码、不会运行测试、不会单独创建非 plan 类型产物。

## 输入

<refactor_input> #$ARGUMENTS </refactor_input>

如果输入为空，询问用户："你想重构什么？请描述目标模块、文件路径、技术债现象，或你希望改善的代码结构。"

## 适用场景

- 模块拆分、层级边界调整、依赖方向整理
- 重复代码收敛、职责漂移修正、命名体系整理
- 架构规则对齐、技能/命令/资产目录一致性治理
- 测试结构重整、可维护性改善、历史技术债治理
- 用户明确要求“重构”“整理结构”“消除技术债”，且默认不改变外部行为

## 不适用场景

- 新增产品能力或用户可见行为变化：使用 `ae:brainstorm` 或 `ae:plan`
- 需求不清、目标不明确：先使用 `ae:brainstorm`
- 未知故障调试或环境修复：使用 `ae:task-loop`
- 只涉及 1-2 个文件的简单直接改动：可直接用 `ae:work`

## 执行方式

构造以下重构计划约束，然后立即调用 `ae:plan`，将约束和原始输入一并传递给 `ae:plan`：

```text
使用 ae:plan 创建重构计划，并应用以下约束：

1. 目标是彻底消除输入中指定的目标技术债，而不是新增功能。
2. 默认保持外部行为不变，包括 CLI、API、工具返回契约、用户可见行为、配置语义和文档产物格式。
3. 在计划中先识别技术债证据和影响范围；未经代码或文档验证的判断必须标记为假设。
4. 明确非目标，禁止借重构顺手清理无关问题。
5. 每个实现单元都必须包含行为保持要求、测试/验证方式和回滚信号。
6. 对缺少测试的高风险区域，计划应先安排特征化测试或等价验证，再执行结构调整。
7. 优先分阶段、小步、可验证、可回滚迁移，避免大爆炸式重构。
8. 计划文件仍写入 docs/ae/plans/，frontmatter 使用 type: plan，title 建议以 refactor- 开头。
9. 若发现输入实际包含用户可见行为变化或新增产品能力，在计划中明确标记“不是纯重构”，并说明需要 ae:brainstorm 或普通 ae:plan 的产品决策。

原始重构输入：#$ARGUMENTS
```

## 交接

`ae:plan` 产出计划后，沿用标准主流程：

```text
/ae-review domain:document <plan-path>
/ae-work <plan-path>
/ae-review plan:<plan-path>
```

永远不要在 `ae:refactor` 中复制 `ae:plan` 的完整流程。`ae:refactor` 只负责强化重构语义，然后交给 `ae:plan`。
