# 重构计划包装器

`ae:refactor` 是 `ae:plan` 的重构专项入口。它不维护独立计划流程或独立模板，而是在进入 `ae:plan` 前补充强约束，让 `ae:plan` 以重构语义创建或修改标准 `type: plan` 文档。

本技能不会直接写代码、不会运行测试、不会单独创建非 plan 类型产物。产出的计划必须使用 `ae:plan` 的 `references/plan-template.md` 结构。普通 `type: plan` 可作为本技能输入；当它被继续改写为重构计划时，必须补齐重构专属的行为保持要求和回滚信号。

## 输入

<refactor_input> #$ARGUMENTS </refactor_input>

如果输入为空，询问用户："你想重构什么？请描述目标模块、文件路径、技术债现象，或你希望改善的代码结构。"

用户回答后，将回答内容作为本次重构输入，继续按后续流程判断输入类型并执行。

## 适用场景

- 模块拆分、层级边界调整、依赖方向整理
- 重复代码收敛、职责漂移修正、命名体系整理
- 架构规则对齐、技能/命令/资产目录一致性治理
- 测试结构重整、可维护性改善、历史技术债治理
- 用户明确要求“重构”“整理结构”“消除技术债”，且默认不改变外部行为

## 不适用场景

- 新增产品能力或用户可见行为变化：使用 `ae:brainstorm` 或 `ae:plan`
- 需求不清、目标不明确：先使用 `ae:brainstorm`
- 未知故障调试或环境修复：使用 `ae:task-loop`
- 只涉及 1-2 个文件的简单直接改动：可直接用 `ae:work`

## 执行方式

如果输入指向一个已有计划（例如路径位于 `ae/plans/`、文件包含 `type: plan` frontmatter，或用户明确说明这是计划文档），先读取计划并询问用户："检测到你传入的是已有计划。你希望直接修改原计划，还是基于它创建一份新的重构计划？"

- 用户选择直接修改原计划：调用 `ae:plan` 时明确要求更新原计划文件。
- 用户选择创建新计划：调用 `ae:plan` 时明确要求保留原计划，并在 `ae/plans/` 创建新的计划文件。

如果输入不是已有计划，跳过“修改原计划还是创建新计划”的询问，直接构造以下重构计划约束并调用 `ae:plan`，将约束和原始输入一并传递给 `ae:plan`。

不管是修改原计划还是创建新计划，都必须先识别原始计划或输入实际承载的非技术需求，再以彻底消除技术债务的实现方式重写或更新计划。重构成本、改动规模、迁移工作量和短期交付压力不得作为降低清债目标的理由；旧接口、旧方法调用、旧配置形态和旧内部扩展点不得作为兼容目标保留。只有与已确认的非技术需求或安全验证边界直接冲突时，才允许保留债务，并必须逐项说明冲突证据。

```text
使用 ae:plan 创建重构计划，并应用以下约束：

1. 先识别原始计划或输入实际要完成的非技术需求，例如用户目标、产品行为、交付结果、约束条件和验收标准。
2. 目标是在满足这些非技术需求的前提下彻底消除目标技术债，而不是按原实现路径继续堆叠债务。衡量标准是：对已识别的技术债逐项给出根除方案；不得把“降低风险”“控制范围”“减少改动量”“节省时间”作为仅缓解、不根除的理由。
3. 默认一步到位替换旧接口和旧调用方式，包括 CLI、API、工具返回契约、配置语义、内部方法签名和文档产物结构；不得规划兼容层、适配器、旧入口保留、双写双读、灰度迁移或“先兼容后清理”的过渡方案。
4. 在计划中先识别技术债证据和影响范围；未经代码或文档验证的判断必须标记为假设。
5. 明确非目标，禁止借重构顺手清理无关问题。
6. 每个实现单元都必须包含新契约验收要求、测试/验证方式和回滚信号；这些要求用于保障彻底重构可验证，不得被解释为兼容旧实现或保守缩小清债范围。
7. 对缺少测试的高风险区域，计划必须先安排特征化测试或等价验证，再执行结构调整；不得因补测试成本高而跳过清债。
8. 允许大规模、跨模块、破坏性内部重组；计划粒度应服务于可验证交付，而不是服务于最小改动或低成本迁移。
9. 每个被保留的技术债都必须标记为 `blocked-debt`，说明它与哪一条非技术需求或安全验证边界冲突；旧接口兼容性、旧调用方迁移成本、工期、人力、改动规模不能作为 `blocked-debt` 理由。
10. 如果用户选择修改原计划，直接更新原计划文件；如果用户选择创建新计划，新计划仍写入 ae/plans/，frontmatter 使用 type: plan，title 建议以 refactor- 开头。
11. 若发现输入实际包含用户可见行为变化或新增产品能力，在计划中明确标记“不是纯重构”，并说明需要 `ae:brainstorm` 或普通 `ae:plan` 的产品决策；随后询问用户是继续基于该计划执行，还是先回到需求/产品决策阶段。

原始重构输入：#$ARGUMENTS
```

## 交接

`ae:plan` 产出计划后，本技能停止在计划交付阶段，不得自动触发 `ae:work` 或任何实现步骤。只提示用户可选择后续动作：

```text
/ae-review domain:document <plan-path>
```

永远不要在 `ae:refactor` 中复制 `ae:plan` 的完整流程。`ae:refactor` 只负责强化重构语义，然后交给 `ae:plan`。

产出物：一份位于 `ae/plans/` 的计划文档路径，格式遵循 `ae:plan` 标准产出。
