# 创建重构计划

`ae:refactor` 是彻底重构与清债计划入口。它与 `ae:plan` 共享标准 `type: plan` 文档结构，但策略不同：`ae:plan` 默认渐进规划并尽量保持既有行为；`ae:refactor` 默认一次性替换旧结构、旧流程或旧产物，并明确清债边界。

本技能不会直接写代码、不会运行测试、不会单独创建非 plan 类型产物。产出的计划必须使用 `ae:plan` 的 `references/plan-template.md` 结构。普通 `type: plan` 可作为本技能输入；当它被继续改写为重构计划时，必须补齐重构专属的行为保持要求、清债目标、被替换旧机制、blocked-debt 理由和回滚信号。

## 输入

<refactor_input> #$ARGUMENTS </refactor_input>

如果输入为空，询问用户："你想重构什么？请描述目标模块、文件路径、旧机制、流程问题、文档结构或你希望彻底替换的产物。"

用户回答后，将回答内容作为本次重构输入，继续按后续流程判断输入类型并执行。

## 适用场景

- 模块拆分、层级边界调整、依赖方向整理
- 文档结构、流程设计、计划结构或已有方案的彻底重组
- 重复代码收敛、职责漂移修正、命名体系整理
- 架构规则对齐、技能/命令/资产目录一致性治理
- 测试结构重整、可维护性改善、历史技术债治理
- 用户明确要求“重构”“整理结构”“消除技术债”，且默认不改变外部行为

## 图谱新鲜度要求

重构计划通常依赖文件关系和影响范围判断。使用 `ae:graph-query` 定位候选文件、依赖或影响面时，必须读取 `freshness`；`freshness.status` 不是 `fresh` 时，图谱只能作为阅读顺序和候选范围线索，不得作为无影响、无依赖、完整覆盖或无需修改的结论。需要高影响结论时，先刷新图谱，或用真实文件、源码搜索、Git 状态和验证命令补证。

## 不适用场景

- 新增产品能力或用户可见行为变化：使用 `ae:prd` 或 `ae:plan`
- 需求不清、目标不明确：先使用 `ae:prd`，必要时可先 `ae:brainstorm`
- 未知故障调试或环境修复：使用 `ae:task-loop`
- 只涉及 1-2 个文件的简单直接改动：可直接用 `ae:work`

## 执行方式

如果输入指向一个已有计划（例如路径位于 `ae/plans/`、文件包含 `type: plan` frontmatter，或用户明确说明这是计划文档），先读取计划并询问用户："检测到你传入的是已有计划。你希望直接修改原计划，还是基于它创建一份新的重构计划？"

- 用户选择直接修改原计划：调用 `ae:plan` 时明确要求更新原计划文件。
- 用户选择创建新计划：调用 `ae:plan` 时明确要求保留原计划，并在 `ae/plans/` 创建新的计划文件。

如果输入不是已有计划，跳过“修改原计划还是创建新计划”的询问，直接按以下重构计划约束创建标准计划文档。可引用 `ae:plan` 的模板结构，但不得把本技能降级为仅转交给其他计划入口的简单封装。

不管是修改原计划还是创建新计划，都必须先识别原始计划或输入实际承载的非技术需求，再以彻底消除技术债务的实现方式重写或更新计划。重构成本、改动规模、迁移工作量和短期交付压力不得作为降低清债目标的理由；旧接口、旧方法调用、旧配置形态和旧内部扩展点不得作为兼容目标保留。只有与已确认的非技术需求或安全验证边界直接冲突时，才允许保留债务，并必须逐项说明冲突证据。

```text
创建重构计划，并应用以下约束：

1. 先识别原始计划或输入实际要完成的非技术需求，例如用户目标、产品行为、交付结果、约束条件和验收标准。
2. 目标是在满足这些非技术需求的前提下彻底消除目标技术债，而不是按原实现路径继续堆叠债务。衡量标准是：对已识别的技术债逐项给出根除方案；不得把“降低风险”“控制范围”“减少改动量”“节省时间”作为仅缓解、不根除的理由。
3. 默认一步到位替换旧接口和旧调用方式，包括 CLI、API、工具返回契约、配置语义、内部方法签名和文档产物结构；不得规划兼容层、适配器、旧入口保留、双写双读、灰度迁移或“先兼容后清理”的过渡方案。
4. 在计划中先识别技术债证据和影响范围；未经代码或文档验证的判断必须标记为假设。
5. 明确非目标，禁止借重构顺手清理无关问题。
6. 每个实现单元都必须包含新契约验收要求、测试/验证方式和回滚信号；这些要求用于保障彻底重构可验证，不得被解释为兼容旧实现或保守缩小清债范围。
7. 对缺少测试的高风险区域，计划必须先安排特征化测试或等价验证，再执行结构调整；不得因补测试成本高而跳过清债。
8. 允许大规模、跨模块、破坏性内部重组；计划粒度应服务于可验证交付，而不是服务于最小改动或低成本迁移。
9. 每个被保留的技术债都必须标记为 `blocked-debt`，说明它与哪一条非技术需求或安全验证边界冲突；旧接口兼容性、旧调用方迁移成本、工期、人力、改动规模不能作为 `blocked-debt` 理由。
10. 如果用户选择修改原计划，直接更新原计划文件；如果用户选择创建新计划，新计划仍写入 ae/plans/，frontmatter 使用 type: plan，title 建议以 refactor- 开头。
11. 若发现输入实际包含用户可见行为变化或新增产品能力，在计划中明确标记“不是纯重构”，并说明需要 `ae:prd` 或普通 `ae:plan` 的产品决策；随后询问用户是继续基于该计划执行，还是先回到需求/产品决策阶段。
12. **design 契约同步更新：** 重构波及的 design 契约必须同步更新，标注破坏性变更清单。当重构涉及已存在的 design 契约（`ae/designs/` 下）时，计划中必须包含 design 契约更新单元。更新方式：创建新日期目录（版本演化），在 `design.md` 中更新受影响维度并更新 Split Manifest。无已存在 design 时跳过此要求。

原始重构输入：#$ARGUMENTS
```

## 交接

`ae:plan` 产出计划后，本技能运行技能内 review 闭环，然后停止在计划交付阶段，不得自动触发 `ae:work` 或任何实现步骤。

### 技能内 review 闭环

产出重构 plan 后调用 `ae:review mode=headless domain=document <plan-path>`，审查者为 `step-granularity-reviewer` + `traceability-reviewer`。`mode=headless` 表示 ae:review 被技能内部调用时不输出"下一步推荐技能"引导，仅返回审查结果给本技能，由 ae:refactor 自身负责下一步引导。

**auto 修复范围：** 清债目标不完整、行为保持要求缺失、破坏性变更未标注。ae:review 返回的 auto 可修复发现由本技能自动应用修复，修复后重新运行审查。

**收敛协议（上限 2 轮）：**
- 第 1 轮：初次审查 → auto 修复 → 重新审查
- 收敛判定：重新审查后无新增 P0/P1 发现即为收敛
- 未收敛处理：2 轮后仍有 P0/P1 阻断，回退用户澄清

### 下一步引导

技能内 review 闭环收敛后，提示用户可选后续动作：

```text
重构计划已就绪。接下来使用 ae:work 执行重构。

可选后续动作：
/ae-work <plan-path>
```

**阻断时引导：** 若技能内 review 闭环未收敛（2 轮后仍有 P0/P1），回退用户澄清。

永远不要在 `ae:refactor` 中复制 `ae:plan` 的完整流程。`ae:refactor` 负责重构计划策略、清债约束和共享计划结构的正确使用，不是 `ae:plan` 的简单封装。

产出物：一份位于 `ae/plans/` 的计划文档路径，格式遵循 `ae:plan` 标准产出。
