# 文档结构化转换器

将 `ae:doc-humanize` 产出的人读等价视图转换回更利于 AI 识别、审查和执行的结构化文件。

**核心约束：等价转换，不新增、不删减、不改意；结构化输出可按目标模板补充流程性“下一步”，该章节不视为输入人读文档的实质语义新增。**

## 与其他技能的关系

- `ae:brainstorm` 是需求真源，产出 `type: brainstorm`，定义做什么、为什么做和范围边界。
- `ae:plan` 是计划真源，产出 `type: plan`，定义怎么做、实现单元、验证和执行边界。
- `ae:refactor` 不是独立文档类型；它只是进入 `ae:plan` 的重构专项入口，最终产物仍是 `type: plan`。
- `ae:doc-humanize` 把结构化真源转换为人读等价视图。
- `ae:doc-structure` 把人读等价视图恢复为结构化真源格式；如果人读文档不是等价视图，而是新增或删改过的自由文档，本技能必须停止并建议回到 `ae:brainstorm` 或 `ae:plan` 做非等价重新梳理。
给 AI 的结构化需求和计划不需要干系人、读者对象、用户画像、业务价值、市场论证、背景介绍或汇报型影响说明。若输入人读文档记录了上游结构化文件，任何上游没有的实质语义都必须视为非等价新增并停止确认；不得因为新增内容看似可映射到需求范围、约束、验收条件、计划影响面或风险，就把它塞入结构化产物。

## 适用场景

- 用户提供人读需求文档（`type: requirements`），需要转换为 AI 结构化需求文件（`type: brainstorm`）。
- 用户提供人读详细设计文档（`type: design`），需要转换为 AI 结构化计划文件（`type: plan`）。
- 用户需要让人读文档重新进入 `ae:plan`、`ae:work` 或 `ae:review` 流程。

## 不适用场景

- 用户要求把 AI 结构化产物变成人读文档，应使用 `ae:doc-humanize`。
- 用户要求从零生成新需求或新计划，应使用 `ae:brainstorm`、`ae:plan` 或 `ae:refactor`。
- 人读文档与目标结构相差甚远、无法等价直接转换时，不在本技能内补写；停止转换并请求用户确认是否改用非等价重新梳理流程。

## 核心原则

1. **模板完全一致** — 输出必须使用 `ae:brainstorm` 的需求模板或 `ae:plan` 的计划模板，不创建相似但不同的结构。
2. **直接兼容** — 输出的 `type: brainstorm` 必须可被 `ae:brainstorm`、`ae:plan` 直接继续使用；输出的 `type: plan` 必须可被 `ae:plan`、`ae:work`、`ae:refactor` 直接使用。
3. **内容等价** — 输出内容必须与输入人读文档完全等价，不添加新需求、实现方案或风险；目标模板要求的流程性“下一步”可按待定问题状态补充，不视为实质语义新增。
4. **可逆转换** — 输出应能再次通过 `ae:doc-humanize` 转回语义等价的人读文档。
5. **往返结构恢复** — 如果输入人读文档来自 `ae:doc-humanize`，输出正文必须恢复为原始结构化文档的规范正文结构；章节名、章节顺序、稳定 ID 布局和实现单元字段应与原模板几乎完全一致。
6. **保留溯源** — 输出必须记录输入人读文档路径作为上游路径，但内容必须自包含，不依赖输入文档继续解释。
7. **目标模板不补内容** — `ae:brainstorm` 和 `ae:plan` 模板只提供结构，不授权补齐输入文档没有的元素；必选字段缺失时只能映射为原文已声明的待定问题，或停止询问。
8. **不可转换则停止** — 输入缺少直接转换所需的结构锚点，或与目标模板差距过大时，停止转换并说明缺口；不得写半成品，也不得自动改用生成式流程。

## 输入处理

读取指定文档，必须先根据 frontmatter `type` 判断输入文件类别，再选择目标结构：

- `type: requirements` → 输入文件是人读需求文件，参考 `ae:brainstorm` 的需求模板结构，转换为 `type: brainstorm`。
- `type: design` → 输入文件是人读设计文件，参考 `ae:plan` 的计划模板结构，转换为 `type: plan`。
- `type: brainstorm` 或 `type: plan` → 已是结构化产物，说明无需转换。
- 无法识别为需求或设计时，停止并询问用户，不得猜测目标结构。

## 工作流程

### Phase 1：读取、分类并解析人读文档

1. 读取完整文档。
2. 先识别输入文件类别：`type: requirements` 是需求文件，`type: design` 是设计文件；分类失败时停止。
3. 提取稳定 ID：需求 ID、设计单元 ID、决策 ID、问题 ID。
4. 识别章节语义：功能需求、验收标准、范围、设计、数据、接口、测试、风险，以及是否存在无法等价映射的干系人、读者对象、用户画像、业务价值、市场论证、背景介绍或汇报型影响说明。
5. 检查是否存在结构化转换缺口，并判断能否等价直接转换。
6. 建立目标字段来源表：输出结构化文件中的每个章节、字段、稳定 ID、验证项和计数，都必须能定位到输入人读文档的具体段落或表格。

### Phase 1.5：不可直接转换时停止

当输入文档与目标模板相差甚远，导致本技能无法在不补写、不推断的前提下直接转换时，停止当前转换。

触发停止的典型情况：

- 缺少可定位的稳定 ID，且无法与原文内容一一对应。
- 缺少验收条件、范围边界、实现单元、验证方式等目标模板必需信息，且原文没有把这些缺口明确表述为待定问题或开放问题。
- 需要从 `ae:brainstorm` 或 `ae:plan` 模板的示例字段反推输入文档没有的内容，才能生成看似完整的结构化文件。
- 输入文档记录了上游结构化文件路径，但包含上游没有的干系人、读者对象、用户画像、业务价值、市场论证、背景介绍、汇报型影响说明或其他实质语义。
- 章节组织与目标模板差异过大，直接转换会需要大量推断或重写。
- 输入文档更像自由叙述、会议纪要、设计草稿或 PRD 摘要，而不是 `ae:doc-humanize` 产物。

停止时必须说明原因、缺失的结构锚点和建议路径；不得写出半成品结构化文件。若用户确认接受非等价重新梳理，再建议改用 `ae:brainstorm`（需求）或 `ae:plan`（设计），并明确这不是等价转换。

### Phase 2：选择目标模板

- 输入文件是需求文件时，只参考 `ae:brainstorm` 的需求模板结构；本技能的 `references/structured-requirements-template.md` 是同构副本和速查。
- 输入文件是设计文件时，只参考 `ae:plan` 的计划模板结构；本技能的 `references/structured-plan-template.md` 是同构副本和速查。
- 不混合两类目标结构，不把需求文件输出为计划，也不把设计文件输出为需求。

### Phase 3：结构化转换

需求文档转换规则：

- `origin` 记录输入人读需求文档路径；`originFingerprint` 按输入文档 frontmatter 生成。
- 正文必须按 `ae:brainstorm/references/requirements-capture.md` 的规范章节顺序恢复输入中存在的语义。必选章节必须有输入原文依据；可选章节仅在输入人读文档存在对应语义时包含，不生成空章节或占位内容。上游结构化文件只能用于结构对照和等价审查，不能作为输出内容来源。
- 每个 `R*` 需求转换为固定格式：描述、验收条件、约束、非功能属性。
- “范围内/范围外”转换为明确范围边界。
- “开放问题”按规划前需解决和推迟到规划分类。
- R* 绑定的验收条件必须恢复到对应需求条目，不能从全局“验收标准/成功标准”反推绑定；如果人读文档丢失 R* 绑定，停止并报告等价性缺口。
- 开放问题必须恢复影响需求 ID 和问题类型标记；如果人读文档丢失 `[影响 R*]` 或问题类型，停止并报告等价性缺口。
- 必须按目标结构化需求模板补充“下一步”：规划前需解决为空时写 `-> /ae-plan`；规划前需解决不为空时写 `-> 恢复 /ae-brainstorm`。该章节是结构化工作流路由信息，不要求输入人读文档包含对应章节。

详细设计文档转换规则：

- `origin` 记录输入人读详细设计文档路径；`originFingerprint` 按输入文档 frontmatter 生成。
- 正文必须按 `ae:plan/references/plan-template.md` 的规范章节顺序恢复输入中存在的语义。必选章节必须有输入原文依据；可选章节仅在输入人读文档存在对应语义时包含，不生成空章节或占位内容。上游结构化文件只能用于结构对照和等价审查，不能作为输出内容来源。
- 每个 `U*` 模块转换为实现单元，保留依赖顺序。
- 文件变更、实现方案、测试设计和验收方案必须进入对应字段。
- 数据库、接口、安全、性能、部署、风险等章节转换为计划的专项设计块。

### Phase 4：自检

1. 输入中的每个 ID 都必须在输出中出现。
2. 输出不得出现输入中没有的新需求、新文件、新接口、新表或新风险。
3. 必选字段缺失时，只有原文已明确表述为待定或开放问题，才可等价映射为开放问题或阻断项；否则必须询问用户或触发 Phase 1.5 停止流程，不得补写或猜测。
4. 输出必须记录输入文档路径，但不得使用“见输入文档”等表达替代正文内容。
5. 如果输入文档记录了上游结构化文件路径，必须把输入人读文档、输出正文与上游结构化文件正文做双向结构对照。若上游存在而输入人读文档缺失实质语义，说明 A→B 已不等价，必须停止并报告缺口，不得从上游补写到输出；若输入人读文档包含上游没有的实质语义，说明 B 已镀金，必须停止并报告新增内容，不得写入输出。
6. 转换完成后自动调用 `doc-equivalence-reviewer`，传入 `sourcePath`、`outputPath`、`conversionDirection`，并在输入文档记录上游结构化文件路径时一并传入 `upstreamPath`。审查必须覆盖上游结构化文件、输入人读文档和输出结构化文件；若存在 high/medium 发现，先修复后再输出完成摘要。

如果已触发 Phase 1.5 停止流程，则跳过 Phase 3-5 的写文件、自检和等价性审查，并在回复中说明未生成结构化文件。

### Phase 5：输出

默认输出到输入文档同目录：

- 人读需求文档 → `*-structured-requirements.md`
- 人读详细设计文档 → `*-structured-plan.md`

输出摘要包含：输出路径、转换类型、ID 数量、自检结果和无法等价转换的缺口。

## 边界

- 不从人读文档缺口中自行发明需求、设计、风险、文件、接口或验证命令。
- 不因为目标结构化模板包含某个章节或字段，就从常识、最佳实践或上游路径中补写输入文档没有的内容。
- 不把人读文档中的汇报型补充内容硬塞进结构化需求或计划；无法等价映射时必须报告为镀金差异。
- 不镀金、不润色扩写为新含义、不修改原意；遇到不明确问题时可以询问用户。
- 不把输入人读文档作为执行时依赖；输出结构化文件必须自包含。
- 不执行代码修改、测试、构建、远程写操作、Issue、PR 或 Release 创建。
- 当缺少必要 ID、验收条件、实现单元字段或验证方式，且无法等价直接转换时，停止并请求用户确认下一步，不得自行补写或自动委派。
