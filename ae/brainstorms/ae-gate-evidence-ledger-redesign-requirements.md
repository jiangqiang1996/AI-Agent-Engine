# ae-gate Evidence Ledger Redesign

## 问题框架
`ae-gate` 的定位应从“相信当前会话能复盘所有事实”转为“校验当前工作区中可复验的证据账本”。新方案不要求兼容当前以 `sessionID`、当前会话历史或子代理输出绑定方式作为可信根的设计，也不受现有参数结构限制；但规划阶段应优先复用已有 proof、指纹和门禁产物中仍正确的能力。

当前要解决的问题是：门禁应该阻断真实缺证、越权、未验证和未审查风险，但不应因为跨会话恢复、重新打开 opencode、子代理没有写文件权限、当前会话历史不可见、运行时字段变化等执行环境差异而误阻断。

## 需求

**门禁模型**
- R1. `ae-gate` 必须以工作区内持久化证据账本作为主要校验对象，而不是以当前会话 ID 或当前会话历史作为主要可信根 → 验收: 重新打开 opencode 或会话 ID 变化后，只要账本证据仍能绑定当前工作区指纹，最终门禁可以复验通过。
- R2. 证据账本必须分别覆盖验证、审查、Git 写操作授权、worktree 决策、需求/计划/交接基线和可选浏览器验收状态 → 验收: 后续计划能按证据域分别定义记录结构、状态、来源、时间、工作区指纹和复验规则，不把多个证据域混成单个实现单元。
- R3. `ae-gate` 必须区分“证据不存在”“证据存在但不可复验”“证据可复验但结论失败”“证据可复验且通过”四种状态 → 验收: 门禁结果中的 blocker、warning、missingEvidence 和 nextSteps 能明确指向对应状态。
- R4. `ae-gate` 必须保留硬门禁能力，不能退化为最终回复声明检查 → 验收: 缺少验证结果、审查失败、Git 写操作未授权、计划/交接基线缺失等正式交付风险仍会阻断。

**可信根与证据写入**
- R5. 可放行正式交付风险的证据必须由受信工具写入或由受信工具在同一次调用中捕获并写入，普通代理手写、转述、摘要或搬运的证据只能作为声明型证据 → 验收: 高可信证据不得仅凭账本内自声明字段判定；缺少受信 proof 元数据、受信捕获通道证据或等价可信根时，即使手写账本条目字段完整也不能被 `ae-gate` 视为验证通过、审查通过或用户授权通过。
- R6. 账本必须同时记录事实来源可信度和写入者可信度，门禁放行以事实来源可信度为准 → 验收: 主代理代写子代理自然语言输出时，不得把 `agent-declared` 来源升级为 `tool-output`、`observable` 或 `user-confirmed`。
- R7. 新方案必须明确本地工作区账本的威胁边界：账本用于工作流证据复验和误阻断恢复，不承诺抵抗拥有任意工作区写权限的恶意篡改者 → 验收: 文档、门禁结果和 proof 不把本地 JSON/Markdown 账本描述为密码学防篡改安全边界；对可疑或不符合受信工具格式的条目必须降级或阻断。
- R8. 账本应具备篡改显著化能力，而非伪装成绝对防篡改能力 → 验收: 每条可放行证据包含 proofKind、producer、原始材料哈希、记录哈希或等价校验信息；字段缺失、格式异常、哈希不匹配、来源级别不满足或缺少可复验调用证明时阻断；本地账本不承诺识别拥有任意工作区写权限者伪造的一致账本。

**跨会话与子代理兼容**
- R9. 新方案必须支持跨会话恢复，不要求最终门禁所在会话能访问原始审查或授权消息历史 → 验收: 通过工作区证据账本和内容哈希即可复验历史证据，当前会话历史只作为可选增强证据。
- R10. 新方案必须支持子代理无法直接写入工作区的场景，同时不得把主代理搬运的子代理输出升级为正式通过证据 → 验收: 主代理只能保存子代理输出的原文、哈希和来源作为声明型审计材料；只有受信审查 proof 工具或受信捕获通道能绑定真实审查运行并生成可放行审查证据。
- R11. 新方案不得把 `sessionID` 变化本身视为失败条件 → 验收: `sessionID` 可记录为审计字段，但不得作为跨会话复验的阻断字段。
- R12. 新方案必须支持同一任务多次验证、重复审查和修复后再审查 → 验收: 账本能选择当前有效证据，不会因为历史失败记录仍存在而误阻断最新有效证据。
- R13. 当前有效证据覆盖历史失败证据时，必须满足同类证据、覆盖范围匹配、时间顺序正确、工作区变更关系清晰、且可信度不低于被覆盖的阻断证据 → 验收: 低可信声明不得覆盖高可信失败审查或失败验证。

**证据可信度**
- R14. 证据账本必须能区分机器可复验证据、工具输出证据、用户确认、代理声明和不可验证声明 → 验收: `ae-gate` 对不同类别采用不同放行规则，声明型证据不能单独放行正式交付风险。
- R15. 验证证据必须由受信验证捕获入口产生，该入口负责执行或接收可观察命令结果并写入命令、退出码、执行时间、输出摘要或输出哈希、执行工作区指纹 → 验收: 命令未执行、退出码非 0、缺少结果、结果不匹配，或仅由代理手写结果时会阻断。
- R16. 审查证据必须由受信审查 proof 入口产生，并包含审查结论、覆盖的 worktree/branch/HEAD/statusSummary、发现严重级别摘要、完整原始审查输出哈希或结构化报告哈希 → 验收: 当前工作区指纹不匹配、存在阻断发现、报告不可读取、来源只是摘要转述或原始输出哈希不匹配时会阻断。
- R17. Git 写操作授权证据必须由受信用户确认入口产生，绑定具体命令参数、目标 worktree、授权时间和授权来源、授权范围、授权时工作区指纹与最终执行参数 → 验收: 泛化授权、命令参数不一致、目标 worktree 不一致、缺少受信用户确认 proof 或只有代理声明时会阻断。
- R18. 对无法机器复验但仍需要记录的事实，账本必须允许保存为声明证据并明确降级 → 验收: 门禁结果允许展示该声明，但不会把它误标为已验证事实。

**用户体验与恢复**
- R19. 门禁失败时必须输出可执行恢复路径，而不只是说明失败 → 验收: 每个 blocker 都有对应 nextSteps，例如重新运行验证、写入审查 proof、补充授权、选择有效计划或交接基线。
- R20. 最终门禁必须优先从账本自动汇总证据并生成采用证据列表 → 验收: 调用方不需要手工重复传入所有验证、审查和授权细节，门禁结果能说明采用了哪些证据。
- R21. `ae-gate` 工具参数必须收敛到最小必要输入 → 验收: 调用方只需传入 workflow、checkpoint 和必要的目标范围或基线路径，除非处于迁移兼容模式。
- R22. 门禁最终证明必须引用本次采用的账本证据 ID 或等价可追溯标识 → 验收: `ae/gates/` 中的证明可追溯到具体证据记录，后续审计能知道每项通过依据。
- R23. 新方案必须允许工作区证据随代码变更失效 → 验收: HEAD、statusSummary、相关文件变更或证据域定义的关键指纹变化后，旧审查/验证证据不再自动放行，除非同类受信工具证据重新覆盖。
- R24. 新方案必须提供误阻断恢复验收矩阵 → 验收: 会话 ID 变化、当前会话历史为空、子代理无法写文件、运行时字段缺失等场景在账本可复验时不阻断；缺真实验证、审查失败、Git 未授权时仍阻断。

**迁移与证据选择边界**
- R25. 迁移兼容模式必须 fail-closed，不能成为旧参数或手写结果绕过新账本门禁的后门 → 验收: 旧参数中的验证结果、审查摘要、Git 操作声明和授权声明只能作为展示、恢复提示或声明型证据；除非能绑定受信 proof 或受信捕获入口，否则不得单独放行正式交付风险。
- R26. Git 写操作授权证据必须与实际 Git 写操作执行证据匹配后才能放行 → 验收: 受信入口记录实际 Git 命令、目标 worktree、执行前后 HEAD/status、退出码和时间；授权 proof 与执行 proof 的命令参数、目标 worktree 和范围任一不一致时阻断。
- R27. 自动选择当前有效证据时必须绑定当前任务基线和证据范围，不能只按时间、可信度或工作区指纹采用最新记录 → 验收: 证据至少能关联当前 workflow run、需求/计划/交接基线、文件范围或验证意图；范围无法判断或与当前基线不匹配时阻断。
- R28. 各证据域必须定义最小失效原则，避免旧证据在相关输入变化后继续放行 → 验收: 验证证据绑定命令、工作目录和相关输入；审查证据绑定 diff、HEAD 或 statusSummary；授权证据绑定目标 worktree 和命令；计划或交接基线变化会触发旧证据重新评估。
- R29. 浏览器验收状态默认可以作为可选证据域，但当需求、计划或交接基线声明浏览器验收、视觉验证或端到端验收为交付标准时必须升级为硬门禁 → 验收: 必需浏览器验收缺失、失败或无法复验时最终门禁阻断。

## 非功能需求
- NFR1. 证据文件格式必须稳定、可人工审阅、可由工具复验 → 验收: 使用结构化文本或 JSON，字段命名稳定，缺字段时有明确错误。
- NFR2. 证据账本不得依赖插件源码仓库布局作为普通用户项目的前提 → 验收: 面向用户项目时只要求通用 `ae/` 工作流产物，不要求存在本仓库源码目录。
- NFR3. 方案必须优先降低误阻断，同时不降低正式交付安全性 → 验收: 跨会话和子代理场景可恢复；未验证、未授权、审查失败仍阻断。
- NFR4. 新方案必须可增量迁移且迁移期不得降低硬门禁强度 → 验收: 可以先引入新账本和新 `ae-gate` 汇总逻辑，再逐步让验证、审查、授权工具写入标准证据；迁移期对缺少受信 proof 的正式交付风险采用阻断或声明型降级，而不是按旧参数直接放行。

## 成功标准
- 重新打开 opencode 继续任务时，历史验证、审查和授权证据能通过账本复验，不因会话 ID 变化失败。
- 子代理不能写入文件时，主代理只能把其输出保存为声明型审计材料；除非经受信审查 proof 入口复验并写入 proof，否则不得放行正式审查门禁。
- 正式交付前，`ae-gate` 的通过结论可以追溯到具体证据 ID 和工作区指纹。
- 缺少真实验证、审查失败、Git 写操作未授权、计划/交接基线缺失仍会阻断。
- 最终回复能引用 `ae-gate` proofPath，同时 proofPath 能反查到采用的账本证据。
- 字段缺失、格式异常、哈希不匹配、来源级别不足或未通过受信 proof 复验的手写/篡改条目不能放行；本地账本不承诺识别拥有任意工作区写权限者伪造的一致账本。

## 范围边界

### 范围内
- 重新定义 `ae-gate` 的门禁模型、证据模型和复验语义。
- 设计工作区持久化证据账本作为主要可信根。
- 定义验证、审查、授权、worktree 决策、基线和浏览器验收的证据要求。
- 定义跨会话、子代理无写权限、历史不可见、会话 ID 变化等场景的预期行为。
- 定义门禁失败时的恢复语义。
- 定义迁移兼容模式的 fail-closed 边界和当前有效证据的选择原则。

### 范围外
- 不要求兼容当前 `ae-gate` 参数结构或校验实现。
- 不要求保留当前基于当前会话历史的可信判定方式。
- 不在头脑风暴阶段确定具体文件 schema、函数拆分、迁移脚本或测试用例实现。
- 不把门禁降级为纯文本提醒或最终回复模板检查。
- 不承诺抵抗拥有任意工作区写权限的恶意本地篡改者；该问题应通过 Git 审计、代码审查或外部安全边界处理。

### 约束
- 面向插件用户的能力不得硬编码本仓库源码布局作为通用前提。
- `ae-gate` 仍然不替代真实测试、构建、浏览器验收或代码审查。
- Git 写操作授权仍必须可追溯到用户明确授权，不能因跨会话便利而放宽为泛化声明。

## 关键决策
- D1. 采用“证据账本推荐”方向 → 理由: 它能同时解决跨会话恢复、子代理无写权限和当前会话历史不可见问题，同时保留硬门禁价值。
- D2. `sessionID` 只保留为审计字段，不作为放行必需字段 → 理由: 会话 ID 是运行时上下文，不是工作事实；绑定它会导致恢复场景误阻断。
- D3. 允许重新设计可信根，不受现有参数结构和当前会话历史绑定方式约束 → 理由: 当前问题可能来自可信根选择错误，局部放宽会继续保留隐性失败点；但仍应复用已有可验证 proof、指纹和门禁产物中正确的能力。
- D4. 声明型证据允许记录但不能单独放行正式交付风险 → 理由: 既保留恢复和说明能力，又避免门禁被文字承诺绕过。
- D5. Git 授权真实性必须由受信用户确认入口解决，不能推迟为普通规划选择 → 理由: 授权真实性是硬门禁安全前提，不是可替换实现细节。
- D6. 验证和审查的通过证据必须来自受信捕获入口，主代理转写只作为审计材料 → 理由: 仅靠账本字段和哈希不能证明命令或审查确实发生。
- D7. 本地账本采用“可复验和篡改显著化”定位，不声称密码学防篡改 → 理由: 普通工作区文件无法抵抗任意本地写权限篡改，需求必须避免虚假安全承诺。
