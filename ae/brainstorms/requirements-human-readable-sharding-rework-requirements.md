# 人读与机器可提取叠加需求文档能力需求规格说明

## AI 解析契约
- canonicalKind: requirements
- humanEquivalent: true
- stableIdsRequired: true
- noImplicitScope: true

## 1. 背景与目标

### 1.1 业务背景

当前 `ae:brainstorm` 产出的需求文件偏向 AI 结构化数据文档，后续再通过 `ae:doc-humanize` 转换为人读文档。这带来两个问题：

- 当需求规模较大时，单个 Markdown 文件过长，容易超过 LLM 可舒适处理的上下文范围。
- 同一份需求需要同时服务人类阅读和 LLM 执行，维护两套互转格式会增加理解与维护成本。

本次需求的目标是让 `ae:brainstorm` 直接产出“人读表达 + 机器可提取结构”叠加在同一份 Markdown 中的需求文档。文档正文必须符合软件开发需求规格说明的阅读习惯，同时通过稳定 ID、固定标题、固定字段标签和分片索引承载机器可读信息，使工具可以快速提取关键信息供 LLM 使用。当需求涉及多个模块或用户明确要求时，应支持主文件引用子文件的按模块分片；主文件必须保留统一各模块关系的全局需求内容，而不是只作为路径列表。

### 1.2 系统目标

| 目标 ID | 目标描述 | 优先级 |
|---------|----------|--------|
| G1 | `ae:brainstorm` 直接生成同一份 Markdown 承载人读表达和机器可提取结构的需求规格说明 | 高 |
| G2 | 需求文件必须让从未接触过该需求的人能够完整读懂背景、目标、范围、需求和验收方式 | 高 |
| G3 | 需求文件保留稳定 ID、固定标题和固定字段标签，支持最小提取能力提取出 LLM 执行所需的重要信息 | 高 |
| G4 | 需求文件支持按模块分片，触发条件仅来自模块数量和用户明确要求 | 高 |
| G5 | 移除机器文档与人读文档互转相关技能，以及专门服务互转一致性比较的代理 | 高 |
| G6 | `ae:plan` / `ae:refactor` 生成的人读与机器可提取计划文档也支持与需求文档一致的按模块分片 | 高 |
| G7 | 定义完善的设计文档结构模板，并支持与需求和计划一致的按模块分片方式 | 高 |
| G8 | `ae:review` 能以主文件和分片文件的关系为审查输入，复用现有文档审查代理检查分片完整性与一致性 | 高 |

### 1.3 范围

**范围内：**
- 定义 `ae:brainstorm` 新的人读与机器可提取叠加需求文档模板。
- 定义最小需求信息提取能力，使 LLM 可以从同一份需求文档中读取结构化内容。
- 定义需求文档按模块分片策略和主/子文件结构。
- 定义计划文档和设计文档的按模块分片策略和主/子文件结构。
- 定义设计文档模板，使其同时服务人类阅读和机器提取。
- 定义与 `ae:plan`、`ae:review` 等后续能力的输入兼容要求。
- 定义分片文档审查契约，使现有文档审查代理能审查主文件和子文件关系。
- 明确哪些文档元素是必选，哪些是按需求类型可选。
- 移除 `ae:doc-humanize`、`ae:doc-structure` 等机器文档与人读文档互转相关技能。
- 移除专门为上述互转技能服务的文档等价性比较代理。

**范围外：**
- 本需求不要求在头脑风暴阶段设计具体 TypeScript API 或内部实现代码。
- 本需求不要求立刻定义数据库 Schema、具体解析算法或测试脚手架。
- 本需求不要求所有需求文档强制分片。
- 本需求不要求按功能数量或行数触发需求、计划或设计文档分片。
- 本需求不要求保留机器专用需求文档与人读需求文档之间的长期互转兼容工作流。
- 本需求不要求新增独立的分片一致性审查代理。

## 2. 功能需求

**文档格式与人读体验**

- R1. `ae:brainstorm` 生成的需求文件必须采用人读需求规格说明格式，并在同一份 Markdown 中保留机器可提取结构。
  - R1-AC1: 新文档包含背景与目标、范围、功能需求、验收标准、约束等软件开发常用章节。
  - R1-AC2: 新文档使用自然语言描述需求，不能只保留机器解析字段。
  - R1-AC3: 新文档通过稳定 ID、固定标题、固定字段标签和表格结构承载机器可提取信息，不再生成另一份机器专用需求文档。
- R2. 需求文件必须移除没有实际实施价值的模板元素。
  - R2-AC1: 默认模板不包含修订历史、空泛的文档目的、独立术语表、交付物清单、等价性检查等不直接影响实施的章节。
- R3. 需求文件必须让首次接触该需求的人能够读懂完整上下文。
  - R3-AC1: 单文件模式下，单个需求文件包含业务背景、系统目标、范围内外、功能需求描述和验收条件；存在待定问题时包含待定问题。
  - R3-AC2: 分片模式下，完整需求以“主文件 + 所有子文件”的文档集为单位自包含。
  - R3-AC3: 分片主文件至少包含每个模块的摘要、目标映射、阅读顺序和子文件链接，不能只是无上下文的路径列表。
- R4. 模板中的可选章节必须按需求类型出现，而不是为了完整性固定生成。
  - R4-AC1: 数据设计仅在涉及数据存储或数据处理时出现。
  - R4-AC2: 接口设计仅在涉及 API 或外部集成时出现。
  - R4-AC3: 非功能需求仅在存在性能、安全、可用性等明确要求时出现。
  - R4-AC4: 需求文档模板应以软件需求规格说明的常见元素作为候选集合；除背景与目标、范围、功能需求、约束和验收标准等核心章节外，多数元素应作为条件可选章节。
  - R4-AC5: 需求文档可以承载软件开发流程之外但影响需求判断、验收或执行边界的内容，例如运营流程、人工审核、组织协作、数据治理、合规要求、迁移要求、发布策略或外部依赖；这些内容必须有明确实施或验收价值，不能作为泛化说明补齐。

**稳定 ID 与信息提取**

- R5. 需求文档必须为重要信息保留稳定 ID。
  - R5-AC1: 系统目标使用 `G*`，功能需求使用 `R*`，验收条件使用 `R*-AC*`，业务规则使用 `R*-BR*`。
  - R5-AC2: 非功能需求使用 `NFR*`，技术约束使用 `TC*`，业务约束使用 `BC*`，风险使用 `RISK*`，关键决策使用 `D*`，待定问题使用 `Q*`。
- R6. 最小提取能力必须能从需求文档中提取 LLM 执行所需的结构化信息。
  - R6-AC1: 最小输出包含元数据、目标、范围、功能需求、验收条件、业务规则、约束和待定问题。
  - R6-AC2: 非功能需求、风险、决策、数据实体和接口信息在文档存在对应章节时提取到对应可选输出字段；不存在时不生成空结构。
- R7. 最小提取能力必须支持筛选读取，减少 LLM 上下文占用。
  - R7-AC1: 第一版至少支持按需求 ID 和模块筛选。
  - R7-AC2: 关键词筛选和多种输出格式属于增强能力，只有在规划确认消费者需要时实现。
- R8. 提取结果必须能明确区分不同来源的信息类型。
  - R8-AC1: 输出结构中功能需求、非功能需求、约束、决策、风险和待定问题分别成组，不混在同一段自然语言中。

**按模块分片**

- R9. 需求文档必须支持按模块分片，而不是所有需求盲目分片。
  - R9-AC1: 当模块数量不大于 1 且用户未要求分片时，`ae:brainstorm` 生成单文件需求文档。
  - R9-AC2: 用户明确要求单文件时，除非文档无法完整写入，否则优先生成单文件。
- R10. 自动分片应使用模块条件触发策略，并允许用户覆盖。
  - R10-AC1: 默认触发条件仅为模块数量大于 1，或用户明确要求分片。
  - R10-AC2: 满足任一触发条件时，`ae:brainstorm` 应建议或生成分片文档；用户明确选择单文件时按 R9-AC2 处理。
  - R10-AC3: `R*` 数量和预估行数不得作为需求文档自动分片触发条件。
- R11. 分片维度必须按模块拆分。
  - R11-AC1: 每个子文件对应一个模块。
  - R11-AC2: 子文件包含该模块的功能需求，以及该模块相关的数据设计和接口设计。
  - R11-AC3: 不得因为需求分组、功能数量或文档长度单独创建分片；跨模块需求必须在主文件中记录跨模块关系，并在相关模块子文件中引用全局关系 ID。
- R12. 分片主文件必须作为索引和全局上下文文件。
  - R12-AC1: 主文件保留背景与目标、范围、分片索引、全局约束和验收标准；存在全局非功能需求、风险、关键决策或待定问题时保留对应内容。
  - R12-AC2: 主文件为每个分片提供模块摘要、目标映射和推荐阅读顺序。
  - R12-AC3: 主文件必须记录统一各模块关系的全局需求内容，包括模块关系、跨模块流程、共享数据、全局约束和跨模块验收关注点；不得只是子文件路径列表。
- R13. 分片子文件必须能够独立表达模块需求。
  - R13-AC1: 子文件包含模块名称、功能需求、验收条件、业务规则，以及该模块相关的数据设计和接口设计。
  - R13-AC2: 子文件引用主文件中的全局决策或问题时必须标明对应 ID。
- R14. 最小提取能力必须支持分片文档的合并提取。
  - R14-AC1: 当输入主文件且 `sharded: true` 时，提取能力能读取主文件声明的子文件并合并输出结构化结果。
  - R14-AC2: 当输入子文件时，提取能力能返回该分片内容，并标明父文件路径。
  - R14-AC3: 当输入主文件且提供 `ids` 或 `modules` 筛选条件时，提取能力应优先通过主文件 `shards` 索引定位并读取匹配子文件；索引不足时才降级读取全部子文件并在 diagnostics 中说明。

**工作流调整**

- R15. `ae:plan` 应能消费新的人读与机器可提取叠加需求文档，或通过最小提取能力获取结构化需求。
  - R15-AC1: 规划阶段不再依赖旧机器专用需求文档的固定章节作为唯一输入。
- R16. `ae:review` 应能审查新的人读需求文档和分片需求文档。
  - R16-AC1: 审查能识别主文件和子文件，并检查需求完整性、范围一致性、稳定 ID 和跨文件引用。
  - R16-AC2: 分片文档审查应由 `ae:review` 编排层构建“主文件 + 子文件集合”的审查上下文，再分发给现有文档审查代理。
  - R16-AC3: `coherence-reviewer` 应检查主子文件 ID 唯一性、父子引用、分片索引覆盖、术语和跨模块关系一致性。
  - R16-AC4: `feasibility-reviewer` 应检查分片发现、批处理、恢复、缺失子文件降级和上下文预算策略是否可落地。
  - R16-AC5: `step-granularity-reviewer` 应检查分片边界、分片级产出物、分片级验证和跨文件执行依赖是否清晰。
  - R16-AC6: `adversarial-reviewer` 应覆盖缺失分片、重复 ID、模块归属不清、主文件退化为路径列表、跨模块需求遗漏等失败场景。
  - R16-AC7: 不新增专门的分片一致性审查代理；若需要确定性完整性检查，应由工具或 `ae:review` 编排前置检查承载。
- R17. 机器文档与人读文档互转相关能力应从 AE 正式能力集中移除。
  - R17-AC1: `ae:brainstorm` 的输出已经是人读与机器可提取叠加需求文档，不再要求通过 `ae:doc-humanize` 生成可阅读版本，也不再要求通过 `ae:doc-structure` 转回机器专用版本。
  - R17-AC2: 移除 `ae:doc-humanize` 技能、命令、帮助入口、模型路由配置和相关注册项。
  - R17-AC3: 移除 `ae:doc-structure` 技能、命令、帮助入口、模型路由配置和相关注册项。
  - R17-AC4: 移除专门服务互转一致性比较的 `doc-equivalence-reviewer` 代理及其注册入口；若该代理被其他非互转流程复用，规划阶段必须先拆分职责再删除互转专用部分。
  - R17-AC5: 旧互转产物不作为新工作流继续维护的输入格式；不提供历史互转产物迁移说明、迁移脚本或长期兼容路径。

**计划与设计文档**

- R18. `ae:plan` 和 `ae:refactor` 生成的计划文件必须采用人读与机器可提取叠加格式。
  - R18-AC1: 计划文档正文必须让首次接触该计划的人能够读懂来源目标、范围、设计、实现单元、验证方式、风险和待定问题。
  - R18-AC2: 计划文档必须保留稳定 ID、固定标题和固定字段标签，支持工具提取 LLM 执行所需的结构化计划信息。
  - R18-AC3: `ae:refactor` 不维护独立文档类型，仍生成或更新 `type: plan` 计划文档，但计划内容必须包含重构专属的行为保持要求和回滚信号。
- R19. 计划文档分片方式必须与需求文档保持一致，仅根据模块数量和用户明确要求触发。
  - R19-AC1: 当计划涉及模块数量大于 1，或用户明确要求分片时，`ae:plan` 应建议或生成分片计划文档。
  - R19-AC2: `U*` 实现单元数量、需求数量和预估行数不得作为计划文档自动分片触发条件。
  - R19-AC3: 用户明确要求单文件时，除非计划无法完整写入，否则优先生成单文件。
- R20. 分片计划主文件必须保留统一各模块关系的全局计划内容。
  - R20-AC1: 主计划文件保留来源与目标、范围、需求追溯、全局高层技术设计、模块关系、跨模块依赖顺序、共享数据或接口边界、全局验证策略、全局风险和分片索引。
  - R20-AC2: 子计划文件按模块承载该模块的专项设计、实现单元、测试场景、验证命令、行为保持要求和回滚信号。
  - R20-AC3: 子计划文件引用主文件中的全局决策、约束、风险或待定问题时必须标明对应 ID。
- R21. 设计文档必须有完善模板，并与需求和计划采用一致的按模块分片方式。
  - R21-AC1: 设计文档模板必须以软件开发流程标准设计元素作为候选集合，包括设计目标、需求追溯、总体架构、模块设计、接口设计、数据设计、流程或状态设计、错误处理、安全设计、性能设计、部署与回滚、验证策略、风险与决策等对实施有直接价值的内容。
  - R21-AC2: 设计文档仅在模块数量大于 1 或用户明确要求时分片，不按功能数量、实现单元数量或行数触发分片。
  - R21-AC3: 分片设计主文件保留统一各模块关系的全局设计内容；子文件按模块承载该模块的详细设计。
  - R21-AC4: 设计文档不得作为旧 `ae:doc-humanize` 互转产物继续维护；它应由新计划文档模板或计划流程中的设计章节直接承载或生成。
  - R21-AC5: 除设计目标、总体架构、模块关系、关键决策和验证策略等核心章节外，多数设计元素应作为条件可选章节，只在对应内容真实影响实施、审查或运维时出现。
  - R21-AC6: 设计文档可以承载软件开发流程之外但影响实施决策的设计内容，例如架构评估、迁移方案、运行维护策略、观测与告警、数据治理、合规约束、人工流程或组织协作边界；这些内容必须有明确实施价值，不能作为泛化说明补齐。
- R22. `ae:review` 必须定义分片审查输入契约，而不是让每个审查代理自行推断文件关系。
  - R22-AC1: 分片审查输入至少包含 `rootDocument`、`shards`、`missingShards`、`duplicateIds`、`parentMismatch`、`globalRelations` 和 `diagnostics`。
  - R22-AC2: `rootDocument` 必须包含主文件路径、frontmatter、全局章节摘要、分片索引和全局关系内容。
  - R22-AC3: `shards` 中每个条目必须包含子文件路径、模块名、父文件声明、稳定 ID 列表和子文件摘要。
  - R22-AC4: 当分片文件缺失、父子引用不一致或稳定 ID 重复时，编排层必须把这些确定性问题作为审查输入证据传递给相关代理。
- R23. 分片完整性的确定性检查应优先由工具或编排层执行。
  - R23-AC1: 确定性检查至少覆盖分片路径存在性、路径位于当前工作区内、`parent` 指向主文件、稳定 ID 不重复、`shards` 索引覆盖子文件和子文件不被误识别为顶层产物。
  - R23-AC2: 确定性检查结果应写入 `diagnostics`，供审查代理做语义判断；代理不应重复承担可由工具稳定判断的文件系统检查。
  - R23-AC3: 确定性检查失败时，`ae:review` 不应静默跳过缺失分片；应在审查报告中给出可恢复诊断。
- R24. 分片语义审查应复用现有文档审查代理。
  - R24-AC1: `coherence-reviewer`、`feasibility-reviewer`、`adversarial-reviewer` 和 `step-granularity-reviewer` 的文档域提示词应补充对分片文档集合的审查职责。
  - R24-AC2: `product-lens-reviewer` 仅在分片策略影响范围、复杂度或产品决策时激活，不因存在分片而必然激活。
  - R24-AC3: `doc-equivalence-reviewer` 不参与新人读与机器可提取叠加文档的分片审查，并随互转能力移除。

## 3. 非功能需求

- NFR1. 文档可读性 → 验收: 默认模板中每个保留章节都必须对实施、规划或审查有直接价值，不生成空壳章节。
- NFR2. LLM 友好性 → 验收: 最小提取能力能在不读取整份长文档的情况下返回指定模块或指定需求的上下文。
- NFR3. 兼容性 → 验收: 新格式必须保留足够稳定 ID，使后续计划、审查和执行可以无歧义引用需求。
- NFR4. 可恢复性 → 验收: 分片文档的主文件必须记录所有子文件路径，子文件必须记录父文件路径，避免跨会话丢失上下文。
- NFR5. 审查可诊断性 → 验收: 分片审查报告必须区分确定性完整性问题和代理语义审查问题，避免把文件缺失、ID 重复等机器可判定问题写成主观建议。

## 4. 需求文档模板要求

### 4.1 必选章节

- 背景与目标：说明为什么做、目标是什么、范围是什么。
- 功能需求：按模块或需求分组列出 `R*` 需求、描述、验收条件和必要业务规则。
- 约束：记录会影响实施或规划的技术约束和业务约束。
- 验收标准：说明整体需求如何被确认完成。

### 4.2 条件可选章节

- 非功能需求：仅在存在性能、安全、可用性、兼容性等明确要求时出现。
- 数据设计：仅在需求涉及数据存储、数据处理或数据实体时出现。
- 接口设计：仅在需求涉及 API、内部接口或外部系统集成时出现。
- 风险与决策：仅在存在重要风险或关键产品/技术决策时出现。
- 待定问题：仅在仍有未解决问题时出现。
- 附录：仅在流程图、状态图等视觉辅助能显著提升理解时出现。
- 扩展需求内容：仅在运营流程、人工协作、数据治理、合规、迁移、发布或外部依赖等内容会影响实施或验收时出现。

### 4.7 分片审查契约

`ae:review` 审查分片文档时，应先构建统一的分片审查输入，再把同一份关系上下文传递给文档审查代理。契约字段如下：

```yaml
rootDocument:
  file: ae/brainstorms/<topic>.md
  format: human-readable-requirements|human-readable-plan|human-readable-design
  type: brainstorm|plan|design
  sharded: true
  globalSections: [背景与目标, 范围, 模块关系, 全局约束, 验收标准]
  globalRelations: [<跨模块关系 ID 或摘要>]
shards:
  - file: ae/brainstorms/<topic>-shards/<module-file>.md
    module: <模块名称>
    parent: ae/brainstorms/<topic>.md
    ids: [R1, R1-AC1]
    summary: <子文件摘要>
missingShards: []
duplicateIds: []
parentMismatch: []
diagnostics: []
```

分片审查职责分配如下：

| 审查者 | 分片审查职责 |
|--------|--------------|
| `coherence-reviewer` | 检查主子文件 ID、术语、父子引用、分片索引和跨模块关系一致性 |
| `feasibility-reviewer` | 检查分片发现、批处理、恢复、缺失分片降级和上下文预算是否可实现 |
| `step-granularity-reviewer` | 检查分片边界、分片级产出物、分片级验证和跨文件执行依赖 |
| `adversarial-reviewer` | 构造缺失分片、重复 ID、模块归属不清、跨模块需求遗漏等失败场景 |

分片完整性检查中的路径存在、父子引用、ID 重复和索引覆盖属于确定性检查，应优先由工具或 `ae:review` 编排层完成；审查代理基于这些诊断继续判断语义完整性和风险。

## 5. 约束

### 5.1 技术约束

- TC1. 新格式必须使用仓库相对路径引用分片文件。
- TC2. 分片主文件中的 `shards` 列表必须足以让工具发现所有子文件。
- TC3. 提取能力不得依赖 `ae:doc-humanize` 作为中间转换步骤。
- TC4. 主需求文件继续使用 AE 现有合法产物类型 `type: brainstorm`，通过 `format: human-readable-requirements` 区分新的人读需求格式。
- TC5. 分片子文件是主需求文件的辅助文件，不作为独立 AE 顶层产物参与恢复；恢复入口以主文件为准。
- TC6. 分片子文件必须放在主文件同目录下的 `<topic>-shards/` 子目录中，避免被 `ae/brainstorms/` 顶层产物扫描误识别为独立需求产物。
- TC7. 分片子文件使用 `type: brainstorm-shard` 标识辅助分片；恢复、门禁和计划入口不得把该类型当作顶层 AE 产物。
- TC8. 主文件和模板中的 `status` 必须继续使用现有 `brainstorm` 产物状态：`drafted`、`review-passed` 或 `completed`。
- TC9. 计划分片子文件使用 `type: plan-shard` 标识辅助分片；恢复、门禁和执行入口不得把该类型当作顶层 AE 计划产物。
- TC10. 设计分片子文件使用 `type: design-shard` 标识辅助分片；主设计文档可由计划引用，但不得重新引入 `ae:doc-humanize` / `ae:doc-structure` 互转工作流。
- TC11. 需求、计划和设计文档的自动分片触发条件必须保持一致：只允许模块数量大于 1 或用户明确要求分片，不得使用功能数量、实现单元数量或行数作为触发条件。
- TC12. 设计文档采用软件开发流程标准设计元素，但接口、安全、性能、部署等条件章节仅在对应设计内容真实存在时出现，不得生成空壳章节。
- TC13. 分片审查不得依赖新增专门代理作为唯一入口；`ae:review` 必须通过编排契约和现有文档审查代理完成主子文件关系审查。
- TC14. 分片路径存在性、父子引用、稳定 ID 重复和分片索引覆盖等确定性完整性检查必须能由工具或编排层输出结构化诊断。

### 5.2 业务约束

- BC1. 不应为了模板完整性生成没有实施价值的章节。
- BC2. 分片必须以模块边界和用户明确选择为依据，不应降低人类阅读完整性。
- BC3. 用户明确要求单文件时，应优先尊重用户选择。
- BC4. 主文件必须承担跨模块理解入口，保留统一各模块关系的全局需求、全局计划或全局设计内容。

## 6. 验收标准

### 6.1 功能验收

- 所有 `R*` 功能需求的验收条件通过。
- 新模板能同时支持单文件和分片文件。
- 最小提取能力能从单文件和分片文件中提取结构化需求内容。
- 计划文档和设计文档能同时支持单文件和按模块分片文件。
- 后续规划和审查可以基于新需求文档继续工作。

### 6.2 非功能验收

- 文档中不存在无实际价值的固定空壳章节。
- 分片场景下，主文件和子文件之间的引用关系清晰且可恢复。
- LLM 可以按模块、需求 ID 或实现单元 ID 加载局部上下文。

## 7. 风险与决策

### 7.1 风险分析

| 风险 ID | 风险描述 | 影响 | 概率 | 应对策略 |
|---------|----------|------|------|----------|
| RISK1 | 人读格式过于自由，导致工具难以稳定提取 | 高 | 中 | 保留稳定 ID、固定标题和固定字段标签 |
| RISK2 | 分片后跨文件引用不清晰，影响规划和审查 | 高 | 中 | 主文件记录完整分片索引，子文件记录父文件和关联 ID |
| RISK3 | 移除互转技能后，历史互转产物或用户习惯受到影响 | 中 | 中 | 通过发布说明告知移除范围，不提供历史互转产物迁移说明、迁移脚本或长期兼容路径 |
| RISK4 | 按模块分片可能让模块设计忽略跨模块扩展性 | 高 | 中 | 主文件必须记录模块关系、跨模块流程、共享数据、依赖顺序和扩展边界 |
| RISK5 | 为分片一致性新增专门代理会与现有文档审查代理职责重叠，增加调度复杂度 | 中 | 中 | 不新增独立分片审查代理；通过 `ae:review` 编排契约、确定性检查和现有代理提示词更新覆盖分片审查 |

### 7.2 关键决策

#### D1. 需求文档以人读格式作为直接产物

**决策：** `ae:brainstorm` 应直接生成 `format: human-readable-requirements` 风格的人读与机器可提取叠加需求规格说明，主文件继续使用现有合法产物类型 `type: brainstorm`。

**理由：** 用户希望需求文件本身符合人类阅读习惯，同时机器阅读内容可由工具快速提取，不再维护机器专用文档与人读文档之间的互转工作流。

#### D2. 分片仅由模块数量和用户明确要求触发

**决策：** 需求、计划和设计文档的自动分片条件保持一致：仅当模块数量大于 1，或用户明确要求分片时启用；功能需求数量、实现单元数量和预估行数都不得作为自动分片触发条件。

**理由：** 模块边界比功能数量或行数更能表达文档拆分后的阅读和执行边界；数量或行数触发会导致同一模块被人为拆碎，降低跨模块关系的可理解性。

#### D3. 分片按模块进行，主文件保留跨模块关系

**决策：** 子文件按模块组织，并承载该模块相关的需求、计划或设计细节；主文件必须保留模块关系、跨模块流程、共享数据、接口边界、依赖顺序和全局约束。

**理由：** 模块是人类阅读和 LLM 局部加载都容易理解的边界，但跨模块关系必须由主文件统一表达，避免各模块分片在设计和执行时各自为政。

#### D4. 移除互转技能和互转专用等价性审查代理

**决策：** 移除 `ae:doc-humanize`、`ae:doc-structure` 以及专门服务互转一致性比较的 `doc-equivalence-reviewer`。

**理由：** 新需求文档是人读表达与机器可提取结构的叠加产物，不再需要在两种需求文档形态之间往返转换，也不再需要专门为互转结果比较等价性的代理。

#### D5. 历史互转产物不提供迁移路径

**决策：** 移除 `ae:doc-humanize` / `ae:doc-structure` 时，不提供历史互转产物迁移说明、迁移脚本或长期兼容路径，直接从正式能力集中移除相关技能、命令、帮助入口、模型路由和互转专用代理。

**理由：** 新工作流以同一份人读与机器可提取叠加需求文档作为唯一持续维护形态，保留迁移路径会延长旧互转模型的维护成本。

#### D6. 最小提取能力以新增工具承载

**决策：** 第一版最小需求信息提取能力应新增为可调用工具，支持按路径、需求 ID 和模块提取结构化需求内容。

**理由：** 工具形式便于 `ae:plan`、`ae:review` 和其他后续能力复用，也能让 LLM 在长文档或分片文档中按需读取局部上下文。

#### D7. `ae:plan` 优先通过提取工具读取需求

**决策：** `ae:plan` 消费新需求文档时，应优先调用最小提取工具获取结构化需求，再按需读取原文补充语义。

**理由：** 工具优先可以统一单文件与分片文档的读取路径，减少规划阶段重复解析 Markdown 的成本。

#### D8. 分片文档默认全部审查，允许用户选择模块审查

**决策：** `ae:review` 审查分片需求主文件时，默认应读取并审查全部子文件；用户主动使用 `ae:review` 时，可以选择只审查某个模块或指定分片。

**理由：** 默认全部审查能保证需求完整性、稳定 ID 和跨文件引用一致性；模块审查作为用户显式选择，支持大文档的局部审查场景。

#### D9. 计划和设计文档沿用需求文档的分片原则

**决策：** `ae:plan` / `ae:refactor` 生成的计划文档，以及计划流程中的设计文档模板，都必须沿用需求文档的分片原则：只按模块数量和用户明确要求触发分片，主文件保留跨模块关系，子文件按模块承载细节。

**理由：** 需求、计划和设计文档使用一致的分片语义，可以降低后续提取、审查、恢复和执行流程的认知成本。

#### D10. 设计文档模板直接在新文档体系中定义

**决策：** 设计文档模板作为新文档体系的一部分定义，支持单文件和按模块分片；它不得依赖旧 `ae:doc-humanize` / `ae:doc-structure` 互转流程生成或维护。

**理由：** 移除互转能力后，设计内容必须由计划流程或计划文档模板直接承载，避免重新引入机器文档与人读文档的双轨维护。

#### D11. 分片一致性审查复用现有文档审查代理

**决策：** 不新增专门的分片一致性审查代理；`ae:review` 应在编排层构建分片审查契约，并把主文件和子文件关系上下文传递给现有文档审查代理。

**理由：** 分片完整性和一致性不是独立审查视角，而是 coherence、feasibility、step-granularity 和 adversarial 等现有文档审查视角的共同输入前提。新增代理会造成职责重叠，并增加调度和报告合并复杂度。

#### D12. 分片确定性完整性检查由工具或编排层承载

**决策：** 分片路径存在性、父子引用、稳定 ID 重复和索引覆盖等可机器判定的问题，应由工具或 `ae:review` 编排层先输出结构化诊断；审查代理基于诊断继续做语义完整性、可行性和风险判断。

**理由：** 文件存在、路径合法和 ID 重复属于确定性检查，交给工具或编排层能减少代理重复判断和遗漏；代理应聚焦需要语义判断的主子文件关系、模块边界和跨模块需求风险。

## 9. 最小提取契约

### 9.1 输入行为

- 输入主文件且 `sharded: false` 时，只解析该文件。
- 输入主文件且 `sharded: true` 且没有筛选条件时，解析主文件和 `shards` 列表中的全部子文件。
- 输入主文件且 `sharded: true` 且提供 `ids` 或 `modules` 筛选条件时，优先通过 `shards` 索引定位匹配子文件，只读取匹配子文件；索引不足时降级读取全部子文件。
- 输入子文件时，只解析该子文件，并返回其 `parent` 路径用于调用方补充全局上下文。
- 输入路径必须位于当前工作区内，分片路径必须使用仓库相对路径。

### 9.2 最小筛选能力

- 支持按 `ids` 筛选 `R*` 需求。
- 支持按 `ids` 筛选 `U*` 实现单元；仅当输入文档存在计划内容时生效。
- 支持按 `modules` 筛选分片或模块章节。
- 支持控制是否包含全局上下文；默认包含目标、范围、约束和待定问题。

### 9.3 最小输出结构

最小输出必须包含：

- metadata：标题、日期、topic、format、sharded、来源文件。
- artifacts：文档类型和分片类型，支持 requirements、plan、design 及其 shard 类型。
- scope：范围内、范围外。
- goals：`G*` 目标。
- requirements：`R*` 需求、模块、描述、`R*-AC*` 验收条件、`R*-BR*` 业务规则。
- implementationUnits：`U*` 实现单元、所属模块、覆盖需求、依赖、文件、方法、测试场景和验证方式；仅当文档存在计划内容时返回。
- designSections：架构总览、模块关系、数据流或状态流、关键决策和专项设计；仅当文档存在设计内容时返回。
- constraints：`TC*` 技术约束和 `BC*` 业务约束。
- questions：`Q*` 待定问题。
- nonFunctionalRequirements：`NFR*` 非功能需求；仅当文档存在对应章节时返回。
- risks：`RISK*` 风险；仅当文档存在对应章节时返回。
- decisions：`D*` 决策；仅当文档存在对应章节时返回。
- entities：数据实体；仅当文档存在对应章节时返回。
- interfaces：接口信息；仅当文档存在对应章节时返回。
- diagnostics：缺失分片、重复 ID、无法解析章节或父子引用不一致等问题。

### 9.4 错误与降级

- 分片文件缺失时，返回可恢复诊断，不应静默忽略。
- 稳定 ID 重复时，返回冲突列表。
- 子文件缺少 `parent` 时，仍可提取该文件内容，但必须在 diagnostics 中标记父文件缺失。
