# Agent Orchestration And Light Gate

## AI 解析契约
- canonicalKind: requirements
- humanEquivalent: true
- stableIdsRequired: true
- noImplicitScope: true

## 问题框架
当前 AE 核心能力主要由技能承载流程、门禁和产物契约，agent 已用于审查、研究、执行分片和工作流专项能力。目标方向是扩大 agent 的数量和功能，让技能更多承担 agent 组合、编排、入口契约和交互协调，而不是把具体功能长期固化在技能正文中。

同时，`ae-gate` 当前定位偏硬门禁，会校验审查证据、Git 授权、文件路径、最终阻断和证明写入。新的目标是削弱为基础完成证明：只判断流程是否完成并返回记录，不再执行额外强校验，例如文件是否被主动篡改；`ae-gate` 的门禁证明统一由主代理写入。子代理只负责形成门禁载荷并回传给主代理，不执行门禁落盘，也不通过工具内部隐式提权绕过权限边界。

## 需求

**Agent 编排模式**
- R1. 定义统一的 agent 编排协议，作为技能组合 agent 的共同契约 → 验收: 后续 `ae:plan` 能基于该协议规划新增 agent、agent 输出格式、错误处理、主技能汇总和迁移步骤。
- R2. 技能应逐步转向编排层，负责入口参数、用户交互、安全边界、agent 调度和最终汇总 → 验收: 核心技能迁移计划能明确哪些职责保留在技能，哪些职责下沉到 agent。
- R3. 具体功能优先由专精 agent 承担，包括需求分析、计划研究、执行分片、验证、审查、综合、风险识别和专项工作流 → 验收: 专精 agent 增量清单覆盖核心生命周期，并说明每类 agent 的输入、输出和适用场景。
- R4. agent 扩充顺序必须遵循“协议优先、再增加专精能力、再逐步迁移所有技能” → 验收: 后续计划中的阶段顺序与该优先级一致，不先做大规模技能迁移。
- R5. agent 应按能力类型重新划分，而不是按技能或生命周期固定绑定；技能本质上是对一个或多个已有能力 agent 的编排 → 验收: 后续计划包含已有 agent 划分评估、目标能力分类、迁移映射和不合理边界的调整方案。

**技能与 Agent 边界**
- R6. 技能不得完全退化为无责任转发器，仍需保留用户交互、调度裁决、跨 agent 冲突处理和最终状态汇总 → 验收: 迁移后的技能仍能解释本次调用做了什么、哪些 agent 参与、最终状态是什么。
- R7. agent 输出应结构化，便于技能组合、比较、合并和降级处理 → 验收: 每类新增 agent 都有明确输出字段或最小输出契约。
- R8. 多 agent 编排必须支持部分失败降级，不因单个非关键 agent 失败导致整个技能不可用 → 验收: 编排协议包含失败状态、可继续条件和主技能汇总规则。
- R9. agent 编排协议必须定义最小通用输出语义，包括状态、摘要、证据、风险、建议动作、可继续条件和冲突标识 → 验收: 新增 agent 即使有专属字段，也能被技能按通用字段汇总和降级处理。

**ae-gate 降级**
- R10. `ae-gate` 应从硬门禁降级为基础完成证明工具，只检验是否完成到指定阶段或最终状态 → 验收: gate 结果不再因审查证明复验、文件篡改校验、强证据绑定等额外检查而阻断。
- R11. `ae-gate` 的状态模型应表达“完成/未完成”：`completed` 表示流程已到达目标阶段且门禁载荷已形成并记录结果；`incomplete` 仅用于目标阶段必要输入缺失、门禁载荷无法形成、或主代理写入链路不可用且无法记录失败状态的情况 → 验收: 验证失败、审查未运行、浏览器未验收等质量或覆盖问题默认进入 warning/记录字段，不再自动使状态变为 `incomplete`。
- R12. `ae-gate` 的门禁证明统一由主代理写入；如果子代理触发 gate，应将门禁载荷返回给主代理，由主代理写入 `ae/gates/` → 验收: 子代理路径不会因缺少文件写入权限而丢失门禁内容，且不存在子代理直接落盘或工具内部隐式提权路径。
- R13. `ae-gate` proof 写入是常规交付要求；常规情况下必须产生 `proofPath`。仅当真实写入失败、文件系统不可用或主代理写入链路不可用时，才允许携带 `proofWriteStatus=failed` 或等价结构化失败状态完成交付 → 验收: 常规交付仍产生 `proofPath`，异常交付必须记录可诊断的写入失败原因。
- R14. `ae-gate` 仍应保留最基础的信息记录，包括工作流、检查点、完成状态、验证命令摘要、审查状态摘要、Git 操作声明和备注 → 验收: 最终返回足以让用户知道本轮是否已完成、哪些验证/审查被声明执行、哪些没有执行。
- R15. `ae-gate` 不应把子代理文件写入权限作为使用前提，也不应因子代理无写权限而取消门禁写入 → 验收: 无写权限子代理可返回待写入门禁载荷，主代理负责落盘。
- R16. `ae-gate` 禁止工具内部隐式提权；权限受限路径统一采用“子代理回传载荷、主代理显式写入”的委托模型 → 验收: 规划中明确主代理写入、子代理载荷回传、delegatedWrite/source/target/proofWriteStatus 记录和失败兜底机制；该能力不绕过用户授权、系统安全边界或 Git 危险操作授权要求。

## 非功能需求
- NFR1. 迁移必须渐进，避免一次性重写所有核心技能 → 验收: 后续计划按协议、专精 agent、单技能试点、批量迁移分阶段组织。
- NFR2. 面向插件用户的运行时能力不得依赖当前源码仓库布局作为普通项目先决条件 → 验收: 新增 agent/技能文案区分插件源码维护语境和普通用户项目语境。
- NFR3. gate 降级后仍需可读、可追踪，但不承担强制质量保证职责 → 验收: 文案从“硬门禁/阻断”调整为“完成证明/基础记录”。

## 成功标准
- 存在一套可被多个技能复用的 agent 编排协议。
- 现有 agent 划分被重新评估，并形成按能力类型组织的目标边界与迁移映射。
- 新增 agent 的职责边界清晰，能够逐步覆盖核心技能中的功能性步骤。
- 至少一个核心技能可作为试点，以技能编排多个专精 agent 的方式运行。
- `ae-gate` 能在子代理无写权限时正常返回门禁载荷，并由主代理统一写入证明文件。
- `ae-gate` 通过主代理显式写入模型完成门禁写入，不被低权限子代理执行环境阻断，也不依赖隐式提权。
- `ae-gate` 不再把审查证明复验、篡改检测或强证据校验作为阻断条件。
- 技能和规则中对 gate 的描述与降级后的“完成证明”语义一致：常规交付必须生成 proof 文件；仅真实写入失败或主代理写入链路不可用时，可携带结构化失败状态交付。

## 范围边界

### 范围内
- 定义 agent 编排协议和输出契约。
- 评估已有 agent 划分是否合理，并规划按能力类型重新划分。
- 规划新增专精 agent 的能力分层。
- 规划核心技能逐步迁移到 agent 编排模式。
- 降级 `ae-gate` 为基础完成证明。
- 规划相关用户侧文案调整，使 gate 不再被描述为强硬门禁。
- 规划所有依赖 gate 语义的技能、规则、reference 和工具描述调用点迁移。

### 范围外
- 本阶段不直接实现代码变更。
- 不一次性迁移所有技能。
- 不取消 agent-browser 环境证明门禁；浏览器命令前置证明仍属于独立硬约束。
- 不移除真实测试、构建、审查本身；只是降低 `ae-gate` 对这些证据的强制校验职责。

### 约束
- 当前项目 `src/` 是插件可分发能力真源。
- 新增内置 agent 必须通过资产常量、catalog、资产文件和注册链路保持一致。
- `ae-gate` 降级不能让子代理写权限限制导致门禁内容丢失；门禁证明统一由主代理完成写入。

## 关键决策
- D1. 采用“协议优先、专精 agent 扩充、逐步迁移技能”的推进顺序 → 理由: 先统一契约能避免新增 agent 后输出不一致、难以组合。
- D2. 技能保留编排和裁决职责，而不是完全退化为薄转发器 → 理由: 用户交互、安全边界、冲突处理和最终汇总需要稳定入口统一承担。
- D3. `ae-gate` 降级为基础完成证明，不再做额外强校验，但常规交付仍应由主代理统一写入门禁证明 → 理由: 用户希望 gate 只确认是否完成；如果子代理没有文件写入权限，可将门禁内容交给主代理统一写入，避免子代理权限限制阻断交付。
- D4. agent 按能力类型划分，技能按任务目标编排一个或多个能力 agent → 理由: agent 应作为可复用能力单元，避免与单个技能或生命周期阶段过度绑定。

### 假设
- 当前 OpenCode 运行时继续支持内置 agent 注册和技能调度 agent。
- 用户接受 gate 降级后，质量保障更多由技能流程、agent 输出和实际验证命令承担，而不是由 gate 阻断承担。
