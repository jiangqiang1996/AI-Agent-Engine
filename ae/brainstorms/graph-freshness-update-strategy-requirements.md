# 知识图谱新鲜度与更新策略

## AI 解析契约
- canonicalKind: requirements
- humanEquivalent: true
- stableIdsRequired: true
- noImplicitScope: true

## 问题框架
插件中的知识图谱能力需要在“查询可用性”和“图谱及时性”之间取得平衡。当前期望不是把图谱做成实时索引，而是让图谱在更新期间仍可正常查询最后一个完整版本，并在需要做计划、审查、重构或影响分析等决策时明确提示新鲜度风险。更新不应在文件编辑的中间状态反复触发，也不应因为多个技能同时判断图谱过期而重复启动多个更新流程。

## 需求

**查询可用性**
- R1. 图谱更新过程中，查询能力应继续使用最后一个完整 active 图谱版本，而不是读取正在构建中的半成品版本 → 验收: 在构建未完成时执行查询，结果明确来自一个已激活版本，且不会暴露未激活版本的部分数据。
- R2. 图谱查询结果应显式表达图谱新鲜度状态，而不是只返回结构结果 → 验收: 查询结果中可区分 `fresh`、`maybe_stale`、`stale` 或 `updating` 等状态，并包含判定依据和可读的新鲜度说明；无法可靠判定时必须降级为 `maybe_stale`。
- R3. 当图谱可能过期但仍可用于低风险定位时，查询应允许继续返回结果，并标注该结果来自旧快照 → 验收: 存在未构建变更时，非阻断查询仍返回图谱结果，同时包含旧版本提示和后续建议。

**更新触发**
- R4. 图谱更新应优先发生在稳定点，而不是每次文件变化后立即触发 → 验收: 产出稳定点刷新策略表，至少区分用户显式刷新、审查前、重构/影响分析前、一批编辑完成后、阶段结束后和阶段开始；阶段开始默认不自动刷新，除非已有过期诊断且当前任务依赖图谱结论。
- R5. 当旧图谱用于高影响场景且可能过期时，流程应先输出结构化刷新要求 → 验收: 在声明“无影响/无依赖/无需修改”、重构影响分析、删除或跨模块修改决策前，若图谱不是 `fresh`，系统必须要求刷新或说明需要额外真实文件/Git diff 证据。
- R6. 当用户拒绝刷新、无法刷新或构建失败时，流程应输出阻断性诊断并禁止把旧图谱作为结论依据 → 验收: 无法获得 fresh 图谱时，系统仍可把旧图谱作为定位线索，但不得输出“无影响”“无依赖”“已完整覆盖”等结论。
- R7. 图谱构建请求应避免等价请求重复并发调度 → 验收: 当已有构建进行中，只有 worktree、scope、include/exclude、depth、mode 语义、过滤配置和构建输入指纹等价的后续请求才能复用已有构建状态；不等价请求必须排队、拒绝或在当前构建结束后重新判定。

**用户反馈**
- R8. 更新中的图谱状态应对用户可见，但不应阻塞只读理解类查询 → 验收: 查询结果或技能总结能说明“正在更新，当前返回旧 active 版本”，并说明何时需要等待新版本。
- R9. 重复触发更新时，应返回可恢复说明，而不是反复要求用户处理锁或重复确认 → 验收: 后续触发者收到“已有构建进行中”的状态、可继续使用旧图谱的边界和建议等待/稍后重试的提示。
- R10. 构建状态应能从崩溃、中断或遗留锁中恢复 → 验收: 构建状态包含可判定的生命周期信息；僵尸 `updating` 状态不会永久阻止刷新，也不会让旧图谱被误标为 `fresh`。

**决策门控矩阵**
- R11. 需求应定义旧图谱在不同使用意图下的最小门控行为 → 验收: 只用于定位候选文件时允许旧图谱并标注；用于声明无影响、无依赖或无需修改时必须刷新或提供真实文件/Git diff 证据；用于重构、删除、跨模块修改影响范围时必须刷新；图谱过期但已读取真实文件和 Git diff 验证时，图谱只能作为线索引用。

## 非功能需求
- NFR1. 图谱存储一致性必须优先于新鲜度 → 验收: 查询不会读取未激活版本，构建失败不会破坏最后一个可用 active 版本。
- NFR2. 更新策略应减少无意义构建 → 验收: 文件编辑中间态不会因每次变更自动触发图谱重建；多个技能不会对同一 scope 同时执行重复构建。
- NFR3. 新鲜度提示必须可被后续 AI 流程解析 → 验收: 返回结果包含结构化状态字段和中文可读说明。
- NFR4. 新鲜度判定必须保守 → 验收: 未跟踪文件、被图谱纳入但 Git 难以覆盖的文件、过滤配置变化或构建期间再次发生变更时，不得把图谱标记为 `fresh`，除非有等价输入指纹证明。

## 成功标准
- 图谱构建期间，用户仍能查询最后一个完整 active 图谱版本。
- 存在未构建变更时，影响分析查询不得直接输出“无影响”结论，除非图谱已刷新或已有真实文件/Git diff 证据支撑。
- 构建进行中再次请求等价 scope 构建时，只返回已有构建状态或复用结果，不启动第二个并行构建。
- 连续编辑多个文件期间，不因每个文件变化自动调用图谱构建。

## 范围边界

### 范围内
- 定义图谱查询期间的新鲜度状态和用户可见反馈。
- 定义稳定点刷新策略，避免中间态反复更新。
- 定义等价构建请求的重复调度边界。
- 定义何时允许继续使用旧 active 图谱，何时必须刷新后再做结论。
- 定义构建状态异常中断后的恢复边界。

### 范围外
- 不要求把知识图谱改造成实时文件监听索引。
- 不要求查询读取构建中的未激活版本。
- 不要求为所有文件变化立即自动构建图谱。
- 不要求提供符号级、运行时动态依赖或深层 AST 分析。

### 约束
- 图谱结果仍是结构快照，不能替代读取真实文件、Git diff、测试、类型检查或审查。
- 更新期间必须保留最后一个完整 active 版本作为可查询基线。

## 关键决策
- D1. 采用“旧 active 可查询 + 新鲜度标注 + 稳定点刷新”的策略 → 理由: 既保证查询不中断，又避免把中间状态误认为最终结构。
- D2. 对重复构建采用 single-flight 或等价的构建输入指纹复用策略 → 理由: 锁可以防止并发写入，但不能证明两个构建请求的输入等价，也不能提供良好的重复调度体验。
- D3. 不采用每次文件变化后即时更新 → 理由: 多文件编辑和重构期间的中间态通常不稳定，频繁构建会产生噪音和成本。

## 依赖 / 假设

### 依赖
- 现有图谱构建和查询能力需要继续支持 active version 语义。
- 后续规划需要确认当前锁机制和存储版本切换是否足以承载 single-flight 状态表达。

## 待定问题

### 推迟到规划
- [影响 R2][技术] 新鲜度状态字段应放在查询结果顶层，还是放在独立 `freshness` 对象中。
- [影响 R4][技术] 稳定点由技能流程显式调用，还是由工具根据 Git 状态和调用上下文判断。
- [影响 R7][技术] single-flight 状态应复用现有锁文件，还是新增轻量构建状态文件。
- [影响 R10][技术] 构建状态生命周期应采用超时、心跳还是构建完成后的输入指纹复核。
