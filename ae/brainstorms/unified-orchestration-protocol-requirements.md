# 统一编排协议：技能转向编排层，功能下沉到专精代理

## 问题框架

当前 AE 插件的 30 个技能各自包含完整的入口解析、交互确认、调度逻辑和执行实现。这种"技能包办一切"的模式导致：

1. **能力复用差** — 开发能力锁在 `ae:work` 内部，测试能力锁在 `ae:test-browser` 内部，其他技能无法复用
2. **场景覆盖不均** — 审查域已有 21 个专精代理，开发域几乎没有子代理，测试/运维/产品等域缺少专职代理
3. **编排逻辑碎片化** — 不同技能的编排模式（参数解析、交互流程、子代理调度）各自实现，没有统一协议
4. **场景扩展困难** — 新增测试/运维/产品等场景时，缺少明确的代理分组和接入规范

目标：定义统一编排协议，将技能重构为编排层（入口/交互/调度/汇总），具体功能下沉到按场景域划分的专精代理。

## 需求

**编排层协议**

- R1. 编排技能必须实现四阶段协议（入口/交互/调度/汇总），每阶段有标准化输入/输出格式 → 验收: 每个编排技能的四阶段输出可被 `ae:plan` 直接引用，无需推断阶段间数据格式
- R2. 入口阶段输出标准化的任务意图（intent + domain + constraints） → 验收: 入口阶段输出包含 intent 标签、目标域名和约束条件列表
- R3. 交互阶段输出确认后的任务上下文（confirmed_context） → 验收: 交互阶段输出包含用户确认的参数、排除项和边界
- R4. 调度阶段通过域代理分发任务，接收域执行结果 → 验收: 调度阶段只与域代理交互，不直接调用专精代理
- R5. 汇总阶段将域执行结果合成为结构化交付物（deliverable + validation） → 验收: 汇总阶段输出包含交付物描述和验证结果

**场景域与代理体系**

- R6. 专精代理按场景域分组，一级域至少包括：探索、产品、设计、开发、测试、审查、运维、文档、知识 → 验收: 代理目录支持按域组织，已实现的域各有独立的域代理和至少一个专精代理，未实现的域在目录中预留位置
- R7. 审查域细分为：需求审查、设计审查、代码审查、文档审查、用例审查 → 验收: 审查域代理能根据任务意图路由到对应审查子类
- R8. 开发域细分为：前端开发、后端开发、调试修复、重构改造 → 验收: 开发域代理能根据任务意图路由到对应开发子类；首批至少实现前端开发、后端开发、调试修复三个专精代理
- R9. 支持任意新场景域的接入，新增域不需要修改编排层协议 → 验收: 新增一个场景域只需定义域代理和专精代理，编排层代码零修改

**域代理契约**

- R10. 域代理接收标准化的域调用请求（task + intent + constraints + domainContext） → 验收: 所有域代理的输入格式一致，domainContext 为域特有扩展点
- R11. 域代理返回标准化的域执行结果（status + summary + evidence + artifacts + findings） → 验收: 所有域代理的输出格式一致，findings 为可选字段
- R12. 域代理负责注入域专业上下文（domainContext），编排层不需要理解域内专业知识 → 验收: 编排层调用域代理时只需提供任务意图和约束，不传递域特有参数

**域内调度**

- R13. 域内调度策略由域代理自行决定，编排协议不规定 → 验收: 不同域代理可使用不同调度模式（并行/流水线/条件选择），编排层无需感知
- R14. 域代理可调度专精代理执行子任务，专精代理的输入/输出遵循统一契约 → 验收: 专精代理接收（task + domainContext + constraints），返回（status + output + evidence）

**基础设施**

- R15. 代理目录（Agent Catalog）按域组织，包含域代理和专精代理的能力描述、选择条件和输入/输出契约 → 验收: 每个域的代理清单可通过域名称查询，选择条件供 LLM 理解
- R16. 选择规则引擎支持能力匹配、范围匹配和上下文匹配三种模式 → 验收: 域代理可根据任务特征自动选择专精代理
- R17. 协调策略模板支持 parallel、pipeline、parallel-then-sequential 和 conditional 四种模式 → 验收: 域代理可声明使用的协调策略，复用共享的调度框架
- R18. 结果聚合器支持 union、merge、best-of 和 reduce 四种聚合模式 → 验收: 域代理可根据场景选择聚合模式，将多个专精结果合并为域执行结果

**已有能力迁移**

- R19. 审查域（ae:review + 21 个审查代理）重构为审查域代理 + 专精代理体系 → 验收: 审查域代理可调度现有审查专精代理完成审查任务
- R20. ae:work 的编排逻辑提取为开发域代理，执行逻辑下沉到开发专精代理 → 验收: ae:work 重构为编排层后，开发能力可通过开发域代理被其他技能复用

## 非功能需求

- NFR1. 新增场景域的接入成本不超过：1 个域代理定义 + N 个专精代理定义 + 域目录注册 → 验收: 新增域不涉及编排层代码修改
- NFR2. 域代理调用的延迟开销不超过直接调用专精代理的 20% → 验收: 简单场景（单专精调度）的域代理开销可忽略
- NFR3. 编排协议与 OpenCode 原生子代理机制对齐，不引入新的运行时依赖 → 验收: 域代理和专精代理通过 Task 工具调用，无需额外运行时

## 成功标准

- 审查域和开发域完成迁移后，`ae:lfg` 可同时调度开发域代理和审查域代理，无需理解域内逻辑
- 新增一个场景域（如运维域）只需定义域代理和专精代理，编排层零修改
- 开发域能力可被 `ae:work`、`ae:lfg`、`ae:task-loop` 等多个编排技能复用

## 范围边界

### 范围内

- 统一编排协议的定义和实现
- 域代理和专精代理的契约定义
- 四大基础设施（代理目录、选择规则、协调策略、结果聚合器）
- 审查域和开发域的迁移
- 场景域分类体系

### 范围外

- 具体域的专精代理实现细节（如前端开发代理的内部提示词设计）
- 测试、运维、产品、文档、知识等域的具体代理实现
- UI/UX 变更
- OpenCode 平台本身的子代理机制变更

### 约束

- 必须与 OpenCode 原生子代理机制对齐，不引入新运行时
- 代理目录和选择规则需基于当前 `AgentDefinitionSchema` 扩展

## 关键决策

- D1. 采用三层调度架构（编排技能 → 域代理 → 专精代理） → 理由: 域代理是复用的关键单元，封装域内调度逻辑，使编排层无需理解域内专业知识
- D2. 编排技能采用四阶段统一契约（入口/交互/调度/汇总） → 理由: 标准化所有编排技能的行为模式，使技能可组合、数据流可预测
- D3. 域内调度策略由域代理自行决定 → 理由: 不同域的调度模式本质不同（审查=并行，开发=流水线+并行），强行统一会过度抽象
- D4. `domainContext` 作为域特有扩展点 → 理由: 保持上行契约统一的同时，允许域代理接收和注入专业参数
- D5. 审查域和开发域作为首批迁移域 → 理由: 审查域已有成熟的代理体系（验证模式可行性），开发域是当前复用痛点最大的域

## 依赖 / 假设

### 依赖

- OpenCode 子代理（Task 工具）支持嵌套调用（编排技能调用域代理，域代理调用专精代理）
- 当前 `AgentDefinitionSchema` 可扩展为域分组结构

### 假设

- OpenCode 的 Task 工具在嵌套调用时不会产生显著的上下文丢失或延迟问题
- LLM 能理解并正确选择域代理（基于代理目录的能力描述）
