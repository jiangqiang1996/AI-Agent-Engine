# 核心技能生命周期通用化

## AI 解析契约
- canonicalKind: requirements
- humanEquivalent: true
- stableIdsRequired: true
- noImplicitScope: true

## 问题框架
AE 核心技能当前容易被理解为只服务软件开发全流程，但用户希望它们抽象为通用任务生命周期阶段。核心目标是保留少量主技能，并让这些技能既能串联完成完整流程，也能独立完成任意阶段或任意类型任务。

## 需求

**核心阶段抽象**
- R1. 核心技能必须按任务生命周期职责定义，而不是按具体产物类型或软件开发固定步骤定义 → 验收: `ae:ideate`、`ae:brainstorm`、`ae:plan`、`ae:refactor`、`ae:work`、`ae:review` 的说明均能对应通用阶段职责。
- R2. 核心流程必须支持完整串联，也必须支持用户从任意阶段直接进入 → 验收: 用户可以直接调用 `ae:work` 执行一句话任务，也可以按 `ideate → brainstorm → plan/refactor → work → review` 串联执行。
- R3. 核心技能必须支持软件开发之外的任务 → 验收: 技能说明不得把软件仓库、代码实现、测试或构建作为所有任务的必需前提；非软件任务可自然降级到通用任务处理。

**阶段职责**
- R4. `ae:ideate` 必须定位为通用构思阶段，用于生成多个候选方向并比较价值、成本和风险 → 验收: 当用户尚未确定做什么时，`ae:ideate` 能输出可选方向，而不是直接进入计划或实施。
- R5. `ae:brainstorm` 必须定位为通用探索阶段，用于明确目标、边界、约束、成功标准和待定问题 → 验收: 对软件功能、测试用例、需求文档、设计文档或非软件任务，都能产出后续计划所需的目标语义。
- R6. `ae:plan` 必须定位为通用计划阶段，用于把目标拆成路径、步骤、依赖、验证方式和产物结构 → 验收: 它可以计划软件开发，也可以计划编写需求文档、测试用例、设计文档或非软件任务。
- R7. `ae:refactor` 必须定位为彻底重构计划阶段，用于对已有方案、结构、流程或产物做一次性替换和清债计划 → 验收: 它不仅能处理代码重构，也能处理文档结构、流程设计或已有方案的彻底重组。
- R8. `ae:work` 必须定位为通用实施阶段，用于实际完成任务或产出目标资产 → 验收: 它可以实施代码，也可以生成需求文档、详细设计、测试用例、计划、报告或其他非软件产物。
- R9. `ae:review` 必须定位为通用审查阶段，用于检查任意产物的质量、一致性、风险、遗漏和可验证性 → 验收: 它可以审查代码、需求、计划、测试用例、设计文档和非软件产物。

**测试用例作为示例任务**
- R10. 编写测试用例必须能复用同一套核心技能流程，而不是必须新增核心主技能 → 验收: 可以通过 `brainstorm → plan → work → review` 分别完成测试目标探索、测试用例设计、测试用例生成和测试用例审查。

## 成功标准
- 核心技能数量保持精简，用户无需学习大量产物专用主入口。
- 每个核心技能都能独立使用，也能消费上游阶段产物继续执行。
- 软件开发仍是重点应用场景，但不再是核心技能语义的唯一边界。
- 编写测试用例、编写需求文档、编写详细设计、实施软件开发和非软件任务都能使用同一套阶段模型表达。

## 范围边界

### 范围内
- 重新定义核心技能的通用阶段职责。
- 明确核心流程支持完整串联与任意阶段直达。
- 明确测试用例编写不作为新增核心主技能，而作为同一生命周期流程的任务类型。
- 明确软件开发之外的任务也应被支持。

### 范围外
- 不在需求阶段决定具体文件结构、Schema、工具参数或代码实现方案。
- 不要求取消现有高级直达技能；是否保留或降级为专家入口留待规划阶段决定。
- 不在本需求中实现技能文案或代码修改。

## 关键决策
- D1. 核心技能按认知阶段定义，而不是按软件工程产物定义 → 理由: 同一套阶段可覆盖软件开发、测试用例、文档编写和非软件任务，减少核心入口数量。
- D2. `ae:work` 作为最小执行入口继续支持一句话直接实施 → 理由: 前置探索和计划阶段应是可选增强，不应阻断明确的小任务。
- D3. 测试用例编写作为任务类型复用核心流程，而不是新增核心主流程技能 → 理由: 可以避免核心入口膨胀，同时保持测试用例从探索到审查的完整生命周期。
