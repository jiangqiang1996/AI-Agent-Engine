# 核心技能生命周期通用化

## AI 解析契约
- canonicalKind: requirements
- humanEquivalent: true
- stableIdsRequired: true
- noImplicitScope: true

## 问题框架
AE 核心技能当前容易被理解为只服务软件开发全流程，但用户希望它们抽象为通用任务生命周期阶段。核心目标是保留少量主技能，并让这些技能既能串联完成完整流程，也能独立完成任意阶段或任意类型任务。

## 需求

**核心阶段抽象**
- R1. 核心技能必须按任务生命周期职责定义，而不是按具体产物类型或软件开发固定步骤定义 → 验收: `ae:ideate`、`ae:brainstorm`、`ae:plan`、`ae:refactor`、`ae:work`、`ae:review` 的说明均能对应通用阶段职责。
- R2. 核心流程必须支持完整串联，也必须支持用户从任意阶段直接进入 → 验收: 用户可以直接调用 `ae:work` 执行一句话任务，也可以按 `ideate → brainstorm → plan/refactor → work → review` 串联执行。
- R3. 核心技能必须支持软件开发之外的任务 → 验收: 技能说明不得把软件仓库、代码实现、测试或构建作为所有任务的必需前提；非软件任务可自然降级到通用任务处理。
- R4. 所有任务类型都必须支持同一套完整生命周期流程: 探索创意方向 → 生成需求 → 审查需求 → 生成计划 → 审查计划 → 执行计划 → 审查执行结果 → 验收: 软件开发、测试用例、需求文档、设计文档和非软件任务都能按该流程完整串联；任一步骤也都可以被用户独立调用。
- R5. 每个阶段完成后必须提供程序固化的下一步流程指引提示词，用户确认后即可进入下一个技能 → 验收: 阶段交接提示不依赖 LLM 临场自由发挥；系统能基于当前阶段、产物路径和可选后续步骤生成稳定提示，用户只需确认即可继续执行下一阶段。

**阶段职责**
- R6. `ae:ideate` 必须定位为通用构思阶段，用于生成多个候选方向并比较价值、成本和风险 → 验收: 当用户尚未确定做什么时，`ae:ideate` 能输出可选方向，而不是直接进入计划或实施。
- R7. `ae:brainstorm` 必须定位为通用探索阶段，用于明确目标、边界、约束、成功标准和待定问题 → 验收: 对软件功能、测试用例、需求文档、设计文档或非软件任务，都能产出后续计划所需的目标语义。
- R8. `ae:plan` 必须定位为通用计划阶段，用于把目标拆成路径、步骤、依赖、验证方式和产物结构 → 验收: 它可以计划软件开发，也可以计划编写需求文档、测试用例、设计文档或非软件任务。
- R9. `ae:refactor` 必须定位为彻底重构计划阶段，用于对已有方案、结构、流程或产物做一次性替换和清债计划 → 验收: 它不仅能处理代码重构，也能处理文档结构、流程设计或已有方案的彻底重组。
- R10. `ae:work` 必须定位为通用实施阶段，用于实际完成任务或产出目标资产 → 验收: 它可以实施代码，也可以生成需求文档、详细设计、测试用例、计划、报告或其他非软件产物。
- R11. `ae:review` 必须定位为通用审查阶段，用于检查任意产物或变更的质量、一致性、风险、遗漏和可验证性 → 验收: 它可以审查需求文件、计划文件、最终产物、代码变更、文档变更、测试用例、设计文档和非软件产物。
- R12. `ae:plan` 和 `ae:refactor` 都必须作为计划生成入口保留，但语义边界不同 → 验收: `ae:plan` 生成尽可能不影响已有功能的渐进式计划；`ae:refactor` 生成倾向于彻底重构、替换旧结构并消除技术债务的计划。
- R13. 本需求后续实现应尽可能采用彻底重构方式消除技术债务，而不是在旧结构上做兼容性补丁 → 验收: 规划阶段必须优先识别应替换的旧语义、旧提示、旧路由和旧交接机制，并给出一次性清理方案；仅在存在明确外部兼容约束时保留旧行为。
- R14. 必须彻底重构现有子代理分类，使其服务通用生命周期阶段和产物审查目标，而不是沿用不合适的旧分类 → 验收: 规划阶段必须盘点现有子代理职责，允许新增缺失的子代理、合并重叠子代理、移除不必要子代理，并给出新的分类依据和启用规则。
- R15. 必须彻底移除当前项目中与本需求相关的不合理或用处不大的技术债务 → 验收: 规划阶段必须列出应删除、替换或合并的旧提示词、旧流程、旧分类、旧路由、冗余代理和无效兼容逻辑；实施阶段不得保留“暂时不用但继续存在”的旧机制，除非有明确外部兼容证据。
- R16. 其他与核心生命周期流程相关的技能、命令、帮助文档、引用文档、审查规则和内部提示都必须做对应调整 → 验收: 规划阶段必须列出受影响资产清单；实施阶段必须同步更新相关技能说明、命令说明、帮助输出、引用文档、审查/门禁提示和测试，避免新旧语义并存或互相矛盾。

**测试用例作为示例任务**
- R17. 编写测试用例必须能复用同一套核心技能流程，而不是必须新增核心主技能 → 验收: 可以通过 `brainstorm → plan → work → review` 分别完成测试目标探索、测试用例设计、测试用例生成和测试用例审查。

## 成功标准
- 核心技能数量保持精简，用户无需学习大量产物专用主入口。
- 每个核心技能都能独立使用，也能消费上游阶段产物继续执行。
- 软件开发仍是重点应用场景，但不再是核心技能语义的唯一边界。
- 编写测试用例、编写需求文档、编写详细设计、实施软件开发和非软件任务都能使用同一套阶段模型表达。
- 所有任务都能表达为“探索创意方向 → 生成需求 → 审查需求 → 生成计划 → 审查计划 → 执行计划 → 审查执行结果”的完整流程，且每个步骤都能独立触发。
- 阶段完成后的下一步指引由程序稳定生成，用户确认后即可按流程进入下一个技能。
- `ae:plan` 与 `ae:refactor` 作为两个计划入口同时保留，用户能根据“渐进规划”或“彻底重构清债”选择合适路径。
- 本需求进入规划和实施时优先采用彻底重构路径，目标是清理旧的软件开发专用语义和流程债务。
- 子代理分类完成彻底重构，新增、合并或移除子代理都以通用生命周期职责和实际审查价值为依据。
- 与本需求相关的不合理、低价值或冗余技术债务被明确识别并移除，不以兼容补丁形式继续累积。
- 所有相关技能、命令、帮助输出、引用文档、审查规则和内部提示完成一致性更新，不残留旧的软件开发专用流程表述。

## 范围边界

### 范围内
- 重新定义核心技能的通用阶段职责。
- 明确核心流程支持完整串联与任意阶段直达。
- 明确所有任务类型都支持完整生命周期流程，且每一步都能独立使用。
- 明确阶段完成后的下一步流程指引需要程序固化，避免依赖临场生成。
- 明确 `ae:plan` 和 `ae:refactor` 都保留为计划生成入口，并区分渐进计划与彻底重构计划。
- 明确本需求后续实现倾向彻底重构和清债，而不是兼容性补丁。
- 彻底重构现有子代理分类，允许按需要新增、合并或移除子代理。
- 彻底移除当前项目中与本需求相关的不合理或用处不大的技术债务。
- 同步调整其他相关技能、命令、帮助文档、引用文档、审查规则和内部提示。
- 明确测试用例编写不作为新增核心主技能，而作为同一生命周期流程的任务类型。
- 明确软件开发之外的任务也应被支持。

### 范围外
- 不在需求阶段决定具体文件结构、Schema、工具参数或代码实现方案。
- 不要求取消现有高级直达技能；是否保留或降级为专家入口留待规划阶段决定。
- 不在本需求中实现技能文案或代码修改。

## 关键决策
- D1. 核心技能按认知阶段定义，而不是按软件工程产物定义 → 理由: 同一套阶段可覆盖软件开发、测试用例、文档编写和非软件任务，减少核心入口数量。
- D2. `ae:work` 作为最小执行入口继续支持一句话直接实施 → 理由: 前置探索和计划阶段应是可选增强，不应阻断明确的小任务。
- D3. 测试用例编写作为任务类型复用核心流程，而不是新增核心主流程技能 → 理由: 可以避免核心入口膨胀，同时保持测试用例从探索到审查的完整生命周期。
- D4. 阶段交接提示词应由程序固化生成，用户只需确认即可进入下一个技能 → 理由: 固定交接能降低学习成本、减少遗漏，并保证完整流程在不同任务类型中保持一致。
- D5. 同时保留 `ae:plan` 和 `ae:refactor` 两个计划生成入口 → 理由: 两者产物同为计划文件，但 `ae:plan` 适合尽量不影响已有功能的渐进计划，`ae:refactor` 适合彻底重构和技术债务清理。
- D6. 本需求后续规划和实施默认走彻底重构清债方向 → 理由: 当前目标是泛化核心技能生命周期语义，若只叠加补丁会继续保留软件开发专用假设和交接流程债务。
- D7. 子代理分类必须重新设计，不能默认保留现有分类 → 理由: 核心技能生命周期泛化后，旧子代理分类可能继续携带软件开发专用偏见或职责重叠，必须允许新增、合并和移除以匹配新的阶段模型。
- D8. 与本需求相关的低价值旧机制应删除或替换，而不是保留为隐性兼容层 → 理由: 用户目标是彻底重构并消除技术债务，保留无用旧机制会增加路由、审查和维护复杂度。
- D9. 核心生命周期泛化必须作为跨资产一致性改造处理 → 理由: 只修改核心技能说明会导致命令、帮助、引用文档、审查规则和内部提示继续暴露旧语义，削弱流程稳定性。

## 待定问题

### 推迟到规划
- [影响 R1-R12][结构] 是否需要在技能 frontmatter、帮助输出和内部提示词中统一引入阶段标签？
  - 推荐方向: 优先把阶段语义统一到技能说明、帮助输出和核心提示词中；是否新增机器可读字段留给规划阶段结合现有资产注册结构判断。
  - 规划判据: 若阶段标签只影响用户理解和路由文案，应避免新增 Schema；若路由、帮助筛选或模型场景选择需要稳定字段，才考虑引入机器可读标签。
  - 风险: 只改文案可能导致内部路由仍按旧语义执行；过早新增字段可能扩大注册、测试和兼容成本。
- [影响 R3][路由] 非软件任务应复用现有文档模板，还是需要通用任务模板？
  - 推荐方向: 优先复用现有需求和计划文档的 AI 解析契约、稳定 ID、范围、成功标准和验证章节；仅为非软件任务补充轻量通用引导，不新增平行主模板。
  - 规划判据: 若现有模板字段能自然表达目标、步骤、依赖、产物和验收，则复用；只有当现有模板强制出现代码、文件、测试或构建语义时，才抽取通用模板或改造模板措辞。
  - 风险: 完全复用可能保留软件偏见；新增模板可能造成核心流程分叉，削弱“同一生命周期模型”的目标。
- [影响 R10-R11][产物] `ae:work` 和 `ae:review` 如何表达非代码产物、最终产物和变更审查的验证与门禁证据？
  - 推荐方向: 非代码产物的验证应以产物路径、需求/计划追溯、审查结论、人工可检查标准和必要的外部证据为主；代码测试、构建和 Git diff 只在任务实际涉及软件时作为证据。
  - 规划判据: 若任务产生可文件化产物，门禁应要求产物路径和审查/一致性证据；若任务不产生文件，应要求可引用的交付摘要、用户确认或明确的无法持久化说明；不得把缺少测试命令等同于失败。
  - 风险: 证据过宽会降低门禁强度；证据过窄会把非软件任务错误判定为未验证或不可交付。
- [影响 R8-R9, R12-R13][结构] `ae:refactor` 是否继续像现在一样包装或复用 `ae:plan`？
  - 推荐方向: 在规划阶段显式比较“继续包装 `ae:plan`”与“抽出共享计划生成内核、让 `ae:plan` 和 `ae:refactor` 作为不同策略入口”两种方案；优先选择能消除职责混淆和重复提示债务的结构。
  - 规划判据: 如果两者只差提示词策略且产物结构完全一致，可以共享底层计划生成能力；如果 `ae:refactor` 需要独立的债务识别、替换策略和破除兼容流程，则不应只是薄包装 `ae:plan`。
  - 风险: 继续包装可能保留语义耦合和技术债务；完全拆开可能造成计划生成逻辑重复、审查和门禁规则分叉。
- [影响 R11, R14][子代理] 新的子代理分类应按阶段、产物类型、风险领域还是审查维度组织？
  - 推荐方向: 规划阶段先盘点现有子代理的真实职责和触发条件，再以通用生命周期阶段为主轴、以风险领域和产物类型为辅助维度重组；不为保留旧分类而保留旧子代理。
  - 规划判据: 若子代理职责能跨任务类型复用且有清晰审查价值，应保留或强化；若只服务旧软件开发路径、职责重叠或触发条件含混，应合并、改名或移除；若新流程缺少关键审查能力，可以新增子代理。
  - 风险: 过度保留会延续技术债务；过度新增会造成代理数量膨胀和路由复杂度上升；过度移除会削弱安全、正确性或产物质量审查覆盖。
- [影响 R13-R15][清债] 当前项目中哪些旧机制属于必须移除的低价值技术债务？
  - 推荐方向: 规划阶段建立清债清单，覆盖旧的软件开发专用语义、重复提示词、职责重叠子代理、无效兼容逻辑、过时路由和低价值流程分支；每项都标注删除、替换、合并或保留理由。
  - 规划判据: 若机制不能服务通用生命周期、缺少明确用户价值、与新阶段模型冲突或仅为历史兼容存在，应删除或替换；若机制有外部兼容约束或明确高价值场景，才允许保留并说明边界。
  - 风险: 清债范围过小会继续累积维护成本；清债范围过大会增加一次性迁移风险，需要用审查和验证覆盖关键入口。
- [影响 R16][资产覆盖] 哪些相关技能、命令、文档、规则和测试必须同步更新？
  - 推荐方向: 规划阶段按资产类型建立影响清单，至少覆盖核心技能、命令别名、帮助输出、引用文档、审查/门禁提示、子代理说明、模型路由和相关测试；逐项标注是否更新、删除、合并或无需改动。
  - 规划判据: 任何面向用户或影响路由/审查/交接的资产，只要提到核心技能职责、流程顺序、产物类型、软件开发前提或下一步指引，都应纳入检查；仅内部维护文档可在明确不影响插件用户语义时豁免。
  - 风险: 漏改资产会造成用户看到互相矛盾的流程说明；过度扩大范围会引入无关改动，需要以“是否影响核心生命周期语义”为边界。
