# 技能编写规范

> **规范以 [AGENTS.md](../AGENTS.md) §3 为准**（仓库内的唯一真源，由 `npm run validate` 强制执行）。
> 本文是它的展开说明：补充可复制的模板、示例与自检清单。

本文描述**如何写一个技能**，不随技能分发给使用者。

---

## 1. 目录与命名

```
skills/<ae-name>/
  SKILL.md          # 必需，目录名必须 == frontmatter 的 name
  references/       # 可选，渐进披露的细则
  scripts/          # 可选，可执行脚本
  tests/            # 可选，脚本单元测试
```

- `name` 只允许小写字母、数字、连字符，不含首尾/连续连字符，≤64 字符。
- 必须以 `ae-` 前缀开头。

---

## 2. Frontmatter

只允许 Agent Skills 规范的 6 个字段，多一个就报错。

```yaml
---
name: ae-example
description: 一句话说清"这个技能做什么 + 什么时候用"，≤1024 字符。
license: GPL-3.0-or-later
compatibility: 运行前置条件（Node 版本、外部 CLI 等）
metadata:
  author: ae-skills
  version: 1.0.0
  ae-group: 需求与设计
---
```

| 字段 | 必填 | 约束 |
|---|---|---|
| `name` | 是 | == 目录名 |
| `description` | 是 | ≤1024 字符；含中英文触发词最佳 |
| `license` | 否 | 字符串 |
| `compatibility` | 否 | 字符串，≤500 字符；**必须与实际依赖一致** |
| `metadata` | 否 | 对象，值全部为字符串 |
| `allowed-tools` | 否 | 空格分隔的字符串 |

> `compatibility` 不要写"需要 Node.js 18+ 以运行本技能附带脚本"这种模板话，
> 除非技能真的带脚本。没有脚本就写实际前置条件。

---

## 3. 多模式技能（`mode=`）

一个技能覆盖两类差异明显的工作时，用**模式**分流，而不是拆成两个技能。

| 模式 | 入口 | 改动量 | 典型例子 |
|---|---|---|---|
| `dev` | 从零/按需求实现 | 按需求自由设计 | 新建页面、新增接口 |
| `fix` | 先诊断再改 | **最小改动** | 修 bug、修样式 |

写法要点：

1. **模式判定表**放在 SKILL.md 靠前位置，说明触发条件与判定细则。
2. **护栏必须按模式分段**——「不改测试代码、最小改动、不引入新功能」这类约束
   只在 `fix` 模式生效，混在一起会污染 `dev` 模式。
3. 共享部分（上下文检测、实现规范、验证闭环）**只写一份**，不要复制。
4. 每个模式一张角色卡，放在 `references/roles/`。
5. 用户显式给 `mode=xxx` 时严格照办；未给时按判定表推断，拿不准先问一句。

现有多模式技能：`ae-frontend`（dev/fix）、`ae-backend`（dev/fix）、`ae-e2e-test`（test-only/script）。

---

## 4. 正文结构

正文 ≤500 行（超了会有 WARN）。超长内容拆到 `references/`，SKILL.md 只留主干。

推荐骨架（**章节名可按技能调整**，只要语义清楚；本合集实际使用的是「何时使用 / 何时不使用」）：

```markdown
# 技能名

## 角色          # 这个技能扮演什么角色
## 何时使用      # 什么时候用
## 何时不使用    # 什么时候不用（只描述职责边界，不点名其它技能）
## 执行流程      # 分步骤，可操作
## 实现要求      # 硬约束：改什么、不改什么
## 产物与日志    # ae/<slug>/ 与 ae/logs/<slug>/
## 安全边界      # 禁止动作
## 完成标准      # 可勾选的验收项
```

### 引用规范

- 相对引用必须真实存在：`references/xxx.md`、`scripts/xxx.mjs`、`assets/xxx`。
- 链接写法 `[标题](references/xxx.md)` 或反引号包裹 `` `references/xxx.md` ``。
- 文件引用统一相对**技能根目录**；`references/` 内部的相互引用相对其所在目录。
- 保持引用只有一层深（`references/xxx.md`），避免 `references/a/b/c.md` 式的嵌套链。

---

## 5. 零交叉引用（硬性）

技能**不得**提到其它技能的名称。

- ❌ `浏览器端到端测试 → 使用 ae-e2e-test`
- ✅ `浏览器端到端测试与取证 → 属于端到端测试范畴`

需要"往哪转"时，只写**职责类别**（前端 / 后端 / 端到端测试 / 单元测试 …），
让调用方自己决定交给谁。

校验：`npm run validate` 的跨技能引用检查。

---

## 6. 宿主无关（硬性）

正文与脚本都不得出现宿主专属名与语法（完整清单见 `docs/development.md` §2，
其中也列出了 `tools/validate.mjs` 仍在拦截的已移除插件工具名）。

需要交互提问时写「使用宿主的交互式提问能力」，不要写具体工具名。
需要子代理时写「若宿主支持子代理派发能力…否则顺序执行」，不要写具体参数。

---

## 7. 脚本

- 纯 Node.js 标准库优先，不引第三方依赖（除非技能自带 `package.json`）。
- 放 `scripts/`，扩展名 `.mjs`（`.js` / `.cjs` 也接受，但 `.cjs` 同样要过 `node --check`）。
- 必须通过 `node --check`。
- **模板字面量里不要写单反斜杠 + 非转义字符**（`\.` 会被 JS 吞掉）。用 `RegExp` 构造或写 `\\.`。
- 写操作前先确认目标路径与权限。
- 密码、令牌一律走环境变量，不落配置文件、不进日志。
- **不得写死技能名**。需要感知归属（如决定 `ae/<slug>/` 产物目录）时，从脚本自身路径推导
  （见 `tools/shared/ae-paths.mjs` 的 `resolveOwningSkillName()`）。
- **入口判定不要把 `process.argv[1]` 与 `import.meta.url` 直接比较**。Node 会把 `import.meta.url`
  解析成 realpath，而 `argv[1]` 保留符号链接 / 联接（junction）路径，两者不等时判定恒假，
  脚本会**静默不执行**（退出码 0、无输出）。两侧都取 realpath 后再比较，或按脚本文件名后缀判定。

多技能共用同一份脚本时，把真源放 `tools/shared/` 并在 `tools/shared-map.json` 登记。

---

## 8. 角色卡

复杂技能可把子职责拆成角色卡，放在 `references/roles/<role>.md`：

```markdown
# 角色：<名称>

## 职责          # 这个角色负责什么
## 触发条件      # 什么时候用这张卡
## 输入契约      # 需要什么输入
## 输出契约      # 产出什么
## 工作流        # 步骤
## 边界          # 不做什么
```

角色卡是**技能内部实现细节**，不是技能之间的接口。技能可以引用自己的角色卡，
但角色卡不得引用其它技能。

---

## 9. 自检清单

提交前逐条确认：

- [ ] `name` == 目录名，且带 `ae-` 前缀
- [ ] frontmatter 只有 6 个允许字段
- [ ] `description` 说清了"做什么 + 何时用"，且不含反向触发词（"本技能过重"这类应放正文）
- [ ] `compatibility` 与实际依赖一致
- [ ] 正文 ≤500 行，引用的 `references/` / `scripts/` / `assets/` 文件都存在
- [ ] `references/` 内部的相互链接都有效
- [ ] `ae/<slug>/` 产物路径与 `ae/logs/<slug>/` 日志路径都属于本技能
- [ ] 没有任何其它技能的名称（`npm run validate` 会验）
- [ ] 没有宿主专属名 / 工具名 / 占位符
- [ ] 没有硬编码密钥；破坏性操作有授权门槛
- [ ] 脚本通过 `node --check`（`.mjs` / `.js` / `.cjs` 都要），必要时补 `tests/*.test.mjs`
- [ ] 脚本没有写死技能名；入口判定没有直接比较 `argv[1]` 与 `import.meta.url`
- [ ] `npm run check` 全绿
