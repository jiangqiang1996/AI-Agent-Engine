# ae:merge-branch 合并后需求完整性验证计划

## 来源与目标

来源需求文档：`docs/ae/brainstorms/2026-05-03-merge-branch-post-merge-validation-requirements.md`

本计划只改造 `ae:merge-branch` 的技能流程文档，让无冲突合并也必须验证来源分支需求在接收分支中是否仍然满足，同时保持低风险合并的效率。该工作不把技能改成自动化脚本，不新增远程写操作，不默认创建合并提交。

## 影响范围

- 主要文件：`src/assets/skills/ae-merge-branch/SKILL.md`
- 参考文件：`docs/ae/reviews/2026-05-03-merge-branch-skill-review.md`
- 上游需求：`docs/ae/brainstorms/2026-05-03-merge-branch-post-merge-validation-requirements.md`

## 技术设计

沿用现有阶段化技能文档结构，在现有安全检查、来源上下文读取、降级理解、执行合并、冲突修复之后新增合并后需求完整性验证阶段。合并前阶段负责形成来源需求基线，合并后阶段负责复用该基线逐项核对状态，最终输出阶段负责呈现可追溯证据。

状态模型保持轻量：每项来源需求只需要记录需求摘要、来源、可信度、关联证据、合并后状态、处理结果。状态只使用 `已满足`、`需修复`、`无法判断`。低可信 diff 推断不能单独支撑 `已满足`。

## 实现单元

### 1. 统一来源分支与接收分支术语

- [ ] 在 `src/assets/skills/ae-merge-branch/SKILL.md` 开头补充术语约定：来源分支是被合入的 ref 或 worktree 绑定分支；接收分支是当前分支。
- [ ] 将容易误解的“目标分支需求”语义改为“来源分支需求”，保留 `target ref` 作为 Git 参数名称。

需求覆盖：R1

测试场景：
- 读者能区分来源分支和接收分支，不会把接收分支需求作为核对基线。

验证：
- 阅读 `src/assets/skills/ae-merge-branch/SKILL.md` 确认术语一致，无残留含混的“目标需求”表述。

### 2. 建立合并前来源需求基线

- [ ] 扩展阶段 2 和阶段 3：要求合并前形成来源需求清单，并标注证据来源和可信度。
- [ ] 明确高可信来源为交接、需求、计划；低可信来源为提交摘要和 diff 归纳。
- [ ] 明确低可信 diff 归纳只提取用户可见行为、公共契约和风险项；大型 diff 只输出低可信摘要和剩余风险，不把实现细节逐项升级为验收清单。

需求覆盖：R1、R8

测试场景：
- 有 AE 交接、需求、计划时，流程要求形成高可信来源需求清单。
- 无 AE 产物时，流程允许 diff 归纳，但必须标为低可信。
- 低可信条目不会被描述成完整验收依据。
- 大型或实现细节密集的 diff 不会被要求逐项完整验收。

验证：
- 阅读阶段 2 和阶段 3，确认来源需求清单、可信度和低可信粒度限制均有明确文字。

### 3. 新增合并后需求完整性验证阶段

- [ ] 在合并应用成功和冲突修复完成之后、最终输出之前新增必经阶段。
- [ ] 明确无冲突合并也必须进入该阶段，不能仅运行 Git merge 和验证命令后结束。
- [ ] 要求基于合并前来源需求清单逐项判断合并后状态：`已满足`、`需修复`、`无法判断`。
- [ ] 明确 `无法判断` 是合法输出状态，不能静默转为 `已满足`。

需求覆盖：R2、R3

测试场景：
- 无冲突合并成功后，流程仍要求逐项核对来源需求。
- 合并后证据不足时，流程要求标为 `无法判断`。
- 来源需求被接收分支现有代码覆盖时，流程要求标为 `需修复` 或询问用户。

验证：
- 阅读阶段顺序，确认所有合并路径都会经过合并后完整性验证。

### 4. 明确验证状态判定规则

- [ ] 扩展验证规则：优先使用来源分支计划、需求文档或降级归纳中的验证命令，再按影响范围补充最小必要验证。
- [ ] 明确来源分支提供的验证命令只作为候选证据；执行前必须展示命令、来源和风险，并取得用户授权。
- [ ] 明确不得执行来源文档中的远程写、破坏性 Git、凭据/环境读取或授权绕过命令，除非用户对具体命令另行明确授权且命令符合全局安全边界。
- [ ] 明确没有可运行验证命令时，必须说明原因；只有代码或测试证据足够时才能标为 `已满足`，否则标为 `无法判断`。

需求覆盖：R5

测试场景：
- 没有验证命令且代码证据不足时，流程要求输出 `无法判断`。
- 来源分支计划给出验证命令时，流程要求先展示并取得授权，而不是直接执行。
- 来源文档包含远程写或破坏性命令时，流程不会把它当作普通验证命令执行。

验证：
- 检查技能文档中验证命令候选、执行授权和危险命令边界均有明确文字。

### 5. 明确合并后修复授权边界

- [ ] 增加合并后新增修复授权边界：合并授权、冲突修复授权、合并后新增代码修复授权、提交授权彼此独立。

需求覆盖：R4

测试场景：
- 发现需新增修复时，流程要求先说明缺口并取得单独授权。
- 用户只授权合并时，流程不会继续做合并后新增代码修复。

验证：
- 检查技能文档中合并、冲突修复、合并后新增修复、提交的授权边界彼此独立。

### 6. 定义快速路径、升级路径和停止条件

- [ ] 增加风险触发审查条件：需求无法映射、当前分支覆盖关键行为、验证失败后修复、涉及安全/数据/API/迁移/外部契约、低可信需求影响核心行为。
- [ ] 明确快速路径：高可信需求、影响范围明确、验证通过、无高风险领域、无未授权新增修复时，可记录证据并进入最终输出。
- [ ] 明确升级路径：高风险、验证失败后修复、低可信核心行为、当前分支覆盖关键路径或需求无法映射时，触发审查、询问用户或标记阻塞。
- [ ] 增加效率停止条件：无法从来源文档、目标 diff、合并后相关文件建立映射时，先标为 `无法判断`；若风险触发条件成立则升级审查；若需要业务判断则询问用户；不得继续开放式全仓搜索。
- [ ] 明确 `无法判断` 不是静默成功：所有 `无法判断` 必须进入用户决策、阻塞或审查之一；低风险也不能仅作为普通剩余风险结束。

需求覆盖：R6、R7

测试场景：
- 高风险或验证失败后修复时，流程要求触发或说明审查状态。
- 需求无法映射时，流程停止升级而不是无限搜索。
- 低风险证据充分时，流程不要求全量测试或固定审查。
- `无法判断` 会进入用户决策、阻塞或审查路径，不会被当作完成证据。

验证：
- 检查技能文档中快速路径、升级路径、停止条件和 `无法判断` 处理顺序均有明确文字。

### 7. 更新最终输出要求

- [ ] 在最终回复要求中增加来源需求核对表。
- [ ] 要求每项需求输出来源、可信度、状态、证据、处理结果。
- [ ] 要求区分变更来源：合并引入、冲突修复、合并后新增修复。
- [ ] 保留现有输出要求：目标输入、解析后 ref、当前分支、上下文来源、验证命令、审查状态、Git 授权、阻塞项。
- [ ] 将门禁表述改为“门禁状态或未运行原因”：当前不要求 `ae:merge-branch` 调用 `ae-gate`，不得用 `workflow: work` 或 `workflow: lfg` 伪装 merge 流程；只有外层 `ae:work` 包裹该任务或未来门禁工具支持 merge workflow 时才运行专用门禁。

需求覆盖：R2、R4、R5、R6

测试场景：
- 最终输出模板能回答来源分支要实现什么、合并后是否满足、证据是什么、验证跑过什么。
- 未运行审查或门禁时，流程要求说明原因和剩余风险。

验证：
- 阅读最终输出要求，确认新增核对表和变更来源分类没有替代原有 Git 授权与验证字段。

## 风险与处理

- 术语风险：Git 语境中“目标分支”可能被误解。处理方式是在技能开头定义来源分支和接收分支，后续统一使用。
- 效率风险：逐项核对可能膨胀成全仓扫描。处理方式是限制证据来源，无法映射时输出 `无法判断` 或升级审查。
- 授权风险：合并后修复可能越过用户合并授权。处理方式是明确新增修复必须单独授权。
- 证据风险：diff 归纳可能误判真实需求。处理方式是标低可信，不能单独支撑完整满足。
- 命令注入风险：来源分支文档中的验证命令可能不可信。处理方式是只作为候选命令，执行前单独展示、授权并过滤危险命令。
- 门禁误用风险：`ae-gate` 当前不支持 merge workflow。处理方式是不要求 `ae:merge-branch` 直接调用 `ae-gate`，只输出不适用原因或外层门禁结果。
