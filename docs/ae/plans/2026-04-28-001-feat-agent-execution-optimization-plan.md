# 代理执行力优化实施计划

## 来源与目标

本计划来源于 `docs/ae/brainstorms/2026-04-28-agent-execution-optimization-requirements.md`。需求文档定义的首阶段目标是建立最小可靠性闭环：任务分流正确、必要阶段不被静默跳过、交付证据可检查、通用性边界不被破坏。

本阶段不追求一次性重构全部 rules、agents、skills、commands、tools。每个改动必须关联明确失败场景，并能说明它如何降低代理失败概率，而不是增加流程仪式。

## 计划深度

深度计划。

原因：该工作跨运行时 rules、主流程 skills、命令入口、工具输出、审查代理触发和测试资产，且用户侧能力必须保持通用，不能泄漏本仓库维护假设。

## 影响对象

- 下游项目中的 opencode 用户：会直接受到运行时规则、技能描述、命令帮助和工具输出影响。
- 默认主代理：需要依赖更清晰的任务分流、阶段门禁和交付证据模型执行任务。
- 子代理与审查流程：需要在相关资产变更时触发适当审查，尤其是 agent-native 可达性审查。
- 插件维护者：需要新增或更新测试，确保规则、技能、工具和帮助输出保持一致。

## 当前仓库证据

- `src/assets/rules/ai-execution-guardrails.md` 已包含证据优先、阶段门禁、Git 权限和交付证明护栏，但尚未完整覆盖 S1-S7 场景矩阵。
- `src/assets/skills/ae-lfg/SKILL.md` 已定义从需求到交付的强管道，但任务分类仍偏“软件/非软件”，容易把简单问答或只读审查卷入重流程。
- `src/assets/skills/ae-work/SKILL.md` 已支持裸提示词复杂度分流，并要求最终调用 `ae-gate`，可作为小修复和轻路径承载点。
- `src/services/gate-service.ts` 已能返回 `pass` / `block`、阻断项、警告、证据和证明路径，但证据来源、缺失证据和建议下一步仍不够明确。
- `src/services/help-catalog-service.ts` 当前主要输出资产目录，缺少“场景到入口”的帮助层。
- `src/assets/commands/ae-commit.md`、`src/assets/skills/ae-work/references/shipping-workflow.md` 和 Git 规则共同约束提交安全，仍需统一“授权后才能提交/推送/跳过 hooks 不可越权”的表述。
- `src/services/review-selector.ts`、`src/services/review-catalog.ts` 和 `src/tools/ae-review-contract.tool.ts` 已支持 agent-native-reviewer 等条件审查，可优先通过触发条件与文档说明增强，而非新增代理。

## 设计原则

- 简单任务走轻路径，复杂任务走完整闭环。
- 证据模型按任务类型最小化，不要求所有任务都有需求、计划、审查和门禁证明。
- 门禁只检查证据完整性和一致性，不替代真实测试、构建、审查或人工决策。
- 只有可观察执行结果、工具输出、审查结果或其他可引用运行证据能支撑“已验证”；用户可引用确认只能支撑授权、范围确认或人工声明，不能单独支撑“验证已执行”。代理自述、用户声明或工具参数自证只能支撑“已声明/未验证”，不得单独使最终门禁通过。
- 验证命令必须来自用户、计划或项目上下文，不在用户侧运行时能力中硬编码本仓库脚本。
- 运行时规则保持短、强、可检查；复杂流程放在技能或引用文档中。
- 面向插件使用者的规则、技能、命令、工具描述不得默认目标项目具有本仓库的目录、构建命令或维护流程。

## 系统分层影响原则

本计划涉及运行时资产、工具、服务、Schema/Catalog 和测试五类边界。执行任一单元时必须按以下分层判断影响范围：

- 工具层只负责 LLM 可调用接口、参数校验、用户可见错误、toast 和服务编排；不得沉淀复杂业务规则。
- 服务层负责可测试的业务判断、证据计算、目录生成、选择逻辑和结果结构；不得依赖 TUI、toast、命令模板或用户侧文案副作用。
- 资产层包括 rules、skills、commands、agents 和引用文档，负责 LLM 行为约束和用户侧可见流程；不得硬编码本仓库维护前提。
- Schema/Catalog 层负责 AE 资产名称、技能目录、命令目录、参数提示与 frontmatter 的一致性；不得出现与资产文件语义漂移的重复事实。
- 测试层优先测试服务层和工具层契约，资产文案只测试关键锚点、引用可达性和禁止项，避免脆弱全文匹配。

任何单元修改跨越两个以上边界时，必须在该单元验证中说明是否影响 `src/services/ae-catalog.ts`、`src/schemas/ae-asset-schema.ts`、opencode permission，以及 SKILL.md 与 TypeScript 服务的双重决策一致性。

本阶段原则上不扩大 opencode 权限。任何对 `opencode.json`、命令入口、技能流程或工具调用路径的修改，都必须检查是否改变只读、文件写入、Git 写操作或远端写操作的权限语义；如必须修改权限配置，必须记录修改前后权限差异、风险和未扩大默认写权限的证据。

## 首阶段范围切片

首阶段硬范围只包含最小可靠性闭环：单元 1、单元 2、单元 3、单元 6 中与本阶段触及资产匹配的增量通用性审计，以及单元 7a 中与路由、门禁、Git 授权、事实/假设输出直接相关的最小测试。

条件进入首阶段的工作：单元 4a、4b、4c、单元 5，以及单元 6 中超出增量审计的全量治理部分。只有当单元 1-3 的实现证明相关能力会阻断 S1-S7 闭环，或当前资产已经存在与安全/通用性硬边界冲突时，才纳入同一交付阶段；否则推迟到后续增强。

## 高层流程

```mermaid
flowchart TD
  A[用户输入] --> B{任务分流 S1-S7}
  B -->|简单问答| C[直接回答或只读查询]
  B -->|模糊想法| D[澄清或 ae:brainstorm]
  B -->|小修复| E[ae:work 轻路径或直接修复]
  B -->|多步骤实现| F[ae:brainstorm → ae:plan 或 ae:refactor → ae:work → ae:review → ae-gate]
  B -->|只读审查| G[ae:review report-only]
  B -->|提交请求| H[Git 安全提交流程]
  B -->|混合意图| I[拆阶段后顺序执行]
  C --> J[事实/假设/风险输出]
  D --> K[需求证据]
  E --> L[验证与 ae-gate(work:work,checkpoint:final)]
  F --> M[计划/验证/审查/ae-gate(workflow:lfg,checkpoint:final)]
  G --> N[发现证据]
  H --> O[status/diff/log/授权/提交结果]
  I --> P[实现验证后再提交]
```

注：节点中使用缩写示意，完整调用格式见 S1-S7 路由与证据矩阵。`ae:plan 或 ae:refactor` 表示按任务性质选择功能计划或重构计划。

## S1-S7 路由与证据矩阵

| 场景 | 输入信号 | 推荐路径 | 允许直接处理 | 必要证据 | 阻断或降级 |
|------|----------|----------|--------------|----------|------------|
| S1 简单问答 | “是什么”“解释”“命令含义”“代码说明” | 直接回答；必要时只读搜索/读取 | 是 | 引用已读文件、帮助输出、官方文档或标注通用知识 | 不进入 LFG、计划、实现、门禁 |
| S2 模糊功能想法 | 目标、范围、验收不清 | 澄清或 `ae:brainstorm` | 否 | 已确认目标、约束、未决问题或需求文档路径 | 模糊需求直接编码必须阻断 |
| S3 小修复 | 明确 bug、错误栈、单点故障 | 直接修复或 `ae:work` 轻路径 | 是 | 定位证据、变更文件、验证命令；使用 `ae:work` 或正式代码交付时调用 `ae-gate workflow:work checkpoint:final` | 无计划允许，但必须记录无需计划原因；范围扩大则暂停并升级计划 |
| S4 多步骤实现 | 新功能、重构、跨文件、架构决策 | `ae:brainstorm` → `ae:plan/refactor` → `ae:work` → `ae:review` → `ae-gate` | 否 | 需求或充分性说明、计划路径、验证、审查通过、最终证明路径 | 无计划进入实现必须阻断 |
| S5 只读审查 | “review”“审查”“不要修改” | `ae:review report-only` | 是，只读 | 审查范围、发现证据、文件/行号、未修改说明 | 默认禁止修改用户工作区源文件、暂存文件或写业务交付产物；如需额外生成用户指定报告文件，必须先获用户授权并列出路径。技能自身按既有流程写入运行时审查产物时，不视为放宽业务写入边界 |
| S6 提交请求 | “提交”“commit”“push”“创建 PR” | `/ae-commit` 或 Git 安全流程 | 仅在明确授权后 | status、diff、log、敏感文件检查、纳入/排除文件、授权、提交结果；push/PR 需独立授权和结果证据 | 未授权提交/推送/创建 PR、跳过 hooks、强推默认分支必须阻断 |
| S7 混合意图 | “实现并测试并提交” | 先按 S3/S4 实现验证，再按 S6 提交 | 分阶段允许 | 阶段拆分、验证结果、门禁/审查、Git 授权与提交证据 | 提交不得早于验证和文件筛选 |

S3 必须升级到 S4 的停点：定位后发现跨模块或超过 2 个生产文件、涉及认证/授权/数据迁移/外部 API/API 契约、引入新抽象、修改公共配置、需要新增流程或用户可见行为决策时，必须暂停轻路径并转入计划流程。

S3 定位阶段只允许读取和搜索文件，不允许修改工作区文件。发现需升级后暂停所有修改操作并转入 S4 计划流程，定位阶段的只读观察结果可作为 S4 的上下文引用。"超过 2 个生产文件"阈值指定位阶段预估影响文件数，而非实际已修改文件数。

| 过早编码 | `ai-execution-guardrails.md`、`ae-lfg`、`ae-work` | 路由信号分散，S1-S7 未成矩阵 | 新增统一路由引用，并在 `ae-lfg`、`ae-work`、帮助输出中引用 |

| 上下文不足 | skills 要求读取计划/文件 | 缺少上下文不足时的阻断或提问条件 | 路由矩阵和 work 轻路径补充“证据不足先读取/询问” |
| 过度修改 | coding guidelines 强调精准修改 | 未与交付证据绑定 | 最终输出列出变更文件和超范围变更风险 |
| 跳过计划 | `ae-lfg` before_work 门禁、`ae-work` 复杂度分流 | 小修复与多步骤边界需更可测 | 在路由矩阵和 gate 测试中固化升级条件 |
| 跳过验证 | `ae-gate` final 阻断空验证 | 用户禁止执行命令时交付语义不清 | 输出降级为未验证/未完成，记录原因和风险 |
| 未验证断言 | 运行时规则已有事实/假设要求 | 主流程最终模板不一致 | 统一最终输出分区：已完成、已验证、未验证、剩余风险 |
| 遗漏边界场景 | 计划和 review 已要求测试场景 | 小修复轻路径可能跳过边界思考 | S3 最小证据要求包含关键边界或说明不适用 |
| 无证据审查 | `ae-review` 已要求证据 | 路由帮助未强调只读审查边界 | 帮助和路由矩阵增加 S5 只读边界 |
| Git 越权 | rules、`ae-commit.md`、权限配置、gate Git 写检测 | shipping 文档与提交命令表述需统一 | 明确未授权不提交、不推送、不跳过 hooks，不因用户泛化要求越过敏感边界 |
| 虚假完成 | gate 和最终输出规则已有防线 | 声明式证据可能伪装为验证事实 | 区分可观察证据和声明证据，声明证据不能支撑“已验证” |
| 工具失败不可恢复 | `ae-gate` 返回 blockers/warnings | 缺失证据和下一步动作不够直接 | 优先增强 `ae-gate` 输出，后续再推广到 recovery/review/help |
| 插件边界泄漏 | 项目规则已有通用性边界 | 用户侧资产缺少明确检查清单 | 增加通用性审计单元和测试，禁止硬编码本仓库维护前提 |

## 最小交付证据模型

| 任务类型 | 必填证据 | 可接受跳过原因 |
|----------|----------|----------------|
| 代码变更 | 变更摘要、相关文件、验证命令与结果、审查状态、Git 操作状态、门禁结果 | 用户禁止执行命令、环境缺失、非 Git 项目、简单小修复无需计划但需说明 |
| 只读审查 | 审查范围、发现列表、每条发现的文件/行号/实际证据、未修改说明 | 范围不明确时要求用户指定；无发现时说明残余风险；若审查技能按既有约定写入运行时审查产物，不计入业务修改 |
| 问答/调研 | 来源、已读文件或外部文档、事实/假设标注 | 未读取本地证据时标注基于通用知识 |
| 无 Git 环境 | 工作区观察、文件路径、验证结果 | 不能提供 git status/diff，明确无 Git 证据 |
| 提交请求 | status、diff、log、暂存/未暂存/未跟踪检查、敏感文件过滤、用户授权、提交后状态 | 发现敏感或无关变更时阻断或要求用户决定 |

### 单元执行约束

每个实现单元必须有唯一主产出，其他变更只能作为支撑改动出现。执行时按以下规则控制边界：

### [ ] 单元 3：增强 `ae-gate` 的可恢复输出

目标：让门禁工具输出能直接告诉代理缺什么、影响是什么、下一步怎么补，同时保留它“不替代真实测试/审查”的定位。

唯一产出：`ae-gate` 返回结构中可行动的缺失证据、证据来源分级、建议下一步和人类可读摘要，且保持现有字段向后兼容。

`GateResult` 新增四个语义分区（具体字段名在实现时确定，但语义必须锁定）：(1) 缺失证据列表——列出当前 gate 判定所需但未提供的证据；(2) 建议下一步列表——为每个 blocker 生成可执行的补救动作；(3) 证据来源分级映射——为 gate 最终判定的每个关键证据标注来源分级；(4) 人类可读摘要。`missingEvidence` 与 `blockers` 并存：`blockers` 描述阻断事实，`missingEvidence` 描述缺失内容；两者语义不互斥。`evidenceSources` 按判定结论级标注（gate 最终 pass/block 的证据来源分级），不按 `evidence` 内部每个字段逐一标注，避免结构膨胀。

证据来源分级枚举值语义锁定：
- `observable_workspace`：可观察的工作区状态或工具执行输出（如 changedFiles、工具运行结果）
- `tool_output`：工具/代理的可引用输出（如审查结果、测试报告）
- `tool_input_declared`：代理在工具参数中声明的值（如 validation_commands、userAuthorizedGitWrite），未经独立执行或用户确认
- `user_confirmation`：用户当前会话中可引用的明确请求或确认
- `not_provided`：未提供任何证据

gate 在此分级下只做证据来源标注和风险提示，不做自动执行验证。标注来源为 `tool_input_declared` 或 `user_confirmation` 的证据不能单独支撑“验证已执行”；`user_confirmation` 只可支撑授权、范围确认或人工确认事实。可支撑“已验证”的执行证据应来自 `observable_workspace` 或 `tool_output`。

需求：覆盖 R4、R18、R19、R20、R21、R23。

依赖：单元 2。

文件：

- `src/services/gate-service.ts`
- `src/tools/ae-gate.tool.ts`
- `src/services/gate-service.test.ts`
- `src/schemas/*` 或其他 `GateResult` 类型定义文件（仅当 `GateResult` 不在 `gate-service.ts` 中定义时）

方法：

- 在 `GateResult` 中增加或规范可行动字段，优先考虑：`missingEvidence`、`nextSteps`、`evidenceSources`、`summary`。
- 先确定唯一公共契约载体（独立 schema/type 模块或 `gate-service.ts` 中集中导出），由 service 返回结构化对象，tool 只做 snake_case 到 camelCase 映射、错误处理和输出格式化；禁止在 tool 层新增 gate 判定字段或重组业务语义。
- `evidenceSources` 区分可观察工作区证据、工具输入声明、用户/代理声明和未提供证据。
- final gate 必须把声明式证据与可观察证据分级；验证命令只有在执行结果或可引用工具输出可核实时才能支撑“已验证”，代理自填 `validation_commands` 或用户口头确认都不能单独通过最终门禁。
- Git 写操作授权必须绑定用户显式请求或确认的可引用证据；`userAuthorizedGitWrite` 当前是代理自填的 boolean，属于 `tool_input_declared` 来源，不能单独作为授权证据。首阶段不依赖自由文本 `notes` 自动推断 `user_confirmation`；`notes` 最多用于记录人工可追溯的上下文摘录。若需要让 gate 接受结构化授权证据，必须在单元 5 或后续阶段新增明确字段与测试后再放行。
- block 场景为每个 blocker 生成建议下一步，例如补传 `validation_commands`、传空 `git_operations`、提供 `no_code_change_reason`、先运行审查。
- 输出文案明确 gate 只验证证据存在性与一致性，不证明测试本身通过。
- 保持现有 `blockers`、`warnings`、`evidence` 字段兼容，避免一次性破坏技能提示词和测试。
- `validation_commands` 在没有可引用执行输出或工具输出时，只视为已声明的验证命令，不得单独标记为已验证。如首阶段不新增验证结果参数，应在 `evidenceSources` 中标注来源为 `tool_input_declared`，并在 `summary` 或 `warnings` 中提示门禁仅记录验证命令声明，不证明命令已成功执行。
- `git_operations` 证据应区分无 Git 写操作、计划执行但未执行、已执行写操作、远端写操作四类；final gate 对已执行但缺授权证据的 Git 写操作必须阻断并标记为越权风险。
- 说明：单元 3 只声明 `ae-gate` 范围内完成 R18-R20。`ae-recovery`、`ae-review-contract`、`ae-help` 仅在单元 4a/4b/4c 进入首阶段时声明对应覆盖；其他工具统一结构化输出推迟到后续阶段。

需遵循的模式：

- 工具参数保持通用，不要求下游项目有固定脚本或目录。
- `showToast` 只能在工具层错误路径调用，service 层保持纯逻辑。
- 工具参数继续使用 snake_case，对应服务层输入使用 camelCase，由 `src/tools/ae-gate.tool.ts` 负责映射；不要把参数命名风格泄漏到 service 层。
- `gate-service.ts` 返回结构化结果、阻断原因和建议动作；`ae-gate.tool.ts` 负责将结果格式化为面向 LLM / 用户的输出。
- service 层不得调用 `ctx.metadata()`、`ctx.ask()`、`showToast` 或读取工具上下文；工具层不得重新实现 gate 判定规则。

测试场景：

- final 缺 `validation_commands` 返回 block，并包含缺失证据和下一步。
- final 缺 `git_operations` 字段返回 block，并提示无写操作时传空数组。
- Git 写操作但未授权返回 block，并提示需要用户明确授权或撤销写操作。
- 未实现结构化授权证据字段前，自由文本 `notes` 不得单独把 Git 写操作升级为已授权。
- 仅由代理声明验证或 Git 授权时，final gate 不得把该声明当作已验证或已授权证据。
- 无代码变更且提供 `no_code_change_reason` 可通过，并标记证据来源为声明。
- 非 Git 环境不崩溃，changedFiles 为空时依赖跳过原因或阻断。

验证：

- `npm run test -- src/services/gate-service.test.ts`
- `npm run typecheck`

### [ ] 单元 4a：增强 `ae-recovery` 可恢复输出

目标：让恢复工具在发现已有产物、多个候选或缺少上游产物时给出可执行下一步，避免无路径或错误阶段调用。

### [ ] 单元 5：统一 Git 安全边界和提交路径

目标：消除提交相关规则、技能、命令之间的潜在张力，确保未经授权不提交、不推送、不跳过 hooks、不修改 Git 配置。

方法：

- 用户要求提交但存在敏感文件时阻断并警告。
- Git 写操作记录未授权时 gate 阻断。
- 只有代理或工具参数声明授权时，gate 必须阻断 Git 写操作。
- push/PR 未获单独授权时阻断。
- 权限配置不得把敏感 Git 写操作设为自动允许。
- 验证失败或未运行时，不把提交当作质量证明。

## 计划时决策

- 首阶段不新增代理，除非执行单元 4b 证明现有 agent-native、research、review 触发无法覆盖可达性或可靠性缺口。
- 首阶段优先增强 `ae-gate`，不一次性迁移所有工具输出格式。
- 帮助可发现性在条件进入首阶段时优先通过 `help-catalog-service` 的场景导向输出增强，而不是要求用户记住更多技能名。
- Git 安全采用规则、技能、命令和 gate 共同约束；提交和推送仍必须由用户明确授权。
- 简单问答和只读审查不强制使用 gate，避免流程过重。

## Deferred to Implementation

- `GateResult` 新增字段的具体命名在实现时结合现有测试和工具输出格式确定，优先保持向后兼容。
- `src/assets/skills/ae-lfg/references/task-routing.md` 为单元 1 的固定产物；若执行阶段发现仍需额外拆分辅助引用文档，只能在保留该文件为唯一事实源的前提下追加。
- 通用性审计测试可先采用关键词和语境白名单，后续再抽象为独立诊断工具。

## 风险与缓解

| 风险 | 缓解 |
|------|------|
| 流程过重，简单任务被迫进入完整 LFG | 路由矩阵明确 S1、S3、S5、S6 的轻路径和跳过理由 |
| 证据模型形式化但无真实验证 | gate 输出区分可观察证据、声明证据和缺失证据 |
| 复杂修复伪装成小修复绕过计划 | S3 定义强制升级停点，跨模块或高风险领域必须暂停并转 S4 |
| 用户侧资产泄漏本仓库维护前提 | 单元 6 增加通用性边界审计 |
| 工具输出兼容性破坏 | 单元 3 保留现有字段，新增可行动字段而非替换结构 |
| Git 安全被命令模板弱化 | 单元 5 将硬边界同步到 rules、skills、commands 和 gate |
| 双重决策漂移 | 同步检查 `ae-lfg` / `ae-work` / `ae-help` 与 help、gate、review service 的语义一致 |
| catalog / frontmatter / help 输出漂移 | 将 `ae-catalog` 一致性作为横切检查；修改 SKILL frontmatter、帮助输出或 TUI 描述时同步检查 description 与 argumentHint |
| 权限语义被入口文案绕过 | 增加 opencode permission 影响评估；命令、技能、工具不得诱导模型绕过 ask/deny 或把敏感操作作为自动步骤 |

## 验收清单

- S1-S7 至少有一组可重复执行的路由与交付证据检查样例。
- 多步骤实现无计划进入实现会被阻断。
- 小修复可走轻路径，但最终必须有验证和 gate 证据或明确降级原因。
- 最终输出能区分已完成、已验证、未验证和剩余风险。
- 声明式证据不得单独支撑“已验证”或 Git 写授权。
- `ae-gate` 输出包含阻断原因、缺失证据、建议下一步和证据来源。
- 未经明确授权的 Git 写操作不得提交、不推送、不跳过 hooks、不修改 Git 配置；若单元 5 未进入，本阶段只声明“未授权会被阻断”，不声明合法授权路径已端到端打通。
- 对单元 4a、4b、4c、5、6 已记录进入判定及不进入理由；如单元 5 未进入，只能声明 gate 范围内的 Git 授权阻断已完成，不能声明所有提交路径已完全收敛。
- 面向插件使用者的运行时能力不要求下游项目采用本仓库目录、脚本、框架或发布流程。
- 修改后的 rules、skills、commands、tools 语义一致，无互斥动作要求。
- 工具层只做参数校验、toast、用户可见错误和服务编排；服务层不依赖 toast、TUI、命令模板或资产文案副作用。
- 修改过的用户侧资产、服务输出和帮助目录在入口定位、证据要求、权限边界上没有语义漂移。
- 满足触发条件时已检查 `ae-catalog`、资产常量和 opencode permission。

## 建议执行顺序

1. 单元 1：建立任务路由引用与场景矩阵。
2. 单元 2：收敛运行时规则与技能交付模板。
3. 单元 3：增强 `ae-gate` 的可恢复输出。
4. 单元 7a：执行首阶段最小测试，覆盖单元 1-3 的路由、证据和 gate 边界。
5. 条件进入判定：单元 1-3 完成后，执行者逐项检查以下条件，对每个条件单元记录进入或不进入的理由：
   - 单元 4a：`ae-lfg` 和 `ae-work` 的恢复路径引用是否需要 `ae-recovery` 输出增强才能让代理在恢复场景下正确选择路径；若已有恢复路径足够清晰，记录不进入理由。
   - 单元 4b：资产变更是否需要更明确的 `agent-native-reviewer` 可达性触发说明；若现有触发条件已足够覆盖本阶段资产变更类型，记录不进入理由。
   - 单元 4c：帮助输出中纯资产目录是否不足以支撑代理路由决策；若路由规范已可在 `ae-lfg` 和 `ae-work` SKILL.md 中直接引用，记录不进入理由。
   - 单元 5：现有提交相关规则、技能、命令之间是否存在导致代理在 S6/S7 场景下能绕过用户授权执行写操作的硬冲突；若只有表述不一致但无实际越权路径，记录不进入理由。
6. 条件执行单元 5：仅当判定发现硬冲突时进入。
7. 单元 6：执行与本阶段修改资产匹配的增量通用性审计；只有全量治理扩展仍保持条件进入。
8. 条件执行单元 4a、4b、4c、5：仅对已被判定进入的单元按编号顺序落地实现与验证。
9. 单元 7b：仅对已执行的条件单元补齐扩展验收样例。

## 交接给 `ae:work`

执行时应从单元 1 开始，分小步落地工作区变更，但不得创建 Git 提交，除非用户明确要求。执行前先检查当前工作区是否已有用户未提交变更；实现期间不得修改本计划文件，除非用户明确要求更新计划。每完成一个单元后运行该单元列出的最小验证；最终运行 `npm run test`、`npm run typecheck`、`npm run build`。这些命令是本插件源码仓库维护语境下的验证命令，不应写入用户侧通用运行时规则。生成的 `docs/ae/gates/` 证明属于运行时交付证据，是否纳入版本控制需按用户要求和仓库约定决定。
