# 代理执行力优化需求

## 问题框架

AE 是面向通用项目的 opencode 插件。它的核心价值不是替某个固定仓库写死流程，而是让代理在不同代码库中更可靠地理解任务、选择能力、执行步骤、验证结果并交付证据。

结合当前 AI 代理常见问题，主要风险包括：过早编码、跳过计划或验证、把未确认假设当事实、调用不到合适能力、工具结果缺少可执行下一步、审查覆盖和交付证明断裂，以及把插件源码仓库自身的维护约定误传播给下游项目。

本次优化以“执行可靠性”为第一优先级，同时从 rules、agent、skills、commands、tools 五类资产寻找通用优化空间。优化结果必须服务所有下游项目中的 opencode 代理，而不是只服务当前插件源码仓库维护者。

首个交付阶段不追求一次性改完所有资产。它应先建立最小可靠性闭环：任务分流正确、必要阶段不被静默跳过、交付证据可检查、通用性边界不被破坏。其他资产优化只有在能关联明确失败场景时才进入首阶段。

## 代表性任务场景

- S1. 简单问答：用户询问概念、命令含义或代码解释，不应强制进入计划或实现流程。
- S2. 模糊功能想法：用户描述方向但未定义目标，应进入头脑风暴或澄清，而不是直接编码。
- S3. 小修复：用户给出明确 bug 或错误信息，应先定位和复现，范围小且清晰时可直接修复并验证。
- S4. 多步骤实现：用户要求新增功能、重构或跨文件改动，应先形成计划，再实现、验证和审查。
- S5. 只读审查：用户要求 review，应保持只读，优先输出发现和风险，不应修改文件。
- S6. 提交请求：用户明确要求提交时，应检查变更、筛选文件、遵守 Git 安全边界。
- S7. 混合意图：用户同时要求实现、测试和提交，应拆分阶段并在提交前完成验证与授权检查。

## 需求

**执行可靠性优先**
- R1. 插件应强化代理在任务开始时的任务分流能力，区分问答、调研、头脑风暴、计划、实现、审查、测试和提交等不同意图。→ 验收: 至少覆盖 S1-S7 的路由用例矩阵，每个用例都有期望技能、允许的直接处理路径和不进入重流程的理由。
- R2. 插件应降低代理跳过必要阶段的概率，尤其是多步骤实现中的需求澄清、计划、实现、验证、审查和交付证明。→ 验收: 多步骤任务必须留下阶段状态、跳过原因、验证或审查证据；缺失必要证据时应阻断交付或明确降级为未完成。
- R3. 插件应要求代理把“已验证事实”和“未经验证假设”分开表达。→ 验收: 面向用户的规则或技能输出约束中包含事实/假设/风险分区要求，并且不依赖特定项目脚本。
- R4. 插件应在交付前要求代理提供通用证据，而不是口头承诺。→ 验收: 按任务类型定义最小证据模型；代码变更、只读审查、问答调研、无 Git 环境和用户禁止执行命令等场景分别有必填证据和可接受的跳过原因。

**Rules 优化**
- R5. 运行时规则应聚焦通用代理行为护栏，避免出现只适用于插件源码仓库的目录、脚本、构建命令或业务模块假设。→ 验收: 面向用户侧规则中没有把本仓库专用结构当成所有项目必须满足的前提。
- R6. Rules 应覆盖 AI 常见失败模式：目标漂移、上下文不足、过度修改、未验证断言、遗漏边界场景、错误 Git 操作和虚假完成。→ 验收: 形成“失败模式→可执行约束→拦截方式”矩阵，每类失败模式至少有一个可检查约束。
- R7. Rules 应避免与技能内指令冲突。→ 验收: 当 rules 和技能同时涉及计划、验证、Git、审查或交付时，语义一致，且不会要求代理执行互斥动作。

**Agent 优化**
- R8. 代理集合应覆盖执行任务所需的关键审查与研究角色，同时避免重复人设造成噪声。→ 验收: 仅当现状盘点发现明确边界冲突或覆盖缺口时，才新增或调整代理；每个调整都关联一个失败场景。
- R9. 与代理可操作性相关的审查应优先关注“用户能做的事代理是否也能做”。→ 验收: 当新增或修改命令、工具、技能、TUI 或代理配置时，审查机制能触发代理原生可达性检查。
- R10. 研究型代理应服务于通用最佳实践和项目局部模式，而不是把外部方案或本仓库经验直接套用。→ 验收: 研究结果必须区分外部参考、当前项目证据和未经验证假设。

**Skills 优化**
- R11. 技能应形成从想法到交付的闭环，但允许根据任务复杂度降级。→ 验收: 简单任务不会被迫进入完整 LFG 流程，复杂任务不会绕过计划和验证。
- R12. 每个技能应明确输入、退出条件、产物、失败恢复方式和可交接下一步。→ 验收: 形成统一技能说明检查清单；首阶段目标技能均通过该清单，而不是分散补充不一致说明。
- R13. 技能之间的职责边界应清晰，避免一个技能同时承担头脑风暴、计划、实现和审查。→ 验收: 需求探索回答 WHAT，计划回答 HOW，工作执行实现，审查评价质量；例外必须有明确理由。
- R14. 前端、浏览器测试、SQL、提示词优化、交接等专项技能应保持可选增强能力，不应成为所有项目的固定门槛。→ 验收: 主流程中这些能力只在适用条件满足时触发，并允许记录跳过原因。

**Commands 优化**
- R15. 公开命令应让用户和代理能稳定触发对应技能，减少必须记忆技能名或长参数的负担。→ 验收: 帮助信息、TUI 命令和 slash 命令在名称、描述、参数提示上保持一致。
- R16. 命令模板应传递用户原始意图，避免在包装命令时改写需求或加入项目专用假设。→ 验收: 命令模板只负责路由、参数沿用和必要模式标记，不擅自决定实现方案。
- R17. 提交类命令应强化安全边界。→ 验收: 未经用户明确要求不提交、不推送、不跳过 hooks、不修改 Git 配置，并能过滤敏感文件和无关变更。

**Tools 优化**
- R18. 工具应返回代理可继续执行的结构化结果，尤其是阻断原因、缺失证据、建议下一步和可引用产物路径。→ 验收: 工具失败时代理能从输出中判断补什么、重试什么或询问用户什么。
- R19. 工具参数应保持最小且通用，不要求下游项目存在固定脚本、目录或框架。→ 验收: 工具描述和参数只使用通用工作流证据，项目特定命令由用户、计划或上下文提供。
- R20. 工具错误应对代理和用户可恢复，避免重复通知或只返回不可行动的失败文本。→ 验收: 关键工具错误输出包含原因、影响、建议下一步和是否可重试。
- R21. 自诊断和门禁工具应支持基于声明与可观察工作区证据检测缺失的必要证据，但不替代真实测试、构建、审查或人工决策。→ 验收: 门禁输出能区分 pass、block、warning，并明确哪些证据来自实际执行、工作区观察或用户/代理声明。

**通用性边界**
- R22. 所有面向插件使用者的能力都不得内置当前插件源码仓库的维护前提。→ 验收: 优化方案中若出现本仓库路径、构建命令或内部同步流程，必须标注为插件源码维护语境，不能写入用户侧通用规则。
- R23. 插件应允许下游项目以自己的验证命令、目录结构、框架和发布流程作为证据来源。→ 验收: 计划或工作流程可以记录项目提供的验证命令，而不是固定要求某个脚本名。
- R24. 优化应优先减少代理失败概率，而不是增加流程仪式。→ 验收: 建立“改动→失败场景→预期拦截方式”追踪表；无法关联实际失败链条的改动默认不进入首阶段。

## 优先级切片

**首阶段必须覆盖**
- R1-R4：任务分流、阶段证据、事实/假设分离、最小交付证据模型。
- R5-R7：通用运行时规则和失败模式矩阵。
- R21-R24：门禁证据边界、通用性边界和改动追踪表。

**首阶段条件覆盖**
- R8-R10：仅在现状盘点证明代理边界或可达性影响执行可靠性时进入。
- R11-R14：优先处理主流程和工作执行相关技能，专项技能只处理会破坏可靠性的边界。
- R15-R17：优先处理默认入口、帮助和提交安全；其他命令一致性可后续推进。
- R18-R20：优先处理交付门禁、审查契约、恢复、帮助等会影响流程闭环的工具输出。

**后续增强**
- 大规模代理体系重组、所有命令元数据统一、所有专项技能模板化、运行时 UI 优化和 CI 门禁接入。

## 成功标准

- 代理在多步骤软件任务中更少跳过澄清、计划、验证、审查和交付证明。
- 代理输出能清晰区分已完成、已验证、未验证和剩余风险。
- 用户能通过命令、帮助或默认入口更容易触发正确流程。
- 新增或修改的运行时能力保持通用，不把当前插件源码仓库的内部约定强加给下游项目。
- 后续 `ae:plan` 不需要重新决定优化优先级、范围边界和验收标准。
- 首阶段完成后，S1-S7 至少有一组可重复执行的路由与交付证据检查样例。

## 范围边界

- 本阶段不实现代码变更，只定义需求和优化方向。
- 不把当前插件源码仓库的构建命令、目录结构、测试脚本或内部维护流程写入用户侧通用能力。
- 不要求所有项目使用同一种测试框架、包管理器、前端框架、数据库或发布流程。
- 不新增会自动修改用户代码的能力，除非后续规划明确其安全边界和授权机制。
- 不把更多流程步骤本身当作目标；目标是提升代理完成任务的可靠性和证据质量。
- 不要求专项技能在所有任务中运行；专项能力只在任务、项目和依赖条件适用时触发。
- 不在首阶段默认新增代理或工具；优先盘点并增强现有能力，除非现有能力无法覆盖首阶段必需需求。

## 关键决策

- 第一优先级选择“执行可靠性”: 用户明确选择该方向，且它能覆盖当前 AI 代理最常见的失败模式。
- 优化对象覆盖五类资产: rules 提供底线，agents 提供专业判断，skills 提供流程，commands 提供入口，tools 提供可验证动作。
- 通用性作为硬边界: 插件是通用插件，任何用户侧能力都不能默认目标项目就是本仓库。
- 证据优先于承诺: 代理完成任务的可信度来自读取、搜索、运行、审查和门禁记录，而不是最终回复中的保证。
- 首阶段优先增强现有资产: 只有当现状盘点证明现有 rules、agents、skills、commands 或 tools 无法承载需求时，才新增资产。

## 考虑过的替代方案

- **优先做能力可达性**: 能改善命令、技能、工具触达问题，但如果代理触达后仍跳步或虚假完成，用户价值有限。
- **优先做质量闭环**: 能提高审查和测试质量，但需要先确保代理不会绕过基本阶段和证据记录。
- **优先做使用体验**: 能降低学习成本，但如果底层流程可靠性不足，只会让用户更快触发不稳定流程。

## 依赖 / 假设

- 当前插件已经具备技能、代理、命令注册、帮助、自诊断门禁和审查契约等基础能力，可作为优化载体。
- 下游项目差异很大，因此所有证据采集和验证命令都应从上下文、计划或用户输入中获得。
- 代理失败不只来自缺少工具，也来自过度自信、上下文不足和流程边界不清。
- 规划阶段需要先盘点现有相关资产的可达性、输入输出、已知缺口和可复用程度，再决定增强还是新增。
