# 前端设计相关技能与代理边界强化

## 问题框架

`ae:frontend-design`、`ae:test-browser`、`design-iterator`、`figma-design-sync` 都涉及前端、截图、浏览器或视觉质量，容易在执行时出现职责重叠。需要强化它们在资产说明中的边界，让用户和 LLM 更容易在不同场景下选择正确能力，并在存在明确执行顺序时主动提示用户下一步应使用哪个技能或代理。

## 需求

**职责边界**
- R1. 明确 `ae:frontend-design` 是前端设计与初版实现入口。→ 验收: 资产文档中明确它不负责完整 E2E、不负责 Figma 像素同步，多轮细化交给专项代理。
- R2. 明确 `ae:test-browser` 是浏览器验收入口。→ 验收: 资产文档中明确它验证页面可用性、关键交互和截图证据，不承担审美设计或 Figma 对齐。
- R3. 明确 `design-iterator` 是多轮审美迭代代理。→ 验收: 资产文档中明确它只对已实现 UI 做小步视觉改进，不扩大产品范围，不替代 Figma 同步。
- R4. 明确 `figma-design-sync` 是 Figma 对齐代理。→ 验收: 资产文档中明确它以 Figma 为准，不自由发挥设计方向，不承担完整 E2E。

**顺序引导**
- R5. 为相关资产加入“下一步提示”规则。→ 验收: 提示只在用户明确需要视觉打磨、Figma 对齐、交互验收，或当前任务结果自然暴露这些后续需求时出现；简单任务完成且无后续风险时允许直接结束。
- R6. 明确常见顺序链路清单。→ 验收: 资产文档覆盖至少以下建议链路：`ae:frontend-design` 初版实现后，如仍需多轮审美打磨则建议 `design-iterator`；如需要浏览器交互验收则建议 `ae:test-browser`；有 Figma 对齐目标时建议 `figma-design-sync`；`figma-design-sync` 完成后，如需要验证真实交互则建议 `ae:test-browser`。

**交接规则**
- R7. 建立四类场景的入口和转交矩阵。→ 验收: 矩阵覆盖“无 Figma 初版设计 / 多轮打磨 / Figma 对齐 / 浏览器验收”，并对每类场景标明首选入口、可选后续和不应使用的能力。
- R8. 避免重复验证链路。→ 验收: `ae:frontend-design` 保持一轮视觉验证，完整浏览器测试明确交给 `ae:test-browser`。

## 成功标准

- 四个能力的入口场景不再模糊。
- 每个资产都包含清晰的“做什么 / 不做什么 / 何时转交”。
- 存在明确执行顺序时，相关资产会主动提示用户下一步应使用哪个技能或代理。
- 用户能更少遇到能力误用、重复验收或被迫进入不必要流程的情况。
- 后续规划可以直接修改对应 Markdown 资产，不需要重新决定产品边界。

## 范围边界

- 不新增技能或代理。
- 不改变工具执行逻辑或运行时行为；允许同步入口 catalog 描述以保持选择提示一致。
- 不修改 agent-browser、Figma MCP 或浏览器测试实现。
- 不做视觉能力的功能扩展，只强化提示词边界、非目标和交接规则。

## 关键决策

- 采用“入口技能负责主流程，专项代理负责深度任务”的模型。
- `ae:frontend-design` 保留最高层设计入口地位，但不得吞并 `design-iterator`、`figma-design-sync`、`ae:test-browser`。
- `ae:test-browser` 定位为验收而非设计质量提升。
- 边界说明必须包含下一步引导，避免用户或 LLM 在自然后续流程中停在错误能力上。
- 下一步引导必须是条件性建议，不应让简单任务默认升级为多阶段流程。

## 依赖 / 假设

- 四个资产的当前定义仍保留，后续只做边界和交接提示增强。
- 顺序引导应以“建议使用”表达，而不是强制所有流程都串联执行。
- 如果后续发现能力误选主要来自 catalog、frontmatter 或命令描述，规划阶段应将这些入口描述纳入修改范围；本需求当前优先约束技能和代理资产正文。
