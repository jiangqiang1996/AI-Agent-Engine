# ae:merge-branch 合并后需求完整性验证

## 问题框架

`ae:merge-branch` 当前流程已经重视 Git 安全、来源分支上下文读取和冲突修复，但合并成功不等于来源分支需求在接收分支中仍然成立。即使没有冲突，当前接收分支已有代码也可能覆盖、绕开或缺失来源分支所需行为。因此该技能需要在合并完成后显式验证“来源分支需求是否被合并后代码满足”，同时避免把每次合并都变成低效的全量审查。

术语约定：来源分支指被合入的分支或本地 worktree 绑定分支；接收分支指执行合并命令时所在的当前分支。

## 需求

**合并后需求完整性**
- R1. 技能必须在执行合并前从来源分支上下文形成可追踪的来源需求清单，并标注每项需求的证据来源与可信度。 → 验收: 来源于交接、需求或计划的条目标为高可信；仅从提交摘要或 diff 归纳的条目标为低可信；低可信条目不得直接作为“完整满足”的充分依据。
- R2. 技能必须在合并后基于可获得证据逐项判断来源需求是否由接收分支当前工作区满足。 → 验收: 无论是否发生冲突，最终输出都包含需求清单、每项状态（已满足 / 需修复 / 无法判断）和对应证据来源；`无法判断` 是允许的显式状态，不能被静默转成已满足。
- R3. 无冲突合并也必须进入合并后需求完整性验证阶段，不能仅因 Git merge 成功就视为完成。 → 验收: 流程文本明确说明“无冲突合并成功”之后仍需执行需求核对、相关验证和必要修复。
- R4. 当核对发现来源需求未被满足或无法判断时，技能必须先说明缺口与证据，再询问用户决策；如需进行合并结果之外的新增代码修复，必须取得单独授权。 → 验收: 对于未满足或无法判断的需求，最终输出包含处理结果、用户决策或阻塞原因，并区分哪些变更来自合并、哪些来自合并后修复。

**验证与审查**
- R5. 技能必须优先使用来源分支计划、需求文档或差异归纳中的验证命令，并根据合并后实际影响范围补充最小必要验证。 → 验收: 最终输出列出验证命令的来源、实际运行结果，以及未运行命令的原因；没有可运行验证命令时，相关需求只能基于代码/测试证据标为已满足，证据不足时标为无法判断。
- R6. 技能应在需求完整性风险较高时触发代码审查，而不是对所有合并固定执行高成本审查。 → 验收: 流程定义触发条件，例如需求无法映射、关键行为被当前分支改动覆盖、验证失败后修复、涉及安全/数据/API/迁移等高风险区域。

**效率**
- R7. 技能必须采用分层验证策略，先做来源需求清单与影响范围核对，再只读取和验证相关文件，避免默认全仓扫描或全量测试。 → 验收: 流程明确区分快速路径和升级路径；低风险、证据充分的合并不要求额外全量审查；需求无法映射到明确文件或验证命令时，应标为无法判断或升级审查，而不是继续开放式全仓搜索。
- R8. 技能应复用合并前已经读取的交接、需求、计划和差异摘要，避免合并后重复做同样的上下文发现。 → 验收: 流程要求在合并前保存需求摘要，并在合并后复用该摘要作为核对基线。

## 成功标准

- 无冲突合并不会绕过来源需求完整性验证。
- 技能最终交付能回答：来源分支要实现什么、合并后是否仍然满足、证据是什么、哪些验证跑过。
- 低风险合并保持快速，不被固定全量测试或全量审查拖慢。
- 高风险或无法判断的合并会升级到修复、用户决策或审查，而不是静默通过。

## 范围边界

- 不要求把 `ae:merge-branch` 改造成全自动 Git 合并工具；它仍是 LLM 执行流程文档。
- 不默认创建合并提交、推送远程分支或执行远程写操作。
- 不要求所有合并都运行全量测试；验证范围应由来源需求、计划命令和影响范围决定。
- 不以当前源码仓库的测试命令作为插件用户项目的通用前提。

## 关键决策

- 采用平衡方案: 将合并后需求完整性核对设为必经阶段，但只在风险触发时升级到更重的审查或更广验证。
- 需求清单必须在合并前形成: 合并后再推断容易被接收分支状态污染，无法稳定判断来源分支原始意图。
- 无冲突合并不能直接完成: Git 层面的无冲突只说明文本或三方合并可应用，不证明业务需求仍成立。
- 合并授权不等于新增修复授权: 合并后为补齐缺失需求而新增或改写代码，需要向用户单独说明并取得授权。

## 依赖 / 假设

- 来源分支可能有 AE 交接、需求或计划产物；没有时允许从提交摘要和 diff 降级归纳，但必须标为低可信推断。
- 验证命令可能来自计划文档、项目约定或影响范围；无法确定时需要向用户说明风险或询问。
