# 模型场景路由配置

## 问题框架

AE 当前大量技能、命令和代理默认继承同一个模型，导致简单任务可能浪费高成本模型，复杂任务又可能拿不到足够强的推理能力。需要实现一套完善的任务感知模型切换能力：用户可以配置少量“用途场景”和高级回退策略，AE 内置资产按任务性质、能力要求和当前可用性自动选择合适模型，而不是要求用户逐个理解并覆盖每个技能、命令或代理。

图像识别/视觉理解需要作为独立场景处理。它与文本任务复杂度不是同一个维度：一个模型可能很强但不支持图像输入，或视觉能力强但不适合作为通用深度编码模型。

参考 oh-my-openagent 的模型切换思路后，本次需求重构的重点是把 AE 从“基础场景配置”提升为“完整模型解析系统”：明确的解析优先级、可解释的模型来源、可选的供应商回退链、模型能力约束、视觉能力守卫，以及模型不可用时的可恢复降级。AE 的默认体验仍应低配置成本，但高级用户应能启用足够完整的模型切换能力。

## 推荐方向

采用“用途场景”命名，而不是“强/中/弱”或“快/中/慢”。模型路由由六层概念组成：

- 资产声明自己偏好的场景，例如 `quick`、`standard`、`deep`、`vision`。
- 用户在 `builtin-opencode.jsonc` 中把场景绑定到具体 opencode 模型标识。
- 场景可声明可选 fallback chain、能力要求和模型参数。
- 注册或调度阶段按固定优先级、可用性和能力约束解析出最终模型字段。
- 无法命中首选模型时按用户配置或用户显式允许的内置安全链路尝试替代模型。
- 仍无法解析时省略模型字段，让 opencode 使用当前会话默认模型，并在诊断中解释原因。

默认稳定场景为：

| 场景键 | 语义 | 典型用途 |
| ------ | ---- | -------- |
| `quick` | 低延迟、低成本、低风险文本任务 | 简短分类、格式转换、轻量摘要、路由判断 |
| `standard` | 默认通用文本任务 | 常规问答、普通代码阅读、常规计划和文档处理 |
| `deep` | 高复杂度文本推理任务 | 架构判断、复杂实现、关键审查、多约束规划 |
| `vision` | 图像识别和视觉理解任务 | 截图分析、Figma/页面视觉核对、图像内容说明 |

## 需求

**模型场景配置**
- R1. 系统应允许用户在 `builtin-opencode.jsonc` 的独立顶层模型场景节点中为稳定场景配置具体模型，而不是直接要求用户逐个配置技能、命令和代理 → 验收: 用户配置 `quick`、`standard`、`deep`、`vision` 等场景后，该配置能被模型场景解析逻辑读取；用户不需要理解每个内置资产的名称。
- R2. 默认模型场景应以用途命名，首批包含 `quick`、`standard`、`deep` 和 `vision` → 验收: 配置说明清楚解释每个场景的预期用途，且图像识别不被归入 `deep` 或 `standard`。
- R3. `builtin-opencode.jsonc` 中的模型场景配置应遵循三层优先级：项目级高于全局级，全局级高于插件级 → 验收: 三层同时配置同一场景时采用项目级；项目级缺失但全局级存在时采用全局级；两者都缺失但插件级存在时采用插件级；项目级允许新增或覆盖模型场景键，但不改变 `mcp` 的项目级限制。
- R4. 插件级配置层可以作为最低优先级承载层，但插件内置默认配置不应预置任何模型场景，避免插件替用户选择具体模型 → 验收: 仅安装 AE 且项目级、全局级、插件级都没有模型场景配置时，所有技能、命令和代理保持当前状态，继续使用 opencode 当前会话的默认模型。
- R5. 模型场景配置节点不得复用 `mcp` 的安全 overlay 规则 → 验收: 项目级配置允许新增或覆盖模型场景键；`mcp` 仍保持只能覆盖既有 MCP 安全字段的限制。
- R6. 系统应校验模型场景配置结构，避免误配被静默忽略 → 验收: 空模型值、非字符串模型值、配置结构错误或无法解析的 JSONC 都能被识别；无任何模型场景配置不视为错误。
- R7. 系统应将模型场景配置问题转化为可恢复中文反馈，而不是只在深层配置加载中抛出不可解释异常 → 验收: 用户能通过插件启动错误、诊断能力或帮助输出看到具体配置层级、场景键和错误原因；不会把无配置场景当作失败。
- R8. 系统应允许用户新增自定义场景键，但 AE 内置资产只依赖稳定场景键 → 验收: 配置中出现非内置场景键不会报错；文档说明自定义场景只对用户自定义资产或后续扩展有意义，AE 内置资产不会因为未知场景而改变行为。

**高级模型解析**
- R9. 每个场景应支持配置首选模型和有序 fallback chain → 验收: 首选模型不可用或不满足能力要求时，系统按用户声明顺序尝试 fallback；每次尝试都能记录失败原因和最终命中项。
- R10. fallback chain 应支持跨供应商候选模型，但不要求用户为每个资产单独配置 → 验收: 用户可在 `quick`、`standard`、`deep`、`vision` 等场景下声明多个供应商/模型候选；资产只声明场景即可继承该链路。
- R11. 场景模型配置应支持与模型选择强相关的运行参数，例如推理强度、token 预算或 temperature → 验收: 用户可为场景或 fallback 候选声明模型运行参数；最终解析结果能标记这些参数是可写入、仅特定路径可写入，还是仅用于诊断。
- R12. 场景模型配置应支持能力要求，例如视觉输入、长上下文或高推理能力 → 验收: 用户可为场景或 fallback 候选声明能力要求；能力要求参与候选过滤，并在失败或未知时进入诊断输出。
- R13. 系统应支持内置推荐 fallback chain 作为低优先级兜底，但默认不在零用户配置时参与 → 验收: 用户没有任何模型场景或兜底配置时，AE 继续继承 opencode 默认模型；只有用户显式启用内置兜底，或在场景配置中允许内置候选时，内置推荐链才参与解析。
- R14. 模型解析应区分“用户显式配置”“内置推荐兜底”“opencode 默认模型”三类意图来源 → 验收: 诊断中可以看到最终模型来自用户配置、内置推荐，还是因为无可用候选而继承默认模型。

**场景缺失与默认模型**
- R15. 任一模型场景缺失时，系统应先判断用户是否允许内置推荐兜底；允许时尝试该场景的内置推荐链，不允许时省略该资产的 `model` 字段并使用 opencode 当前默认模型 → 验收: 缺失 `quick`、`standard`、`deep` 或 `vision` 时，诊断能显示未配置、是否允许内置兜底、是否命中内置推荐；未允许兜底时显示继承默认模型。
- R16. 没有任何可用文本场景或允许的文本兜底时，系统应保持当前默认模型行为 → 验收: 三层配置和允许参与的内置推荐都未提供可用文本模型时，资产注册不写入模型字段，不阻断纯文本任务，并在诊断中说明继承默认模型。
- R17. `vision` 未配置且没有允许使用的可用视觉兜底时，明确需要图像输入或截图理解的路径不得把视觉判断当作已验证结论 → 验收: 截图分析、Figma 视觉核对、视觉设计验收等路径提示缺少可用视觉模型；若继续执行，只能作为非门禁参考或标记为未验证，不能用于通过视觉验收。
- R18. `vision` 已配置或命中允许的视觉兜底时，系统应验证候选模型是否满足已知视觉能力要求 → 验收: 已知不支持视觉的模型不会被静默用于视觉验收；能力未知模型只能产生非门禁参考结论，门禁级视觉验收必须使用已确认支持视觉的模型，除非用户显式确认接受未验证风险。
- R19. 系统应定义模型可用性判断的证据等级，避免注册期做有副作用的远程探测 → 验收: 诊断区分静态可解析、已知可用、供应商已连接、运行时失败等状态；注册期不得执行可能产生计费或网络副作用的模型试探调用。

**资产自动路由**
- R20. AE 内置资产应声明自己需要的模型场景，而不是硬编码具体模型名称 → 验收: 内置资产的模型选择可以随用户配置变化而变化；资产声明只表达场景偏好，不包含具体供应商或模型名。
- R21. 系统应覆盖所有内置命令、代理和可间接路由的技能路径，而不是只覆盖少数高置信资产 → 验收: 每个内置命令和代理都有明确路由状态：直接场景、间接场景、继承默认模型或不适用；没有未分类资产被静默遗漏。
- R22. 对没有直接 `model` 字段落点的技能，系统应尽可能通过命令包装、子代理、工具调度或后续子流程实现间接模型切换 → 验收: 诊断中能区分“直接应用场景”和“仅子流程应用场景”；无法直接写入模型字段的技能必须说明具体限制和影响范围。
- R23. 常规资产默认使用 `standard`，明显低风险/低复杂度的路由、摘要、格式化任务使用 `quick`，复杂推理、关键审查或跨文件综合任务使用 `deep` → 验收: 所有内置资产都有经过审查的默认场景映射，且复杂审查、规划、跨文件综合不会落到 `quick`。
- R24. 涉及截图、Figma 视觉核对、图像内容理解或设计视觉判断的资产应优先使用 `vision` 场景 → 验收: 浏览器截图分析、Figma 对齐、视觉设计验证等路径能引用 `vision` 场景；纯文本前端代码修改不必强制使用 `vision`。
- R25. 系统应支持根据任务输入动态细分路由，而不仅仅按资产静态分类 → 验收: 同一资产在轻量摘要、复杂架构审查、视觉验收等不同输入下可以选择不同场景；动态判断结果必须可解释。
- R26. 动态路由只在存在运行时模型选择入口的路径中直接生效；静态 `model` 字段路径只能使用注册期解析结果 → 验收: 诊断明确标记某资产支持动态切换、仅支持静态场景、仅支持子流程动态切换或不适用；不会声称无法动态切换的路径已完成动态路由。
- R27. 动态路由与用户资产级显式模型冲突时应遵循用户可配置的覆盖策略 → 验收: 用户可选择资产级模型绝对锁定、允许能力升级覆盖、或仅视觉/安全类强能力需求可覆盖；诊断显示本次采用的覆盖策略。

**用户控制与兼容性**
- R28. 用户显式配置的具体资产模型应优先于同一配置层级内的场景默认值，以保留高级覆盖能力 → 验收: 同一层级同时存在资产级 `model` 和场景默认值时，资产级 `model` 生效。
- R29. 跨配置层级解析时应先比较项目级、全局级、插件级优先级，再在同一层级内比较资产级模型和场景模型 → 验收: 项目级场景覆盖全局资产级模型；全局资产级模型覆盖插件级场景；该矩阵被文档化并有测试覆盖，避免全局资产模型静默覆盖项目级场景。
- R30. 用户应能选择是否启用内置推荐 fallback chain，以及内置兜底是否允许跨供应商 → 验收: 用户可以关闭内置兜底；关闭后系统只使用用户配置和 opencode 默认模型。
- R31. 配置文档应强调“场景键稳定、具体模型由用户环境决定”，但 AE 可以提供可覆盖的内置推荐链作为高级默认能力 → 验收: 用户可以配置任意 opencode 支持的模型标识；内置推荐链被标注为建议而非硬依赖。

**解析与可观察性**
- R32. 模型解析应产生可解释的来源信息，至少区分“项目级资产模型”“项目级场景”“全局资产模型”“全局场景”“插件级资产模型”“插件级场景”“内置推荐兜底”“opencode 默认模型” → 验收: 调试或诊断输出能说明某个资产最终为什么写入或没有写入 `model` 字段；用户能判断是配置缺失、层级覆盖、能力不满足、fallback 命中还是资产未声明场景导致的结果。
- R33. 模型解析优先级应稳定且文档化，避免规划或实现阶段引入隐式规则 → 验收: 解析顺序清楚表达为项目级资产模型、项目级场景、全局资产模型、全局场景、插件级资产模型、插件级场景、用户允许的内置推荐兜底、最后省略模型字段使用 opencode 默认模型。
- R34. 系统应提供场景配置诊断，展示当前有效场景映射、来源层级和是否允许内置兜底 → 验收: 用户无需阅读源码即可看到 `quick`、`standard`、`deep`、`vision` 当前是否配置、来自哪一层、是否允许内置推荐参与。
- R35. 系统应提供 fallback 与能力诊断，展示候选链路、能力要求、能力元数据状态和可用性证据等级 → 验收: 用户能看到每个候选为什么命中、跳过或降级，以及能力未知或元数据过期的风险提示。
- R36. 系统应提供内置资产路由总览，展示每个内置资产的静态默认路由和直接/间接应用状态 → 验收: 用户能区分静态默认路由和动态输入模拟结果；未提供任务输入时不把静态默认路由展示为最终模型。
- R37. 诊断应支持按资产名查询静态解析结果 → 验收: 用户输入某个内置命令或代理名后，诊断能返回声明场景、直接/间接应用状态、最终模型来源、fallback 尝试记录，以及未声明场景或继承默认模型的原因。
- R38. 诊断应支持按任务输入模拟动态解析结果 → 验收: 用户输入任务描述后，诊断能返回动态路由判断、匹配规则、置信度、覆盖策略和最终模型来源；输出明确这是模拟结果而非所有未来输入的保证。
- R39. 模型字符串解析应支持必要的规范化、别名和供应商候选匹配，但必须可解释、可关闭且不覆盖用户显式模型 → 验收: 解析结果展示原始输入、规范化结果、别名规则或供应商匹配规则；用户关闭该能力后按原始模型标识处理。

## 成功标准

- 当用户将 `quick` 绑定到低成本或低延迟模型、将 `deep` 绑定到强推理模型时，简单任务和复杂任务可以按用户意图自动分流。
- 用户只需要理解少量稳定用途场景，不需要审计所有 AE 技能、命令和代理。
- 视觉理解拥有独立配置入口，避免文本强模型被误用为视觉模型。
- 插件未配置任何模型场景且用户未显式启用内置兜底时，用户体验与当前默认模型行为一致。
- 现有用户显式模型配置不会被新增场景路由意外覆盖。
- 用户能够通过诊断解释任一内置命令或代理的静态默认模型来源，并能对具体任务输入模拟动态模型来源，而不是只能猜测注册结果。
- 模型不可用、供应商未连接或能力不满足时，系统能在无副作用证据边界内自动尝试允许的合理候选并解释最终选择。
- 同一资产面对不同任务输入时，在存在运行时模型选择入口的路径中可以在 `quick`、`standard`、`deep`、`vision` 等场景之间做可解释的动态切换；静态路径必须清楚标记限制。

## 范围边界

- 不要求 AE 管理 opencode 自身模型提供商认证、密钥、计费或远程账号连接。
- 不要求 AE 实时评测真实价格、速度或模型质量；价格/速度/质量语义来自用户配置、内置静态建议或已有能力元数据。
- 不要求 AE 保证所有第三方模型能力信息永远准确；能力未知或元数据过期时必须可诊断、可降级、可由用户覆盖。
- 不要求 AE 在第一阶段为每个资产暴露独立 UI；资产级覆盖可以先通过配置文件和诊断能力完成。
- 不要求改变 opencode 自身模型提供商、认证或模型解析机制。
- 不要求模型切换绕过 opencode 当前支持的 `model` 字段或会话机制；无法直接切换的路径必须明确标记为间接应用或不适用。

## 关键决策

- 使用用途场景命名: 比“强/中/弱”更能表达资产意图，也避免把速度、成本和质量混成一个轴。
- 单独设置 `vision`: 图像识别能力与文本推理复杂度正交，必须独立配置。
- 默认场景控制在四个: 先覆盖主要价值点，避免配置矩阵过大。
- 资产声明场景而非模型: 让内置资产保持可分发和可移植，用户配置负责绑定具体模型。
- 插件级可以提供可关闭的推荐链: AE 可以内置推荐 fallback，但必须低于用户配置，且零用户配置时默认不参与，避免替用户选择具体模型。
- 借鉴供应商回退链但不强制: 参考实现中的 fallback chain、可用性检查和能力约束是目标能力的一部分；AE 必须让它们受用户配置和诊断约束。
- 要求解析结果可解释: 参考实现会区分 override、category-default、provider-fallback、system-default；AE 也应让用户知道最终模型来自哪里，并解释每个 fallback 尝试。
