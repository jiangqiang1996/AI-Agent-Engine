# 模型场景路由配置

## 问题框架

AE 当前大量技能、命令和代理默认继承同一个模型，导致简单任务可能浪费高成本模型，复杂任务又可能拿不到足够强的推理能力。需要让用户只配置少量“用途场景”模型，AE 内置资产再按任务性质自动引用对应场景，而不是要求用户逐个理解并覆盖每个技能、命令或代理。

图像识别/视觉理解需要作为独立场景处理。它与文本任务复杂度不是同一个维度：一个模型可能很强但不支持图像输入，或视觉能力强但不适合作为通用深度编码模型。

## 推荐方向

采用“用途场景”命名，而不是“强/中/弱”或“快/中/慢”。默认稳定场景为：

| 场景键 | 语义 | 典型用途 |
| ------ | ---- | -------- |
| `quick` | 低延迟、低成本、低风险文本任务 | 简短分类、格式转换、轻量摘要、路由判断 |
| `standard` | 默认通用文本任务 | 常规问答、普通代码阅读、常规计划和文档处理 |
| `deep` | 高复杂度文本推理任务 | 架构判断、复杂实现、关键审查、多约束规划 |
| `vision` | 图像识别和视觉理解任务 | 截图分析、Figma/页面视觉核对、图像内容说明 |

## 需求

**模型场景配置**
- R1. 系统应允许用户在 `builtin-opencode.jsonc` 的独立顶层模型场景节点中为稳定场景配置具体模型，而不是直接要求用户逐个配置技能、命令和代理 → 验收: 用户配置 `quick`、`standard`、`deep`、`vision` 等场景后，AE 内置资产可通过场景间接获得模型；该节点不复用 `mcp` 的安全 overlay 规则。
- R2. 默认模型场景应以用途命名，首批包含 `quick`、`standard`、`deep` 和 `vision` → 验收: 配置说明清楚解释每个场景的预期用途，且图像识别不被归入 `deep` 或 `standard`。
- R3. `builtin-opencode.jsonc` 中的模型场景配置应遵循三层优先级：项目级高于全局级，全局级高于插件级 → 验收: 三层同时配置同一场景时采用项目级；项目级缺失但全局级存在时采用全局级；两者都缺失但插件级存在时采用插件级；项目级允许新增或覆盖模型场景键，但不改变 `mcp` 的项目级限制。
- R4. 插件级配置层可以作为最低优先级承载层，但插件内置默认配置不应预置任何模型场景，避免插件替用户选择具体模型 → 验收: 仅安装 AE 且项目级、全局级、插件级都没有模型场景配置时，所有技能、命令和代理保持当前状态，继续使用 opencode 当前会话的默认模型。
- R5. 系统应校验模型场景配置并提供可观察反馈，避免误配被静默忽略 → 验收: 未知场景键、空模型值、非字符串模型值、配置结构错误或无法解析的 JSONC 都能产生明确中文提示；无任何模型场景配置不视为错误。

**场景缺失与默认模型**
- R6. 任一模型场景缺失时都不从其他场景自动降级或升级，而是省略该资产的 `model` 字段并使用 opencode 当前默认模型 → 验收: `quick`、`standard`、`deep` 或 `vision` 任一场景未配置时，声明该场景的资产不写入 `model` 字段；不出现 `quick` 自动升级到 `standard`、`standard` 自动升级到 `deep`、`deep` 自动降级到 `standard` 等跨场景替代行为。
- R7. 没有任何可用文本场景时，系统应保持当前默认模型行为 → 验收: 三层配置均未提供可用文本场景时，资产注册不写入模型字段，也不报错。
- R8. `vision` 缺失时只在明确需要图像输入或截图理解的路径提示用户，纯文本前端代码修改不提示 → 验收: 截图分析、Figma 视觉核对、视觉设计验收等路径提示 `vision` 未配置并标记视觉能力不保证；不需要图像输入的前端实现路径继续按文本场景或默认模型执行。

**资产自动路由**
- R9. AE 内置资产应声明自己需要的模型场景，而不是硬编码具体模型名称；技能若没有直接模型字段落点，应通过其触发的命令、代理或子流程间接应用场景 → 验收: 内置资产的模型选择可以随用户配置变化而变化；无法直接写入模型字段的技能不会被规划阶段强行实现为不存在的配置能力。
- R10. 常规资产默认使用 `standard`，只有明显低风险/低复杂度的路由、摘要、格式化任务才使用 `quick`，只有复杂推理、关键审查或跨文件综合任务才使用 `deep` → 验收: 规划阶段能先为少数高置信资产给出默认场景映射，其余资产保持默认模型或 `standard`，且不会把所有资产都升级到 `deep`。
- R11. 涉及截图、Figma 视觉核对、图像内容理解或设计视觉判断的资产应优先使用 `vision` 场景 → 验收: 浏览器截图分析、Figma 对齐、视觉设计验证等路径能引用 `vision` 场景；纯文本前端代码修改不必强制使用 `vision`。

**用户控制与兼容性**
- R12. 用户显式配置的具体资产模型应优先于场景默认值，以保留高级覆盖能力 → 验收: 同一配置层级内，资产级显式 `model` 高于场景默认值；跨层级时仍遵循项目级高于全局级、全局级高于插件级，避免全局资产模型覆盖项目级场景配置。
- R13. 配置文档应强调“场景键稳定、具体模型由用户环境决定”，不把某个供应商模型写成所有用户必须使用的默认前提 → 验收: 用户可以配置任意 opencode 支持的模型标识，AE 不把特定供应商作为硬依赖。

## 成功标准

- 简单任务可以自动使用更便宜或更快的模型，而复杂任务可以使用更强模型。
- 用户只需要理解少量稳定用途场景，不需要审计所有 AE 技能、命令和代理。
- 视觉理解拥有独立配置入口，避免文本强模型被误用为视觉模型。
- 插件未配置任何模型场景时，用户体验与当前默认模型行为一致。
- 现有用户显式模型配置不会被新增场景路由意外覆盖。

## 范围边界

- 不要求插件内置默认绑定任何具体模型；插件级默认应为空，以免替用户选择供应商或模型。
- 不要求第一阶段为每个内置资产暴露独立模型配置项；资产级覆盖仅作为用户已有显式配置的优先级保护。
- 不要求运行时自动评测模型质量、速度或价格；场景到具体模型的选择由用户负责。
- 不要求 AE 检测某个模型是否真实支持图像输入；视觉场景缺失或能力不确定时应给出清晰提示，并继续使用 opencode 当前默认模型。
- 不要求改变 opencode 自身模型提供商、认证或模型解析机制。
- 不要求第一阶段完成所有内置资产的全量分类；优先覆盖视觉路径、关键审查/综合任务和轻量路由等高置信资产。

## 关键决策

- 使用用途场景命名: 比“强/中/弱”更能表达资产意图，也避免把速度、成本和质量混成一个轴。
- 单独设置 `vision`: 图像识别能力与文本推理复杂度正交，必须独立配置。
- 默认场景控制在四个: 先覆盖主要价值点，避免配置矩阵过大。
- 资产声明场景而非模型: 让内置资产保持可分发和可移植，用户配置负责绑定具体模型。
- 插件级默认不配置模型场景: AE 不应默认替用户选择具体模型；没有任何场景配置时保持当前继承默认模型的行为。

## 依赖 / 假设

- 已核对现有代码：`src/services/agent-registration.ts` 会从内置代理 Markdown 构建 agent 配置，并保留用户已有 `config.agent` 覆盖。
- 已核对现有代码：`src/services/command-registration.ts` 会从 catalog 和命令文件生成 command 配置，并保留用户已有 `config.command` 覆盖。
- 已核对现有配置：`src/services/builtin-opencode-config-service.ts` 已支持三层 `builtin-opencode.jsonc` 加载与字段合并，可作为新增模型场景配置的承载方向。
- 已核对现有配置：`src/services/builtin-opencode-config-service.ts` 对 `mcp` 有项目级安全 overlay 限制；模型场景必须使用独立于 `mcp` 的合并和校验规则。
- 假设 opencode 的 agent 或 command 配置支持 `model` 字段；skill 是否有直接模型字段落点留给规划阶段基于实际 API 校验，若不支持则通过命令、代理或子流程间接应用。
