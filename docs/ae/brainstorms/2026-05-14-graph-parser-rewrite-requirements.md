# 知识图谱解析重构需求

## AI 解析契约
- canonicalKind: requirements
- humanEquivalent: true
- stableIdsRequired: true
- noImplicitScope: true

## 问题框架
现有知识图谱生成逻辑以文件级浅层正则解析为主，会把 AE 插件提示词中的技能、命令、工具、代理名称解析成资产引用关系。这类关系会污染通用项目图谱，并且当前模型无法表达文件内部节点、文件与内部节点、跨文件内部节点调用等更细粒度关系。

本次目标是彻底重构知识图谱生成能力，使图谱从“文件关系快照”升级为“通用代码与文本结构图谱”：既能保留文件与文件之间的引用关系，也能表达文件主体与内部语义节点之间的关系，以及跨文件语义节点之间的调用、继承、实现、引用等关系。重构成本、旧 schema 兼容和旧图谱数据迁移不作为限制。

## 需求

**解析范围与噪声移除**
- R1. 图谱生成逻辑必须移除 AE 提示词资产引用解析，不再把 `ae:skill`、`ae-command`、`/ae-command`、工具名或代理名解析成 `ae_ref`、`asset` 节点或同等语义关系 → 验收: 在 `src/assets/skills/**/*.md`、`src/assets/commands/**/*.md`、`src/assets/agents/**/*.md` 中出现 AE 技能、命令、工具、代理名称时，生成结果只保留真实文件/文本关系，不生成 AE 资产节点或 AE 资产关系。
- R2. 图谱仍必须解析常规文本文件引用关系，包括 Markdown 链接、引用式链接、相对路径、根路径和可解析的文档到文档或文档到代码文件引用 → 验收: Markdown 文档中的本地链接能解析到工作区内目标文件；外部 URL 不作为内部文件关系。

**文件级关系**
- R3. 图谱必须支持文件与文件之间的关联关系，包括源码 import/include/require/use/package/module 引用、文本链接、配置引用和可解析的相对路径引用 → 验收: 查询单个文件依赖时能返回内部目标文件、外部依赖标记、关系类型、来源位置和解析置信度。
- R4. 文件级关系必须比现有正则解析更准确，避免把正则字面量、关键字、类型导入片段或代码文本误判为依赖 → 验收: 现有 `graph-parse-service` 中暴露的误报模式不再出现在图谱关系中，例如把 `{`、`type`、正则片段解析成外部依赖。

**文件内部节点**
- R5. 图谱必须表示文件主体与内部节点之间的包含关系，内部节点至少包括模块/包、类、接口、枚举、函数、方法、构造器、字段或变量声明中能被解析器稳定识别的项目 → 验收: 查询文件详情时能返回该文件内的主要内部节点、节点类型、名称、稳定 ID、源码位置范围和父子层级。
- R6. 内部节点 ID 必须在同一文件内容未变时保持稳定，并能区分同名重载、同名嵌套节点或不同作用域节点 → 验收: 同一文件内两个同名方法或嵌套函数不会合并为同一节点；重复构建后 ID 保持一致。
- R7. 图谱必须定义统一节点标识模型，能无歧义区分文件节点、内部节点、外部依赖节点和未解析候选节点 → 验收: 查询接口可用全图唯一节点 ID 定位节点；内部节点结果同时返回所属文件路径、本地节点路径或符号路径；文件重命名、同名节点、重载和嵌套节点的 ID 稳定边界有明确说明。

**跨文件内部节点关系**
- R8. 图谱必须支持文件 A 中函数或方法节点到文件 B 中函数或方法节点的调用关系 → 验收: Java 中 `A.a()` 调用 `B.b()` 时，图谱能表达 `A` 文件中的 `a` 方法节点到 `B` 文件中的 `b` 方法节点的 `call` 关系，并保留调用位置。
- R9. 图谱必须支持类型结构关系，包括类继承、接口实现、类型引用和构造调用 → 验收: 最小样例能分别产生 `extends`、`implements`、`type_reference` 和 `construct` 或同等语义关系；无法精确解析时不得标记为确定关系。
- R10. 图谱必须支持字段、属性或变量引用关系，但允许在动态语言中以候选关系表达 → 验收: 静态可解析样例能产生字段/属性/变量引用关系；动态或无法绑定目标的样例以 `candidate` 或 `unresolved` 返回。
- R11. 当跨文件内部节点无法精确解析时，图谱必须降级到可解释的候选关系，而不是静默丢失或伪造确定关系 → 验收: 查询结果能区分 `resolved`、`candidate`、`unresolved` 或同等置信度状态，并说明无法精确解析的原因类别。

**语言与格式覆盖**
- R12. TypeScript/JavaScript 必须覆盖模块导入、导出函数/类/方法节点、命名导入函数调用、默认导入函数或类构造调用；动态属性调用可降级为候选或未解析 → 验收: TS 和 JS 各有样例测试，输出文件关系、内部节点、至少一个跨文件 `call` 或 `construct` 关系和置信度。
- R13. Java 必须覆盖 package/import、类/接口/枚举、方法/构造器/字段节点、跨文件直接方法调用、类继承、接口实现和构造调用 → 验收: Java 样例测试能精确解析 `A.a()` 到 `B.b()` 的调用，并至少覆盖一个继承或实现关系。
- R14. Python 必须覆盖 import/from-import、模块级函数、类、方法节点、`from module import func` 后的直接函数调用和类构造调用；动态调用可降级为候选或未解析 → 验收: Python 样例测试输出文件关系、内部节点、一个跨文件直接函数调用关系和无法绑定动态调用的降级结果。
- R15. Go 必须覆盖 package/import、函数、方法、结构体节点、跨包函数调用和同包方法调用；接口动态分派可降级为候选或未解析 → 验收: Go 样例测试输出文件关系、内部节点、一个跨文件函数调用关系和一个方法调用关系。
- R16. Markdown 和常见文本文件必须覆盖本地链接、引用式链接、相对路径、根路径和外部 URL 标记；不解析自然语言中的 AE 技能或命令名称为资产关系 → 验收: Markdown 样例测试覆盖文档到文档、文档到代码文件、外部 URL 和代码块中的非关系文本。
- R17. 图谱架构必须面向主流编程语言和常见文本文件格式扩展，允许不同语言解析深度不同，但必须通过统一节点、关系和置信度模型呈现 → 验收: 新增语言解析器不需要改写存储核心或查询核心，只需注册语言解析能力和映射规则。

**查询与使用体验**
- R18. 查询能力必须支持文件级视图，输入文件路径后返回该文件依赖的内部文件、外部依赖、关系类型、位置、置信度和截断信息 → 验收: 用户能查询“某文件依赖哪些文件”，并能区分完整结果和截断结果。
- R19. 查询能力必须支持文件内部结构视图，输入文件路径后返回内部节点树或节点列表 → 验收: 输出包含节点 ID、节点类型、名称、父节点、位置范围和所属文件。
- R20. 查询能力必须支持节点依赖和节点影响范围，输入节点 ID 后返回该节点直接依赖、直接调用、被引用或被调用的节点和文件 → 验收: 用户能查询“某方法调用了哪些方法”和“哪些节点影响某节点”，结果包含方向、关系类型和置信度。
- R21. 查询能力必须支持文件到文件、文件到节点、节点到文件和节点到节点的路径查询 → 验收: 路径结果以节点数组和关系数组表达混合路径，并标注是否包含候选关系、是否被截断、搜索成本或深度限制。
- R22. 图谱输出必须保留足够证据用于审查和调试，包括 source/target 节点、关系类型、位置范围、解析器来源、置信度、外部/内部标记和 unresolved 原因 → 验收: 任一关系都能追溯到文件路径、行列范围或明确的解析来源；无法定位时必须标注而不是假装有精确位置。

**构建与兼容边界**
- R23. 本次允许破坏性重构图谱存储 schema、构建流程和查询接口，不要求兼容旧版本图谱数据或旧 `ae_ref` 语义 → 验收: 旧图谱数据可被明确判定为不兼容并提示重建；不需要迁移旧 schema。
- R24. 图谱构建必须在 Windows x64、Linux x64、macOS x64 和 macOS arm64 上保持可运行；支持的 Node.js 版本以项目 package 与 CI/文档声明为准 → 验收: 支持平台上的依赖安装、构建和测试不依赖用户手工本机编译步骤。
- R25. 解析器不可用、文件超大、语法错误或语言不支持时必须有结构化降级结果，且不得用降级绕过必选语言在支持平台上的验收 → 验收: 必选语言样例测试在支持平台上不得因解析器不可用被跳过；非必选语言或异常文件必须返回降级状态和原因。

## 非功能需求
- NFR1. 准确性优先于保留旧行为 → 验收: 删除 AE 资产引用和减少误报比兼容旧查询结果更重要。
- NFR2. 可扩展性优先于一次性硬编码 → 验收: 语言解析器、文本解析器、关系解析器和查询展示应有清晰边界，新增语言不需要复制核心流程。
- NFR3. 性能必须适合中型仓库使用 → 验收: 以 1,000 个可解析文本/代码文件作为最小基准，全量构建目标为 60 秒内完成，典型查询目标为 5 秒内返回；若环境差异导致无法满足，必须输出耗时、文件数、节点数、关系数、失败数、跳过数、结果上限、截断标记和搜索成本，供规划阶段调整索引或降级策略。
- NFR4. 运行时独立性必须保持 → 验收: 图谱运行时代码不能依赖本源码仓库布局；解析器资源和内置资产必须能随插件分发结构定位。

## 成功标准
- 不再出现 AE 提示词资产引用污染图谱。
- 图谱能同时回答文件级、文件内节点级和跨文件节点级关系问题。
- Java 方法调用示例 `A.a()` 到 `B.b()` 能被精确解析；动态语言无法精确绑定的调用能可解释降级。
- TS/JS、Java、Python、Go、Markdown 均有按语言矩阵定义的可验证样例测试。
- 查询结果能清楚区分已解析、候选和未解析关系。

## 范围边界

### 范围内
- 彻底重构图谱生成逻辑、存储模型和查询能力。
- 移除 AE 技能、命令、工具、代理引用解析。
- 引入通用 AST 或语法解析器策略，尽可能覆盖主流语言和常见文本格式。
- 支持文件节点、内部节点、文件到文件关系、文件到内部节点关系、内部节点到内部节点关系。
- 为必选语言和格式补充测试。

### 范围外
- 兼容旧图谱 schema 或迁移旧图谱数据。
- 保留 AE 资产图谱或 AE 提示词专项依赖分析能力。
- 把注释中的任意自然语言描述解析成确定调用关系。
- 对所有主流语言达到同等深度的符号解析精度。
- 执行运行时动态分析、真实编译器类型检查或跨进程运行时调用追踪。

### 约束
- 跨平台是硬约束；安装体积不是首要约束，但解析器选型仍需记录依赖体积、平台覆盖、安装失败降级和维护成本。
- 允许破坏性重构内部接口。
- 面向插件用户的运行时能力不得依赖本仓库专用路径或开发态配置。

## 关键决策
- D1. 采用“彻底重构”而非局部修补 → 理由: 当前以文件路径字符串和正则关系为核心的模型无法自然表达内部节点与跨节点关系。
- D2. 删除 AE 资产引用解析，不保留开关，也不在本次保留 AE 资产专项图谱 → 理由: 知识图谱应表达通用项目关系，AE 提示词资产引用属于插件内部提示词噪声；本次接受失去该专项诊断能力。
- D3. 解析器策略以跨平台和覆盖面为优先，安装体积不作为首要约束 → 理由: 用户明确认为包数量和源码体积不是主要问题，但插件需要跨平台可运行；依赖体积和维护成本仍需在规划中显式比较。
- D4. 推荐在规划阶段优先评估纯 JS/WASM 或跨平台预构建解析器方案，并允许多解析器后端共存 → 理由: 单一原生解析器方案可能带来平台兼容风险，多后端可在覆盖面和可靠性之间取得平衡。
- D5. 允许旧图谱不兼容并要求重建 → 理由: 新模型需要表达节点层级、位置、置信度和跨节点关系，旧 schema 兼容会显著拖累模型设计。

## 依赖 / 假设

### 依赖
- 后续规划需要评估可用的多语言 AST/语法解析器生态及其跨平台分发方式。
- 后续规划需要定义新图谱 schema、索引策略和查询接口。

### 假设
- 用户接受新增依赖和较大范围重构，只要最终跨平台且解析能力更强。
- 不要求所有语言在第一版达到 Java 级别的调用解析深度，但必选语言必须满足各自最小验收矩阵，架构必须支持后续增强。
