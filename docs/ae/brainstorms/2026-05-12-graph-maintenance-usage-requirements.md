# 图谱维护与使用增强需求

## AI 解析契约
- canonicalKind: requirements
- humanEquivalent: true
- stableIdsRequired: true
- noImplicitScope: true

## 问题框架
当前文件关系图谱已支持浅层依赖解析、active version、JSON 分片、基础依赖/影响/健康查询，但对后续 AI 任务的帮助仍偏底层：查询结果主要是文件和边，缺少能快速理解项目结构的摘要、模块语义、入口识别、关系解释和按需加载策略。目标是让图谱成为接手项目、规划修改、评估影响范围时的优先上下文入口，在减少读取源码 token 的同时保持构建和查询性能可控。

已验证的当前边界：`src/tools/ae-graph-build.tool.ts` 描述首版仅支持 `depth=shallow`；`src/services/graph-parse-service.ts` 使用正则解析 import/require/include、Markdown 链接和 AE 资产引用；`src/services/graph-storage-service.ts` 使用 `schemaVersion: 2`、active version 和固定阈值 JSON 分片；本次 `ae-graph-query mode:stats` 返回“图谱存储文件格式不受支持”，说明查询侧还需要存储格式诊断和恢复体验。

## 需求

**图谱价值密度**
- R1. 图谱必须提供面向 AI 快速接手的项目结构摘要，而不只是文件和边列表 → 验收: 查询入口能分别返回目录/模块级概览、核心入口、主要关系类型、孤立区域和建议优先阅读清单；默认摘要结果不超过 20 个条目，并能作为后续任务上下文使用。
- R2. 图谱必须记录可追溯的文件和目录提示信息，帮助判断“这个文件为什么重要” → 验收: 文件或目录节点可暴露所属模块、入口/测试/配置/文档等角色标签、引用热度和摘要来源；自然语言职责摘要缺失时返回空值或降级标记，不得把低置信启发式伪装成事实摘要。
- R3. 图谱必须支持从任务目标反推最小上下文包 → 验收: 文件、目录、关键词、变更范围四类输入分别有明确输出；默认返回不超过 10 个推荐阅读文件、10 条直接依赖或上下游关系、5 个相关文档，并标注可延迟读取项。
- R4. 图谱必须区分关系的类型、来源和置信度，使 AI 能判断关系是否可靠 → 验收: 查询结果能显示关系来源是 import、require、Markdown 链接、AE 资产引用、配置引用、测试覆盖关系或推断关系，并包含解析方式、行号或置信度。

**分层图谱与查询体验**
- R5. 图谱必须按使用场景提供分层结果，避免每次查询加载完整明细 → 验收: 至少支持摘要层、模块层、文件关系层和可选深度层的查询语义；默认返回摘要或 top-N，只有用户或技能需要时才展开详细边。
- R6. 图谱查询必须面向常见任务提供预设模式 → 验收: 支持“接手项目”“修改前影响评估”“找入口”“找测试”“找配置”“找文档”“审查风险区”“理解某目录”等高层查询意图，并返回结构化结果而非要求调用者组合多个底层模式。
- R7. 图谱使用说明必须指导后续技能先用图谱再读源码，并定义禁止依赖图谱的降级条件 → 验收: 相关技能或规则能说明何时查询图谱；当 schema 不支持、scope 不匹配、图谱构建时间早于关键文件修改、当前 Git diff 未覆盖、置信度低或存储损坏时，必须读取真实文件或先重建图谱，且不把图谱替代测试、类型检查或源码确认。

**维护、增量和恢复**
- R8. 图谱维护必须能发现并解释存储不可用、过期或分片缺失状态 → 验收: 当 `graph.json` schema 不支持、active version 缺失、manifest 缺失、chunk 缺失或分片格式错误时，查询返回可恢复诊断，说明可执行的重建或修复路径。
- R9. 图谱增量更新必须在可证明安全的场景保持关系正确，并在高风险场景降级全量 → 验收: 普通修改会刷新该文件旧边；删除会移除节点和相关边；引用目标修改会刷新引用方；Git 可确认的重命名会迁移路径或触发全量；新增/删除/重命名等结构性变更无法保证正确时必须显式全量重建。
- R10. 图谱必须支持按 scope 管理多个目标范围且结果可解释 → 验收: 构建和查询返回 scope、active version、文件数、关系数、分片摘要和排除规则摘要；不同 scope 的 manifest、active version、分片目录和索引不得互相覆盖；scope 不匹配时提示应使用哪个 target、可选 scope 列表或如何重建。

**性能与 JSON 分片**
- R11. 图谱存储必须让查询按需读取分片，避免为了小查询加载完整图谱 → 验收: 单文件依赖、影响范围、目录概览、stats/core 等查询只读取必要索引或相关分片；默认小范围查询读取分片数不超过 3 个或给出超过原因；结果中报告读取的分片数量或使用的索引。
- R12. JSON 分片必须有稳定 manifest、索引和异常诊断，支撑大仓库可恢复读取 → 验收: manifest 描述 schema、版本、scope、chunk 列表、文件/关系计数、校验信息、索引位置和生成时间；缺失、不一致或校验失败时，查询返回具体问题位置和重建/修复建议，不静默返回不完整结果。
- R13. 图谱构建必须在性能和详细度之间提供明确档位 → 验收: 构建参数或配置能表达 shallow、semantic、deep 等层级或等价能力；默认 shallow 档不执行高成本语义生成；semantic/deep 档必须说明可能增加的耗时、缓存产物和适用场景。
- R14. 图谱必须控制输出 token 体积 → 验收: 查询默认返回摘要、计数、top-N 和可继续展开的游标/路径；默认结构化输出不超过 80 条结果项；大结果必须截断并说明如何继续查询，不直接输出完整大图。

**阶段化交付**
- R15. “所有方案并行”必须表现为路线图并行，而不是首期一次性交付所有能力 → 验收: 后续计划至少拆为 MVP、增强层和深度层；MVP 覆盖存储诊断恢复、摘要/top-N、现有浅层关系的按需查询和图谱优先使用说明；语义摘要、deep 层、复杂多 scope 优化和高级预设意图可作为后续阶段。

## 非功能需求
- NFR1. 运行时独立性必须保持不变 → 验收: 面向插件用户的图谱能力只依赖当前工作区、`docs/ae/graphs/` 产物和可选用户配置，不要求目标项目具备本仓库源码结构。
- NFR2. 构建和查询必须安全处理路径与敏感文件 → 验收: 不越过当前 worktree，不跟随越界符号链接，默认排除敏感文件，并在保存排除规则前获得工具权限。
- NFR3. 图谱结果必须区分事实、推断和摘要 → 验收: 由源码关系解析得到的事实、由规则推断得到的关系、由摘要生成得到的说明分别标注来源或置信度。
- NFR4. 新格式必须具备兼容或清晰迁移路径 → 验收: 旧 schema、未知 schema 或损坏存储不会导致不可解释失败；查询返回重建、迁移或清理建议。

## 成功标准
- 后续 AI 接手一个项目时，能够先通过图谱得到高价值结构上下文，再选择少量关键文件阅读，而不是全盘搜索和读取。
- 修改前影响分析能更快定位直接相关文件、间接影响区、测试文件和配置入口。
- 大仓库中查询小范围信息时，不需要加载完整图谱和全部分片。
- 图谱损坏、过期或格式不匹配时，用户能得到明确可恢复提示。

## 范围边界

### 范围内
- 图谱构建、维护、查询技能的需求定义。
- 图谱详细度、语义价值、查询体验、性能、分片和恢复行为。
- 后续技能如何使用图谱减少 token 的工作流要求。

### 范围外
- 不要求生成可视化 UI。
- 不要求一次性实现完整语言 AST 或符号级调用链。
- 不要求图谱替代真实源码阅读、测试、类型检查、构建或浏览器验收。
- 不要求默认调用外部 LLM 为所有文件生成自然语言摘要。

### 约束
- 默认实现必须保持低成本、可恢复和可解释；高成本深度能力应可选。
- 公开技能和工具说明不得把本仓库结构写成下游项目的通用前提。
- JSON 分片方案必须支持本地文件系统和版本化快照，不依赖外部数据库服务。

## 关键决策
- D1. 采用“所有方案并行”的分层组合路线图，而不是首期一次性交付所有能力 → 理由: 单独做语义增强会受大仓库性能限制，单独做存储性能又不能提升 AI 理解价值；分层路线图能同时保留方向完整性和计划可收敛性。
- D2. 默认先交付高价值摘要和按需展开，而不是完整深度 AST → 理由: 当前图谱价值瓶颈是 AI 可用信息密度和查询体验，深度解析应作为可选层逐步引入。
- D3. 将存储诊断和恢复作为核心需求 → 理由: 当前查询已暴露“图谱存储文件格式不受支持”，如果不可恢复，图谱优先规则会降低而非提高效率。

## 依赖 / 假设

### 依赖
- 依赖现有 `ae:graph-build` 和 `ae:graph-query` 作为入口语义。
- 依赖 `docs/ae/graphs/` 作为当前本地 JSON 图谱产物位置。

### 假设
- 后续规划可以决定具体 schema、索引和分片布局，本需求只要求行为和验收结果。
- 深度语义摘要可以先通过规则和结构启发式实现，之后再考虑可选 LLM 摘要或语言服务增强。
