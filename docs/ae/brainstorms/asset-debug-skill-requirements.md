# 资产调试技能

## 问题框架

用户在 opencode 会话中使用技能、工具、代理、命令或规则等资产执行任务后，可能发现代理的实际执行路线偏离资产原本意图。用户通过对话纠正后虽然完成了当前任务，但原始资产没有被修复，下一次仍可能重复同样偏差。

“资产调试”技能要把这种一次性的会话纠偏转化为可持久化的资产修复：对比资产标准流程与当前会话中的实际执行逻辑，识别偏差点，生成修复方案，并在安全边界内更新项目级资产或创建项目级覆盖资产。首版优先服务普通 opencode 项目中的自然语言资产；本仓库源码维护场景作为扩展要求处理，不能污染通用用户侧流程。

## 需求

**入口与资产识别**
- R1. 新技能应提供独立入口，建议命名为 `ae:asset-debug`，用于修复 opencode 当前会话中生效资产的执行流程偏差。 → 验收: 用户能通过技能名或对应命令触发该流程，并理解其适用场景是“任务完成后修复导致偏航的原始资产”，不是普通代码调试或执行审查。
- R2. 用户传入资产名时，技能必须定位该资产在当前会话中的生效定义与来源层级。 → 验收: 对技能、代理、命令、规则等首版自然语言资产，输出能说明识别到的资产类型、项目级或全局来源、是否存在项目级覆盖以及被分析的标准定义来源；工具、hook、service、schema 等代码实现资产首版只做诊断和修复建议，除非运行在本仓库源码维护场景且规划已显式授权代码修改。
- R3. 用户未传入资产名时，技能应优先从当前会话历史中识别候选资产；自动选择必须满足最低证据门槛，无法满足时必须要求用户确认或手动指定。 → 验收: 自动识别至少具备触发入口、实际调用链或用户确认的纠偏对象之一；存在多个候选资产、候选证据不足、工具调用历史不可用或会话历史不可用时，技能不会擅自修改资产，而是要求用户提供资产名、偏航实际行为、纠偏后的期望行为和相关消息片段摘要。

**偏差分析**
- R4. 技能必须对比资产标准执行流程与当前会话实际执行逻辑，形成明确偏差清单。 → 验收: 偏差清单至少包含标准预期、实际行为、纠偏对话证据、影响范围和推荐修复层级；当会话证据不足时，偏差分析必须基于用户提供的结构化纠偏摘要并标注证据置信度。
- R5. 技能必须区分“提示词/定义层面的调整”和“服务代码层面的逻辑调整”。 → 验收: 对每个偏差点，技能能标注更适合修改 SKILL.md、agent/command/rule 文本、工具描述，还是需要修改工具、服务、schema、selector 等代码逻辑。
- R6. 技能必须考虑 SKILL.md 与代码的双重决策机制。 → 验收: 当资产行为同时由自然语言指令和 TypeScript 服务逻辑决定时，技能会先识别运行时权威来源、字段一致性要求和可能的有意双轨差异；无法裁决时输出人工决策项，不自动同步修改代码。

**修复执行**
- R7. 对项目级自然语言资产，技能可在用户授权的当前工作空间内直接修改。 → 验收: 项目级 `SKILL.md`、agent、command、rule 等文件可被更新；修改前后必须使用仓库相对路径报告变更范围，并说明是否属于首版可自动修复范围。
- R8. 对全局纯自然语言资产，技能不得修改全局文件；只有在该资产类型的项目级覆盖路径和优先级已验证时，才可在当前项目中创建同名项目级资产覆盖全局资产。 → 验收: 全局技能、代理、命令或规则若仅由文本定义，修复结果是在当前项目下生成覆盖资产，并附带该资产类型的发现路径、冲突判定、生效优先级和覆盖验证方式；若覆盖机制无法验证，则只输出诊断和人工修复建议。
- R9. 对全局代码实现资产，技能不得修改全局代码，首版也不得承诺自动复刻并覆盖其行为。 → 验收: 工具、hook、service、schema 或插件代码等全局代码资产只输出偏差诊断、最小补丁建议、风险说明和人工迁移路径；只有后续版本在明确支持矩阵、权限边界、覆盖机制和验证标准后，才可考虑项目级脚本或 tools 复刻。
- R10. 首版不得默认把纯自然语言资产升级为脚本或 tools 混合形态；升级只能作为规划后的增强项。 → 验收: 当文本修正足够时，只生成最小文本补丁；当偏差来自流程易错、状态判断复杂或需要可验证证据时，技能可提出升级建议，但不在首版自动新增可执行脚本或工具。
- R11. 修改资产时必须检查当前工作空间内所有引用该资产的入口、目录、帮助文本、命令模板、转发逻辑和测试是否受到影响，并同步修复必要引用。 → 验收: 每次修复都输出“引用影响检查”结果，列出已检查的引用点、受影响项、同步修改项和无需修改的理由；若资产逻辑变更会影响调用约定、参数提示、命令别名、catalog、帮助输出或测试断言，必须同步更新，不能只修改资产本体。

**安全与边界**
- R12. 技能禁止直接修改当前工作空间以外的任何资产。 → 验收: 对全局资产、用户主目录、外部插件安装目录或其他项目目录，只允许读取必要定义并创建当前项目覆盖，不执行写入；所有读写目标必须解析规范化真实路径并确认位于当前工作空间根目录内，拒绝路径穿越以及会导致写入工作空间外的符号链接、junction 或等价链接。
- R13. 技能必须保护用户未授权变更和并发工作。 → 验收: 修复前检查目标文件当前状态并记录基线哈希或等价证据；写入前重新校验基线未变化；遇到无关已有修改或并发变化时不回滚、不覆盖，若同一文件存在冲突则要求用户决定。
- R14. 技能读取和报告资产定义时必须最小化敏感信息暴露。 → 验收: 不读取 `.env`、私钥、凭证文件或任意用户主目录敏感文件；输出前脱敏绝对路径、token、密钥、cookie、认证头、个人目录和私有 URL，只展示最小必要片段或摘要。
- R15. 技能必须在修复后执行或给出验证协议。 → 验收: 最终输出包含资产识别结果、偏差清单摘要、已修改或创建的项目级资产、修复前失败样例、修复后同样输入的期望行为、可执行验证命令或复现实验；无法自动验证时必须标注剩余风险和人工验收方式。

## 成功标准

- 用户在一次会话中纠正过的执行路线偏差，可以被转化为资产级修复，降低下次同类任务重复偏航的概率。
- 技能能安全处理项目级和全局资产差异：项目级自然语言资产可直接改；全局自然语言资产仅在覆盖机制已验证时创建当前项目覆盖；全局代码资产首版只诊断和给出人工迁移建议，不越界写入。
- 修复建议不会只停留在“改提示词”，而能明确识别哪些偏差需要同步调整服务代码、工具描述、schema 或选择逻辑。
- 技能修复不会造成引用漂移：凡是入口、命令、帮助、catalog、转发模板或测试仍引用旧逻辑的地方，都应被识别并同步处理或明确说明不受影响。
- 当无法可靠识别资产或无法安全修改时，技能会停止并要求用户确认，而不是猜测或静默改错对象。

## 范围边界

- 当前目标是新增“资产调试”技能及其必要的注册、目录、命令和帮助入口；首版不新增 TypeScript 工具或可执行脚本，除非规划阶段证明文本资产修复无法满足最低验收且用户明确授权增强范围。
- 首版通用用户侧范围限于技能、代理、命令、规则等自然语言资产的诊断、文本修复和项目级覆盖；工具、hook、service、schema 等代码资产默认只输出建议。
- 本仓库源码维护场景可额外同步 `SKILL`、`COMMAND`、`ae-catalog.ts`、命令注册和帮助输出，但必须标注为插件源码仓库开发语境，不作为下游项目通用前提。
- 对任何资产逻辑变更，引用影响检查属于修复的一部分；不得把引用点同步留给后续人工猜测。
- 不提供跨项目或全局资产的直接写入能力。
- 不保证自动修复所有资产偏差；当偏差涉及外部工具、模型行为或权限限制时，技能应输出可执行的最小修复或明确失败原因。
- 不替代 `ae:review` 的通用代码/文档审查；资产调试关注“当前会话实际路线与资产标准流程不一致”的因果修复。
- 不替代 `ae:save-rules` 的通用规则沉淀；只有当偏差根因属于资产定义或执行决策时才修改资产。

## 关键决策

- 资产调试定位为“会话纠偏后的资产修复”: 它发生在用户已经通过对话把任务拉回正轨之后，目标是修复导致偏差的资产，而不是重新执行原任务。
- 默认优先修复项目级自然语言资产: 这是首版最小可交付路径，也最接近用户在会话中纠偏后的即时价值。
- 全局资产只创建经验证可生效的项目级覆盖: 覆盖优先级未验证时，技能应停留在诊断和建议模式，避免制造“已修复但下次仍走全局定义”的假成功。
- 偏差分析必须输出修复层级: 仅靠自然语言补丁容易掩盖真正由工具代码、选择器、schema 或 catalog 决定的行为，因此需求要求显式区分定义层与代码层；代码层首版以建议为主，避免过度承诺。
- 混合形态增强后置: 对执行可靠性要求高的资产，脚本和工具可能有价值，但必须在后续规划中证明覆盖机制、权限边界和验证收益。

## 依赖 / 假设

- opencode 当前会话历史可能被代理或工具访问；如果无法访问，首版必须要求用户提供资产名、偏航实际行为、纠偏后的期望行为和相关消息片段摘要。
- 项目级资产覆盖全局资产的优先级必须逐资产类型验证；未经验证的资产类型不得自动创建覆盖并宣称生效。
- 本仓库已有资产常量化和 catalog 同步规范，新增公开技能时需要在插件源码维护语境下同步维护 `SKILL`、`COMMAND`、`ae-catalog.ts`、命令注册和帮助输出，并通过测试或脚本校验一致性。

## 待定问题

### 推迟到规划

- [影响 R2/R3][技术] 规划阶段需要确认当前 opencode 运行时能提供多少会话历史、工具调用历史和已加载资产来源；不足时采用 R3 定义的结构化用户补充输入。
- [影响 R8][技术] 规划阶段需要逐类确认项目级技能、代理、命令、规则覆盖全局资产的路径、命名、优先级和覆盖验证方式；未验证类型首版只读诊断。
- [影响 R9/R10][技术] 全局代码资产复刻和脚本/tools 混合增强不进入首版自动修复范围；后续版本若需要支持，必须先形成支持矩阵、权限模型和验证标准。
- [影响 R11][技术] 规划阶段需要定义引用影响检查的搜索策略、引用类型清单和同步修复判定标准，尤其是命令模板、帮助输出、catalog、测试断言和技能间转发关系。
- [影响 R15][技术] 规划阶段需要定义修复后的验证协议：是重放会话片段、构造最小复现提示，还是运行特定测试/命令，并明确非确定性模型行为下的人工验收标准。
