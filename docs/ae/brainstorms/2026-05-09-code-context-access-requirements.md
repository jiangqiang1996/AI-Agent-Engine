# 代码上下文访问能力

## 问题框架

AI 在大型代码库中工作时，真正需要解决的不是“必须拥有一个代码索引后台服务”，而是能以低延迟、低 token 成本、较高可信度理解代码结构、符号位置、依赖关系和变更影响。独立服务、HTTP、SQLite、Tree-sitter、Worker Threads 和文件监听等实现选择都应视为可替换方案，而不是用户价值本身。

非技术需求可以概括为：让 AI 更快找到正确代码上下文；让用户能理解、控制和信任这项能力；让该能力默认安全、可降级、不会干扰正常会话；让未来规划可以根据成本、复杂度和收益重新选择实现方式。

## 非技术需求摘要

**核心用户价值**
- AI 应减少重复扫描，把更多上下文预算用于分析和修改核心逻辑。
- AI 应能回答“定义在哪里、哪里引用、依赖什么、改动会影响什么”等代码理解问题。
- 查询结果应比普通全文搜索更结构化、更可验证，但不要求一次性覆盖所有语言和所有关系类型。
- 首版最小闭环应覆盖定义位置、引用候选和文件级依赖；符号摘要、影响候选和深层调用链属于增强能力。
- 首版验证对象为本地 TypeScript/Node 工作空间，优先覆盖 `.ts`、`.tsx`、`.js`、`.jsx` 文件和常见配置文件；其他语言和跨语言关系不作为首版闭环要求。

**用户控制与可预期性**
- 用户应能明确知道该能力当前是否可用、是否正在更新、结果是否可能过期。
- 用户应能手动触发准备、更新、清理或禁用相关数据。
- 非用户明确触发的操作不得悄悄启动重型后台流程或阻塞会话。

**安全与隐私**
- 默认不处理敏感文件、依赖目录、构建产物和疑似凭证内容。
- 对外暴露的项目信息应最小化，错误信息不得泄露不必要的绝对路径或秘密值。
- 任何持久化数据都应支持清理，并且不应成为用户项目的版本控制负担。

**可靠性与降级**
- 当上下文能力不可用、过期或部分失败时，AI 应明确降级到现有搜索/读取流程，而不是给出伪精确答案。
- 单个文件、语言或工作空间失败不应使整个能力不可用。
- 结果必须可追溯到文件和位置，便于 AI 或用户复核。
- 使用索引、缓存或其他上下文数据时，如果上下文数据不可用、缺失、损坏、过期或权限受限，系统必须返回可执行的处置措施，而不是只返回失败。
- 电脑重启、opencode 闪退、进程被杀或任务中断后，系统应能识别上次状态并给出恢复、刷新或重建建议。
- 查询发生在刷新或重建期间时，系统应明确说明正在更新，并提供不会无限等待的处理路径；至少必须允许降级到普通搜索，若存在上一版可用结果则必须允许使用旧结果并标记过期。
- 若首版采用完全按需、无持久化、无后台刷新形态，则中断恢复和更新中状态的首版要求收敛为安全失败、不中断会话、不产生伪精确结果，并清理临时状态。

**性能与规模预期**
- 首版面向中小型本地工作空间，目标规模约为 1000-5000 个文本文件；超出该规模时允许提示用户降级或手动缩小范围。
- 已准备好的重复查询应明显快于重新全仓扫描；首版可接受的目标是常见查询在 1 秒内返回候选结果。
- 首次准备或刷新可以较慢，但必须非阻塞或可取消，并向用户说明当前状态。
- 成功不以精确节省 token 数为硬指标，而以减少重复目录扫描、减少无关文件读取和更快进入相关文件为观察指标。

## 替代方向探索

**方向 A：完整后台索引平台**
- 描述: 构建独立服务、持久索引、增量更新和高级查询。
- 优点: 长期能力最完整，适合频繁查询和大型仓库。
- 缺点: 维护面大，生命周期、安全、升级、跨平台和解析准确性都变成产品负担。
- 适合: 已证明简单方案无法满足，并且用户愿意接受长期后台服务成本。

**方向 B：按需代码上下文工具箱**
- 描述: 先提供一组按需、短生命周期的结构化查询能力，复用已有文件搜索、语言服务、轻量缓存或临时扫描；只在必要时缓存局部结果。
- 优点: 启动成本低，不需要长期 daemon；更符合“需要时查、不可用就降级”的用户心智。
- 缺点: 极大仓库的重复查询性能可能不如完整索引；高级调用链能力可能分阶段交付。
- 适合: 当前最值得优先验证的方向，用更小实现证明 AI 是否真的会更快、更准。

**方向 C：会话级上下文记忆**
- 描述: 不追求全仓库索引，而是在每次会话或任务中逐步沉淀已读文件、符号候选、关系判断和验证证据。
- 优点: 最贴近 AI 实际工作流，避免为未查询内容付出预处理成本。
- 缺点: 跨会话复用弱；首次探索仍可能较慢；难以回答全局影响范围问题。
- 适合: 主要目标是减少同一任务内反复扫描，而不是提供全局代码智能。

**推荐方向**
- 优先选择方向 B，并保留向 A 演进的接口边界。理由是当前最确定的用户价值是“AI 更快、更准地获得代码上下文”，而不是“用户需要维护一个索引服务”。按需工具箱能更快验证价值、减少安全和生命周期负担，并允许在实际瓶颈出现后再引入持久索引或后台服务。

## 需求

**上下文查询体验**
- R1. AI 可以请求首版结构化代码上下文 → 验收: 对支持范围内的代码，首版至少返回定义位置、引用候选和文件级依赖三类结构化结果；结果包含相对路径和可复核位置。
- R2. 查询结果必须表达可信度和新鲜度 → 验收: 返回内容明确标记来源、生成时间或是否来自缓存；当无法确认准确性时，结果使用“候选”或“需复核”语义，而不是伪装成确定结论。
- R3. AI 使用该能力时必须可降级 → 验收: 能力不可用、上下文数据不可用、超时、结果为空或部分失败时，系统提示 AI 使用现有搜索和文件读取流程继续任务，并说明降级原因。

**用户控制**
- R4. 用户可以手动管理上下文数据 → 验收: 用户能够查看状态、触发刷新、清理缓存或禁用该能力；非用户明确触发的路径不得启动重型预处理。
- R5. 状态反馈面向决策而非内部实现 → 验收: 状态至少表达“可用、准备中、过期、部分失败、不可用”和建议下一步；不要求用户理解底层索引、服务或存储实现。

**中断恢复与并发状态**
- R6. 异常中断后必须安全失败 → 验收: 电脑重启、opencode 闪退、进程被杀或查询中断后，不得把未完成结果伪装成最新结果；下一次使用时必须能降级到普通搜索，或提示用户重新准备上下文。
- R7. 持久化或缓存形态必须可识别异常状态 → 验收: 若实现保存上下文数据、缓存、快照或索引，电脑重启、opencode 闪退、进程被杀或刷新中断后，下一次状态查询能识别数据是可用、过期、部分写入或需要重建。
- R8. 上下文数据不可用时必须给出恢复措施 → 验收: 查询时如果上下文数据缺失、不可访问、损坏、版本不兼容、过期或权限受限，系统必须明确返回状态、原因、建议动作和当前可用替代路径；建议动作至少包括刷新、重建、清理后重建、缩小范围或降级到普通搜索中的适用项。
- R9. 更新中状态必须有可执行路径 → 验收: 若实现存在准备、刷新或重建过程，查询遇到更新中状态时必须返回更新状态；必须提供降级到普通搜索的路径；若存在上一版可用结果，必须提供使用旧结果并标记过期的路径；等待完成可以作为可选路径，但不得无限阻塞。
- R10. 恢复行为不越过用户控制边界 → 验收: 异常恢复可以清理临时状态、标记过期或提示用户刷新，但电脑重启、opencode 闪退或新会话启动后不得自动继续重型刷新、全量重建或长期后台服务；跨重启/闪退后只能在用户再次确认后继续。状态识别可以跨会话，自动继续执行仅限同一 opencode 会话内同一次用户触发的操作。

**安全与隐私**
- R11. 默认安全处理项目内容 → 验收: 默认排除敏感文件、依赖目录、构建产物和疑似凭证内容；`.env*`、私钥、证书、云凭证、SSH 配置和疑似密钥命中的内容不得进入上下文数据；若用户扩大范围，系统仍不得记录秘密值本身。
- R12. 持久化数据最小化且可清理 → 验收: 若实现需要保存数据，保存内容只用于上下文查询，使用相对路径标识项目内容，不保存源码片段或秘密值，按工作空间隔离，并提供清理入口；保存位置不得默认进入版本控制。

**渐进交付**
- R13. 首版不要求全语言全关系覆盖 → 验收: 首版目标限定为本地 TypeScript/Node 工作空间，至少覆盖 `.ts`、`.tsx`、`.js`、`.jsx` 文件和常见配置文件；未覆盖语言、文件类型或关系场景必须返回可理解的降级说明。
- R14. 高级关系能力可以分阶段扩展 → 验收: 符号摘要、影响候选、调用链、跨语言符号引用和全局影响范围等能力可以作为后续增强，不阻塞首版交付定义位置、引用候选和文件级依赖。
- R15. 技术形态可替换 → 验收: 后续规划可以选择按需扫描、语言服务、临时缓存、持久索引或后台服务中的任意组合，只要满足本需求文档的用户可见行为和安全边界；首版不要求为了未来形态预先实现通用抽象层。

## 成功标准
- AI 在典型任务中减少重复目录扫描和重复文件读取，用户能观察到更快进入相关代码文件。
- 在本地 TypeScript/Node 工作空间中，AI 能完成三个首版验收样例：查找某函数或类的定义位置、查找某符号引用候选、判断某文件的直接依赖或被依赖候选。
- 对已支持的查询类型，结果能稳定给出相对路径和可复核位置，而不是仅返回泛泛的文本摘要。
- 当能力不可用或不确定时，AI 能清楚说明降级，并继续通过普通工具完成任务。
- 查询遇到更新中、异常中断恢复后或数据可能过期时，系统能明确给出降级路径；存在上一版可用结果时能给出使用旧结果并标记过期的路径；跨重启或闪退后继续重型任务前必须再次取得用户确认。
- 上下文数据不可用时，用户或 AI 能看到原因、建议动作和替代路径，不会被阻断在“上下文查询失败”状态。
- 用户不需要理解或维护复杂后台服务，也能知道能力状态并进行必要的刷新或清理。
- 默认配置不会索引或持久化明显敏感内容。

## 范围边界
- 包含: 本地 TypeScript/Node 工作空间的代码上下文查询、状态反馈、默认安全排除、清晰降级；若实现包含缓存、持久化或刷新机制，则包含用户触发的刷新/清理和异常恢复状态反馈。
- 不包含: 远程代码库索引、实时协作编辑、索引数据备份、代码语义正确性的绝对保证。
- 不作为首版硬要求: 独立 daemon、HTTP 接口、SQLite、Tree-sitter、Worker Threads、文件监听、全语言 AST、10 层调用链。
- 允许后续引入: 如果规划证明必要，可以引入持久索引、后台服务、增量更新或专用查询协议，但它们必须服务于本文件定义的用户价值；若出现服务化或协议化实现，默认只能本机访问，必须具备当前用户和工作空间边界，拒绝跨 Origin 浏览器访问，错误信息不得暴露绝对路径或秘密。

## 关键决策
- 将“代码索引服务”重构为“代码上下文访问能力”: 避免过早绑定后台服务形态，让规划优先验证用户价值。
- 首选按需与渐进式能力: 先解决定义、引用候选和文件级依赖这些高频上下文问题，再根据真实瓶颈扩大索引深度。
- 默认保守安全边界: 代码上下文能力天然接触项目结构和内容，必须默认排除敏感信息并提供可清理路径。
- 降级是产品能力的一部分: 不可用时继续工作比追求复杂服务自愈更重要。

## 依赖 / 假设
- opencode 已有基础文件搜索、内容搜索和文件读取能力，可作为降级路径。
- 用户更关心 AI 是否更快定位相关代码，而不是底层是否存在长期运行的索引服务。
- 部分高级查询可以接受候选结果，只要系统明确表达可信度和复核方式。
