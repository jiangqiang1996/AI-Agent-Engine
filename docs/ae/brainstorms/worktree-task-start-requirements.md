# 每次执行任务前提示创建 Worktree

## 问题框架

当前 `ae:work` 已要求在默认分支上创建新分支或使用 worktree，但提示策略偏向“默认分支保护”。用户希望把它提升为更稳定的任务启动习惯：每次进入会修改项目文件的正式实现型任务时都提示创建独立 worktree，并同步创建对应分支。核心担忧是该策略会不会破坏 AE 的跨会话恢复能力。

已验证的现状：`ae:work` 的准备环境阶段包含“检查当前分支；若在默认分支上：创建新分支或使用 worktree”；`ae-recovery` 根据当前 `ctx.worktree` 下的 `docs/ae/*` 产物恢复；代码审查状态文件 `.opencode/review-state.json` 会校验当前分支名以避免跨分支状态混淆；当前会话的工具上下文不会因为执行 `git worktree add` 自动切换到新 worktree。也就是说，如果 opencode 仍运行在原工作空间，产物会写入原工作空间；只有在对应 worktree 中启动或交接 opencode 后，执行产物才会写入该 worktree。

## 需求

**首版：任务启动与安全边界**
- R1. 每次进入会修改项目文件的正式实现型任务时，代理应先判断当前目录是否为 Git 仓库且 `git worktree` 可用；只有满足时才提示用户是否创建独立 worktree，并说明会同时创建对应分支。→ 验收: Git 项目中 `ae:work` 或主流程进入实现前会出现 worktree 选项，而不是只在默认分支上提示；非 Git 项目跳过询问并记录 `worktree_decision: not_applicable`。
- R2. 用户选择不创建新 worktree 时，流程应允许继续在当前工作区和当前分支执行，但必须在最终交付的 Git 操作状态中记录未创建 worktree。→ 验收: 不因用户拒绝 worktree 而阻断任务；最终交付记录 `worktree_decision: rejected` 并能追踪该选择。
- R2a. 使用 `ae:lfg` 时，除初始澄清阶段的少量必要询问外，后续应尽可能静默执行到结束；在用户未通过参数明确禁用 worktree 的情况下，Git 项目默认使用 worktree，不再询问是否创建。→ 验收: `ae:lfg` 在进入实现前不会展示“是否创建 worktree”的选择；前置阶段一次性收集目标、约束、验收、worktree/Git 授权范围等必要决策；后续仅在授权不足、安全风险或必须由用户决策的阻断项出现时提问。
- R3. 创建 worktree、创建分支或切换分支前必须获得用户显式授权。→ 验收: 代理不会静默执行 `git worktree add`、`git switch`、`git checkout`、`git branch` 等 Git 写操作。
- R4. Git 写操作授权必须记录可引用证据。→ 验收: 授权证据至少包含授权来源、授权内容和覆盖的命令范围；最终门禁不能只依赖布尔声明。
- R5. 门禁必须识别 worktree 相关 Git 写操作。→ 验收: `git worktree` 与创建/切换分支命令均被归类为 Git 写操作，并进入授权证据检查。
- R6. 创建 worktree 后，当前 opencode 会话不得误报自己已经切换到新 worktree。→ 验收: 只要当前会话的 `ctx.worktree` 仍指向 A，所有 AE 产物归属都明确为 A。
- R7. 如果用户决定在 B worktree 执行，首版必须要求用户在 B 中重新启动 opencode 后再执行代码修改。→ 验收: 不扩展或假定 `ae:handoff` 支持目标 worktree；不允许 A 会话通过 shell 工作目录指向 B 来修改代码、配置、测试或其他项目文件，同时把 AE 产物、审查状态或门禁证明写回 A。

**首版：恢复与执行证据归属**
- R8. 恢复范围必须以当前 opencode 会话的 `ctx.worktree` 为边界。→ 验收: `ae-recovery` 只读取当前工作空间的 `docs/ae/*` 产物，不跨 worktree 查找或恢复。
- R9. 执行产物必须归属于实际运行 opencode 的工作空间。→ 验收: 首版在 B 目录重新启动 opencode 后，执行记录、验收结果、审查报告和门禁证明都写入 B；A 只保留转移前的来源产物。
- R10. 审查状态不得只依赖分支名复用。→ 验收: 首版采用保守策略，新 worktree、新分支、同分支不同 worktree 或无法证明变更状态一致时，一律视为未审查；审查复用证明机制作为后续增强。
- R11. `review_status` 必须附带来源分类。→ 验收: 首版至少在最终交付或门禁输入中区分审查运行结果、审查报告路径、未运行原因和仅声明证据。

**首版：关联产物与交接处理**
- R12. 创建 B worktree 后，A 会话只允许执行窄范围启动交接操作：自动迁移当前任务已确定的 AE 需求/计划产物到 B，即使这些文件在 A 中仍未跟踪。→ 验收: 本次读取或生成的 `docs/ae/brainstorms/*-requirements.md` 与 `docs/ae/plans/*-plan.md` 按仓库相对路径复制到 B，创建缺失目录，且不会遗漏未跟踪文件。
- R13. 如果无法唯一确定当前任务关联产物，必须询问用户；不得靠最近修改时间或相近 topic 批量复制 `docs/ae/*`。→ 验收: A 中存在多个候选需求或计划时，代理先让用户选择，而不是静默复制所有文档。
- R14. 所有新 worktree 的本地目录必须创建在当前项目根目录同级的 `../worktrees/<name>` 直接子目录下。→ 验收: `git worktree add` 的目标路径不接受任意外部路径、嵌套路径或 option-like 输入。
- R15. 创建 B worktree 后，A 会话只允许在 B 写入当前会话核心交接 Markdown，并给出新会话继续提示词。→ 验收: B 中存在 `docs/ae/handoffs/<timestamp>-worktree-handoff.md` 或等价明确路径；内容包含用户目标、已确定决策、已迁移产物、待办事项、验证要求、Git/worktree 状态和继续执行约束；A 的终止提示包含该路径，并要求用户在 B 的 opencode 新会话先读取交接文件、需求文档和计划文档再继续。

**后续增强：状态真源**
- E1. 如果需求和计划在 A 生成但执行转移到 B，则 B 中的计划副本成为唯一可变执行状态真源。→ 验收: 任务完成标识、执行备注、验证结果、审查报告和门禁证明只更新 B。
- E2. A 中原计划必须退出活跃恢复候选或显式标记为已转移。→ 验收: 用户之后在 A 运行恢复时，不会把已转移到 B 执行的旧计划当作当前可继续执行计划。
- E3. 执行阶段用户打断会话并变更需求时，变更应记录在当前执行 worktree 中，不自动同步回原工作空间。→ 验收: 小范围变更更新 B 中计划副本的执行项或验收标准；范围或目标变化时在 B 中生成修订需求/计划并建立替代关系；除非用户明确要求人工归档或合并，不回写 A 中的原需求/计划。

**设计约束**
- C1. 首版以“提示、授权、固定目录、迁移当前任务需求/计划、写入交接文件、明确执行归属、避免证据错位”为最小交付，不做跨 worktree 双写同步或状态真源切换。
- C2. `ae:handoff` 不能被假定为已经支持切换目标 worktree；如果要用 handoff 承载 B 会话执行，必须先证明或扩展其目标工作空间能力。
- C3. rules 只能补充默认偏好和话术，不能承担流程阻断、证据记录或恢复契约；稳定行为必须落在可分发、可测试的技能或服务能力中。

## 成功标准

- 普通 `ae:work` 每次正式实现前都能看到清晰的 worktree 创建选项；`ae:lfg` 在未显式禁用 worktree 时默认创建 worktree，不展示重复选择。
- 拒绝 worktree 不会破坏任务执行；接受 worktree 不会破坏恢复、审查范围或交付门禁。
- 用户能明确知道当前任务产物会写入哪个工作空间，以及后续恢复应从哪个工作空间启动。
- 首版能明确提示跨 worktree 执行的产物归属；后续增强可进一步保证只有一个可变执行状态真源。
- 后续实现有明确边界：提示行为、恢复兼容、审查状态隔离和 Git 授权分开处理。

## 范围边界

- 不在头脑风暴阶段实现 `git worktree add` 自动化。
- 不要求问答、只读审查或纯文档整理任务创建 worktree；若文档任务通过 `ae:work` 修改项目文件，则按正式实现型任务处理。
- 不绕过 Git 写操作授权门禁。
- 不移除审查状态文件的分支隔离逻辑。
- 不允许在 A 会话中通过 shell 工作目录指向 B 来执行代码、配置、测试或其他项目文件修改，同时把 AE 证据写回 A。
- 不在创建 worktree 时批量复制所有 AE 需求、计划或审查产物；只迁移当前任务已确定的需求/计划和交接 Markdown。
- 不要求执行阶段的需求变更自动同步回原工作空间。

## 关键决策

- 推荐把“每次正式实现前提示创建 worktree”写入 `ae:work` 的准备环境阶段，而不是只放在 rules。理由：技能步骤比 rules 更接近实际流程，且可随插件分发和测试。
- rules 可以作为补充约束，用来描述偏好和默认话术，但不应承担流程契约。理由：rules 对 LLM 有约束力但缺少可测试的行为入口，容易被更具体的技能步骤覆盖。
- 恢复功能本身不应绑定全局分支名。理由：当前恢复核心是当前 worktree 下的产物与 frontmatter 指纹，保留这一点能让 worktree 模式自然隔离。
- 首版固定 worktree 目录为当前项目根目录同级的 `../worktrees/<name>`。理由：减少散落目录和跨项目误操作，目标路径可由任务名或分支名净化生成并在冲突时询问用户。
- 产物归属以 opencode 会话的 `ctx.worktree` 为准，而不是以最近创建的 Git worktree 为准。理由：AE 工具读取和写入都通过当前工具上下文定位仓库根目录，恢复也从该目录查找产物。
- 后续增强应坚持一个任务只能有一个可变执行计划真源。理由：A 中生成的原计划与 B 中执行态计划如果同时维护完成状态，会导致恢复和验收引用的状态不一致。
- 后续增强仍不做 A/B 双写同步。理由：执行阶段的新需求、计划修订和验收变化必须贴近实际代码变更所在 worktree，否则会出现代码与证据错位。

## 依赖 / 假设

- 假设用户的目标是“提示并授权创建 worktree”，不是“无提示自动创建 worktree”。
- 假设正式实现型任务主要由 `ae:work` 或 `/ae-lfg` 的实现阶段承载。
- 假设不同 worktree 各自拥有独立工作区文件；如果 AE 产物未提交或未复制，新 worktree 默认不可见这些未跟踪产物。
- 假设用户可以在新 worktree 目录中重新启动 opencode；通过 handoff 指定目标 worktree 属于后续增强，不作为首版前提。
- 假设 A 工作空间可能存在多个未被 Git 管理的需求或计划，不能把目录级复制作为安全默认行为。
- 假设 B worktree 是实际执行代码变更的位置时，B 也应保存与该执行相关的验收和恢复证据。

## 待定问题

### 推迟到规划
- [影响 R1][技术] worktree 名称和分支名称应如何从任务描述、计划标题或需求 topic 生成，并如何处理冲突。
- [影响 R4][技术] Git 授权证据由 `ae-gate` 新参数、notes 引用还是会话上下文引用承载。
- [影响 R12/R13][技术] 如何从当前会话、显式 plan path、frontmatter `origin` 和恢复候选中判定唯一关联产物。
- [影响 R10][技术] 审查状态如何证明来自当前工作空间和当前变更状态，而不只依赖分支名。
- [影响 R11][技术] `review_status` 来源分类由 `ae-gate` 新参数、审查报告路径还是最终交付模板承载。
- [影响 R15][技术] 交接 Markdown 的稳定模板是否需要抽成独立引用文件或工具能力。
- [影响 E3][技术] A 中原计划如何写入“执行已转移”的只读标记，以及跨 worktree 路径如何表达。
- [影响 E3][技术] 执行阶段需求变更在 B 中应更新原计划副本，还是生成修订版需求/计划并通过替代关系串联。
- [影响 C2][技术] 后续是否需要扩展 `ae:handoff` 的目标工作空间能力。
- [影响 C3][技术] 是否需要新增测试覆盖“仅修改 rules 不足以稳定改变技能行为”的文档/资产一致性。
