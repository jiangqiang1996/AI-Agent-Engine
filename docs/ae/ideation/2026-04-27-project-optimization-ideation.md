# 创意构思：当前项目优化与增强方向

## 落地上下文

本次构思基于当前 AE opencode 插件仓库。项目核心是由 `src/assets/skills/`、`src/assets/agents/`、`src/assets/commands/`、`src/assets/rules/` 组成的资产体系，以及 `src/tools/`、`src/services/`、`src/schemas/` 中的工具与契约实现。运行时产物写入 `.opencode/`，公开入口包括 `/ae-lfg`、`/ae-help` 和多个 `ae:*` 技能。

近期仓库文档和扫描显示，当前项目的主要优化机会不在于继续堆叠更多技能或代理，而在于防止资产漂移、契约不一致、技能边界模糊、代理不可达、跨平台命令不可执行、Git 行为越权，以及 handoff/recovery 语义误导。

外部网络研究在当前环境中不可用，本次主要依据仓库扫描、近期 AE 文档和项目规范完成。

## 排名想法

### 1. 资产一致性健康检查

**描述：** 建立一个校验器，自动比对 `SKILL.md` frontmatter、`ae-catalog.ts`、资产常量、工具 schema、README/usage guide/help 输出、运行时 `.opencode/` 产物之间的名称、数量、描述、参数提示和引用关系。
**理由：** 当前项目的高频风险是“同一事实存在多处声明”，例如技能数量、工具数量、frontmatter 与 catalog 的一致性。把一致性变成测试或诊断入口，会直接降低长期维护成本。
**缺点：** 初版需要明确哪些字段必须字面一致，哪些字段只要求语义一致；语义一致难以完全自动化。
**置信度：** 92%
**复杂度：** 中
**状态：** 未探索

### 2. 技能边界契约

**描述：** 为每个 `ae:*` 技能抽取或声明结构化边界，包括适用场景、不适用场景、是否写文件、允许产物、禁止行为、推荐后续技能、回退技能，并用测试或审查规则校验。
**理由：** `ae:ideate`、`ae:brainstorm`、`ae:plan`、`ae:work`、`ae:review` 等技能之间存在强阶段关系。边界如果只写在自然语言中，LLM 和用户都容易误路由。
**缺点：** 需要避免把提示词文档过度结构化，导致维护负担超过收益。
**置信度：** 88%
**复杂度：** 中
**状态：** 未探索

### 3. 跨平台命令契约测试

**描述：** 扫描技能、命令、文档和测试中的 shell 片段，标记 `&&`、`mktemp`、heredoc、Unix 路径、PowerShell 5.1 不兼容写法等风险，并要求给出平台限定或 Windows/Unix 双版本。
**理由：** 当前运行环境是 Windows，AE 技能又经常包含可执行命令。命令片段不可执行会直接破坏工作流体验。
**缺点：** 命令片段识别可能误报，需要先从明确模式开始，而不是尝试完整解释 shell 语义。
**置信度：** 84%
**复杂度：** 中
**状态：** 未探索

### 4. 未授权 Git 操作护栏

**描述：** 为技能、代理和命令提示词增加静态扫描或运行时 guard，检测可能诱导未经授权的 `git commit`、`git push`、`git commit --amend`、`git reset --hard`、`--no-verify` 等行为。
**理由：** 未授权提交是高信任风险。仅依赖系统提示约束不够稳，应把这类行为约束下沉为仓库资产检查或工具执行护栏。
**缺点：** 运行时 guard 需要获取用户授权上下文，静态扫描则只能覆盖提示词层面的风险。
**置信度：** 86%
**复杂度：** 中到高
**状态：** 未探索

### 5. Recovery/Handoff 语义回放

**描述：** 为 `ae-recovery`、`ae-handoff`、`ae:lfg` 和阶段回退策略建立 fixture 场景，模拟缺失 brainstorm、存在多个 plan、上下文指纹不匹配、交接摘要不完整等情况，断言恢复阶段、后续技能、回退技能和交接内容。
**理由：** 恢复与交接的失败通常不是类型错误，而是把用户带到错误阶段。语义回放能保护跨会话连续性。
**缺点：** 需要设计稳定 fixture，避免测试过度绑定当前文案。
**置信度：** 87%
**复杂度：** 中
**状态：** 未探索

### 6. 工具/技能契约快照与自诊断

**描述：** 生成工具和技能的契约报告，包含参数 schema、适用/不适用场景、错误返回、metadata、测试覆盖、示例调用、最近构建和运行时同步状态，并可通过用户入口查询。
**理由：** AE 是面向 LLM 的插件，工具和技能契约就是产品 API。自诊断能减少用户报错前的排查成本，也能帮助维护者发现公开接口变化。
**缺点：** 如果报告只是静态文档，容易再次漂移；最好由代码生成。
**置信度：** 80%
**复杂度：** 中
**状态：** 未探索

## 拒绝摘要

| # | 想法 | 拒绝理由 |
|---|------|---------|
| 1 | 单独新增更多场景专用技能 | 当前更大的问题是现有资产治理和边界清晰度，继续新增技能会放大漂移。 |
| 2 | 把 `ae-review-contract` 泛化为所有流程的决策引擎 | 有潜力，但相对抽象且实施负担较高，更适合在可达性/契约治理成熟后再评估。 |
| 3 | 每次 work/review 后自动生成 solution 沉淀 | 有复利价值，但可能带来额外流程噪音，且本次焦点下优先级低于资产治理。 |
| 4 | 统一 rewrite 所有手写清单为代码生成 | 与资产一致性健康检查重复，作为其后续变体更合适。 |
| 5 | 代理能力营养标签 | 表达有启发性，但更像契约报告的展示层。 |
| 6 | 自解释失败报告统一格式 | 有价值，但范围横跨所有工具错误处理，短期不如先解决可达性和一致性基础问题。 |
| 7 | 运行时产物完全不可变模式 | 方向正确，但属于资产一致性健康检查中的更严格策略，不单独保留。 |
