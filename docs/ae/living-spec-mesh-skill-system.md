# Living Spec Mesh 技能系统

本文记录 AE 插件源码仓库中的 LSM 技能链设计，供实现、测试和审查对齐。它是插件源码维护语境，不要求普通下游项目具备这些目录。

## 目标

- 统一 `ae:lsm-*` 技能命名空间
- 将规格、设计、原型、测试、构建和验收拆成独立阶段
- 保持显式上游路径、稳定 ID 和通用审查入口

## 技能链

| 阶段 | 技能 | 输出 |
| --- | --- | --- |
| 规格 | `ae:lsm-spec` | `R-*` 需求与上游边界 |
| 设计 | `ae:lsm-design` | `U-*` 实现映射 |
| 原型 | `ae:lsm-prototype` | 原型资产、跳过理由、受影响 ID |
| 测试 | `ae:lsm-test` | `TC-*` 测试用例 |
| 构建 | `ae:lsm-build` | 构建报告、验证命令、Git 状态 |
| 验收 | `ae:lsm-acceptance` | `V-*` 验收证据、未验证项、残余风险 |

## 规则

- 只接受显式上游路径或会话交接路径
- 不通过历史目录盲扫选择上游产物
- 原型阶段遇到浏览器验证时先过 `ae:chrome-devtools`
- 最终审查仍统一交给 `ae:review`

## 审查输入

当输入同时包含显式上游路径、追溯表和跨阶段产物时，按通用混合范围审查。
仅有 `R-*`、`U-*`、`TC-*`、`V-*` 字面形态时，不自动判定为 LSM 完整链路。

## 分流判定

LSM 链路不是默认软件交付路径。`ae:prd`、`ae:plan`、`ae:work`、`ae:lfg` 与 `ae:brainstorm` 仍是通用入口；只有用户显式选择并满足触发条件时，才进入 LSM 链路。下表给出可观测的分流判据，供用户和审查者对照执行：

| 触发场景 | 推荐流程 | 可观测判定 |
|---------|---------|-----------|
| 单文件 bug 修复 | `ae:work` 或 `ae:plan + ae:work` | 输入仅含错误描述、日志或单文件路径，无需求/设计/测试用例分层 |
| 给已有功能加一项小改动 | `ae:plan + ae:work` | 输入是改动描述，且不要求生成 `R-*/U-*/TC-*/V-*` 追踪 |
| 探索性发散讨论 | `ae:brainstorm` 或 `ae:ideate` | 输入是开放式问题，无明确交付物 |
| 多阶段软件工程交付（需求→设计→测试→实现→验收） | LSM 链路 | 用户显式提及"Living Spec Mesh"、"完整 LSM 链路"或显式调用 `ae:lsm-*`；或输入已是 LSM 模板产物 |
| 一站式自动化交付 | `ae:lfg` | 用户输入"lfg"或显式调用 `/ae-lfg` |

分流判定是建议而非强制门禁；用户始终保留显式选择权。审查者在 ae:review 中遇到 LSM 完整产物链时按通用混合范围处理，遇到普通流程时不得引入 LSM reviewer。

## 真实痛点对照

LSM 链路面向多阶段软件工程交付的真实问题，每项痛点对应可观测的用户损失：

- **多人并行的多阶段软件交付容易脱节**：需求、设计、测试与验收分散在不同会话或不同文档中，LLM 无法跨阶段对齐；用户损失表现为"实现完成后才发现与设计不一致需返工"，或"测试用例覆盖不到原始需求"。LSM 链路通过 `R-* → U-* → TC-* → V-*` 显式 ID 追踪让每个阶段的产物指向上游来源。
- **跨阶段产物缺乏 ID 追踪**：通用 `ae:plan + ae:work` 只承载本阶段的步骤拆分，不承诺跨阶段稳定 ID；多次迭代后无法回答"这条测试用例对应哪个需求"或"这个实现单元覆盖了哪些验收证据"。用户损失表现为"未追踪的需求被遗忘导致漏交付"。LSM 链路要求每个模板 frontmatter 携带 `traceTable.inputs/outputs`，实现链上可机读追溯。
- **验收证据未与需求闭环**：通用流程下"实现完成"与"验收通过"是两件事，但缺乏机制保证验收时回到原始需求逐条核验；用户损失表现为"上线后才发现某条需求其实未真正实现"。LSM 链路通过 acceptance 阶段强制产出 `V-*` 验证证据并指回 `R-*`，配合 ae-review-proof 的硬阻断，确保缺 `V-*` 时不能写入 passed 审查证明。

这些痛点不是普通项目的常见诉求；只有用户已经在做多阶段软件交付且对追溯链有真实需求时，LSM 才能产生回报。

## 替代方案对比与 ROI

LSM 体系的存续基于以下方案对比与采纳结论：

| 替代方案 | 优点 | 缺点 | 是否采纳 |
|---------|------|------|---------|
| 弃用 LSM 体系，删除 6 技能 + 模板 | 简化技能目录；减少维护负担 | 已实现并通过既有测试，删除会丢失现有产物追溯能力；多阶段软件交付场景将回退到无 ID 追溯的 plan/work | 不采纳 |
| 冻结 LSM 不再新增能力，但保留现有 | 维护成本最低 | 当前已暴露的 4 项缺口（识别启发式、V-* 硬阻断、reviewer 选择、远程写守护）将永久存在；ae:review 与 LSM 永远不闭环 | 不采纳 |
| 完成增量改造闭合 ae:review 与 LSM 契约 | 保留 LSM 已实现资产；通过 frontmatter 机读字段、proof 层硬阻断与回归测试守护闭合现有缺口；不引入新技能或新工具 | 引入模板 frontmatter 字段维护负担 | **采纳** |
| 把 LSM 提升为默认软件交付路径 | 强制规范 | 违反"LSM 不成为默认流程"外部行为保持；伤害普通项目用户 | 不采纳 |

ROI 论证：完成增量改造后用户能做的具体事如下：

- 直接对任意 LSM 产物路径执行 `ae:review`，自动触发追溯+证据审查，不需手动指定 `kind=mixed` 或 reviewer 列表。
- 信任 `ae:review` 通过即等于 `V-*` 证据齐全，proof 层硬拒绝缺证据的 passed 写入。
- 放心使用 `ae:review` 处理普通代码或文档审查，回归测试守护普通流程不被 LSM 劫持。
- 放心阅读 LSM 文档，自动化测试守护文档不引入 GitHub 远程写命令。
- 按本节分流判定表自助选择流程，避免误用 LSM 链处理一次性 bug 修复。

LSM 使用频次未量化为已知风险：当前没有运行时使用统计采集机制。本文档保留分流判定与替代方案对比章节，未来若 LSM 调用频次显著低于普通 plan/work，可在后续决策中重新评估"冻结 / 弃用 LSM"。
