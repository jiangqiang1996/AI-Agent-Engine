# 角色卡设计模式

本文件讲**怎么把一个角色设计好**：职责边界、触发条件、命名、产出质量。格式规范见 `references/role-card-conventions.md`。

---

## 1. 设计原则

- 一个角色只承担一个明确职责，不写成"什么都能做"的万能助手。
- 职责必须能落到**可验证的交付物**上，不能只写人格设定或口号。
- 排除项和职责同等重要：编排层靠排除项判断何时换角色。
- 触发条件写可观察的输入状态，不写主观判断。
- 输入契约写清"缺什么就回报什么"，让角色不猜。
- 输出契约写清字段与证据，让多个角色的产出可以直接合并。
- 角色卡是纯 Markdown，不写宿主专属语法、不写具体工具调用。

---

## 2. 一个角色该有多窄

用三条自检问题判断角色是不是切得太宽或太窄：

1. **能不能一句话说清交付物？** 不能，说明职责太宽或太虚。
2. **能不能说清"这件事不归我"？** 不能，说明边界缺失。
3. **能不能在输入缺失时明确回报而不是硬猜？** 不能，说明输入契约不合格。

角色太宽的典型信号：一个角色卡同时覆盖设计、实现、测试三类产出。角色太窄的典型信号：角色只做一件没有独立价值的机械动作，且没有专属输入输出契约——这种情况应留在技能正文里，不建卡。

---

## 3. 触发条件怎么写

| 写法 | 可用性 | 说明 |
|------|--------|------|
| "设计文档已产出且包含数据流" | 可用 | 可观察的输入状态 |
| "需要审查的时候" | 不可用 | 主观判断 |
| "当用户明确要求安全审查时" | 可用 | 触发来源清晰 |
| "总是执行" | 不可用 | 等于没有条件 |

条件要覆盖三档：**明确派发**、**明确不派发**、**边界情况**（例如只有需求没有设计时怎么办）。

---

## 4. 命名建议

- 文件名用 kebab-case，语义指向职责：`security-reviewer`、`api-designer`、`test-auditor`。
- 名字体现专业身份，而不是顺序或工具：`step-2`、`tool-runner` 这类名字不可取。
- 避免 `helper`、`assistant`、`generic`、`misc` 这类泛化名——它们无法区分角色，也容易在多技能合集中撞名。
- 角色标题（`# 角色：<角色名>`）用一句人类可读的名字，便于在分派列表里辨认。

---

## 5. 质量标准

一份合格的角色卡应该满足：

- [ ] 能说明自己**不该**处理什么。
- [ ] 能给出可验证的产出或清晰结论，而不是"建议进一步确认"。
- [ ] 触发条件可判定，编排层不需要额外猜测。
- [ ] 输入契约写明了输入不足时的处理方式。
- [ ] 输出契约的字段可被合并层直接使用。
- [ ] 工作流最后一步是自检。
- [ ] 不含宿主专属工具名、宿主专属路径、宿主专属 frontmatter 字段与宿主专属占位符。
- [ ] 不要求跳过验证、跳过用户确认，也不给出推送远程、创建分支或发布之类的破坏性或不可逆操作流程；需要外部协作时只输出摘要、证据与建议。

---

## 6. 更新既有角色卡

- 先读取旧角色卡全文，识别仍然有效的职责边界、触发条件、输入输出契约与禁止事项。
- 变更前写出草案：保留哪些旧内容、修改哪些段落、删除或重写哪些段落、为什么。
- 只做最小编辑，不要整篇重写——整篇重写最容易丢掉旧的安全边界和禁止事项。
- 职责范围扩大、删除旧的安全边界或禁止事项时，单独向用户确认风险。
- 校验失败时只修复导致失败的最小问题；涉及语义或边界的修复需要再次确认。
