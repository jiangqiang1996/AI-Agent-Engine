# 角色卡规范

角色卡（role card）是多角色协作型技能的标准组成：每个角色一个 Markdown 文件，放在技能目录的 `references/roles/` 下。角色卡让"谁来做"这件事从技能正文里独立出来，可以被单独分发、单独校验、单独复述。

角色卡是**纯 Markdown**：没有 frontmatter，没有宿主专属字段，没有占位符约定，因此可以随技能安装到任何支持 Agent Skills 的宿主。

---

## 1. 位置与命名

| 项目 | 约定 |
|------|------|
| 目录 | 技能目录下的 `references/roles/` |
| 文件名 | kebab-case，与角色语义一致，例如 `security-reviewer.md` |
| 标题行 | `# 角色：<角色名>`（角色名用中文或英文短名） |
| 编码/换行 | UTF-8，Markdown 表格与列表均可使用 |

文件名不要使用 `helper`、`assistant`、`generic` 这类泛化名。文件名表达职责（`api-designer`、`test-auditor`），不要表达工具或顺序（`step-2`、`reviewer-final`）。

---

## 2. 固定结构

角色卡由一个标题行和五个二级段落组成，段落顺序固定，内容不得为空：

```markdown
# 角色：安全设计审查者

## 职责

- 负责：审查设计中的认证、授权、数据边界与敏感信息处理，给出可验证的整改项。
- 不负责：不修改设计文档本身，不做性能压测，不对业务优先级排序。

## 触发条件

- 派发：设计文档已产出，且包含数据流、接口契约或权限模型。
- 不派发：只有需求描述没有设计，或设计已被其他角色标记为待重写。

## 输入契约

- 输入：设计文档正文 + 关联需求条目编号。
- 前置条件：设计中的数据流与接口边界已明确到可判断的程度。
- 缺失处理：信息不足时回报缺失项清单，不猜测结论。

## 输出契约

- 输出：按严重级别排序的问题清单，每项包含位置、风险说明、证据、整改方向。
- 证据：每条问题必须引用设计文档中的具体段落。
- 禁止：不代替编排层下结论，不给出与设计无关的通用安全建议。

## 工作流

1. 通读设计文档，标记涉及数据流、权限与敏感数据的段落。
2. 逐项对照边界与责任划分，记录可验证的失败场景。
3. 对每条问题补齐证据与整改方向，按严重级别排序。
4. 自检：确认每条问题都有证据，且没有越出职责边界的建议。
```

### 2.1 `## 职责`

回答两个问题：**交付什么**、**不交付什么**。

- 用一句话写清交付物（"给出一份带证据的整改清单"），不要写人格设定或口号。
- 必须写排除项。排除项写清"交回谁"，编排层才知道何时换角色。
- 职责范围与相邻角色重叠时，在排除项里点名边界，例如"接口契约由接口设计角色负责，本角色只审查其中的权限部分"。

### 2.2 `## 触发条件`

回答两个问题：**什么时候派发**、**什么时候不派发**。

- 派发条件写成可观察的输入状态（"设计文档已产出且包含数据流"），不要写主观判断（"看起来比较重要"）。
- 不派发条件同样要写，它决定了编排层是否跳过本角色。
- 条件涉及多档输入时，用分行列表写清每档的处理方式。

### 2.3 `## 输入契约`

回答：**吃什么**。

- 输入内容与格式写具体：文档正文、文件路径清单、结构化字段。
- 前置条件写"缺少就无法开工"的最小条件。
- 缺失处理写降级方式（回报缺失项而不是猜测）。这一条是角色卡可靠性的关键。

### 2.4 `## 输出契约`

回答：**吐什么**。

- 输出结构写字段与顺序，让合并层能直接拼接多个角色的结果。
- 证据要求写清"每条结论需要附带什么"，避免无法追溯的结论。
- 禁止项写清这个角色不允许做的动作（不改文件、不下最终结论、不越界给建议）。

### 2.5 `## 工作流`

回答：**怎么做**。

- 用 3-6 步编号流程，每步一个动作。
- 最后一步固定是自检：对照输出契约逐项核对。
- 步骤里不写具体工具调用语法，只写需要的能力（读文件、检索、执行只读检查等）。

## 3. 角色卡与正文内联说明

| 情况 | 做法 |
|------|------|
| 角色需要独立分派、独立上下文 | 写成角色卡 |
| 角色只是正文里的一个小步骤 | 留在正文，不建卡 |
| 技能只有一张角色卡 | 通常说明没有拆分必要，留在正文更清晰 |
| 角色之间输入输出没有差异 | 合并成一张卡 |
| 同一角色的多个变体 | 用一张卡 + 不同触发条件表达，不复制文件 |

判定标准：**能否在不读技能正文的情况下，独立把一张卡交给另一个人或另一个会话执行？** 不能，就说明该内容应留在正文里。

---

## 4. 宿主如何分派角色卡

角色卡本身不携带分派逻辑。技能正文负责说明如何把角色卡交给执行方，并必须给出降级路径。

标准措辞（可直接复制到技能正文）：

> 若宿主支持子代理派发能力，将下列角色卡**并行**分派，每卡一份独立上下文；
> 若不支持，则在当前会话内**顺序**执行同一批角色卡，产出格式不变。

要点：

1. 只描述**能力**，不写具体工具名。不同宿主对同一能力的叫法不同（派发子代理、启动子会话、派生代理等）。
2. 并行与顺序必须产出**同一种格式**，否则降级后合并层无法处理。
3. 每张卡要能独立完成：它自带输入契约与输出契约，不依赖上一张卡的中间产物。
4. 依赖关系（角色 A 的输出是角色 B 的输入）要显式写出来，避免并行分派时产生竞态。

## 5. 反例

| 反例 | 问题 | 改法 |
|------|------|------|
| 角色卡里写"使用子代理工具派发" | 宿主专属写法 | 写"若宿主支持子代理派发能力" |
| 角色卡里写绝对路径配置目录 | 宿主专属路径 | 写"技能目录"或相对路径 |
| 职责写成"负责整个项目" | 无边界 | 写交付物 + 排除项 |
| 触发条件写成"需要的时候" | 不可判定 | 写成可观察的输入状态 |
| 输出契约只写"给出建议" | 不可合并 | 写字段与顺序 |
| 一个文件里写三个角色 | 无法独立分派 | 拆成三张卡 |
| 段落缺"输入契约" | 无法判断输入是否齐备 | 补齐五段 |
