# 角色卡创建与更新

角色卡（role card）是多角色协作型技能的标准组成：每个角色一个 Markdown 文件，放在技能目录的 `references/roles/<role>.md` 下，用固定段落描述"谁来做、什么时候做、吃什么、吐什么、怎么做"。

角色卡是纯 Markdown，**不含 frontmatter，不含任何宿主专属语法**，可以随技能一起安装到任何支持 Agent Skills 的宿主。

## 适用场景

- 为多角色技能新增角色：审查者、规划者、实现者、验收者、复盘者等。
- 修改既有角色的职责边界、触发条件、输入输出契约或工作流。
- 把散落在技能正文里的角色说明，整理成可独立分派、可独立校验的角色卡。

## 不适用场景

- 单角色、单流程的技能：直接在技能正文写步骤即可，不需要角色卡。
- 新建整个技能目录：使用 `ae-skill-creator`。
- 通用代码、文档、设计审查：使用 `ae-review`。
- 只需要一段提示词片段：直接写进技能正文，不要新建角色卡。

## 角色卡格式

每个角色卡包含一个标题行和五个固定二级段落，顺序固定、每段非空：

```markdown
# 角色：<角色名>

## 职责

## 触发条件

## 输入契约

## 输出契约

## 工作流
```

| 段落 | 回答的问题 | 内容要点 |
|------|------------|----------|
| `## 职责` | 这个角色负责什么、不负责什么 | 一句交付物说明 + 明确的排除项 |
| `## 触发条件` | 什么时候派发它 | 派发条件 + 不派发条件 |
| `## 输入契约` | 它吃什么 | 输入内容与格式、前置条件、输入不足时的处理 |
| `## 输出契约` | 它吐什么 | 输出结构与字段顺序、证据要求、禁止动作 |
| `## 工作流` | 怎么做 | 编号步骤，最后一步是自检 |

完整字段规范、命名规则与反例见 `references/role-card-conventions.md`；职责边界与措辞的设计要点见 `references/agent-design-patterns.md`；分派与降级措辞见 `references/dispatch-patterns.md`。

## 工作流

### 第 1 步：理解意图

1. 判断是新建角色卡还是更新既有角色卡。
2. 确认角色归属的技能目录。角色卡必须放在该技能自己的角色目录下，不跨技能混放。
3. 确认角色名（kebab-case，如 `security-reviewer`）与角色标题（如 `安全设计审查者`）。
4. 用户没有说明职责边界时，先列出候选职责范围让用户确认，不要自行臆断范围。

### 第 2 步：定位与新建

- 目标文件：`<目标技能目录>/references/roles/<role>.md`。
- 目标不存在时，运行脚手架生成骨架：

  ```bash
  node <本技能目录>/scripts/init_role.mjs security-reviewer --output <目标技能目录> --title "安全设计审查者"
  ```

  `--output` 省略时写入当前目录下的角色目录；指向 `.md` 文件时直接写入该文件。
- 目标已存在时不要重复初始化。脚手架拒绝覆盖既有文件是预期的安全语义，直接进入第 3 步。

### 第 3 步：逐段填写

按"职责 → 触发条件 → 输入契约 → 输出契约 → 工作流"的顺序填写，每段至少写清要点，不留占位符：

1. **职责**：写交付物 + 排除项（明确交给谁、哪些事不做）。
2. **触发条件**：写派发条件 + 不派发条件，让编排层能据此决定是否调用。
3. **输入契约**：写输入内容、格式、前置条件，以及输入不足时的回报方式。
4. **输出契约**：写输出结构与字段顺序、每条结论的证据要求、禁止的动作。
5. **工作流**：写 3-6 步编号流程，最后一步是自检（对照输出契约核对）。

### 第 4 步：校验

```bash
node <本技能目录>/scripts/quick_validate.mjs <目标技能目录>/references/roles/security-reviewer.md
```

校验项：标题行、五个固定段落齐全且非空、段落顺序、无 frontmatter、无宿主专属语法。发现问题就地修复后重新校验。

校验脚本退出码：0 通过，1 失败，2 有告警。

### 第 5 步：交付

向用户说明：新增或更新了哪些角色卡文件、每个角色的一句话职责、校验结果，以及角色卡由谁分派、如何分派（见 `references/dispatch-patterns.md`）。

## 更新既有角色卡

1. 先读取旧角色卡全文，不要在没读懂旧内容时直接覆盖。
2. 列出保留项、修改项、删除或重写项，并说明原因。
3. 只做最小编辑：保留仍然有效的职责边界、触发条件、输出契约和禁止事项。
4. 职责边界扩大、删除旧的安全边界或禁止事项时，必须单独向用户确认。
5. 改完重新校验，并给出逐段差异摘要。

## 角色卡与正文内联说明的取舍

| 情况 | 做法 |
|------|------|
| 角色需要独立分派、独立上下文 | 写成角色卡 |
| 角色只是正文里的一个小步骤 | 留在正文，不建卡 |
| 技能只有一张角色卡 | 通常说明没有拆分必要，留在正文更清晰 |
| 角色之间输入输出没有差异 | 合并成一张卡 |
| 同一角色的多个变体 | 用一张卡 + 不同触发条件表达，不复制文件 |

## 禁止事项

- 不在角色卡里写宿主专属语法：宿主专属工具名、宿主专属路径、宿主专属 frontmatter 字段、宿主专属占位符。
- 不写具体工具调用语法，改写为能力描述（见 `references/dispatch-patterns.md`）。
- 不把角色写成"什么都做"的万能助手；每个角色必须有明确排除项。
- 不在一张卡里塞多个角色。
- 不覆盖既有角色卡；脚手架拒绝覆盖是预期安全语义。
- 不在只读角色的卡里要求写文件、改仓库或执行破坏性操作，除非职责本身就是执行类角色。
- 不让角色卡引用不存在的文件。
