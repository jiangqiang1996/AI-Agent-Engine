# 各步骤执行细则

本文件是 `ae-align-verify` 的执行细则。**执行每个步骤前先读取对应章节。**

---

## 第零步：定位最新设计与对应需求

若范围不含步骤 0，跳过本步第 4 条的跳转判定，但仍需确定设计真源与需求真源。

1. 若参数含 `design=<路径>`，直接使用该路径作为当前设计真源；否则扫描 `ae/design/` 目录，按目录名日期后缀（`-YYYY-MM-DD`）降序排列，取最新设计目录作为当前设计真源。
   - `ae/design/` 不存在或为空时，提示用户先运行 `ae-design` 创建设计，或通过 `design=<路径>` 显式提供，并停止执行。
2. 若参数含 `prd=<路径>`，直接使用该路径作为当前需求真源；否则从当前设计的 `overview.md` 或 frontmatter 中提取其引用的需求路径；若未显式引用，按名称前缀在 `ae/prd/` 中匹配对应需求目录。
3. 提取所有 `key=value` 参数、自然语言范围短语和路径参数后，剩余非 `key=` 形式的纯文本视为裸提示词需求内容，作为当前需求真源，并标记为**非全量需求**。
4. 范围含步骤 0 时：存在对应需求 → 进入第一步；不存在需求 → 跳过第一步，直接进入第二步。范围不含步骤 0 时：本条不执行，直接进入范围内的首个步骤。

---

## 第一步：设计对齐需求

调用 `ae-design` 技能，以当前需求目录为输入重新生成设计。
`ae-design` 从标准位置 `ae/prd/` 与 `ae/design/` 自动发现产物；使用自定义路径时需确保产物已置于标准位置，或通过 `design=` / `prd=` 指定。额外参数透传给 `ae-design`。

- **对齐前必须判断需求是否为当前项目的全量需求**：若需求仅覆盖部分模块（含裸提示词需求），只对齐该需求提及的模块和内容，**禁止删除或修改需求未提及的模块**。
- 对齐后的设计即为后续所有步骤的唯一设计真源。
- 禁止镀金，不新增需求未声明的设计内容。
- 一步到位，不保留过渡版本。

---

## 第二步：源码对齐设计

调用 `ae-work` 技能，以当前设计目录为输入，将当前项目源码对齐到设计。额外参数透传给 `ae-work`。

- **对齐前必须判断设计是否为当前项目的全量设计**：若设计仅覆盖部分模块，只对齐该设计提及的模块和内容，**禁止删除或修改设计未提及的模块及其源码**。
- 修复过程中**以设计为准，设计空缺时以需求为准**。
  "设计空缺"指当前设计目录中不存在对应模块的设计文件，或设计文件中未覆盖该模块/维度的内容。
- 禁止镀金，不实现设计未声明的功能。
- 一步到位，不考虑兼容更新。

---

## 第三步：单元测试

先对齐单元测试脚本到设计用例，再执行，确保全部通过。额外参数透传给 `ae-unit-test`。

### 对齐测试脚本

1. 从当前设计目录定位 `modules/<NN>-<m>/test-cases.md`，提取设计用例清单。
2. 检查项目测试目录（如 `tests/`、`src/test/`）是否存在对应单元测试文件（按模块名 / 类名 / 函数名匹配）：
   - **不存在** → 调用 `ae-unit-test`，从设计用例编译测试骨架、生成并执行。
   - **存在** → 在命令层对齐测试逻辑：设计用例新增则补对应测试，删除则删对应测试，修改则改对应测试逻辑；对齐后调用 `ae-unit-test` 执行已有测试。
3. 对齐只处理设计用例与现有脚本的 diff，**不新增设计未声明的测试**。

### 修复

- 测试失败时使用 `ae-backend-fix` 修复，修复以设计为准，设计空缺时以需求为准。
- 禁止镀金，不为设计未声明的场景编写测试。
- 一步到位，确保全部单元测试通过后进入下一步。

---

## 第四步：接口测试

对齐接口测试脚本到设计用例并执行，确保全部通过。额外参数透传给 `ae-api-test`。

### 对齐并执行

1. 从当前设计目录定位 `modules/<NN>-<m>/test-cases.md`，提取设计用例清单。
2. 检查 `ae/api-test/` 是否存在已有接口测试脚本：
   - **不存在** → 调用 `ae-api-test` 新建模式，从设计用例编译接口测试骨架、生成并执行。
   - **存在** → 将已有脚本传入 `ae-api-test` 触发更新模式，在已有脚本基础上增删改并自动执行。
3. 对齐只处理设计用例与现有脚本的 diff，**不新增设计未声明的接口测试**。

### 修复

- 测试失败时使用 `ae-backend-fix` 修复，修复以设计为准，设计空缺时以需求为准。
- 禁止镀金，不编写设计未声明的接口测试。
- 一步到位，确保全部接口测试通过后进入下一步。

---

## 第五步：E2E 测试

先对齐 E2E 测试脚本到设计用例，再执行，确保全部通过。**默认使用 Edge 浏览器。**
额外参数透传给 `ae-e2e-test`，可覆盖默认浏览器与 mode。

### 对齐测试脚本

1. 从当前设计目录定位 `modules/<NN>-<m>/test-cases.md`，提取设计用例清单。
2. 检查 `ae/e2e-test/` 是否存在已有 `.spec.ts` 测试脚本：
   - **不存在** → 调用 `ae-e2e-test`（默认 script 模式），从设计用例编译 Playwright 骨架、生成并执行。
   - **存在** → 在命令层对齐测试逻辑：新增则补对应测试脚本，删除则删，修改则改逻辑；对齐后调用 `ae-e2e-test` 执行已有测试。
3. 对齐只处理设计用例与现有脚本的 diff，**不新增设计未声明的页面流程测试**。

### 修复

- 测试失败时使用 `ae-frontend-fix` 修复，修复以设计为准，设计空缺时以需求为准。
- 禁止镀金，不编写设计未声明的页面流程测试。
- 一步到位，确保全部 E2E 测试通过。
