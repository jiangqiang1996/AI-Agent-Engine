# 迭代任务循环

目标驱动的自包含迭代执行器。子代理隔离实施 + `ae-review` 审查闭环，每轮实施委托子代理执行以隔离中间上下文，不产出需求/设计文档。

**适用场景：** 探索性调试、环境搭建、遗留代码修复
**不适用场景：** 有明确设计 → `ae-work`；需求不明确 → `ae-prd`；代码审查 → `ae-review`

## 核心原则

1. **交互全部前置** — Phase 0 解决所有用户问题，此后直至 Phase 3 禁止交互式提问能力或任何形式提问
2. **成功条件锁死** — Phase 0 确认的成功条件列表不可在循环中修改；条件有误属于瓶颈退出
3. **原始目标为真** — 用户原始目标文本作为实施依据
4. **子代理隔离实施** — 每轮实施通过子代理派发能力（若宿主支持子代理派发能力）委托子代理执行（搜索、编辑、验证均在子代理内完成），主会话仅保留子代理返回的结构化摘要；禁止在主会话内直接编辑文件或运行实施命令
5. **ae-review 审查闭环** — 每轮变更后调用 `ae-review` 技能的 autofix 模式，审查发现驱动修复
6. **双重退出校验** — `ae-review` 无阻断发现 AND 成功条件全部达成，两者独立校验不互蕴含
7. **遇到歧义自行决策** — 循环体中不确定情况自行选择最优解，不得暂停或退出
8. **上下文隔离** — 子代理的中间过程（文件搜索、代码阅读、编辑操作、验证输出）不进入主会话上下文；主会话仅累积每轮结构化摘要和审查结论，保持上下文精简

## 能力抽象

本技能只依赖下列宿主能力，不依赖任何特定宿主的工具名、目录或参数写法：

| 能力 | 用途 | 常见别名 |
|------|------|----------|
| 文件读取能力 | 读取项目文件、依赖清单、配置 | Read / read_file / 读取文件 |
| 命令执行能力 | 执行验证命令、版本控制查询 | Bash / bash / shell |
| 文件编辑能力 | 实施变更（通常在子代理内完成） | Edit / Write / 编辑文件 |
| 子代理派发能力 | 派发实施子代理 | 派发子代理 / subagent |
| 交互式提问能力 | 仅 Phase 0 与 Phase 3 使用 | AskUserQuestion / question |

**并行/降级范式：** 若宿主支持子代理派发能力，审查与实施任务可并行派发，每任务一份独立上下文；若不支持，则在当前会话内顺序执行同一批任务，产出格式不变。

## 输入

<goal> #用户输入 </goal>

如果 `<goal>` 为空，询问用户："你想完成什么目标？"

**ae-work 排除规则：** 输入解析时无视 `ae-work` 或 `/ae-work` 前缀，不作为执行技能注入；全流程禁止调用 `ae-work` 技能。

## 子代理委托规范

### 角色选择

角色卡是纯 Markdown，位于 `references/roles/`，不绑定任何宿主的代理标识：

| 任务性质 | 角色卡 |
|----------|--------|
| 通用 / 不确定 | `references/roles/general.md`（通用执行者） |
| 调试修复为主 | `references/roles/backend-fix.md`（后端修复执行者） |
| 后端代码为主 | `references/roles/backend-dev.md`（后端开发执行者） |
| 前端开发（视觉/逻辑/设计还原） | `references/roles/frontend-dev.md`（前端开发执行者） |
| 前端修复（视觉/交互/接口/a11y） | `references/roles/frontend-fix.md`（前端修复执行者） |
| 前端浏览器测试/验收 | `references/roles/e2e-test-runner.md`（端到端测试执行者） |

> 上表的角色卡是本技能的**内部职责定义**，不绑定任何宿主的代理标识。委派时把对应角色卡全文随 prompt 一并传入；若工作区内存在语义等价的技能（如 `ae-backend-fix`、`ae-frontend-fix`、`ae-e2e-test`），优先委派该技能。

**并行派发**：若宿主支持子代理派发能力，将下列角色卡**并行**分派，每卡一份独立上下文；若不支持，则在当前会话内**顺序**执行同一批角色卡，产出格式不变。

### 子代理 prompt 模板

委托子代理时 prompt 必须包含所选角色卡的全文（`references/roles/<role>.md`）与以下全部要素：

```
## 项目上下文
项目类型: <全新 / 存量>
技术栈: <如 React+TypeScript+Vitest / Java+Spring+JUnit / 无>
可复用资产: <已有组件/工具函数列表，或"无">
实现约束: <必须使用检测到的技术栈，不得引入不一致的新依赖；优先复用已有资产>

## 任务目标
<用户原始目标文本>

## 成功条件
<全部成功条件列表，标注各条件当前达成状态 ✅/❌>

## 本轮触发
<上轮审查发现摘要 或 未达成的成功条件列表>

## 约束
- 只针对未达成的成功条件变更，禁止修复与目标无关的审查发现
- 禁止提问，禁止调用 ae-work，不确定时自行选择最优解
- 变更后运行相关验证命令确认变更有效性

## 返回要求
返回结构化摘要，格式：
变更摘要: <文件路径列表 + 每个文件的变更说明>
验证结果: <执行的验证命令及结果>
阻塞问题: <遇到的问题，或"无">
```

### 子代理失败处理

子代理返回错误、未产出有效变更或返回格式不可解析时，计入瓶颈计数（+1），不中止管道；主会话记录失败原因后继续退出判定流程。

### 技术栈约束

存量项目时子代理必须使用检测到的技术栈，不得引入不一致的新依赖；全新项目时按目标选择最简技术栈。可复用资产优先复用，需新建时在返回摘要的变更说明中标注原因。

## 后台命令执行

需要在不阻塞当前会话的情况下运行长时间命令（如启动开发服务、跑长时间测试）时：

1. 首选使用宿主的命令执行能力，以后台方式启动命令并把输出写入日志文件，再单独读取日志文件确认结果。
2. 若宿主的命令执行能力不支持后台执行，可直接使用本技能附带的 `scripts/async-bash.mjs`（后台启动 + 日志落 `ae/logs/task-loop/`），它实现了后台启动 + 日志读取的通用做法。

无论采用哪种方式，都不得让长生命周期命令阻塞当前会话；必须以"启动 → 轮询/读取日志 → 判定结果"的方式推进。

## 工作流

### Phase 0：准备（允许交互）

#### 0.1 解析用户目标 — 解读 `<goal>`，识别核心意图与约束
#### 0.2 扫描项目状态 — 自动检测项目上下文，不询问用户：

| 检测层 | 内容 | 信号 |
|--------|------|------|
| 项目类型 | 全新 / 存量 | `package.json`、`pom.xml`、`build.gradle`、`go.mod`、`Cargo.toml`、`requirements.txt`、`pyproject.toml`、`src/` 等 |
| 技术栈 | 语言 + 框架 + 构建工具 + 测试框架 | 依赖文件中的框架标识、配置文件存在性 |
| 可复用资产 | 已有组件 / 工具函数 / 配置 / 测试基础设施 | 源码目录结构、已有封装模块 |

存量项目 → 识别技术栈并扫描可复用资产，生成项目上下文摘要供子代理使用；全新项目 → 标记"无现有技术栈"，子代理按目标自行选择最简技术栈。扫描失败不阻断流程，标记"项目检测不可用"后继续。同时返回是否有相关实现（是/否）+ 实现概况，供 Phase 1 条件性跳过判定。
#### 0.3 ae-grill 深度追问 — 调用 `ae-grill` 技能对用户目标进行逐层追问，逐个澄清决策歧义。`ae-grill` 一问一答推进共识，产出共识清单、决策依赖和遗留风险。目标描述清晰无歧义时（如明确的 bug 修复或单文件配置变更）可跳过此步骤，直接进入 0.4
#### 0.4 推导成功条件 — 基于 0.1 目标解读、0.2 项目状态、0.3 ae-grill 共识清单与遗留风险，推导 3-8 条可客观验证的成功条件，格式 `SC-N: 描述 [verify: 验证命令或检查方式]`。验证方式为可执行的命令、测试命令或文件存在性检查。ae-grill 遗留风险中与目标直接相关的条目应反映到成功条件中（如增加"遗留风险 X 不触发"或"遗留风险 X 有降级方案"的条件）

**软件任务边界覆盖（涉及代码变更时）：** 成功条件必须覆盖以下边界类别，每类至少一条：

| 边界类别 | 说明 |
|----------|------|
| 正常路径 | 核心功能在标准输入下正确工作 |
| 空值/缺失 | 空输入、null、缺失字段、空集合 |
| 边界值 | 最小值、最大值、临界值、超长输入 |
| 错误路径 | 无效输入、异常状态、资源不存在 |
| 幂等性（如适用） | 重复执行不产生副作用 |

非软件任务（无代码变更）不要求边界覆盖。
#### 0.5 展示确认清单 + 用户确认 — 展示目标解读、项目上下文摘要（项目类型 + 技术栈 + 可复用资产）、ae-grill 共识摘要（关键决策结论）、成功条件列表；用户确认后锁死

> **Phase 0 结束。⛔ 此后直至 Phase 3，禁止任何用户交互。**

### Phase 1：条件性首次子代理实施

根据 0.2 扫描结果：

- **无相关实现** → 按"子代理委托规范"通过子代理派发能力（若宿主支持子代理派发能力）委托子代理执行首次变更，传入全部成功条件（均未达成）作为触发；主会话保留子代理返回的结构化摘要
- **已有相关实现** → 跳过 Phase 1

完成后无条件进入 Phase 2。

### Phase 2：子代理实施 + ae-review 循环（禁止交互）

**参数：** 上限 30 轮，瓶颈阈值连续 3 轮无新增达成的成功条件。一轮 = 一次完整的"子代理实施 → `ae-review` autofix 模式"调用。

#### Step 1：子代理委托实施

按"子代理委托规范"使用子代理派发能力（若宿主支持子代理派发能力）委托子代理执行本轮实施。

变更触发来源为双重路径：
- (a) 上轮 ae-review 有未通过项 → 将审查发现摘要作为本轮触发传入子代理 prompt
- (b) 审查通过但成功条件未全部达成 → 将未达成的成功条件作为本轮触发传入子代理 prompt
- 首轮触发：Phase 1 跳过时以成功条件未达成为触发源；Phase 1 已执行变更时可直接进入 Step 2 审查

主会话仅保留子代理返回的结构化摘要（变更摘要、验证结果、阻塞问题），不保留子代理内部的搜索、编辑和验证中间过程。

#### Step 2：ae-review 审查闭环

- **软件任务**（涉及代码文件变更）：`ae-review mode=autofix goals=<成功条件列表>`
- **非软件任务**（无代码变更）：`ae-review mode=autofix goals=<成功条件列表>`
- **混合任务**：按软件任务处理，审查范围描述同时包含代码和文档质量方向
- 成功条件列表通过 `goals=` 参数传入 `ae-review`，激活目标对齐角色卡逐条校验变更是否达成各项目标

**失败处理：** ae-review 整体失败（技能不可用等）时管道中止，报告已完成步骤、失败步骤和原因；部分专精角色卡失败时以已有审查发现继续，在最终报告标注未完成审查维度。

#### Step 3：退出判定

每轮结束后对每个未达成的成功条件执行其 verify 方法，通过则标记达成并记录证据。有新增达成则瓶颈计数归零，无新增则 +1。

**独立校验两项：** ① ae-review 无阻断发现 ② 成功条件全部达成（verify 全通过，非由审查结论蕴含）。两项同时满足 → Phase 3（全部通过 ✅）。

不满足时按优先级：
| 优先级 | 条件 | 动作 |
|--------|------|------|
| 1 | 瓶颈计数 ≥ 3（连续 3 轮无新增达成的成功条件） | Phase 3（瓶颈退出 ⚠️） |
| 2 | 轮次 ≥ 30 | Phase 3（上限退出 ⚠️） |
| 3 | 其他 | → 回到 Step 1 |

#### → 回到 Step 1

### Phase 3：退出处理（允许交互）

**全部通过 ✅** — 输出 DONE，逐条列出每条成功条件的通过证据（文件路径、代码片段或测试结果）。

**瓶颈退出 ⚠️** — 展示诊断摘要（总轮次、通过/未通过条件及受阻原因、最近 3 轮子代理变更摘要、审查发现重复模式），用交互式提问能力提供选项：继续尝试 / 结束任务 / 切换方案。

**上限退出 ⚠️** — 展示进度摘要（总轮次 30、通过/未通过条件、最近 3 轮子代理变更摘要与变化趋势），用交互式提问能力提供选项：继续尝试 / 结束任务 / 切换方案。

## 产物路径

| 类型 | 路径 |
|------|------|
| 循环运行记录 | `ae/task-loop/run-<timestamp>.md` |
| 轮次日志 | `ae/task-loop/logs/` |
| 通用日志 | `ae/logs/task-loop/` |

本技能只写 `ae/task-loop/` 与共享的 `ae/logs/`，不写其他技能的产物目录。运行记录至少包含：原始目标、成功条件列表、每轮子代理摘要、每轮审查结论、最终退出类型与证据。

## 边界

- 不产出需求文档或设计文档，产物只有代码、配置与本技能的运行记录。
- 循环体（Phase 1-2）内禁止任何形式提问，歧义自行决策并记录。
- 成功条件在 Phase 0 后不可修改；条件有误按瓶颈退出处理。
- 不得调用 `ae-work` 技能；实施全部通过子代理完成。
