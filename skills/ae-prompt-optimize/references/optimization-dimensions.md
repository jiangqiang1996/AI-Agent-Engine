# 六个优化维度

本技能的优化只做**最小必要改写**：把用户已经说清楚的内容原样保留，只补齐缺失、消除歧义、重排结构。
每个维度都给出「检测信号 → 改写动作 → 禁止事项」，供阶段 4 逐维执行与自检。

---

## 维度总览

| # | 维度 | 英文标识 | 一句话目标 | 是否允许补充新信息 |
|---|------|----------|-----------|-------------------|
| 1 | 清晰度 | clarity | 一次阅读即可理解完整意图 | 否 |
| 2 | 上下文 | context | 补齐执行所需的已知背景 | 是（仅"有关"分支，需可观察依据） |
| 3 | 结构 | structure | 把口语化叙述改写为结构化任务描述 | 否 |
| 4 | 约束 | constraints | 显式写出边界、禁止项、必须遵守的规则 | 否 |
| 5 | 输出格式 | output format | 明确产出形态与验收口径 | 否 |
| 6 | 示例 | examples | 用正例/反例钉住"要什么、不要什么" | 是（需与用户意图一致） |

---

## 1. 清晰度（clarity）

**检测信号**

- 目标缺失："帮我搞一下那个东西"
- 范围模糊："优化一下"
- 对象不清："改一下文件"
- 条件缺失："做个功能"
- 动词空洞："处理一下"、"完善一下"
- 一句话包含多个并列任务但没有分界

**改写动作**

1. 把空洞动词替换为具体动作（"处理" → "重构/排查/补齐"）
2. 把模糊对象替换为可定位的指称（"那个文件" → "src/parser.ts"）
3. 把范围写成一个可枚举的集合（"几个模块" → "src/a.ts、src/b.ts"）
4. 拆开一句话中的多个任务，用编号或分段表达

**禁止事项**

- 不得替用户决定没表达的目标；宁可标注模糊点也不臆断

---

## 2. 上下文（context）

**检测信号**

- 提示词依赖当前工作空间的既有事实（技术栈、目录结构、已有组件、运行环境）但未说明
- 提示词像是只写了一半的"续写请求"

**改写动作**

1. 补入用户已提及的事实，原样保留
2. 补入文件系统可见的事实（依赖清单中的框架标识、目录结构、已有工具函数），并**标注来源**
3. 补入运行环境前提（目标平台、构建方式、可用命令）

**禁止事项**

- "无关"分支下**禁止**补充工作空间上下文
- 不得凭空假设文件路径、模块名或技术栈
- 补充内容必须能给出可观察依据（用户已提及或文件系统可见），否则不补

**来源标注写法**：`（依据：项目依赖清单中已声明 X 框架）`

---

## 3. 结构（structure）

**检测信号**

- 提示词是单段长叙述或多句并列流水账
- 任务、要求、验收标准混在一起
- 关键信息埋在段落中部

**改写动作**

1. 按"目标 → 背景 → 任务清单 → 约束 → 验收标准"分块
2. 并列任务用有序列表，每条一行一个动作
3. 验收标准独立成块，与任务描述分开
4. 保持用户的原有语言与术语

**禁止事项**

- 不得新增用户未提过的任务、章节或步骤
- 不得为了"看起来完整"补写与目标无关的段落

---

## 4. 约束（constraints）

**检测信号**

- 用户已经说了"不要怎样 / 只能怎样 / 保持怎样"，但散落在叙述中
- 提示词完全没写边界，实施方需要猜测

**改写动作**

1. 把散落的限制条件集中到独立的"约束"块
2. 保留用户原始措辞，不改写强度（"必须"不降级为"建议"）
3. 用户明确排除的内容原样保留在排除项中

**禁止事项**

- 不得擅自添加用户没有要求的约束
- 不得删除或弱化用户已声明的约束

---

## 5. 输出格式（output format）

**检测信号**

- 用户说"写一份文档 / 改这个函数 / 给我个表格"，但没说清产出落到哪、什么形态
- 提示词会让实施方在 Markdown 表格、代码块、纯文本之间随机选择

**改写动作**

1. 明确产出形态（文件路径 + 格式，或代码块 + 语言，或表格 + 列定义）
2. 明确交付口径（需要包含哪些章节/字段、是否需要示例）
3. 若用户已指定格式，原样保留

**禁止事项**

- 不得强行指定用户未提及的技术实现形式；只约束"产出形态"，不约束"如何实现"

---

## 6. 示例（examples）

**检测信号**

- 描述抽象，实施方对"做到什么程度"没有把握
- 用户自己给了例子但例子没被整理进提示词

**改写动作**

1. 需要时给出一个最小正例，钉住期望的形态或粒度
2. 用户提供了例子时，原样搬入优化后的提示词
3. 例子只示范形态，不示范与目标无关的具体内容

**禁止事项**

- 不得虚构与用户业务不符的例子
- 不得把例子写成"必须照抄的模板"，改变用户意图

---

## 逐维自检清单

优化完成后逐项确认：

- [ ] 清晰度：每个动词、对象、范围是否都可定位、无歧义？
- [ ] 上下文：补充的每一条是否有可观察依据并标注来源？"无关"分支是否完全没有补充？
- [ ] 结构：是否按目标/背景/任务/约束/验收分块，且没有新增任务？
- [ ] 约束：用户已声明的限制是否集中保留且未被弱化？
- [ ] 输出格式：产出形态与验收口径是否明确，且未越界规定实现方式？
- [ ] 示例：例子是否必要、是否与用户意图一致、是否被原样搬入？

整体自检：

- [ ] 用户原始意图是否完整保留？
- [ ] 优化结果是否未与原始逻辑违背？
- [ ] 用户提到的引用是否都已保留且未被修改？
- [ ] 是否未添加任何元描述或引导文本？
