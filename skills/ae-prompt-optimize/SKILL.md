# 提示词优化

## 角色与目标

将用户随意输入的提示词优化为结构化、利于 AI 执行的提示词，并**落盘成文件**，让用户可以随时复制到任何会话、任何工具中使用。

优化必须忠实于用户原始意图，禁止与原始逻辑违背。本技能**不创建会话、不导航任何界面、不代替用户执行目标任务**——它只产出两样东西：聊天中可直接复制的优化版提示词，和 `ae/prompt-optimize/` 下的同名文件。

## 适用场景

- 用户输入口语化、模糊或结构松散的提示词，希望提升 AI 执行效果。
- 用户提示词信息不足、意图不清，需要先追问澄清再优化。
- 用户希望拿到一份可以复制到别处使用的"标准版"提示词。
- 用户通过 `mode=auto` 或 `mode=pause` 参数预先指定确认策略，希望一键拿到结果。

## 不适用场景

- 用户提示词已经结构化、清晰且无需优化。
- 用户要求直接执行任务而不是优化提示词（本技能只产出提示词，不执行目标任务）。

## 能力抽象

本技能只依赖下列宿主能力，不依赖任何特定宿主的工具名、目录或参数写法：

| 能力 | 用途 | 常见别名 |
|------|------|----------|
| 文件读取能力 | 读取工作空间文件以判断上下文相关性 | Read / read_file / 读取文件 |
| 文件写入能力 | 落盘优化后提示词 | Write / write_file / 写入文件 |
| 命令执行能力 | 必要时查看目录结构与依赖清单 | Bash / bash / shell |
| 交互式提问能力 | 意图澄清与优化结果确认 | AskUserQuestion / question |

## 执行流程

### 阶段 0：解析参数

解析用户输入中的 `mode` 参数，决定阶段 5 的确认策略：

| 参数值 | 含义 | 阶段 5 行为 | 阶段 6 行为 |
|--------|------|-------------|-------------|
| `mode=auto` | 直接给最终结果 | 跳过对比确认提问 | 落盘并直接给出最终提示词 |
| `mode=pause` | 给出对比后再确认 | 展示"原始 / 优化后"对比后用交互式提问能力确认 | 确认后落盘并给出最终提示词 |
| 未提供 | 给出对比后再确认 | 同 `mode=pause` | 同 `mode=pause` |

参数解析规则：

1. 支持 `key=value`、`key:value`、`--key=value`、纯值自动推断四种形式（AE 技能参数通用约定）。
2. 纯值 `auto` 或 `pause` 自动推断为 `mode` 参数。仅当 `auto`/`pause` 作为独立 token 出现时才推断为 `mode`；若嵌入在句子中作为普通词语（如"帮我优化 auto 这个词的用法"），按普通提示词处理，不推断为 `mode`。
3. `mode` 参数缺失或值非 `auto`/`pause` 时，按"未提供"处理。
4. `mode` 只影响阶段 5 的确认策略，**不跳过阶段 2 的意图澄清**——提示词本身信息不足时仍需先澄清（`mode=auto` 下澄清最多进行 1 轮）。
5. `mode` 是**普通文本参数**，不是任何宿主工具的开关；解析后只在本次技能执行内生效。

### 阶段 1：解析用户输入

1. **识别引用**：扫描提示词中用户明确提到的引用：
   - 以 `/` 开头的命令引用
   - 以 `@` 开头的代理或文件引用
   - 包含 `:` 或 `-` 连接的多词标识符（如 `ae-brainstorm`、`task-loop`）

   匹配到的引用原样保留，不校验其是否真实存在，不当作普通词语对待。

2. **命令前缀保留**：如果提示词以 `/命令名 ` 开头（命令名后跟空白），把 `/命令名 ` 作为不可修改的前缀保留，只对空白之后的参数部分做阶段 4 优化。阶段 2-3 可参考命令前缀语义作为上下文，但优化对象仅限参数部分；命令前缀本身不修改、不展开、不校验是否存在。优化结果始终保持 `/命令名 优化后参数` 形式。

3. **提取实际提示词**：识别引用和命令前缀后，将可优化部分与不可修改部分分离，准备对可优化部分进行优化。

### 阶段 2：意图澄清

用户原始提示词可能存在信息不足或意图模糊的情况。在进入优化前，必须评估提示词的清晰度：

**模糊信号检测：**

| 信号 | 示例 |
|------|------|
| 目标缺失 | "帮我搞一下那个东西" — 无明确目标 |
| 范围模糊 | "优化一下" — 优化什么？哪些方面？ |
| 对象不清 | "改一下文件" — 哪个文件？改什么内容？ |
| 条件缺失 | "做个功能" — 什么功能？给谁用？有什么约束？ |
| 动词空洞 | "处理一下"、"完善一下" — 具体做什么操作？ |

**追问规则：**

1. 如果检测到模糊信号，使用交互式提问能力向用户发起追问，每次只问一个最关键的澄清问题。
2. 追问问题必须聚焦于对优化结果影响最大的缺失信息（目标、范围、对象、约束）。
3. 追问问题附带推荐理解方向，帮助用户快速补充信息。
4. 用户补充信息后，合并到原始提示词，重新评估清晰度。
5. 最多追问 3 轮（`mode=auto` 下最多 1 轮）；如果达到上限仍不清晰，以当前最佳理解为基础继续优化，并在产物的"仍存模糊点"中标注。
6. 如果提示词足够清晰（目标明确、范围可界定、无关键信息缺失），跳过追问，直接进入阶段 3。

**与深度追问技能的区别：**

- 本技能的追问是快速澄清提示词意图，1-3 轮内完成，目的是让优化有足够输入。
- `ae-grill` 技能是对已有方案的逐层决策压力测试，追问更深入、更系统。
- 如果追问过程中发现用户需要深度探讨决策合理性，建议转交 `ae-grill` 技能。

### 阶段 3：工作空间相关性分析

在优化前，判断用户提示词是否与当前工作空间的文件相关：

- **相关信号**：提示词显式或隐式指向当前工作空间内的文件、目录、模块、代码符号、配置、资产或项目结构。例如提到具体路径、文件名、模块名、技能名、命令名，或描述针对当前项目的修改、审查、构建、测试等操作。
- **无关信号**：提示词是通用问答、纯概念讨论、与当前项目无关的外部任务，或用户已提供完整自包含上下文。

判断结论决定阶段 4 的上下文维度策略：

| 相关性 | 优化策略 |
|--------|----------|
| 无关 | 禁止镀金、禁止蔓延边界。仅对非引用部分做结构化与清晰度优化，不补充工作空间上下文，不假设文件路径或技术栈 |
| 有关 | 可结合当前工作空间情况适度优化。补充的上下文必须有可观察依据（用户已提及、文件系统可见），并标注来源；不得凭空假设 |

工作空间相关性判断的依据必须可复核：若结论为"有关"，至少说明一条可观察信号；若证据不足，按"无关"处理。

### 阶段 4：六维优化

对非引用部分的文本按六个维度执行优化，维度定义与检测信号见 [六个优化维度](references/optimization-dimensions.md)：

1. **清晰度（clarity）** — 消除歧义表述，使 AI 能一次理解完整意图
2. **上下文（context）** — 仅在"有关"分支下，根据可观察依据补充隐含信息并标注来源
3. **结构（structure）** — 将模糊、口语化的表述转为结构化的任务描述（目标、背景、任务、约束、验收）
4. **约束（constraints）** — 把用户已声明的限制条件集中显式化，不擅自新增
5. **输出格式（output format）** — 明确产出形态与验收口径，不越界规定实现方式
6. **示例（examples）** — 需要时给出正例/反例，钉住期望形态；用户提供的例子原样搬入

**硬规则（绝不可违反）：**

- 不得改变用户原始意图和逻辑。
- 优化后的提示词不得与原始逻辑违背：用户未要求的步骤、范围、约束不得擅自添加；用户明确排除的不得擅自保留。
- 用户提到的引用原样保留，不做任何修改。
- 优化后提示词应直接表达目标任务，避免在下游再次触发提示词优化流程。
- "无关"分支下禁止补充工作空间上下文；禁止凭空假设文件路径、模块名或技术栈。
- 如果优化后提示词涉及浏览器操作，必须明确要求执行方通过标准 Playwright（`npx playwright`）操作浏览器；需要完整 E2E 工程能力时明确指向 `ae-playwright-verify` 技能。

**自检清单**：按 [六个优化维度](references/optimization-dimensions.md) 末尾的逐维自检清单逐项确认。

### 阶段 5：用户确认

1. **展示优化结果**：直接输出优化后的完整提示词，不得包含"这是优化后的提示词"、"优化结果如下"等任何元描述或引导文本。
2. **参数分流**：
   - `mode=auto`：跳过对比确认提问，展示后直接进入阶段 6。
   - `mode=pause` 或未提供 `mode`：展示"原始提示词 / 优化后提示词"对比，然后使用交互式提问能力询问用户选择，选项包括：
     - **采用当前版本** — 直接落盘并交付
     - **继续修改** — 结合用户新的输入继续优化
   - 交互提问必须提供选项，不能只做开放式提问。
3. **多轮修改**：若用户选择继续修改，根据反馈迭代调整，修改完成后再次展示并询问确认。
   - 始终以原始输入作为参考锚点，避免多轮迭代后偏离原始意图。
   - 若用户修改意见与硬规则冲突（如要求删除引用），告知冲突但遵从用户最终决定。
   - 每轮修改后重新执行自检清单。
4. **确认落盘**：用户明确选择"采用当前版本"后方可进入阶段 6。`mode=auto` 跳过本步骤。

### 阶段 6：落盘与交付

1. **落盘**：把最终优化后的提示词写入 `ae/prompt-optimize/<slug>-<YYYYMMDD-HHMMSS>.md`，文件格式见 [优化后提示词文件模板](references/artifact-template.md)。
2. **回报**：在聊天中给出优化后提示词正文（与文件中的完全一致）+ 产物文件路径。
3. **不做的事**：不创建新会话、不导航任何界面、不代替用户执行目标任务。

## 产物路径

| 类型 | 路径 |
|------|------|
| 优化后提示词 | `ae/prompt-optimize/<slug>-<YYYYMMDD-HHMMSS>.md` |
| 日志 | `ae/logs/prompt-optimize/` |

本技能只写 `ae/prompt-optimize/` 与共享的 `ae/logs/`，不写其他技能的产物目录。同一 slug 多次优化生成不同文件，不覆盖历史版本。

## 输出要求

- 优化结果展示必须干净利落：直接输出提示词内容本身，不得包含任何元描述或引导文本。
- 落盘后附一句产物路径说明即可，不重复展示附录内容。
- 追问时每次只问一个问题，并给出选项。
- 失败时输出错误信息和可恢复的提示词全文，提供重试或手动复制选项。

## 验证方式

- 内容校验：优化结果同时存在于聊天输出与产物文件的"优化后的提示词"章节，且两处完全一致。
- 引用校验：用户提到的引用在优化后提示词中逐字保留。
- 维度校验：六个维度的自检清单全部通过，且"无关"分支下没有任何补充的工作空间上下文。
- 落盘校验：产物文件存在于 `ae/prompt-optimize/`，文件名符合 `<slug>-<YYYYMMDD-HHMMSS>.md`。

## 禁止事项

- 不得改变用户原始意图和逻辑。
- 不得在"无关"分支补充工作空间上下文。
- 不得凭空假设文件路径、模块名或技术栈。
- 不得跳过阶段 5 的用户确认（除非 `mode=auto`）。
- 不得创建新会话，不得导航任何界面，不得在本技能内执行目标任务。
- 不得把附录内容混入"优化后的提示词"章节。
