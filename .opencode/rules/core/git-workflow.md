# Git 工作流规范

## 分支策略

### 分支命名

| 类型 | 格式 | 示例 |
|------|------|------|
| 功能 | `feat/<简短描述>` | `feat/add-agent-tool` |
| 修复 | `fix/<简短描述>` | `fix/tool-execution-error` |
| 重构 | `refactor/<简短描述>` | `refactor/hook-layer` |
| 文档 | `docs/<简短描述>` | `docs/api-reference` |
| 测试 | `test/<简短描述>` | `test/tool-integration` |

### 分支流程

1. 从 `main` 创建功能分支
2. 开发完成后创建 Pull Request
3. 通过代码审查后合并到 `main`
4. 删除已合并的功能分支

## 提交规范

### 提交信息格式

```
<类型>(<范围>): <简短描述>

<详细描述>（可选）
```

### 类型标识

| 类型 | 说明 |
|------|------|
| `feat` | 新功能 |
| `fix` | 修复 Bug |
| `refactor` | 重构（不改变外部行为） |
| `docs` | 文档变更 |
| `test` | 测试相关 |
| `chore` | 构建/工具变更 |
| `perf` | 性能优化 |

### 示例

```
feat(tools): 添加审查契约工具

支持根据审查类型生成审查团队配置，
返回门控规则和模式边界。
```

```
fix(hooks): 修复消息转换中的空值处理

当消息内容为空时，跳过转换而非抛出异常。
```

### 提交粒度

- 每次提交只做一件事
- 提交内容必须可独立运行
- 禁止提交未完成的代码（WIP）
- 禁止提交调试代码（console.log 等）

## 禁止事项

- 禁止强制推送到 `main` 分支
- 禁止提交敏感信息（密钥、Token、密码等）
- 禁止提交 `node_modules`、`.env` 等文件
- 禁止在提交信息中包含无关内容

## 危险 Git 操作授权

- 对当前工作区执行 `reset --hard`、`clean -fd`、覆盖 checkout、rebase、删除分支、pull 合并等可能改变或丢弃本地状态的操作前，必须取得用户对目标仓库、目标分支和具体命令的明确授权。
- 插件维护专项能力可以指导或执行本地 `git pull`、`git reset --hard`、`git clean`，但必须先确认目标是 AE 插件安装/源码维护目录，而不是用户业务项目，并提示会丢弃或覆盖的本地状态。
- 面向普通下游项目的通用工程流程不得把 destructive Git 命令作为默认步骤；如需处理工作区冲突，应先输出状态、风险和可选方案，让用户选择。
- 即使用户授权本地 destructive 操作，也不等于授权 push、force push、PR、release、跳过 hooks 或修改 Git 配置；这些操作仍需单独明确授权。
