# 保存会话执行流程

将当前会话中已经形成的执行流程提炼为可复用的项目级技能。

## 核心约束

1. 默认只能创建当前工作空间内的项目级技能，写入 `.opencode/skills/<skill-name>/SKILL.md`。
2. 禁止写入全局技能目录。
3. 如果当前工作空间不是 `ai-agent-engine` 插件源码仓库，禁止修改插件源码资产目录，例如 `src/assets/skills/`。
4. 如果当前工作空间是 `ai-agent-engine` 插件源码仓库，必须按本仓库的公开技能定义方式注册，而不是只写 `.opencode/skills/`。
5. 普通项目模式生成的技能必须符合 opencode 官方技能规范：
   - 技能目录名使用小写字母、数字和连字符。
   - `SKILL.md` 必须包含 YAML frontmatter。
   - frontmatter 必须包含 `name` 和 `description`。
   - `name` 必须与技能目录名完全一致。
   - 技能内容必须是 Markdown。
6. 本插件源码模式使用 AE 公开技能内部约定：frontmatter `name` 为 `ae:<name>`，目录名为 `ae-<name>`。这是 AE 插件源码注册约定，不适用于普通项目模式。
7. 定义技能时允许额外定义工具或编写脚本供技能调用；是否需要工具或脚本必须由流程需求驱动，不得为了包装简单步骤而过度实现。

## 输入

可选参数：目标技能名或流程关注点。

如果用户未提供目标技能名，先根据会话流程生成一个简短的 kebab-case 技能名。

### 名称归一化

先把用户输入归一化为“核心名” `<name>`，再按保存模式派生目录、frontmatter 和命令名。

| 用户输入 | 核心名规则 |
|---|---|
| `/ae-foo` | `foo` |
| `ae:foo` | `foo` |
| `ae-foo` | `foo` |
| `foo` | `foo` |
| 中文句子、动词短语、包含空格的描述 | 视为流程关注点，生成简短 kebab-case 核心名 |

派生规则：

- 普通项目模式：目录名和 frontmatter `name` 都使用 `<name>`。
- 本插件源码模式：目录名为 `ae-<name>`，frontmatter `name` 为 `ae:<name>`，命令名为 `ae-<name>`。
- 不得生成 `ae-ae-*`、`ae:ae-*` 或目录名与 frontmatter 混用的结果。

## 快速路由

1. 先判定保存模式：
   - 普通项目模式 → 只允许写 `.opencode/skills/`，除非用户明确授权工具或配置改动。
   - 本插件源码模式 → 写 `src/assets/skills/`，并更新强制注册链路。
   - 不确定 → 暂停并询问用户，不能继续设计草案。
2. 再判定配套产物：
   - 默认只写 `SKILL.md`。
   - 需要稳定结构化接口 → 工具。
   - 只服务技能内部 → 脚本。
   - 不确定 → 默认不创建工具，询问用户。
3. 所有写入前必须展示完整草案、目标路径、保存模式、同步文件和配套产物，并获得明确确认。
4. 用户确认前，不得创建目录、写入临时文件或修改注册文件。

## 执行流程

### 第一步：提取会话流程

回顾当前会话，提取可复用的执行流程，而不是逐字记录聊天内容。

重点识别：

- 用户的原始目标和关键约束
- 助手采用的阶段划分
- 读取、搜索、编辑、验证、审查、门禁等关键动作顺序
- 用户确认点或必须暂停提问的节点
- 不能自动执行的操作边界
- 最终交付格式和验收证据
- 本流程未来复用时需要参数化的内容

必须排除：

- 一次性的文件路径，除非它们是流程本身要求的固定位置
- 临时调试输出
- 与流程无关的工具噪声
- 用户未确认的推测性规则

### 第二步：识别保存模式

先判断当前工作空间是否为 `ai-agent-engine` 插件源码仓库。识别必须简单有效：优先使用少量高置信度信号，不做大范围扫描，不用模糊关键词猜测。

#### 识别步骤

1. 确定当前工作空间根目录，而不是从任意子目录推断：优先使用运行环境提供的 workspace root；无法获取时使用当前 Git 仓库根目录；如果不在 Git 仓库内，则使用当前工作目录。不得向父级目录递归扩大范围，除非用户明确要求。
2. 读取根目录 `package.json`，检查 `name` 是否为 `ai-agent-engine`。
3. 检查两个最小源码注册锚点是否同时存在：
   - `src/schemas/ae-asset-schema.ts`
   - `src/services/ae-catalog.ts`
4. 如果仍不确定，再检查以下辅助锚点，不要一开始就扫描全仓库：
   - `src/tools/index.ts`
   - `src/assets/skills/`
   - `opencode.json`
   - `.opencode/skills/save-session-flow/SKILL.md` 或 `src/assets/skills/save-session-flow/SKILL.md`

#### 判定规则

- **直接判定为本插件源码模式**：`package.json` 的 `name` 为 `ai-agent-engine`，且两个最小源码注册锚点都存在。
- **直接判定为普通项目模式**：`package.json` 不存在，或 `package.json` 的 `name` 明确不是 `ai-agent-engine`，且两个最小源码注册锚点都不存在。
- **必须询问用户确认**：出现以下任一情况：
  - `package.json` 的 `name` 为 `ai-agent-engine`，但两个最小源码注册锚点不完整。
  - `package.json` 的 `name` 不是 `ai-agent-engine`，但存在任一最小源码注册锚点。
  - 只有 `save-session-flow` 技能存在性命中。
  - 当前工作空间看起来是某个更大仓库的子目录，无法确认根目录。

`save-session-flow` 技能存在性只能说明“该技能曾被安装或复制到此工作空间”，不能单独证明当前工作空间是 `ai-agent-engine` 插件源码仓库。

进入草案设计前，必须先向用户或在内部记录中给出以下判定摘要；如果判定结果为“需要用户确认”，必须暂停并提问：

```markdown
保存模式判定

- workspace root: <路径>
- package.json name: <不存在|值>
- src/schemas/ae-asset-schema.ts: <存在|不存在>
- src/services/ae-catalog.ts: <存在|不存在>
- 判定结果: <普通项目模式|本插件源码模式|需要用户确认>
- 理由: <一句话>
```

#### 不推荐的识别方式

- 不要通过 README 文本中出现 “AI Agent Engine” 或 “AE” 判定；普通项目可能复制了文档片段。
- 不要通过 `.opencode/skills/` 是否存在判定；普通项目也会有项目级技能。
- 不要通过 `node_modules`、构建产物或 `.opencode/plugins/` 判定；这些是运行时或依赖产物，容易缺失或过期。
- 不要递归扫描整个仓库寻找同名文件；优先检查固定锚点路径，避免慢且误报高的识别。

保存模式：

- **普通项目模式**：写入 `.opencode/skills/<skill-name>/SKILL.md`，不修改插件源码注册文件。
- **本插件源码模式**：写入 `src/assets/skills/ae-<name>/SKILL.md`，并按需同步 schema、catalog、命令注册链路、帮助可见性和相关文档。

如果信号不完整但疑似本插件源码仓库，先向用户确认保存模式，不要猜测。

### 第三步：设计目标技能

将提取结果整理为一个新的技能草案。

草案必须包含：

- `name`：普通项目模式下使用小写字母、数字和连字符组成，并与目录名一致；本插件源码模式下使用 `ae:<name>`，目录名为 `ae-<name>`
- `description`：一句话说明技能用途
- `# 标题`
- 适用场景
- 输入说明
- 分阶段执行流程
- 用户确认点
- 写入或修改文件时的边界
- 如需配套能力，明确工具或脚本的用途、输入、输出、调用时机和失败处理
- 完成后的汇报格式

如果流程会创建、修改或删除文件，必须明确要求在写入前展示草案并等待用户确认。

### 配套工具或脚本判定

设计草案时同步判断是否需要配套产物：

| 场景 | 默认选择 | 禁止事项 |
|---|---|---|
| 仅需 LLM 读写、搜索、总结和调用现有工具 | 只写 `SKILL.md` | 不新增工具或脚本 |
| 需要重复执行本地转换、批处理或辅助校验，但不需要暴露给 LLM | 技能子目录脚本 | 不注册为公开工具 |
| 需要结构化参数、稳定 IO、路径安全、外部 API、复杂校验或稳定错误返回 | opencode 工具 | 不把工具逻辑塞进脚本 |
| 不确定是否需要工具 | 默认不创建工具，询问用户 | 不得自行扩大范围 |

优先级：能用技能文档清晰完成时不新增工具；脚本足够时不新增工具；只有需要被 opencode 工具系统调用时才定义工具。

### 第四步：展示草案并请求确认

在写入任何文件前，向用户展示：

````markdown
计划创建技能：<目标路径>
保存模式：<普通项目模式|本插件源码模式>

```markdown
<完整 SKILL.md 草案>
```

计划同步的注册或文档文件：
- <文件 1>
- <文件 2>

计划创建的配套工具或脚本：
- <无|工具路径|脚本路径>

请选择：
1. 确认保存
2. 修改后保存：<修改意见>
3. 取消
````

只有用户明确选择确认保存，才进入写入步骤。

明确确认包括：用户输入 `1`、`确认保存`、`保存`、`可以保存`、`按这个保存`、`没问题，保存`。不算明确确认：`看起来不错`、`继续`、`你觉得呢`、只提出修改意见但未明确说保存。

如果用户选择“修改后保存”，必须先根据修改意见生成修订版草案并再次展示；只有用户确认修订版后，才可写入。只有当用户明确说“按上述修改直接保存，无需再次确认”时，才可跳过二次确认，但写入前仍必须简短回显最终目标路径、保存模式、技能名和变更范围。

### 冲突处理

如果目标技能、工具或脚本已存在，按下表处理：

| 用户选择 | 动作 |
|---|---|
| 覆盖 | 展示将被覆盖的目标路径和新草案，再次确认后覆盖 |
| 改名 | 重新归一化名称，重新计算路径、frontmatter、命令名和草案，再次展示确认 |
| 合并 | 先读取旧文件，展示合并草案和冲突点，再次确认后写入 |
| 取消或不明确 | 停止，不写入任何文件 |

### 第五步：写入技能

#### 普通项目模式

确认后执行以下检查：

1. 检查 `.opencode/skills/<skill-name>/` 是否已存在。
2. 如果目标技能已存在，先展示冲突并询问是否覆盖或改名。
3. 创建目录 `.opencode/skills/<skill-name>/`。
4. 写入 `.opencode/skills/<skill-name>/SKILL.md`。
5. 如果需要配套工具，在 `.opencode/tools/<tool-name>.ts` 下创建工具文件，并在技能文档中写明工具名称、参数和调用时机。
6. 普通项目工具必须使用 opencode 官方 `tool()` 定义，参数使用 Zod 描述，description 使用中文说明适用场景、输入、输出和失败处理。
7. 普通项目工具默认以文件名作为工具名；如果当前 opencode 环境无法确认会自动加载 `.opencode/tools/*.ts`，必须在写入前询问用户是否允许更新项目配置或改为脚本方案。
8. 如果只是脚本，在该技能子目录下创建脚本，例如 `.opencode/skills/<skill-name>/scripts/<script-name>`，并在 `SKILL.md` 中使用相对路径引用。
9. 脚本必须写明调用命令、输入、输出、依赖前提和失败降级。优先使用项目已有运行时；如需新增依赖，必须单独请求用户确认。
10. 写入后读取文件，确认 frontmatter 和目录名一致；如创建工具或脚本，同时确认工具文件结构、脚本相对路径和技能文档引用一致。
11. 如无法自动验证工具加载或脚本运行，完成汇报中必须标记为“结构检查通过，运行时生效仍需重载或手动调用验证”。

不得修改 `opencode.json`，除非用户明确要求。

#### 本插件源码模式

确认后按本仓库公开技能定义方式同步注册：

强制项：写入技能真源、更新 schema、更新 catalog、确保 `/ae-help` 可发现。

条件项：只有触发对应条件时才新增命令文件、README、usage guide、工具、服务、测试或脚本。

1. 检查 `src/assets/skills/ae-<name>/` 是否已存在。
2. 如果目标技能已存在，先展示冲突并询问是否覆盖、合并或改名。
3. 创建或更新 `src/assets/skills/ae-<name>/SKILL.md`，frontmatter 使用 `name: ae:<name>`。
4. 更新 `src/schemas/ae-asset-schema.ts`：
   - 在 `SKILL` 常量中添加新条目。
   - 确认 `COMMAND.<KEY>` 可由 `SKILL` 自动派生出 `ae-<name>`；`COMMAND` 常量值不包含 `/`。
   - 用户调用形式为 `/ae-<name>`，由命令注册或 TUI 展示层追加 `/`。
   - 在 `AeSkillNameSchema` 中加入新技能常量。
5. 更新 `src/services/ae-catalog.ts`：
   - 先观察现有 catalog 分组含义和技能列表顺序，再在对应位置添加条目；不得默认固定加入某个位置。
   - 使用 `SKILL.<KEY>`、`COMMAND.<KEY>` 和 `skillDir(SKILL.<KEY>)`，不得硬编码技能名。
   - `description` 与 `SKILL.md` frontmatter 语义一致。
   - `argumentHint` 与 `SKILL.md` frontmatter 的 `argument-hint` 字面一致；如果没有参数提示，两处都不要添加或都保持空值。
6. 只有当统一 catalog 模板无法表达命令行为时，才新增或更新 `src/assets/commands/ae-<name>.md`；否则依赖 `command-registration.ts` 的默认技能调用模板自动注册命令。
7. 如果需要配套工具，按本仓库工具创建方式实现：
   - 在 `src/tools/<tool-name>.tool.ts` 创建工具定义，使用 `@opencode-ai/plugin/tool` 和 Zod 参数描述。
   - 在 `src/schemas/ae-asset-schema.ts` 的 `TOOL` 常量中添加工具名。
   - 在 `src/tools/index.ts` 导入并注册工具。
   - 如涉及核心逻辑，优先放入 `src/services/`，必要时补充 `src/schemas/` 或 `src/utils/`，保持依赖方向为 `tools/ → services/ → schemas/utils`。
   - 如工具面向用户暴露，更新 `README.md`、`docs/ae/usage-guide.md` 或相关专题文档；如帮助输出需要覆盖，确认 `ae-help` 数据来源保持一致。
   - 为工具或服务补充测试，优先放入 `tests/tools/`、`tests/services/` 或 `tests/schemas/`。
8. 如果只是脚本，在该技能子目录下创建脚本，例如 `src/assets/skills/ae-<name>/scripts/<script-name>`，并在 `SKILL.md` 中使用相对路径引用；不要把仅服务单个技能的脚本注册为公开工具。
9. 更新公开文档：
   - 新增公开技能或工具时，必须确保 `/ae-help` 可见；不要在 README 或用户手册中手写完整重复清单。
   - `README.md`：只有当新技能属于稳定主入口、安装后使用说明、更新卸载流程或开发资产说明的范围时才补充。
   - `docs/ae/usage-guide.md`：只有当新技能属于用户手册现有稳定场景、入口表或同类章节时才补充。
   - 如存在与该技能直接相关的专题文档，也同步更新。
   - 如果不更新 README 或 usage guide，完成汇报中说明原因，例如“完整能力清单由 `/ae-help` 自动生成，无需手写重复清单”。
10. 如新增技能或工具改变帮助输出，确认 `/ae-help` 的数据来源仍来自 catalog 或工具注册链路，不手写重复清单。
11. 运行验证命令，至少包含 `npm run typecheck`；若改动 TypeScript 注册、命令模板、工具、服务、schema 或文档生成逻辑，应优先运行 `npm run test` 和 `npm run build`。
   - `npm run typecheck`：验证类型、schema 和 catalog 编译正确。
   - `npm run test`：验证注册链路、工具、服务或帮助输出行为正确。
   - `npm run build`：生成运行时插件产物，确保重新加载后可生效。
   - 完成汇报中区分“代码验证通过”和“运行时需重载 opencode 后生效”。
12. 写入后读取关键文件，确认技能名、目录名、catalog、命令名、工具名、脚本路径和文档说明一致。

不得只把技能写入 `.opencode/skills/` 后宣称完成；在本插件源码模式下，`src/assets/skills/` 是受版本控制的公开技能真源。

### 第六步：完成汇报

保存成功后，按以下格式汇报：

```markdown
已保存技能：`<目标 SKILL.md 路径>`

保存模式：<普通项目模式|本插件源码模式>
技能名：`<skill-name>`
用途：<description>
同步文件：<如适用，列出 schema/catalog/commands/README/usage-guide>
配套产物：<无|工具|脚本及路径>
验证：<列出已运行命令，并说明 frontmatter、目录名、命令名和文档一致性检查结果>
```

如果用户取消，明确说明未写入任何文件。

## 质量标准

- 技能描述必须面向未来复用，而不是只描述本次会话。
- 流程步骤必须可执行、可验证。
- 用户确认点必须清晰，不得把确认隐含在流程中。
- 普通项目模式生成的技能不得依赖本插件源码仓库的动态注册能力。
- 本插件源码模式生成的技能必须纳入本仓库的正式注册链路，确保命令、帮助和文档同步可发现。
- 配套工具必须有清晰的 LLM 可调用接口；配套脚本必须保持在技能子目录内，避免污染项目级公共工具面。
