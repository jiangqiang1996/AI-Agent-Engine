# 交付门禁与最终交付

本文件定义 `ae-work` 阶段四的质量检查、审查证据门禁和最终交付模板。仅在所有执行循环任务完成、`references/verification.md` 输出 `verification_result` 后加载。

## 质量检查

1. **运行核心质量检查**：交付前运行完整测试套件和 lint（由编排层执行，不下放给子代理）。

2. **代码审查（必需）**：每项变更都要审查，深度随变更风险调整。

   - **完整审查（默认）**：调用 `/skill:ae-review`，审查当前实现产生的 Git diff 或会话变更，并传递设计路径作为实现意图上下文。设计路径不得作为文档审查目标，不得触发需求或设计文档审查、深化或转换。
   - **内联自审（豁免）**：仅在以下四条全部为真时允许——纯增量（仅新文件）、单一关注点、遵循模式（无新颖逻辑）、忠实于设计。豁免时在交付证据中记录四条逐项判断。

3. **审查闭环（最终验证通过后、最终交付之前执行）**：

   - 对实际改动文件运行审查闭环，确保实现与 design 契约一致且无遗漏缺陷。存在 design 契约时把"契约一致性"写入审查 goals。
   - 审查发现中与 design 契约不一致的代码、测试覆盖缺口、验证未通过的发现属于可自动修复范围：编排层直接应用修复（或派对应 persona 子代理修复），修复后重新审查。
   - **收敛协议（上限 2 轮）**：第 1 轮初次审查 → 修复 → 重新审查；重新审查后无新增 P0/P1 发现即为收敛；2 轮后仍有 P0/P1 阻断时回退实现（继续在当前会话修复实现问题），不进入最终交付。

4. **最终验证清单**：

   - 已消费 `verification_result` 和实际 `validation_commands`
   - 已消费 design 契约对照核验结果（当存在 design 契约时）
   - 所有任务已完成（omp todo 全部勾销）
   - 测试覆盖——新增/变更行为有对应测试
   - Lint 通过；代码遵循已有模式；无控制台错误或警告
   - 需求追溯完整；推迟问题已在执行中解决
   - 交接文件继续执行场景已记录执行基线声明；若实现中出现阻断性需求/设计歧义，已记录用户对具体实现决策的确认

## 审查证据门禁（metadata.json 核验）

正式代码交付前，必须读取 `ae/reviews/*/metadata.json`（本轮审查对应 run-id 的目录；无法确定本轮 run-id 时取最新 `generatedAt`/时间戳目录）并逐项核验：

### metadata.json 字段表（冻结契约）

| 字段 | 类型 | 门禁用途 |
|------|------|----------|
| `generatedBy` | string，固定 `"ae-review"` | 确认产物由 `/skill:ae-review` 生成，手写或其他来源的 metadata 不放行 |
| `proofKind` | string，固定 `"ae-review-proof"` | 确认是审查证明产物 |
| `reviewRunIdOrMessageRef` | string | 本轮审查 run-id，绑定审查报告目录 |
| `sourceReviewRef` | string | 审查原始输出文件引用 |
| `worktree` | string（绝对路径） | 与当前 `git rev-parse --show-toplevel` 输出比对 |
| `branch` | string | 与当前 `git branch --show-current` 输出比对 |
| `head` | string（commit sha） | 与当前 `git rev-parse HEAD` 输出比对 |
| `statusSummary` | string（`git status --porcelain` 的 sha256 或文本） | 与当前 `git status --porcelain` 汇总比对 |
| `reviewStatus` | `"passed"` \| `"failed"` | 正式交付必须为 `passed` |
| `hasBlockingFinding` | boolean | 正式交付必须为 `false` |
| `targetCoverage` | 可选 | 目标覆盖说明，存在时纳入证据 |
| `reviewOutputHash` | string（sha256） | 审查原始输出的哈希，记录进交付证据，用于事后审计 |

### 门禁规则

- `reviewStatus: "passed"` 且 `hasBlockingFinding: false`，否则阻断交付。
- `worktree`、`branch`、`head`、`statusSummary` 四字段必须与当前 Git 指纹**逐项一致**；任一不一致视为陈旧证据（审查后工作区又发生了变化），必须重新审查，不得放行。
- metadata.json 缺失、字段缺失或 JSON 不可解析时，视为无审查证据：正式代码交付阻断；确无审查工具可用时按"未运行审查"处理（见下）。
- 审查证明为指纹一致性校验（无会话历史防伪）：metadata.json 本身不能独立作为通过依据，必须搭配同会话中真实的 `/skill:ae-review` 子代理输出（`sourceReviewRef` 指向的审查报告存在且内容与 metadata 一致）；普通任务正文、手写摘要不能独立作为通过依据。
- 门禁核验结果（metadata 路径、四字段比对结论、reviewOutputHash）写入最终交付证据。

### 未运行审查

`review_status: not_run` 仅用于无代码变更、审查工具不可用或非正式交付说明，必须搭配未运行原因；正式代码交付不得用该状态放行。

## 最终证据汇总（必需，最终写操作之后执行）

- 汇总 `verification_result` 中实际运行的 `validation_commands` 和一一对应的 `validation_results`（每条含 `command`、`exit_code`、`output`、`executed_at`）；正式交付所依赖的验证结果 `exit_code` 必须为 0。
- 汇总 `review_status`；正式代码交付必须为 `passed`，除非本轮无代码变更或审查不可用且最终回复明确标记为无法完成交付。
- 汇总 Git 写操作；没有时明确说明无；有时必须列出命令参数（`git_operation_args`）和覆盖相同参数的授权证据（`git_authorization_evidence`），用户口头授权声明不能替代具体命令参数证据。
- 汇总工作区决策；`transferred`（A→B 转移）/ `cancelled`（取消）只作为提前终止状态，不进入正式功能交付。隔离工作区实施并 apply/merge 回主工作区的交付，记录 `isolated` 决策和合并后核验结论。
- 交接文件继续执行且无设计路径时，必须引用交接文件作为执行基线；补充说明只能描述执行基线，不得把继续执行写成"任务无需设计"。
- 验证或审查存在阻断项时，先补齐阻断项再进入交付，不得宣称交付完成。

最小交付证据场景：

- 无 Git 写操作：说明无 Git 写操作，记录工作区决策。
- 非 Git 项目或隔离派发不可用：必须说明降级为当前工作区串行执行及风险，不得静默跳过。
- 单独使用本技能且未显式指定执行位置：必须有按任务大小推荐并询问用户的记录。
- Git worktree A→B 转移：A 端终止状态是"执行已转移 / 等待用户在新工作空间重启"，不是"功能交付完成"；A 的终止提示必须包含目标工作区路径、交接文件路径和简短交接提示，不得输出普通交付分区。B 端最终功能交付引用交接文件作为执行基线。

## 最终交付模板

正式代码或功能交付统一使用以下分区。执行完毕时提示词必须尽可能简洁，只报告结果和证据；不追加"下一步"、"后续操作"、"建议用户提交/部署/继续处理"等额外描述，除非存在阻断、未验证项或用户明确要求。

```md
## 已完成
- 事实性完成项，最多 3 条

## 已验证
- 实际运行的验证命令与结果，最多 3 条

## 未验证 / 无法验证
- 无；或未运行/无法运行项及原因，最多 2 条

## Git 操作状态
- 无；或本次执行的 Git 写操作与授权证据
- 工作区决策、当前分支和 HEAD

## 审查状态
- 代码审查状态和证据路径（ae/reviews/<run-id>/metadata.json）；或未运行原因

## 剩余风险
- 无；或仍需用户知道的真实风险，最多 2 条
```

使用规则：

- "已验证"只能写入可观察工作区状态、工具输出或可引用执行结果支撑的事实。
- 仅来自用户口头确认、工具参数或子代理自述的内容，必须放入"未验证 / 无法验证"或"Git 操作状态"。
- 执行完成后不输出独立的"下一步"或"后续操作"章节；若需要用户动作，只能在对应分区用一句话说明必要动作。
- 问答和只读审查可使用更轻量的对应输出，不强制套用整份模板。

## 交付步骤

1. **准备证据上下文**：识别可观察行为（UI、CLI、API）。UI 行为可用 omp browser prelude（eval 内 `browser.open` 等）实际打开核验。
2. **更新设计状态**：仅在用户明确要求，或设计/交接文件声明需要状态回写时，将设计的 `status: active` 更新为 `status: completed`。这只是交付状态记录，不得改写需求、设计、实现方案或验收标准；交接文件继续执行场景默认不修改需求或设计文档。此步骤改变工作区时，必须纳入最终交付摘要和 Git 状态核验。
3. **提交（仅在用户明确要求时）**：执行 `git add` / `git commit` 前必须取得用户对目标仓库、目标分支、工作区、完整命令参数和授权来源的明确授权；未授权时停止提交步骤。提交后重新检查 Git 状态，确保交付说明覆盖最新 HEAD 和 Git 写操作状态。
4. **通知用户**：只按最终交付模板输出简洁结果。

### 下一步引导

审查闭环收敛后，按以下规则提示下一步：

- **通过（闭环收敛，无阻断）**："实施已完成并通过一致性审查。建议使用 `/skill:ae-review` 做一次深度全量审查，或任务结束。"
- **阻断（闭环未收敛，2 轮后仍有 P0/P1）**：回退实现，不进入最终交付；提示"实施存在阻断项，需继续修复后重新验证。"

不自动调用深度审查或继续实施；只输出建议，由用户决定后续动作。

## 质量检查清单

交付前验证：

- [ ] 所有任务已完成
- [ ] 测试覆盖通过
- [ ] Lint 通过
- [ ] 代码遵循已有模式
- [ ] 提交消息遵循约定式格式（如有提交）
- [ ] 代码审查已完成且 metadata.json 门禁通过
- [ ] 交付摘要包含摘要、测试说明和证据上下文
