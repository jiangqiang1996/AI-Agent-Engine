# 执行工作流

本文件定义 `ae-work` 阶段一的启动门禁与阶段三的执行循环规则。

## 执行前验证

修改任何项目文件之前，必须确认以下清单全部满足。任一项未满足时，停止执行并返回补齐：

- Git 状态检查已实际运行并记录：`git status --short`、`git branch --show-current`、`git log --oneline -1`，记录当前分支、工作区脏状态、最近提交和可观察工作区路径。Git 命令失败时记录失败输出和 `git_context: not_git`；非 Git 场景不得伪造 branch 或 HEAD，隔离工作区派发降级为当前工作区串行执行并说明风险。
- 工作区决策已完成并取得用户确认：当前工作区直接执行 / 派 omp task 子代理（`isolated: true`）隔离执行后 apply/merge / 用户授权的 Git worktree A→B 转移。单独使用本技能且未显式指定执行位置时，必须按任务大小给出推荐并询问，不得自行默认。
- 工作区决策值已确定并记录：`current`（当前工作区）/ `isolated`（隔离工作区实施）/ `transferred`（Git worktree 转移）/ `cancelled`（用户取消）。
- 风险评估已展示并确认。未创建隔离工作区不等于允许直接在默认分支实施；当前在默认分支继续时，必须二次确认风险（默认分支 + 脏工作区会污染历史），并在最终交付说明中记录风险接受证据。用户选择取消时立即终止，只输出取消状态，不得修改任何文件。

## design 契约核验准备

修改项目文件前，检测是否存在 design 契约。存在时将契约维度作为实现对照依据，无 design 时降级为现状行为。

**检测**：检查 `ae/designs/` 下是否存在与当前任务匹配的 design 目录。匹配规则：设计路径或交接文件中引用了 design 目录，或按设计标题/需求描述名在 `ae/designs/` 下找到对应目录。

**契约读取**：读取 `overview.md` 获取模块导航和产物清单，按产物清单读取各维度独立文件（`architecture.md`、`security.md`、`observability.md`、`non-functional.md`、`design-spec.md`、`constraints.md`、`cross-mapping.md` 以及 `modules/<NN>-<m>/` 下的 `api.md`、`database.md`、`ui-ux.md`、`test-cases.md`）。只读取存在的文件。

**对照依据准备**：将以下维度作为实现对照依据，按 `overview.md` 产物清单确定哪些维度存在：

- `ui-ux`：布局家族、组件契约、token、状态机
- `api`：端点、Schema、错误码
- `database`：schema、约束、索引
- `architecture`：模块边界、依赖方向
- `security`、`observability`、`non-functional`：对应约束

对照依据写入每个子代理 prompt 的任务描述部分，要求实现时对照核验一致性。最终对照检查在 `references/verification.md` 中完成。

## 任务分析与分组

从设计文档提取实现单元时，解析 `- [ ] **单元 N：**` 格式，提取每个单元的文件列表和验证命令。设计文档格式无法识别或提取结果为空时，降级为手动任务拆分；不得因无法识别设计格式而停止执行。

### 执行策略

| 策略 | 适用场景 |
|------|----------|
| 内联（inline） | 1-2 个小任务，或并行组内没有可并发的多个任务；编排层直接实施，不派子代理 |
| 串行（serial） | 3+ 有依赖的任务，或所有分组都只有 1 个任务，无法获得并行收益；按依赖顺序逐个派发 |
| 并行（parallel） | 任一分组包含 2 个及以上互不冲突的任务；同一轮一次性派发全部子代理 |

### 并行分组规则

编排层构建"文件到任务单元"映射来判断并行安全：

- 若两个任务单元的文件范围、状态、迁移、配置、公共契约、测试夹具或共享中间产物存在交集，或任一任务依赖另一任务的未完成输出，则这两个任务**不得**进入同一并行组，降级为串行（按依赖排序）。
- 互不重叠的任务单元归入同一并行组（标记 `is_parallel_safe=true`）；多个并行组按组顺序（G1, G2, G3...）串行推进，组内并行。
- 分组结果和冲突矩阵作为调度上下文写入每个子代理 prompt。

### 调度上下文硬约束

每个子代理 prompt 的调度上下文必须包含：任务 ID、允许文件、禁止文件、禁止命令、验证命令、冲突上报要求，并直接约束子代理：

- 只处理分配给自己的文件和任务；不得暂存、提交、运行全量测试套件。
- 不得修改共享配置、锁文件、迁移文件或未分配文件。
- 不得启动服务、浏览器功能测试、E2E、集成测试，或任何会占用端口、数据库、缓存、固定临时目录等共享资源的命令。
- 传给子代理的验证命令必须先过滤为执行安全命令；若验证需要全量测试或共享资源，子代理必须在返回结果中报告由编排层执行。
- 遇到跨任务依赖、文件冲突、共享资源需求或需要共享中间产物时，必须停止并在 evidence 中报告，不得自行越界。

## 失败处理

子代理返回 `failed` 或 `partial` 时：

- 已完成的执行结果和变更保留。
- 失败的任务标记为需要串行重试。
- 先运行 Git diff/status 识别真实修改。
- 发现越权或污染修改时停止并请求用户决策，不得直接串行重试，不得自动覆盖或回滚。
- 在下一轮中单独派一个子代理执行失败任务。
- 重试仍失败时，报告失败原因并询问用户。
- 测试失败先派 `agent: "test-triage"` 分诊根因，再按分诊结果决定修复路径。

## 测试与进度

变更前查找已有测试文件。新行为添加新测试、变更行为修改测试、删除行为移除测试。

编写测试前检查设计的测试场景是否覆盖正常路径、边界情况、错误/失败路径和集成场景。任务完成前检查回调/中间件、集成测试覆盖、失败时的孤立状态、跨接口一致性和错误策略。

每次重要变更后运行相关测试。每 2-3 个单元后审查简化机会。用 omp todo 保持任务列表更新，记录阻碍和发现。

## 编排层汇总职责

子代理完成后，编排层必须：

1. 收集全部子代理返回的 `{status, output, evidence}`。
2. 检查其中的冲突、越权或 partial/failed 证据。
3. 独立运行 Git diff/status 检查真实修改文件，不只依赖子代理自报。
4. 将真实修改文件与每个任务的允许文件比对，确保无跨任务文件冲突或越权修改。
5. 隔离工作区实施的任务审阅后 apply/merge 回主工作区，合并冲突由编排层解决。
6. 修复集成问题（必要时派 backend-fix persona 子代理）。
7. 运行统一验证命令。
8. 更新 omp todo 最终任务状态。
9. 在验证和交付阶段执行最终检查，记录验证、审查和 Git 操作状态。

## Git 写操作

仅当用户已明确要求提交时，逻辑单元完成且测试通过后创建提交。不使用 WIP 消息。使用约定式格式。未获授权时只保留工作区变更并汇报建议提交点。

执行 `git add`、`git commit`、创建分支或 `git worktree add` 等 Git 写操作前，必须取得用户对目标仓库、目标分支、工作区、完整命令参数和授权来源的明确授权，并把命令纳入交付证据的 `git_operations`、`git_operation_args` 和 `git_authorization_evidence`；授权不足时不得执行。

## 输出契约

本阶段必须输出执行状态、失败处理结果和需要验证阶段核验的变更证据要求。子代理自报不作为真实修改证据，编排层必须在验证阶段独立核验 Git diff/status。
