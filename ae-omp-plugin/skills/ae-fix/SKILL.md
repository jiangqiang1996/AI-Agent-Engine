# 修复技能（ae-fix）

统一修复入口：按模式参数或上下文推测路由到 frontend / backend 两种修复流程。frontend 模式以 DOM 结构化数据诊断为主、截图为辅，具备上下文检测→诊断→修复→验证内部闭环；backend 模式走错误分析→上下文检测→根因定位→修复实现→回归验证。两种模式共享边界纪律：不修改对方域代码、不修改测试代码。

## 模式判定

第一个参数为 `frontend` 或 `backend` 时显式路由到对应模式，剩余参数作为问题描述。否则将完整输入作为问题描述，按以下信号综合推测：

### 信号 1：问题描述关键词

- 前端信号词：页面、样式、布局、按钮、点击、渲染、DOM、CSS、组件、表单、路由、白屏、闪烁、对齐、间距、响应式、无障碍、aria、截图、视觉、UI、前端、echarts、canvas、svg、动画、滚动、弹窗、下拉、输入框、checkbox、radio、tab、modal、dialog、toast、loading、骨架屏、占位
- 后端信号词：接口返回、500、400、404、502、503、API 报错、数据库、SQL、异常、崩溃、空指针、NPE、事务、并发、序列化、权限拒绝、token 失效、后端、服务端、controller、service、mapper、repository、dao、entity、dto、vo、interceptor、filter、middleware、定时任务、消息队列、缓存、连接池、线程、锁

### 信号 2：当前变更文件类型

经 omp bash 运行 `git diff --name-only` 与 `git status --short` 检查工作空间变更：

- 变更以 `.tsx`、`.jsx`、`.vue`、`.css`、`.scss`、`.less`、`.html`、`.svelte`、`.astro` 为主 → frontend
- 变更以 `.java`、`.py`、`.go`、`.rs`、`.kt`、`.php`、`.rb`、`.c`、`.cpp` 为主 → backend
- `.ts`/`.js` 按路径推断：路径含 `server`、`api`、`backend`、`middleware`、`controller`、`service`、`dao`、`repository` → backend；路径含 `component`、`page`、`view`、`client`、`src/app`、`pages` → frontend

### 信号 3：URL 参数

问题描述中包含 URL（http/https 开头）→ 倾向 frontend（需浏览器验证）。

### 推测规则

1. 仅命中前端信号 → frontend 模式
2. 仅命中后端信号 → backend 模式
3. 前后端信号同时命中 → 询问用户选择 frontend 或 backend
4. 无任何信号 → 询问用户选择 frontend 或 backend

推测后先告知用户推测结果和依据，再执行对应模式流程。

## 执行方式

编排层按对应模式章节的流程直接执行；需要隔离工作区或并行处理多个独立问题时，派通用 task 子代理执行，prompt 中传入：对应模式章节的方法论全文（或要点）、问题描述、涉及文件清单、边界纪律。修复完成后由编排层核验变更文件列表。

## frontend 模式（前端修复）

前端修复专家流程：按「先视觉后逻辑」顺序处理视觉修复、交互逻辑修复、状态管理修复和 API 联调修复。以 DOM 结构化数据诊断为主、截图为辅，具备检测→诊断→修复→验证内部闭环。

### 适用场景

- 纯页面美化修复：CSS 属性错误、布局偏差、间距/对齐问题、响应式断点问题、颜色/字体不一致
- 页面交互修复：事件绑定失败、状态管理 bug、条件渲染错误、表单联动问题、路由跳转异常
- 前端接口联调修复：API 调用错误、请求/响应数据处理问题、认证集成问题、加载/错误/空态处理缺失
- 无障碍属性修复：ARIA 属性缺失/错误、焦点管理问题、键盘导航失效、对比度不达标
- 混合问题修复：同时涉及视觉和交互/接口的复合问题

不适用：从零创建新页面或组件、设计稿还原实现（均属开发任务，走 `/skill:ae-work`）；生成或维护测试文件（走 `/skill:ae-test` e2e 模式）；后端业务逻辑修复（backend 模式）。

### 诊断顺序

按「先视觉后逻辑」顺序处理，消除推诿：

1. **先查 DOM/样式（视觉问题）**：经 omp browser prelude 获取渲染后的元素节点、计算样式和布局几何
2. **再查交互逻辑/状态管理（逻辑问题）**：检查事件绑定、状态流转、API 调用

### 执行流程

1. 解析问题描述和可选 URL，识别涉及的组件、页面、接口和数据模型
2. **上下文检测**：用 glob/grep 扫描代码库已有的组件结构、数据流、状态管理模式（Context/Zustand/Redux/Pinia 等）、数据获取模式（fetch/axios/React Query/SWR 等）、已有 hooks/工具函数、目录结构与模块边界，以及设计信号（CSS 变量 `--color-*`/`--spacing-*`/`--font-*`、tailwind 配置、间距/网格模式），确保修复与现有模式一致
3. **DOM 结构化诊断（主诊断依据）**：经 browser prelude 打开目标页面（需本地开发服务器已启动），用 `tab.evaluate` 采集问题元素的节点树、`getComputedStyle` 计算样式和 `getBoundingClientRect` 布局几何；用 `tab.observe`/`tab.ariaSnapshot` 获取可交互元素与可访问性树
4. **截图辅助确认（辅诊断依据）**：必要时 `tab.screenshot` 保存到 `ae/screenshots/`（保存前确保目录存在），用于视觉问题确认与修复前后对比
5. **登录状态检测**：打开目标页面后检测是否需要登录（URL 含 `/login`/`/signin`/`/auth`、存在密码输入框、存在登录按钮）。如检测到登录页面，提示用户在浏览器窗口完成登录，每 5 秒检测一次，最长等待 300 秒；超时后询问用户选择：继续等待/跳过登录以当前状态继续/终止验收
6. **诊断问题**：
   - 视觉层面：CSS 属性、布局、间距、对齐、响应式、颜色、字体
   - 交互层面：事件绑定、状态管理、条件渲染、表单联动、路由
   - 接口层面：API 调用、请求/响应处理、认证集成、加载/错误/空态
7. **修复代码**（最小改动原则），遵循项目已有开发模式和编码规范（见下方修复参考）
8. **验证修复效果**：经 browser prelude 重新采集 DOM 数据对比（计算样式、布局几何、断言表达式），必要时截图对比；交互问题重放触发路径确认
9. 输出变更文件列表、诊断说明和修复依据、验证结果

### HTML/CSS 编码规范

- 语义化标签（`<header>`/`<nav>`/`<main>`/`<article>`/`<section>`/`<aside>`/`<footer>`），不滥用 `<div>`
- 标题层级 `<h1>` → `<h6>` 不跳级，一个页面只有一个 `<h1>`
- 按钮用 `<button>` 不用 `<div onclick>`；表单字段必须有 `<label>`；图标按钮必须有 `aria-label`
- 优先用 Tailwind 默认值（`gap-10` 代替 `gap-[40px]`）；组件全宽（`w-full`），宽度约束由父级包装 div 处理
- 使用 `min-h-[100dvh]` 而非 `h-screen`；Grid 优先于 Flex 百分比计算
- 动画仅 `transform` 和 `opacity`；形状一致性：一个圆角比例贯穿全页
- WCAG AA 最低对比度；`:focus-visible` 焦点环不可移除；为 `prefers-reduced-motion` 提供降级

### 交互逻辑修复参考

| 交互类型 | 典型问题 | 修复参考 |
|---------|---------|---------|
| 表单联动 | 字段间依赖失效、动态校验缺失 | 恢复字段依赖、补充校验规则 |
| 条件渲染 | 权限控制错误、状态切换异常 | 修正条件判断、恢复正确渲染分支 |
| 状态机 | 状态转换条件错误 | 修正转换条件、恢复副作用 |
| 拖拽排序 | 排序事件丢失 | 恢复拖拽事件、修正排序算法 |
| 分页加载 | 请求参数错误、数据追加异常 | 修正请求参数、恢复数据追加逻辑 |
| 搜索筛选 | 防抖失效、请求未取消 | 恢复防抖、补充请求取消 |
| 文件上传 | 进度/预览缺失 | 恢复进度处理、补充预览 |

### 接口联调修复参考

- 接口定义采集优先级：1) 从项目代码提取（API 路由、类型定义）→ 2) 从用户提供信息提取
- 修复请求/响应数据结构转换、字段名映射和类型转换
- 修复 mock 数据替换为真实 API 调用的问题

### 状态管理修复参考

- 必须实现加载态（Loading 指示器/骨架屏/禁用交互）
- 必须实现错误态（错误提示/重试按钮/降级展示）
- 必须实现空态（空数据提示/引导操作）
- 服务端状态与客户端状态分离管理

### 认证集成修复参考

- Token 注入：从存储读取注入请求头
- 401 处理：拦截响应跳转登录或刷新 Token
- 刷新机制：过期时自动刷新，队列等待
- 登录状态同步：跨组件共享

### 可访问性修复参考

- 键盘导航：全局 tabindex 策略、焦点顺序、快捷键
- ARIA 属性：role 体系、aria-label/describedby/live 统一规范
- 焦点管理：焦点陷阱、焦点恢复、skip-to-content
- 屏幕阅读器：语义化标签、alt 文本策略、live region

### frontend 边界纪律

- 只修改前端代码（CSS/HTML/JS/TS/JSX/TSX/Vue 等）
- **不修改后端业务逻辑代码**（发现后端问题时在输出中标注，建议走 backend 模式）
- **不修改测试代码**（测试修复由 ae-test 的 self-fix 负责）
- 不执行 Git 写操作
- 浏览器操作一律通过 omp browser prelude
- 不从零创建新页面或组件；不做设计决策推断
- 修复视觉/交互问题时，本地开发服务器应已启动

### frontend 完成标准

- 问题已修复且经 browser prelude 验证（DOM 数据对比，必要时截图对比）
- 变更文件列表已输出
- 修复代码与现有代码风格一致

## backend 模式（后端修复）

后端修复专家流程：错误分析、根因定位、修复实现和回归验证。遵循项目现有架构规范，确保修复不破坏接口契约和数据校验。

### 适用场景

- 后端接口返回错误（500、400、404 等）
- 业务逻辑 Bug
- 数据处理错误
- 异常或崩溃问题排查
- 性能问题修复（后端）

不适用：前端视觉/交互修复（frontend 模式）；测试代码修复（ae-test self-fix）；从零开发新功能（`/skill:ae-work`）。

### 执行流程

```
错误分析 → 上下文检测 → 根因定位 → 修复实现 → 回归验证
```

1. **错误分析**：解析问题描述或错误信息，分析错误现象和复现条件，识别涉及的接口和数据模型
2. **上下文检测**：用 glob/grep 查找项目中已有的后端模式——API 路由和接口定义、数据访问层模式（Repository/DAO/ORM）、业务逻辑组织方式（Service 层/Domain 层）、中间件和拦截器模式、错误处理和异常体系、数据校验模式、目录结构与模块边界，确保修复与现有架构一致
3. **根因定位**：追踪调用链，定位根因。参考上下文检测发现的已有模式，判断问题是否偏离项目约定。定位手段按成本递增：
   - **静态追踪**：read/grep 沿调用链阅读代码，结合日志输出与错误栈定位可疑帧
   - **LSP 能力**：使用 omp 提供的 LSP 能力（跳转定义、查找引用、符号大纲）精确追踪符号的定义处与全部调用点，确认影响面
   - **omp debug（DAP 调试器）**：复现路径不明确或状态相关 bug（并发、事务、缓存）时，经 `xd://debug` 使用 DAP 调试：`launch`/`attach` 启动或挂接进程（Delve/debugpy/rdbg 等按语言适配）→ `set_breakpoint` 在可疑帧下断点（可按文件行号、函数名或条件）→ `continue`/`step_over`/`step_in`/`step_out` 控制执行 → `stack_trace` 查看调用栈 → `scopes`/`variables`/`evaluate` 检查变量与表达式求值 → `terminate` 结束会话。同一时间只保留一个调试会话；调试结束后核对进程已退出
4. **修复实现**：最小改动，遵循项目现有架构规范——接口契约一致（请求/响应结构不变）、数据校验完整、错误处理不吞没异常且保留原始上下文、代码组织单一职责、优先使用项目已引入的依赖库
5. **回归验证**：验证修复效果，确认无回归——修复点功能正常、相关调用链未受影响、接口契约未破坏、数据校验仍完整。有可运行的项目测试时经 omp bash 运行相关测试子集佐证（不修改测试本身；测试失败按 ae-test 统一失败处理流程诊断）
6. 输出变更文件列表、根因分析和修复说明

### backend 边界纪律

- 只修改与 Bug 直接相关的后端文件
- **不修改前端代码**（发现前端问题时在输出中标注，建议走 frontend 模式）
- **不修改测试代码**（测试修复由 ae-test 的 self-fix 负责）
- 不执行 Git 写操作
- 不修改配置文件或构建脚本（除非 Bug 就在此）
- 不引入新功能，仅修复问题

### backend 完成标准

- 根因已定位（有调用链或调试证据支撑）
- 修复已实现且已验证无回归
- 接口契约未破坏、数据校验仍完整
- 变更文件列表已输出

## 通用开发规范

- **代码组织**：单一职责；模块边界清晰，依赖方向单向，禁止循环依赖
- **错误处理**：不吞没错误，不忽略异常；错误向上传播时保留原始上下文；区分可恢复与不可恢复错误
- **依赖管理**：优先使用项目已引入的依赖库
- **二开约束**：只对本次修复的代码应用规范；发现现有代码问题时在输出中标注，不自行修改
