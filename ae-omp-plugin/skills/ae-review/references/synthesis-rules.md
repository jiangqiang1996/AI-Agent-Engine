# 合并层规则（内联执行，无聚合脚本）

全并行架构的后处理规则。所有激活子代理在同一轮一次性派出，只找问题不做修复；合并层由**编排模型内联执行**以下文字规则，负责去重、冲突解决、因果分析和修复方案生成。禁止跳过任何子步骤。

## 5 步综合流水线

### 5.1 校验

根据 findings schema（`references/findings-schema.json`）检查每个子代理返回的 JSON。丢弃缺少必填字段的发现。记录格式不正确的代理。

### 5.2 置信度门控

- 代码发现：抑制低于 0.60 的发现（P0 在 0.50+ 保留）；0.60-0.69 仅在明确可操作时包含；0.70-0.84 附完整证据报告；≥ 0.85 仅从代码验证后报告
- 文档发现：抑制低于 0.50 的发现（P0 在 0.50+ 保留）；0.50-0.59 标记为残余风险；0.60-0.84 附完整证据报告；≥ 0.85 确定，报告
- 需求文档发现：仅保留 P0/P1，抑制所有 P2/P3；新增 INFO 工程建议（置信度 0.5-0.8）
- 设计文档发现：严格按需求范围，抑制"建议改进"类的发现；新增 INFO 工程建议（置信度 0.5-0.8）

将低于阈值的文档发现存储为残余风险。

### 发现级别

| 级别 | 含义 | 行为 |
|------|------|------|
| P0 | 阻断：无法继续后续阶段 | 必须修复 |
| P1 | 阻断：契约不一致/缺失关键字段 | 必须修复 |
| P2 | 改进：已提及内容的优化建议 | 抑制（不报告；设计/代码/测试用例审查按 persona 规则例外产出） |
| P3 | 建议：风格/惯例建议 | 抑制（不报告） |
| INFO | 工程建议：需求未提及但工程上必要 | 报告，标注"建议补充"，用户决定 |

### 5.3 合并去重 + 冲突解决 + 因果分析（合并层核心）

#### 5.3.1 指纹去重

使用 `normalize(file) + normalize(location.type) + normalize(location.line|section) + normalize(title)` 生成指纹。

- 代码发现 location.type 为 `code`，使用 `line` 字段
- 文档发现 location.type 为 `document`，使用 `section` 字段

当指纹跨代理匹配时：
- 如果发现建议**相反的操作**，不合并——保留两者，转入冲突解决
- 否则合并：**同一问题保留最高严重级别和最高置信度**，合并证据，记录所有同意的审查者
- 归属于置信度最高的代理，减少其他代理的计数

#### 5.3.2 冲突解决

同一问题被多个代理标记为不同 severity 时，取最高 severity 保留。建议方向相反的发现保留双方，标记为 `conflict` 并写入冲突证据。

#### 5.3.3 因果分析

遍历所有发现的 `causes` 和 `caused_by` 字段构建依赖图，识别"修复 A 自动解决 B"的链式关系：

1. 构建 finding ID 之间的依赖图（有向图）
2. 检测环依赖并断开（标记为 `circular_dependency`，保留双方）
3. 识别根因发现（无 caused_by 的发现）：修复根因可自动消除其 causes 列表中的所有发现
4. 将被自动解决的发现标记为 `auto_resolved_by: <root_finding_id>`，从待修复队列中移除
5. 生成修复方案时优先排列根因发现，减少实际需要执行的修复数量

### 5.4 排序

- 代码发现：严重级别 → 置信度 → 文件路径 → 行号
- 文档发现：严重级别 → 置信度 → 文件路径 → 章节顺序

根因发现排在同严重级别的前列，因其修复可消除下游发现。

### 5.5 高风险零发现对抗

如果满足以下全部条件，触发对抗式补充审查：
1. 变更包含高风险信号（security/migration/api）
2. 所有激活代理均返回空 findings
3. 变更行数 >= 50

触发时对全部变更文件进行补充审查，补充审查结果重新进入合并层。

## 修复方案生成与执行

```
所有代理并行找问题
        ↓
   合并去重（5.3.1）
        ↓
   冲突解决（5.3.2）
        ↓
   因果分析（5.3.3）
        ↓
   生成修复方案
        ↓
   执行修复（仅 auto-fix/无头模式）
```

**生成修复方案：** 对每个待修复发现，根据 suggested_fix 生成最小编辑方案。根因发现优先排列，被 auto_resolved 的发现不生成独立修复方案。

**执行修复：** 仅在 `mode=autofix` 或 `mode=headless` 时执行。应用修复队列中的所有 `auto` 发现，修复轮次上限 2 轮。应用前复核每项不触发受保护产物、安全边界或互斥建议。

## 模式驱动的展示

- **交互模式** — 应用 `auto` 修复，展示因果分析结果和剩余待处理发现
- **auto-fix 模式** — 应用 `auto` 修复，保留其余发现，输出因果链供用户理解
- **report-only 模式** — 不应用修复，仅展示发现和因果分析
- **无头模式** — 单轮应用 `auto` 修复，结构化文本输出，包含无法安全应用的未决项

展示格式见 `references/review-output-template.md`。

## 受保护产物

丢弃任何建议删除以下目录中文件的发现：
- `ae/prds/`
- `ae/designs/`
- `ae/solutions/`

## 质量门

1. 每个发现都是可操作的
2. 没有因未仔细阅读代码/内容导致的误报
3. 严重级别校准正确
4. 位置信息准确（代码发现：行号；文档发现：章节）
5. 受保护产物得到尊重
6. 发现不重复 linter 输出
7. 因果链无环依赖（合并层已保证）

## 禁止事项

- 代理不得执行修复，只找问题
- 不要重写整个文件/文档来修复一个小问题
- 不要添加用户未讨论过的新功能/新章节
- 不要创建单独的审查文件或添加元数据章节到源文件
