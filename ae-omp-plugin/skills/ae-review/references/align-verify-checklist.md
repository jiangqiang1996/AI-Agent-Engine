# 对齐校验清单

移植自 AE 的 ae-align-verify 流程（设计对齐需求 → 源码对齐设计 → 单元/接口/E2E 测试对齐）。在 ae-review 中作为**审查侧校验清单**使用：当审查对象涉及对齐交付链路（设计文档、按设计实现的源码、按设计用例编写的测试）时，逐项核对以下清单并为每项给出证据；发现项按 findings schema 产出。执行侧的对齐/修复流程属 `/skill:ae-work`、`/skill:ae-design`、`/skill:ae-test`、`/skill:ae-fix`。

全程禁止镀金：只校验"已声明内容是否正确对齐"，不建议新增未声明的功能、抽象、配置项或防御逻辑。

## 0. 真源定位校验

- [ ] **设计真源**：审查输入是否明确指定了设计目录（`design=<路径>`）？未指定时，`ae/designs/` 下按目录名日期后缀（`-YYYY-MM-DD`）降序的最新目录是否被用作真源？`ae/designs/` 不存在或为空时是否已停止并声明"无设计真源"？
- [ ] **需求真源**：是否明确了需求来源——显式 `prd=<路径>` / 设计的 `overview.md` 或 frontmatter 引用的需求路径 / 按名称前缀在 `ae/prds/` 匹配 / 裸提示词需求内容（标记为非全量需求）？
- [ ] **全量性判定**：是否判定了需求/设计是否为当前项目的**全量**？仅覆盖部分模块时（含裸提示词需求），对齐与审查是否只限于该需求/设计提及的模块，未触及其余模块？

## 1. 设计对齐需求校验

- [ ] 设计中每个模块/单元是否可追溯到需求条目（引用需求锚点或路径）？
- [ ] 是否存在需求未声明的设计内容（镀金）？存在即产出发现。
- [ ] 是否保留过渡版本/迁移方案（应一步到位，不保留过渡）？
- [ ] 需求已提及但设计缺失/不一致的条目是否逐条列出？

## 2. 源码对齐设计校验

- [ ] 源码实现是否与设计声明的模块、接口、数据结构一致？
- [ ] 修复/实现取向是否正确：**以设计为准，设计空缺时以需求为准**？"设计空缺"指当前设计目录中不存在对应模块的设计文件，或设计文件未覆盖该模块/维度。
- [ ] 是否实现了设计未声明的功能（镀金）？
- [ ] 设计仅覆盖部分模块时，是否改动了设计未提及的模块及其源码？改动即产出发现。
- [ ] 是否存在残留文件没有随本次对齐正确修改（半截改动）？

## 3. 测试对齐校验（单元 / 接口 / E2E）

- [ ] 是否从当前设计目录定位了 `modules/<NN>-<m>/test-cases.md` 并提取设计用例清单？
- [ ] 项目测试目录（如 `tests/`、`src/test/`）与 `ae/tests/api/`、`ae/tests/e2e/` 中，设计用例是否有对应测试脚本？
  - 不存在 → 应由 `/skill:ae-test` 从设计用例编译测试骨架（校验：是否确实缺失）
  - 存在 → 校验脚本与设计用例的 diff 对齐：用例新增则补测试、删除则删测试、修改则改测试逻辑
- [ ] 对齐是否只处理设计用例与现有脚本的 diff，未新增设计未声明的测试？
- [ ] E2E 脚本是否与设计声明的页面流程一致（浏览器验证经 omp browser 能力执行）？
- [ ] 测试失败时修复是否以设计为准（设计空缺回退需求），且未为设计未声明的场景编写测试？（后端修复 → `/skill:ae-fix backend`；前端修复 → `/skill:ae-fix frontend`）

## 4. 范围与执行纪律校验

- [ ] 执行范围声明是否与实际动作一致？自然语言范围短语按边界合并：`跳过<步骤>` → 从该步骤下一编号开始；`从<步骤>开始` → 该编号到末尾；`只跑<步骤>` → 仅该步骤；`到<步骤>为止` → 从 0 到该编号；`<步骤>到<步骤>` → 闭区间。多短语组合取起始最大值与结束最小值；起始大于结束时范围矛盾，应停止并声明。
- [ ] 额外 `key=value` 参数与流程默认值冲突时，是否以参数为准？
- [ ] 是否按序执行且前一步骤未通过不进入下一步骤？跳步即产出发现。
- [ ] 全程是否遵守：禁止镀金、一步到位、不考虑过渡和迁移？

## severity 指引

- 需求/设计已声明但对齐缺失或矛盾（追溯断裂、实现偏离、测试缺口）→ P0/P1
- 镀金（实现了未声明内容）、半截改动 → P1
- 范围纪律违反（跳步、参数未生效）→ P2
- 文档属性类小问题（术语漂移、格式）→ 交 document-reviewer 维度处理，不在本清单重复产出
